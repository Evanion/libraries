# Configuration

A feature flag is a record of stored intent. `@evanion/feature` uses a structured configuration to define not just whether a feature is "on" or "off," but under what conditions it should be activated for specific users.

## The Problem: Brittle and Implicit Feature Logic

In many applications, feature flags are simple booleans. When a feature becomes more complex—for example, "Enable for staff only" or "Enable only in the UK"—the logic ends up scattered across the codebase in `if` statements.

This creates several problems:
- **Logic Drift**: Different parts of the app might implement the "staff only" check slightly differently.
- **Invisible Dependencies**: If "Feature B" requires "Feature A," you must remember to check both in every single location.
- **Configuration Fragility**: Changing a rollout percentage or a date window requires a code deployment rather than a simple configuration change.

## Solution: Declarative Feature Definitions

`@evanion/feature` uses a declarative configuration. You define the "intent" (is it enabled?) and the "rules" (when is it active?) in a single place. The library then handles the resolution logic.

```ts
const features = createFeatures([
  { 
    key: 'express-pickup', 
    enabled: true, 
    dependsOn: ['new-checkout'] 
  },
]);
```

### The Configuration Schema

| Field | Meaning |
| :--- | :--- |
| `key` | The unique identifier for the feature. |
| `enabled` | The master switch. If `false`, the feature is off for everyone. |
| `dependsOn` | A list of other features that must be `enabled` for this one to activate. |
| `rules` | Activation rules (OR-ed). If any rule matches, the feature is active. |
| `seed` | A bucketing seed for rollouts. Defaults to the `key`. |
| `freezeTimeAtBuild` | If true, `plan()` resolves time windows at build-time for static sites. |
| `variants` | The named variants this feature splits across (see [Variants](/feature/variants)). |
| `variantBy` | The context field used to bucket variants. Defaults to `targetingKey`. |
| `variantSeed` | Bucketing seed for the variant split. |

## Resolution Precedence

When you call `resolve()`, the library follows a strict hierarchy to determine if a feature is active.

1. **The Kill Switch**: If `enabled === false`, the feature is off. No rules are evaluated.
2. **The Dependency Chain**: If any feature in `dependsOn` resolves to `false`, this feature is off.
3. **The Default State**: If `enabled === true` and there are no rules, the feature is on.
4. **The Rules**: If rules exist, they are OR-ed. If any rule matches, the feature is on. Inside a rule, conditions are AND-ed.

**Crucially**, this is not a "first-match" system. The outcome is deterministic regardless of the order of rules, allowing you to add new rules without worrying about their position in the list.

## Dependency Cascades

Dependencies are transitive and one-way. If you have a chain `A $\rightarrow$ B $\rightarrow$ C`, turning off `A` automatically disables both `B` and `C`.

```ts
createFeatures([
  { key: 'a', enabled: true },
  { key: 'b', enabled: true, dependsOn: ['a'] },
  { key: 'c', enabled: true, dependsOn: ['b'] },
]);
```

Evaluating in dependency order ensures that the cascade works at any depth. This is handled internally by the library, so you can declare your features in any order.

### Configuration Errors
`createFeatures` validates the dependency graph at construction. It will throw a `FeatureConfigError` if it detects:
- **Cycles**: e.g., `A` depends on `B`, and `B` depends on `A`.
- **Unknown Dependencies**: A feature depends on a key that isn't configured.
- **Duplicates**: Two features share the same key.

## Defining Rules and Conditions

Rules allow you to activate features based on the user's context.

```ts
{
  key: 'beta-banner',
  enabled: true,
  rules: [
    { id: 'internal', when: [{ field: 'roles', op: 'contains', value: 'staff' }] },
    { id: 'ramp', rollout: { percent: 10 } },
  ],
}
```

### Condition Operators

| `op` | Effect | Example |
| :--- | :--- | :--- |
| `before` / `after` | Checks if `now` is before/after an instant. | `value: '2026-10-01T00:00:00Z'` |
| `day-of-week` | Checks if `now` falls on specific weekdays in a zone. | `zone: 'Europe/Stockholm'`, `value: ['mon']` |
| `eq` / `ne` | Strict equality or inequality. | `value: 'bookseller'` |
| `in` / `not-in` | Checks if the value is in/not in an array. | `value: ['admin', 'staff']` |
| `contains` | Checks if the field (array) contains the value. | `value: 'staff'` |

**Important**: To ensure consistency across different timezones, all date-time strings must include an offset (e.g., `+09:00` or `Z`). Strings without offsets are rejected at construction to prevent "floating" time windows.

## Type-Safe Keys and Variants

If you define your configuration as an array literal, TypeScript infers the keys and variant names automatically.

If your configuration comes from a JSON file or variable, you can provide a schema interface to maintain type safety:

```ts
interface Flags {
  'new-checkout': never;
  'express-pickup': { variant: 'control' | 'blue'; value: never };
}

const features = createFeatures<Flags>(config);
```

This ensures that calling `features.isEnabled('wrong-key')` is a compile error, and `features.variantOf('express-pickup')` correctly returns `'control' | 'blue' | undefined`.
