## How to Install an Observer

When an `@evanion/feature` feature is off for a customer, the decision says whether the kill switch, a rollout, a parent or a time window turned it off, and the caller usually discards that decision. An observer keeps it.

You install the observer as the `observe` option when calling `createFeatures`. The store calls it once for each call in the table below, and the event carries the value that call returned.


### The Four Event Types

Every `@evanion/feature` event carries a standard envelope: the `at` instant, a `subject` read off the context's `targetingKey` by default, and the `version` option of `createFeatures` when you set one. The payload depends on the call:

| Event Type   | Call                             | Payload                                                         |
| :----------- | :------------------------------- | :-------------------------------------------------------------- |
| `resolve`    | `resolve(context)`               | A record of decisions for every configured feature.             |
| `is-enabled` | `isEnabled(key, context)`        | The specific decision for that one key.                         |
| `plan`       | `plan(context)`                  | The build-time partition of settled vs. deferred features.      |
| `toggle`     | `toggle(key, enabled, context?)` | The result of the change, a refused `unknown-feature` included. |

`variantOf` and `valueOf` report nothing, and `isEnabled` for a key the store was not built with reports nothing either. `isEnabled` resolves the whole store to answer one question, and its event carries only the one decision the caller received:

```ts twoslash file=libs/feature/docs/examples.md region=observe-one-key

```

## An observer never awaits and never changes an outcome

An `@evanion/feature` observer is called and the engine immediately moves on. If the observer returns a promise, the engine attaches a rejection handler but **does not await** the result. This ensures that a slow audit transport (e.g., a network call) never slows down the user's request.

Measured at forty features on an Apple M1 Pro under Node 24.20.0, the bare call ran at 23 microseconds, a synchronous no-op observer at 41, and an `async` no-op observer at 44. The deep freeze described below accounts for that difference, and the emit and the thenable check stay within run-to-run noise of the bare call. So the number anyone should care about is what their own hook body does.

### Read-Only Payloads

When an observer is installed, the library deeply freezes the decision records before emitting them. This prevents an observer from accidentally modifying a decision and changing the outcome for the user. The caller receives the same frozen object, so `resolve`, `plan` and `toggle` on an observed store answer a value that throws a `TypeError` on a write.

The freeze happens only under an installed observer, so the package behaves differently under two configurations. At forty features the freeze adds 18 microseconds to a 23 microsecond `resolve`, and freezing on every call would charge that to every user of the package whether or not they observe anything. A store nobody observes hands its record to nobody else, so the freeze protects nothing there. An application that edits a decision installs no observer, or copies the record first.

## When an observer throws

If an `@evanion/feature` observer throws an error or returns a rejected promise, the engine catches it and forwards it to `onObserveError`. The original call to `resolve` or `isEnabled` still returns the correct value to the user; the failure of the observer does not crash the application.

```ts twoslash file=libs/feature/docs/examples.md region=observe-failure

```

With no `onObserveError`, the engine writes one `console.warn` per distinct failure, at most twenty per store, and none when `NODE_ENV` is `production`. An `onObserveError` that throws is reported the same way, and the engine does not call it again for that event.

## Records in flight are lost at exit

Because `@evanion/feature` never awaits an observer, a promise it never awaited and a buffer the application has not drained are both gone when the process exits. Drain the buffer before the process exits.

If your transport is asynchronous (e.g., a remote logging service), the observer pushes events into a local buffer and returns, and the application drains that buffer at a concurrency it owns.

```ts twoslash file=libs/feature/docs/examples.md region=observe-buffer

```

A server drains on `SIGTERM`. A browser drains on `visibilitychange` and writes with `navigator.sendBeacon`, because an unload cancels a `fetch` the page had already started. A native client writes to a local queue that persists across a process restart. A phone's operating system suspends a process without warning, so an application reporting from a phone drains on the background transition.

`Features` declares no `drain()`. Every real transport already owns a flush, and a store-level one would have to agree with it.

## `correlateBy` and what reaches an event

An `@evanion/feature` event carries no `EvaluationContext`. It carries the instant the call settled on, the value the call returned, and a subject identifier copied out as a string or number. `correlateBy` names the context field that identifier is read from, and it defaults to `targetingKey`.

```ts twoslash file=libs/feature/docs/examples.md region=observe-correlate

```

The default discloses nothing on its own. The engine evaluates in your own process and sends nothing upstream, and the subject on an event is the value your application put on its own `EvaluationContext` a moment earlier. A library that returns a caller its own data discloses nothing, and an application that forwards the event off the box has made that decision itself. An application bucketing on a raw customer ID points `correlateBy` at a field carrying a pseudonym.

## Exposure tracking is not what this seam carries

The `observe` option of `@evanion/feature`, the seam this page covers, reports a **decision** (observation). An **exposure** is a customer seeing the feature, and the seam does not report one.

### The Observation Gap

Observation happens when `resolve()` is called. In a server-side render, this occurs once per request. If your store has 40 features, the one `resolve` event carries 40 decisions. However, the user might only actually see 3 of those features on the page.

If you use the observer to track experiment "exposures," your data will be heavily skewed by features that were resolved but never actually rendered.

### The Correct Pattern: The Client-Side Ping

Server Components cannot track when they are actually seen by a user. So the application records exposure where it renders, in a small client component, off the decision it already holds. The component calls `useFeature('checkout-cta')` and records `decision.variant`, `decision.assignment?.source`, `decision.assignment?.bucket` and `decision.rule` in an effect:


The server render runs no effect, so it records nothing. This ensures that an exposure is only recorded if the component is actually delivered to the browser and mounted, providing the only accurate denominator for your A/B test results.

`useFeature` returns the whole decision, which carries every field that record needs. `useVariant` returns `variant` and `value` alone, so a component that only renders the assigned variant calls that one, and a component that writes an exposure record calls `useFeature`.

## What the seam does cover

An `@evanion/feature` observer covers decisions, as decisions. An operator reads the `no-rule-matched` breakdown and the `dependency-off` cause off a `resolve` event. An auditor reads a `toggle` event to see what was turned off and which dependants went with it, and a `version` on every event shows which configuration each replica decided under during a rollout.

[API reference](../api) lists every option `createFeatures` takes, `observe`, `onObserveError`, `correlateBy` and `version` among them.
