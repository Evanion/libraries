# Observing

`observe` is the primary hook for monitoring feature flag decisions in real-time. By installing an observer on your feature store, you can receive a stream of events every time a flag is resolved or modified.

## The Problem: The "Black Box" of Feature Resolution

When a feature is disabled for a user, it's often a mystery *why*. Was it the master kill switch? A failed rollout? A dependency that was off? A time window that expired?

Without observability, you are forced to manually trace the dependency graph or guess based on the user's context. `observe` turns the resolution engine into a transparent stream of events, allowing you to audit every decision in real-time.

## How to Install an Observer

You install an observer as an option when calling `createFeatures`. The observer is a callback that is executed every time an entry point is called.

### The Four Event Types

Every event carries a standard envelope (`at` timestamp, `subject` identifier, and `version`). The payload depends on the entry point:

| Event Type | Entry Point | Payload |
| :--- | :--- | :--- |
| `resolve` | `resolve(context)` | A record of decisions for every configured feature. |
| `is-enabled` | `isEnabled(key, context)` | The specific decision for that one key. |
| `plan` | `plan(context)` | The build-time partition of settled vs. deferred features. |
| `toggle` | `toggle(key, enabled)` | The result of the configuration change. |

**Performance Note**: `isEnabled` resolves the whole store to answer one question. If you need to check multiple flags, call `resolve()` once and read from the result.

## Design Constraints for Observers

To ensure that observability doesn't become a performance bottleneck or a source of crashes, the library enforces several strict rules:

### 1. Observers Never Block
The engine calls the observer and immediately moves on. If the observer returns a promise, the engine attaches a rejection handler but **does not await** the result. This ensures that a slow audit transport (e.g., a network call) never slows down the user's request.

### 2. Read-Only Payloads
When an observer is installed, the library deeply freezes the decision records before emitting them. This prevents an observer from accidentally modifying a decision and changing the outcome for the user.

### 3. Error Isolation
If an observer throws an error or returns a rejected promise, the engine catches it and forwards it to `onObserveError`. The original call to `resolve` or `isEnabled` still returns the correct value to the user; the failure of the observer does not crash the application.

## Handling the Event Stream

Because the library never awaits an observer, you must handle the "fire and forget" nature of these events.

If your transport is asynchronous (e.g., a remote logging service), you should push events into a local buffer and drain that buffer at a concurrency you control.

```ts no-run
const pending: FeatureEvent<Flags>[] = [];

const features = createFeatures(definitions, {
  observe: (event) => {
    pending.push(event);
  },
});

// Drain the buffer on process exit or via a background timer
process.on('SIGTERM', async () => {
  await transport.send(pending.splice(0));
});
```

## Observation vs. Exposure: The RSC Perspective

In a modern full-stack architecture, especially with React Server Components (RSC), it is critical to distinguish between the **decision** (Observation) and the **experience** (Exposure).

### The Observation Gap
Observation happens when `resolve()` is called. In a server-side render, this occurs once per request. If your store has 40 features, the observer emits 40 events. However, the user might only actually see 3 of those features on the page. 

If you use the observer to track experiment "exposures," your data will be heavily skewed by features that were resolved but never actually rendered.

### The Correct Pattern: The Client-Side Ping
To track actual exposure in an RSC environment, you should trigger the event at the render site. Since Server Components cannot track when they are actually seen by a user, you should use a small client-side "Tracking Component."

```tsx
// components/ExposureTracker.tsx
'use client';
import { useEffect } from 'react';

export function ExposureTracker({ feature, variant }) {
  useEffect(() => {
    analytics.exposure({ feature, variant });
  }, [feature, variant]);

  return null;
}
```

Then, in your Server Component:

```tsx
// app/page.tsx
async function Page() {
  const decision = features.resolve({ userId: '123' }).['new-feature'];
  
  return (
    <div>
      {decision.enabled && (
        <>
          <ExposureTracker feature="new-feature" variant={decision.variant} />
          <NewFeatureComponent />
        </>
      )}
    </div>
  );
}
```

This ensures that an exposure is only recorded if the component is actually delivered to the browser and mounted, providing the only accurate denominator for your A/B test results.
