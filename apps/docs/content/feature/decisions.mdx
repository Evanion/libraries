# Decisions

Resolving a feature is more than a boolean check. To make a feature flag useful for debugging and operations, you need to know not just *if* a feature is enabled, but *why* it is enabled (or disabled).

## Resolving Features

There are two primary ways to check a feature's state:

1. **`features.isEnabled(key, context)`**: Returns a simple boolean. This is the fastest way to check a flag in your business logic.
2. **`features.resolve(context)`**: Returns a complete record of every feature in the store and its current decision.

**Performance Tip**: Call `resolve()` once per request and store the result. Calling `isEnabled()` repeatedly is expensive because it re-evaluates the entire dependency graph for every single call.

### Example: Resolving a Request
```ts
const decisions = features.resolve({ 
  now: novemberFirst, 
  targetingKey: 'cust-0101' 
});

// {
//   'new-checkout': { key: 'new-checkout', enabled: true, reason: 'rule-match', rule: 'after-launch' },
//   'express-pickup': { key: 'express-pickup', enabled: true, reason: 'default-on' },
// }
```

## Anatomy of a Decision

A `Decision` object provides a detailed audit trail for every feature. While `enabled` is the only field your application needs, the other fields are designed for operators.

| Field | Meaning |
| :--- | :--- |
| `enabled` | The final answer (true/false). |
| `reason` | Why the feature resolved this way (e.g., `rule-match`, `dependency-off`). |
| `rule` | The specific rule that matched (used when `reason` is `rule-match`). |
| `blockedBy` | The immediate parent that forced this feature off. |
| `cause` | The root ancestor that is off for its own reason. |
| `variant` | The assigned variant (if the feature declares variants). |
| `value` | The value associated with the assigned variant. |
| `assignment` | Details on how the variant was assigned (e.g., `weighted`, `pinned`). |

### Understanding the "Reason"
The `reason` field tells you exactly which part of the logic decided the outcome:

| `reason` | Meaning |
| :--- | :--- |
| `default-on` | Enabled because it has no rules. |
| `rule-match` | Enabled because a specific rule matched. |
| `explicitly-off` | Disabled because `enabled` was set to `false`. |
| `no-rule-matched` | Enabled by default, but no rules were met; carries a per-rule breakdown. |
| `dependency-off` | Disabled because a parent dependency is off. |

## Reading the Dependency Cascade

When a parent feature is disabled, it triggers a cascade. If you have a chain `A $\rightarrow$ B $\rightarrow$ C` and you turn off `A`, the decisions for `B` and `C` will both report `reason: 'dependency-off'`.

- `blockedBy` identifies the immediate edge (e.g., `C` is blocked by `B`).
- `cause` walks the chain to the root failure (e.g., `C` is ultimately off because `A` is `explicitly-off`).

This allows an operator to see a "Blocked" flag and immediately identify the root cause without manually tracing the dependency graph.

## Why a Rule Did Not Match

When a feature resolves to `false` because of `no-rule-matched`, the decision includes a detailed breakdown of every rule and why it failed.

```ts
// { 
//   key: 'k', 
//   enabled: false, 
//   reason: 'no-rule-matched', 
//   rules: [
//     { rule: 'rule-d69c7f2b', matched: false, failed: { field: 'role', op: 'eq', value: 'bookseller' } }
//   ] 
// }
```

If a condition failed, the `failed` object names the exact field, operator, and value that caused the mismatch. If a rollout failed, the `rollout` object provides the bucket and percentage.

## Managing State with `toggle`

`toggle` is the only way to modify the stored intent of a feature. It sets the `enabled` property and returns a report of which dependents will be affected by the change.

```ts
const result = features.toggle('new-checkout', false);
// { ok: true, key: 'new-checkout', enabled: false, willDisable: ['express-pickup', 'demo-night'] }
```

This allows a UI to confirm a change before applying it: "Turning off New Checkout will also disable Express Pickup and Demo Night. Proceed?"

## Inspecting the Store

You can inspect the internal state of the feature store using these properties:
- `features.keys`: Every configured key, in order.
- `features.config`: The deeply frozen configuration object.
- `features.definition(key)`: The specific definition for one feature.
- `features.dependants(key)`: A list of all features that depend on the given key.
