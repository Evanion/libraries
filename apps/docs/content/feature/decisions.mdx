## Resolving Features

`@evanion/feature` gives you two primary ways to check a feature's state:

1. **`features.isEnabled(key, context)`**: Returns a simple boolean. It returns `false` for a key the store was not built with.
2. **`features.resolve(context)`**: Returns a complete record of every feature in the store and its current decision.

Both are pure functions of the configuration and the context, and both write nothing. `context` is optional, and a context with no `now` field reads the clock at the call.

`isEnabled()` evaluates the whole dependency graph on every call, so a request that reads several flags calls `resolve()` once and keeps the record.

## Anatomy of a Decision

A `Decision` object from `@evanion/feature` provides a detailed audit trail for every feature. While `enabled` is the only field your application needs, the other fields are designed for operators.

| Field        | Meaning                                                                   |
| :----------- | :------------------------------------------------------------------------ |
| `enabled`    | The final answer (true/false).                                            |
| `reason`     | Why the feature resolved this way (e.g., `rule-match`, `dependency-off`). |
| `rule`       | The specific rule that matched (used when `reason` is `rule-match`).      |
| `rules`      | One outcome per rule (used when `reason` is `no-rule-matched`).           |
| `blockedBy`  | The immediate parent that forced this feature off.                        |
| `cause`      | The first ancestor that is off for a reason of its own.                   |
| `variant`    | The assigned variant (if the feature declares variants and resolved on).  |
| `value`      | The value associated with the assigned variant.                           |
| `assignment` | Details on how the variant was assigned (e.g., `weighted`, `pinned`).     |

Every field except `enabled` is output only. Nothing in the library reads them back to decide anything.

### Understanding the Reason

The `reason` field tells you exactly which part of the logic decided the outcome:

| `reason`          | Meaning                                                                     |
| :---------------- | :-------------------------------------------------------------------------- |
| `default-on`      | Enabled because it has no rules.                                            |
| `rule-match`      | Enabled because a specific rule matched.                                    |
| `explicitly-off`  | Disabled because `enabled` was set to `false`.                              |
| `no-rule-matched` | `enabled` is `true` and rules exist, but none matched; carries a breakdown. |
| `dependency-off`  | Disabled because a parent dependency is off.                                |

## Managing State with `toggle`

`toggle` is the only way to modify the stored intent of a feature in `@evanion/feature`. It sets the `enabled` property, applies the change at once, and returns a report of which dependants went off with it. The store below is the same three-flag chain, before any toggle:

`willDisable` holds only the dependants that resolved on before the write and off after it. Both sides are evaluated against one context, the optional third argument of `toggle(key, enabled, context)`, and with none both read an empty context at the current time. `willDisable` is empty when enabling. This allows a UI to report the full effect of a change: "Turning off Express Pickup also disabled Demo Night Booking." A key the store was not built with returns `ok: false` and never throws.

## Inspecting the Store

You can inspect the state of an `@evanion/feature` store using these properties:

- `features.keys`: Every configured key, in configuration order.
- `features.config`: The deeply frozen configuration array.
- `features.definition(key)`: The specific definition for one feature, or `undefined`.
- `features.dependants(key)`: Every feature that depends on the given key, transitively, in dependency order.
