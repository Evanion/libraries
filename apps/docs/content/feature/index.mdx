# @evanion/feature

**Manage complex feature rollouts with dependency-aware toggles.**

Most feature flag systems treat every flag as an independent switch. But in real-world product development, features are rarely independent. A "Express Pickup" feature might depend on the "New Checkout" being enabled first. If the parent is off, the child must be off, regardless of its own settings.

`@evanion/feature` solves this by implementing a hierarchical decision engine. It ensures that feature dependencies are respected transitively: if a parent flag resolves to "off," all its dependents are automatically disabled without requiring manual updates to every child flag.

## The Problem: The "Divergent State" Trap

When features have dependencies, managing them as independent flags leads to inconsistent states. For example, you might accidentally enable "Express Pickup" for a user who isn't on the "New Checkout" flow.

To prevent this, you would either have to:
- **Write manual checks** in every component: `if (features.newCheckout && features.expressPickup)`.
- **Manage state manually**: Update every child flag whenever a parent changes.

Both approaches are error-prone and clutter your business logic with infrastructure concerns.

## Solution: Dependency-Aware Resolution

`@evanion/feature` moves the dependency logic into the resolution engine. When you ask if a feature is enabled, the library automatically checks the entire dependency chain.

## Architecture: Core vs. React

The library is split into two parts to maximize flexibility and performance:

### 1. The Core (`@evanion/feature`)
The core is a framework-agnostic engine. It has no dependencies and runs anywhere: in a Node.js API, a build script, or a serverless function. It provides the pure functions needed to resolve flags and plan rollouts.

### 2. The React Adapter (`@evanion/feature/react`)
The React adapter provides a `FeatureProvider` and specialized hooks (`useFeature`, etc.) to make the core accessible within a React tree. To keep the core lean and RSC-compatible, the adapter is a separate entry point.

## Understanding a "Decision"

When you resolve a feature, the library returns more than just a boolean. It returns a **Decision** object:


- **`enabled`**: The final answer (true/false).
- **`reason`**: A human-readable explanation of *why* the feature is on or off.

The `reason` field is critical for operators and developers. If a feature is unexpectedly off, the reason will explicitly state which parent dependency blocked it, eliminating the guesswork during debugging.

## Design Principle: The Store Never Writes

A key design choice in `@evanion/feature` is that the resolution process is a pure function of `(config, context, now)`.

The engine never writes resolved values back into the configuration. This ensures:
- **Audit Integrity**: Your configuration remains a record of *intent*, not a log of results.
- **Temporal Consistency**: If a time-windowed flag expires, `resolve()` immediately starts returning `false` for all dependents without needing a database update.
- **Statelessness**: Multiple processes resolving the same context at the same time will always agree.
