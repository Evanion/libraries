# Rollouts

A rollout allows you to release a feature to a specific percentage of your users. The goal is to ensure that the experience is stable and consistent: if a user is in the "10%" cohort, they must stay in that cohort across different requests, processes, and devices.

## The Problem: The "Unstable Experience"

Many simple rollout implementations use a random coin flip for every request. This is unacceptable for a real product because:
- **User Confusion**: A user might see a new feature on one page, but it disappears on the next.
- **Data Corruption**: If a feature changes how data is saved, flipping the flag mid-session can lead to corrupted records.
- **Impossible Debugging**: It is impossible to reproduce a bug if the user's feature set is changing every second.

## Solution: Stable, Deterministic Bucketing

`@evanion/feature` uses a deterministic hashing approach to ensure a user's experience is locked. Instead of randomness, it computes a "bucket" based on a seed and a targeting value.

### How a Bucket is Derived
The library uses **MurmurHash3** to hash the combination of the `seed` and the `targetingKey` (e.g., a user ID). This hash is normalized into a value between `[0, 1)`.

This approach provides three critical guarantees:
1. **Stability**: The result is a pure function of the input. The same user always lands in the same bucket.
2. **Decorrelation**: Because the `seed` defaults to the feature key, a user will land in different buckets for different features. A user who is "lucky" and gets into a 1% rollout for Feature A is not automatically in the 1% rollout for Feature B.
3. **Monotonicity**: The bucket value is independent of the percentage threshold. If you raise a rollout from 10% to 25%, you only *add* new members to the cohort. No one who already had the feature will suddenly lose it.

## Defining a Rollout

A rollout is defined as a conjunct of a rule. A rule that has both a `when` condition and a `rollout` will only match if the user satisfies the conditions AND falls within the bucket range.

```ts
{ 
  rollout: { 
    percent: 25, 
    by: 'targetingKey', 
    seed: 'holiday-cohort' 
  } 
}
```

| Field | Default | Meaning |
| :--- | :--- | :--- |
| `percent` | (Required) | The threshold (0 to 100). |
| `by` | `'targetingKey'` | The field in the context used for bucketing. |
| `seed` | The feature key | The salt used for the hash. |

### Edge Cases and Constraints
- **Missing Targeting Keys**: If the context does not carry the field specified in `by`, the rollout is automatically rejected. This prevents "incomplete" users from accidentally getting into a ramp.
- **Data Types**: Only `string` and `number` are usable as bucketing values. Objects, booleans, or nulls are treated as absent.
- **Exact Bounds**: A `percent` of `0` includes nobody; `100` includes everybody.

## Why MurmurHash3?

Many libraries use a simple modulus (e.g., `hash % 100`). This is problematic because it only uses the "low bits" of the hash, which can lead to poor distribution (modulo bias). 

`@evanion/feature` uses MurmurHash3's finalization to mix the entire 32-bit word, ensuring a uniform distribution. It also uses length-prefixed seeding to prevent "collision attacks" where different combinations of seeds and values produce the same hash.

## Exported Primitives

For snapshot testing or predictive analysis (e.g., "Which 1,000 users will see this ramp?"), the library exports the underlying primitives:

```ts
import { bucketOf, inRollout, murmur3 } from '@evanion/feature';
```

These functions allow you to compute the result of a rollout without creating a full feature store.
