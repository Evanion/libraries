## Stable, Deterministic Bucketing

`@evanion/feature` keeps a customer in a rollout from one page to the next, because a customer who loses the new checkout between two pages cannot finish an order and nobody can reproduce the bug they report. It computes a bucket from a seed and a targeting value, using the hash behind the `inRollout` call [Getting Started](../getting-started#ask-which-tenth-a-customer-is-in) asked about two customers.

<Probe package="feature" probe="rollout" />

The probe calls `inRollout(id, 10, 'new-checkout')` for any id you type, and the section below derives the bucket behind its answer.

### How a Bucket is Derived

The library hashes the `seed` and the `targetingKey` (e.g., a customer ID) with **MurmurHash3** into a bucket in `[0, 1)`, and a customer is in a rollout when the bucket times 100 is below `percent`.

This approach provides these guarantees:

1. **Stability**: The result is a pure function of the input. The same user always lands in the same bucket.
2. **Decorrelation**: Because the `seed` defaults to the feature key, a user will land in different buckets for different features. A customer in the new checkout's 1% is not, for that reason, in express pickup's 1%.
3. **Monotonicity**: The bucket value is independent of the percentage threshold. If you raise a rollout from 10% to 25%, you only _add_ new members to the cohort. No one who already had the feature will suddenly lose it. Lowering it removes the highest buckets first.

## Defining a Rollout

An `@evanion/feature` rollout is one more condition of the rule that carries it. A rule that has both a `when` list and a `rollout` matches only if the customer satisfies the conditions AND falls within the bucket range.

```ts twoslash file=libs/feature/README.md region=rollout-spec

```

| Field     | Default          | Meaning                                      |
| :-------- | :--------------- | :------------------------------------------- |
| `percent` | (Required)       | The threshold (0 to 100).                    |
| `by`      | `'targetingKey'` | The field in the context used for bucketing. |
| `seed`    | The feature key  | The salt used for the hash.                  |

A feature-level `seed` on the definition replaces the key for every rollout in that feature, and a rule's `rollout.seed` replaces it for that rule alone. Set a seed only to correlate two features deliberately, for example to keep a pair of flags rolling out to the same cohort.

### Edge Cases and Constraints

- **Missing Targeting Keys**: If the context does not carry the field specified in `by`, the rollout is automatically rejected, even at 100%. So a context with no customer id never joins a rollout.
- **Data Types**: Only `string` and `number` are usable as bucketing values. Objects, booleans, or nulls are treated as absent.
- **Exact Bounds**: A `percent` of `0` includes nobody; `100` includes every context that carries the bucketing field.

## Why MurmurHash3?

Many libraries use a simple modulus (e.g., `hash % 100`). This is problematic because it only uses the "low bits" of the hash, and a hash such as FNV-1a mixes those bits poorly, which skews the distribution.

`@evanion/feature` uses MurmurHash3's finalization to mix the entire 32-bit word and takes the bucket from all 32 bits, ensuring a uniform distribution over 2^32 buckets. It also length-prefixes the seed, so a seed and value pair such as (`ab`, `c`) can never hash the same as (`a`, `bc`), and flags whose keys share a prefix do not share buckets.

## Exported Primitives

For snapshot testing or predictive analysis (e.g., "Which 1,000 customers will see this rollout?"), `@evanion/feature` exports the underlying primitives `bucketOf`, `inRollout` and `murmur3`:


These functions allow you to compute the result of a rollout without creating a full feature store. `inRollout(value, percent, seed)` is the whole of what a rollout decides once the bucketing value is known, and `bucketOf(value, seed)` returns the bucket it compares.
