# Variants

A feature flag doesn't have to be a simple on/off switch. Often, you want to test multiple versions of a feature—such as two different button labels for an A/B test—and ensure that each user sees the same version consistently. This is where **Variants** come in.

## The Problem: The "Inconsistent Experience"

When running an A/B test, you might use a random coin flip to decide which variant a user sees. But if the user refreshes the page, they might see a different variant. This not only ruins the user experience but also invalidCates your experimental data, as users are exposed to multiple versions of the same feature.

`@evanion/feature` solves this by using deterministic bucketing. A user's variant is a pure function of their ID and the feature's configuration, ensuring they see the same version across every request, process, and device.

## How Variants Work

When a feature is enabled and declares variants, the library assigns one of those variants to the user.

### Key Concepts:
- **Weight**: Each variant has a weight. These are relative, not absolute. A split with weights `3` and `1` results in a 75%/25% distribution.
- **Value**: You can attach a specific value to a variant (e.g., `control: 'Blue Button'`, `compact: 'Green Button'`). This allows your components to remain agnostic of the variant names.
- **Assignment Source**: The `assignment` field tells you how the variant was chosen (e.g., `weighted`, `pinned`, or `sticky`).

## Deterministic Bucketing and Order

To ensure stability, the library hashes the user's targeting key and a seed. The resulting bucket determines the variant.

### The Importance of `order`
By default, variants are bucketed based on their position in the configuration array. However, if you reorder the array in a future deploy, you might accidentally shift users from one variant to another.

To prevent this, you can provide an explicit `order` property. This pins the variant to a specific bucket range regardless of its position in the array, ensuring that updates to the config don't reshuffle your users.

## Advanced Variant Control

### Pinning via Rules
You can override the weighted distribution for specific users. For example, you might want all "Staff" members to see the `blue` variant regardless of their bucket.

```

When a rule matches, the variant is "pinned." The `assignment.rule` field identifies which rule caused the override, and the `bucket` is absent because no random assignment took place.

### Sticky Variants
If you change the weights of a variant, some users will naturally move to a different bucket. To prevent this, you can use `stickyVariants` to store a user's prior assignment in their session state.

```

A sticky entry wins over the weights, ensuring that a user who has already seen a variant continues to see it even after the rollout percentages change.

## Edge Cases

### Missing Targeting Keys
If a user's context is missing the field used for bucketing (e.g., they are not logged in), the library assigns the **fallback** (the first variant in the bucketing order). This ensures the app still renders a valid version of the feature.

### Features that resolve "Off"
If a feature is disabled or blocked by a dependency, it carries no variant, no value, and no assignment. `assignVariant` only runs for features that have successfully resolved to "on."
