## How Variants Work

When an `@evanion/feature` feature is enabled and declares variants, the library assigns one of those variants to the customer from the same bucket [Rollouts](../rollouts) derives, under a separate seed. A customer who saw two variants would count in both arms of the test, so the assignment never moves between requests.

```

### Weights, Values and Assignment

- **Weight**: Each variant has a weight. These are relative, not absolute. A split with weights `3` and `1` results in a 75%/25% distribution.
- **Control**: The first variant in bucketing order is the control, the one a customer gets when nothing else decides.
- **Value**: You can attach a specific value to a variant (e.g., `blue: { label: 'Get it' }`). This allows your components to remain agnostic of the variant names. A variant that declares no value leaves `value` off the decision.
- **Assignment Source**: The `assignment` field tells you how the variant was chosen: `weighted`, `pinned`, `sticky`, or `fallback`.

```

## Bucketing Order and Seed

`@evanion/feature` walks a feature's variants in order, and each one takes a band of the bucket range as wide as its share of the weight. The bucket's band decides the variant.

### The Importance of `order`

By default, the walk follows each variant's position in the `variants` array. If you reorder the array in a future deploy, the bands move, and customers move between variants with them.

An explicit `order` on each variant fixes its position in the walk, so reordering the array moves nobody. It does not fix the bands: a weight change still moves the boundaries. A configuration document a store reads as JSON is refused unless every variant declares `order`.

```ts twoslash file=libs/feature/docs/examples.md region=variant-order

```

### The Variant Seed

`variantSeed` defaults to the feature's `seed` (or its key) followed by `:variant`, so the split is bucketed apart from the rollout. Setting it to the rollout's own seed correlates the two: every member of a 50% rollout sits below the same 0.5 boundary a 50/50 split uses, and all of them get the control.

## Advanced Variant Control

### Pinning via Rules

You can override the weighted distribution of an `@evanion/feature` variant for specific customers. For example, you might want every bookseller to see the `blue` variant regardless of their bucket.

```ts twoslash file=libs/feature/docs/examples.md region=variant-pin

```

When a rule matches, the variant is "pinned." The `assignment.rule` field identifies which rule caused the override, and the `bucket` is absent because no weighted assignment took place.

### Sticky Variants

If you change the weights of a variant, some customers move to a different variant. To prevent this, your application hands back a customer's prior assignment in the context's `stickyVariants` field, keyed by feature, from wherever it keeps session state. The library reads it and writes no storage of its own.

```ts twoslash file=libs/feature/docs/examples.md region=variant-sticky

```

A sticky entry wins over the weights, ensuring that a user who has already seen a variant continues to see it even after the weights change. A rule pin still wins over a sticky entry, and an entry naming a variant the feature no longer declares is ignored.

## Edge Cases

### No Bucketing Value

If a customer's context is missing the field used for bucketing (e.g., they are not logged in), `@evanion/feature` assigns the control, and `assignment.source` reads `fallback`. This ensures the app still renders a valid version of the feature.

```ts twoslash file=libs/feature/docs/examples.md region=variant-fallback

```

### Features that resolve "Off"

If an `@evanion/feature` feature resolves off for any reason, it carries no variant, no value, and no assignment. Here no rule matched. A variant is assigned only for a feature that has resolved on.
