## `createFeatures(definitions, options?)`

```ts
function createFeatures<
  const D extends DefinitionsOrConfig,
  O extends Record<
    Exclude<
      keyof O,
      keyof FeatureOptions<AsSchema<InferSchema<DefinitionsOf<D>>>>
    >,
    never
  >,
>(
  definitions: D,
  options?: O & FeatureOptions<AsSchema<InferSchema<DefinitionsOf<D>>>>,
): Features<
  AsSchema<InferSchema<DefinitionsOf<D>>>,
  'observe' extends keyof O ? true : false
>;

function createFeatures<S extends Record<keyof S, VariantInfo | never>>(
  definitions: DefinitionsOrConfig<NoInfer<Extract<keyof S, FeatureKey>>>,
  options?: UnobservedOptions<S>,
): Features<S, false>;

function createFeatures<S extends Record<keyof S, VariantInfo | never>>(
  definitions: DefinitionsOrConfig<NoInfer<Extract<keyof S, FeatureKey>>>,
  options: FeatureOptions<S>,
): Features<S, true>;
```

Validates the dependency graph, deep-clones and freezes the configuration, and
returns the store.

The first parameter can be provided as either a bare definitions array or a
whole document. A `@evanion/feature` author writing four flags in a file passes
the array, while a process whose poller already fetched a document passes that
document without unwrapping it. `DefinitionsOf<D>` recovers the array out of
either form, which is what keeps the variant names inferred from a literal.

When `createFeatures` is called over a document, it throws where
`parseFeatureConfig` reports; both functions call one checker. A store built
from a document lifts the envelope into `features.version` and
`features.envelope`.

| Overload        | Call shape                                              | What it checks                                                                                                                        |
| --------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| First, inferred | An array literal, written inline; no type argument      | Keys, variant names and each variant's value come from the literal. `const` is what keeps those literal types                         |
| Second, named   | A schema the caller names, e.g. configuration from JSON | `createFeatures<Flags>(config)` checks every definition's key against `keyof Flags`; a key `Flags` does not declare fails at the call |

A caller who holds the definitions in a variable writes
`as const satisfies Definitions<Flag>` after the array literal. `satisfies`
checks the literal and leaves the variable the literal's own type, so the first
overload reads the variant names off it. The annotation
`const definitions: Definitions<Flag> = [...]` gives the variable the wider type,
whose `variants` is optional, and `variantOf` then answers `string | undefined`
for every key it covers.

`createFeatures` throws `FeatureCycleError`, `UnknownDependencyError` or
`DuplicateFeatureError` here; evaluation raises none of them. See
[`FeatureConfigError`](#featureconfigerror) and the five classes under it for
what each carries.

### How a misspelled option gets caught

The options settle the second type argument. The first signature reads them as
the type parameter `O` and answers `'observe' extends keyof O ? true : false`,
so a call that writes `observe` at the call site gets the frozen store and a
call that passes no options at all gets the mutable one. `O`'s constraint,
`Record<Exclude<keyof O, keyof FeatureOptions<S>>, never>`, names no member of
`FeatureOptions` and the parameter intersects the two. A type parameter inferred
from an object literal takes the literal's own type, so the compiler runs no
excess property check of its own, and that constraint is what keeps a misspelled
option an error at all. The compiler anchors that error on the `createFeatures`
callee and names no property. A call passing `{ observ: () => undefined }`
reports `TS2769: No overload matches this call`, and the first overload's line
carries `Record<"observ", never>` with `Type '() => undefined' is not assignable
to type 'never'` under it. A reader finds the misspelled name inside that printed
signature.

### Why the schema-naming case takes two signatures

The pair below it exists because TypeScript infers no type argument once a
caller supplies one. `createFeatures<Flags>(config, { observe })` would read `O`
from its default and answer the unobserved form, so the schema-naming case takes
one signature per answer: `UnobservedOptions<S>`, which pins `observe` to
`undefined`, answers `Features<S, false>`, and `FeatureOptions<S>` answers
`Features<S, true>`.

The list stops at three signatures. TypeScript elaborates every candidate for a
failed call while a signature list holds three or fewer, and reports a single
candidate against the argument nodes once the list holds more, which put the
error for a misspelled option on the definitions array.

### Which form a call without a clear answer gets

A call whose options settle neither question answers the frozen form. Options
held in a variable annotated `FeatureOptions<S>`, and a wrapper that forwards an
optional `observe` parameter, both hide the observer from the compiler and both
take that branch, so the compiler refuses a write the runtime refuses once the
observer turns out to be there.

A caller who installs no observer gets the mutable form back by leaving
`observe` out of the options altogether, and `satisfies UnobservedOptions<S>` on
such an object checks the other members without disturbing that answer. An
options object that names `observe` and holds `undefined` in it works only
against the pair that takes a named schema, because the inferring signature asks
whether `O` names the member at all and answers the frozen form for a value that
names it. A wrapper forwarding an optional `observe` parameter has no annotation
available at all: `{ observe } satisfies UnobservedOptions<S>` does not typecheck,
since the forwarded parameter's type is not `undefined`. Such a wrapper branches
on the parameter and calls `createFeatures` once per branch, and its own caller
then reads the union of both forms and narrows it.

See [Observing](/feature/observing) for what an observer receives.

## `Features<S>`

`S` is the schema, so every key position is `keyof S & FeatureKey` and every
variant position is what that key's schema entry declares. `K` below is
`keyof S`.

The second parameter is `Frozen`. A store built with an observer freezes what it
emits and answers the caller with that same object, so `resolve`, `plan` and
`toggle` answer the deeply readonly form for such a store and the mutable form
for a store built without one.

### Naming `Frozen` in an annotation

Take this type off `createFeatures`, and name it in an annotation only where a
declaration demands one. `const store = createFeatures([...])` carries the
`Frozen` the call settled, and `store.resolve()` then answers one form. The
annotation `const store: Features<Flags> = createFeatures([...])` leaves
`Frozen` at its `boolean` default and `resolve` answers the union of both forms,
which assigns to neither `Decisions<Flags>` nor `DeepReadonly<Decisions<Flags>>`.
`DeepReadonly` maps the `Date` a rule outcome can carry to a `ReadonlyDate`, and
that one field is what the union splits on. A declaration that must name the
type names the second parameter with it, `Features<Flags, false>` for a store
built with no observer and `Features<Flags, true>` for one built with an
observer. A function that takes either store names both parameters and stays
generic over `Frozen`.

| Member                           | Returns                                                          | Notes                                          |
| -------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| `keys`                           | `readonly (keyof S & FeatureKey)[]`                              | every key, in configuration order              |
| `config`                         | `readonly FeatureDefinition<keyof S & FeatureKey>[]`             | the stored intent, deeply frozen               |
| `version`                        | `string \| number \| undefined`                                  | the installed document's version               |
| `envelope`                       | `ConfigEnvelope`                                                 | that document's members, deeply frozen         |
| `definition(key)`                | `FeatureDefinition<keyof S & FeatureKey> \| undefined`           |                                                |
| `dependants(key)`                | `readonly (keyof S & FeatureKey)[]`                              | transitive, in dependency order                |
| `resolve(context?)`              | `FrozenWhenObserved<Frozen, Decisions<S>>`                       | a decision per feature; writes nothing         |
| `isEnabled(key, context?)`       | `boolean`                                                        | `false` for an unknown key                     |
| `variantOf(key, context?)`       | `S[K]['variant'] \| undefined`                                   | `undefined` for a key declaring no variants    |
| `valueOf(key, context?)`         | `S[K]['value'] \| undefined`                                     | `undefined` for a key declaring no variants    |
| `plan(context?)`                 | `FrozenWhenObserved<Frozen, Plan<S>>`                            | build-time partition                           |
| `for(context?)`                  | `BoundFeatures<S, Frozen>`                                       | the store bound to one context and one instant |
| `toggle(key, enabled, context?)` | `FrozenWhenObserved<Frozen, ToggleResult<keyof S & FeatureKey>>` | the only writer; reports `willDisable`         |
| `reload(config)`                 | `ReloadResult`                                                   | installs a candidate document, or refuses it   |

`resolve`, `plan`, `variantOf`, `valueOf` and `toggle` all default `context.now`
to `new Date()` at the call.

`variantOf` and `valueOf` take their types off `Decisions<S>[K]`, so a reader of
either sees what the decision for that key carries. Over the store
[Variants](/feature/variants) builds,
`features.variantOf('checkout-cta', { targetingKey: 'user-1' })` answers
`'control'`, and `features.valueOf` on the same key and context answers
`undefined`, because the control variant declares no value.

Both answer `undefined` for a feature that resolved off. On a key whose schema
entry is `never` the return type is `undefined` on its own.

To install a new document, use `reload`, which is the only operation that
writes to `version` and `envelope`. In contrast, a `toggle` leaves both members
unchanged because they identify the document served by a publisher, whereas a
toggle is a local write. If a candidate is refused, every member above remains
at its previous value. See [Distribution](/feature/distribution).

### How `@evanion/feature` handles store types

To store a feature set that arrives at runtime—such as a store `parseFeatureConfig` builds from a fetched document—you use the bare `Features` type. Because `S` defaults to [`Schema`](#schema), the bare form names a store whose schema is determined at runtime.

This bare form is the standard for framework declarations. A Nest provider token holding a store built from a document, a member of Astro's `locals`, and a React Router context each write `features: Features | undefined`.

If you build a store from a literal, it will not fit that slot. When you use `createFeatures([...])`, the compiler infers a schema; the `variantOf` method then answers the variant names that schema declares. Because of this specific inference, the compiler refuses the assignment to the bare form with `TS2322` on the types `variantOf` returns. To fix this, a declaration holding a store built from a literal must name its schema: `Features<Flags>`.

### Handling frozen states in `@evanion/feature`

The bare `Features` form leaves `Frozen` at `boolean`, which means `resolve` and `plan` on the slot answer the union of both freezes.

This affects how decisions are passed through your application:

- A loader carrying the decisions to a page returns `snapshot()` as the bare `DecisionSet`, which holds either freeze.
- A build step names its plan `FrozenWhenObserved<boolean, Plan>`.

## `features.for(context?)`

To ensure a series of feature checks are evaluated against the same moment in time and the same user data, you can bind the store to a specific context. The `features.for(context?)` function performs this by returning a [`BoundFeatures<S, Frozen>`](#boundfeatures).

This handle reads `context.now ?? new Date()` exactly once at the moment of the call; every subsequent method called on that handle resolves using that same instant. This prevents a request from straddling a window boundary. For example, without a handle, calling `isEnabled` at 23:59:59 and again one second later could yield different answers for a `now` rule set for midnight. By using a handle, the result remains consistent for the duration of the request.

If the context provides an explicit `now` value, it takes precedence. This allows tests to pin the clock to a specific moment.

Because a toggle writes intent for every caller rather than asking a question about a specific context, the handle carries no `toggle` method; callers must toggle directly on the store.

A common use case for this pattern is in a NestJS service, an Express handler, or an Astro middleware. These environments can build one handle per request to ask multiple questions without threading the context through every function call or re-reading the clock.

## `BoundFeatures`

<!-- reference @evanion/feature#BoundFeatures example=bound-context -->

`BoundFeatures<S, Frozen>` represents the answers for a single context with the evaluation instant settled. It is the return value of `features.for(context)`.

The handle provides the following members:

- `context`: The context every method resolves against, preserving the caller's own fields and the settled `now` value.
- `resolve()`
- `isEnabled(key)`
- `variantOf(key)`
- `valueOf(key)`
- `plan()`
- `snapshot(options?)`

Each method asks the store the same question as the corresponding member of `Features`, but with the context and instant already supplied. The return types match those of the store; for instance, a store built with an observer will return the deeply readonly form from `resolve` and `plan`.

The settled instant is available as an ISO 8601 string via `snapshot().now`. If `context.now` is an invalid `Date`, it is kept as given. In this case, `resolve()` will still answer, but `snapshot()` will raise the `FeatureConfigError` naming `context/now` (the same error raised by `features.snapshot`).

The handle does not memoise decisions. If a `toggle` or `reload` occurs on the store between two calls on one handle, the second call will reflect that change. This ensures the handle always answers based on the truth held by the store, rather than a stale document.

This binding pattern is mirrored in `@evanion/acl`, where `authorize(subject)` binds a subject in the same way.

The example shows the store being built once, with a handle built per request from a shopper to ask three questions at one single instant.

## `bucketOf`

<!-- reference @evanion/feature#bucketOf example=primitives -->

To determine which bucket a subject falls into during a rollout, `@evanion/feature` uses `bucketOf`. This function calculates a value in `[0, 1)` for a rollout seeded with `seed`. Because the bucket is a pure hash of the pair, it remains consistent across different evaluations, processes, and hosts.

The system provides 2^32 buckets. Since the bucket value does not depend on a percentage, raising a rollout is purely additive; a member who is already in a rollout will never move out.

Snapshot tooling and a test over one rollout call it. A caller passes the seed the rule carries, which `resolve` reads off `rollout.seed`, then the feature's `seed`, then the key.

## `inRollout`

<!-- reference @evanion/feature#inRollout example=primitives -->

To check if a specific value is included in a rollout, `@evanion/feature` provides `inRollout`. This function answers whether a value is inside a `percent` rollout seeded with `seed`. It compares the bucket strictly below the threshold, meaning 0% includes nobody, and since every bucket is below 1, 100% includes everybody.

## `murmur3`

<!-- reference @evanion/feature#murmur3 example=variant-primitives -->

To ensure consistent hashing, `@evanion/feature` implements `murmur3`. This is MurmurHash3, x86 32-bit, operating over the UTF-8 bytes of the input to return an unsigned 32-bit integer. Both `bucketOf` and `configDigest` rely on it, meaning any port to Swift or Kotlin must produce the same numbers.

The package walks the UTF-8 bytes itself, asking its host only for arithmetic and string indexing. An unpaired surrogate encodes as U+FFFD, the same result produced by the Encoding Standard's encoder, ensuring the bytes agree with `TextEncoder` for every possible input.

## `assignVariant`

<!-- reference @evanion/feature#assignVariant example=variant-primitives -->

To determine which variant a user receives for a feature that has resolved on, `@evanion/feature` uses `assignVariant`. If a feature declares no variants, it returns `undefined`.

The function evaluates three possible answers in this order:

1. **Sticky assignments:** A prior assignment stored on `stickyVariants` wins if it names a variant the feature still declares.
2. **Weighted assignments:** If the context carries a usable bucketing value, the weights determine the answer.
3. **Control fallback:** The control answers last. This is the honest answer for an incomplete context: the feature resolved on, so the calling code needs a variant to render, and the control admits nobody to the experiment.

Because only `decide` knows which rule matched, a pin from a matching rule beats all three of these options, and `decide` applies it accordingly.

The definition passed to this function must come from `createFeatures` or have passed `validateVariants` independently. If a weight is non-finite, negative, or sums to zero across the set, or if two variants share an `order`, the function does not throw; instead, the outcome is deterministic and wrong.

## `variantSeedOf`

<!-- reference @evanion/feature#variantSeedOf example=variant-primitives -->

To establish the seed used for variant bucketing, `@evanion/feature` provides `variantSeedOf`. This function gives the seed that `assignVariant` buckets on. If a definition names a `variantSeed`, it gets that string unchanged; otherwise, it receives `${seed ?? key}:variant`.

By default, the seed appends to whatever the rollout seeds on, ensuring the two buckets are independent. If the same pair were hashed for both, every member of a 20% rollout would fall into the lowest 20% of the variant space; consequently, a 50/50 split would give all of them the control, and the experiment would measure nothing.

## `evaluateCondition`

<!-- reference @evanion/feature#evaluateCondition example=evaluate-condition -->

To determine if a specific rule requirement is met, `@evanion/feature` provides `evaluateCondition`.

Every entry point that resolves a decision reaches this function through the rule walk, which asks it for each condition in a rule's `when` and stops at the first one that answers `false`. A caller who holds a condition and a context can call it to get the engine's own answer, which is the mechanism used by a test over one rule and a snapshot tool.

If a condition is defined over a field the context does not carry, it never holds; for this reason, `ne` and `not-in` answer `false` on an absent field. If a `day-of-week` condition names a zone that this runtime cannot format, it raises the host's `RangeError`. While `validateConfig` and `createFeatures` refuse such a zone when the configuration is supplied, a condition written by hand may have passed neither.

## `canonical`

<!-- reference @evanion/feature#canonical example=identity-primitives -->

To ensure that two logically identical configurations produce the same hash regardless of how they were serialized, you need a stable text representation. The `canonical` function solves this by writing one text for a value, ensuring every object's keys are written in sorted order. This allows a producer in another language to emit keys in any order and still agree with a hash taken over the same configuration.

The tool maintains a strict boundary between object keys and array elements: array order survives. Because `in: ['a', 'b']` and `in: ['b', 'a']` test the same membership, sorting a list would claim an equality the function does not generally possess, so `canonical` writes two different texts for them. A document that reorders a list is treated as a document somebody edited.

To handle JavaScript's type idiosyncrasies, `@evanion/feature` applies the following rules:

- An `undefined` property is dropped, so an absent key and a key written as `undefined` agree.
- A `Date` is written as its ISO 8601 string.
- A `bigint` is written as its digits with a trailing `n` (e.g., `10n` for `BigInt(10)`).
- `NaN`, `Infinity`, and `-Infinity` are written behind a `number:` tag (e.g., `number:NaN` for `NaN`).
- Functions and symbols are written using their own `toString()`.

These distinctions are necessary because `JSON.stringify` loses precision—it returns `undefined` for functions and symbols, throws for `bigint`, and writes `null` for all three non-finite numbers. Since `evaluateCondition` compares an attribute condition's value with `===`, a rule holding `eq: NaN` must match no context, whereas one holding `eq: Infinity` matches a context carrying that number. `ruleId` derives a rule's id from this text, meaning those three rules require three distinct ids.

Note that `configDigest` does not read this text. It performs a walk that writes non-finite numbers as `null`. This prevents a discrepancy where one holder parses `1e999` as `Infinity` and another, who cached the document via `JSON.stringify`, holds it as `null`.

To optimize performance, a value that two paths reach is written once and the second path reads a memo. In a diamond 22 levels deep containing 23 objects and 2^22 paths to its leaf, the memo walks 23 of them in 34ms, whereas bare recursion costs 2.8s. The resulting text remains the same—88MB for that diamond—because JSON carries no sharing. At 25 levels, both this function and `JSON.stringify` throw `RangeError: Invalid string length`; a document too deep to digest is a document too deep to serve.

## `ruleId`

<!-- reference @evanion/feature#ruleId example=identity-primitives -->

To identify a rule within a `Decision`, you use `ruleId`. This function determines the id a rule carries, prioritizing an explicit `rule.id` if it exists. If a control plane assigns an id at rule creation, that value wins and the derivation never runs; similarly, an author can write `id: 'staff-only'` to ensure a specific name appears in logs.

When an id must be derived, `ruleId` produces a string starting with `rule-` followed by eight hex digits of FNV-1a over the text of what the rule matches on: each condition, and the rollout's `by` and `seed`. This derivation is stable even if a rule is inserted above it, the list is reordered, a ramp is moved, or the document is emitted by a producer in another language. This is superior to a positional `#0`, which changes as soon as the list moves.

The derivation specifically excludes `rollout.percent`. Because `by` and `seed` decide which subjects a rule can reach and `percent` decides how many of them it reaches now, an operator moving the percentage is running the same rule harder. Including the percentage in the hash would rename the rule on every ramp, causing an event stream from before the ramp to join to nothing after it. Consequently, two rollout rules on one feature that share conditions, `by`, and `seed` will derive the same id unless the author separates them with an explicit `rule.id`.

When calculating a rule's identity, boundaries are processed to eliminate ambiguity between different representations of the same moment in time. A window condition's boundary is hashed as epoch milliseconds, so one instant written three ways reads as one value.

For a boundary that names no valid instant—a string, or a value `Instant` does not admit that a document parsed out of JSON carried in, such as `null`, an object, a boolean, or an array—the package treats the value as literal text and hashes it as its own text. Consequently, two hosts reading the rule against their own zones still derive one id, and two rules carrying different unusable boundaries keep different ids.

To handle values that do not represent a valid point in time, `@evanion/feature` provides exceptions for `Number.NaN` and for a `Date` holding no instant:

- Both are hashed as the text `NaN`, meaning one condition shape derives one id for either. For example, `ruleId` over a rule whose only condition is `{ field: 'now', op: 'after', value: Number.NaN }` and over the same condition carrying `new Date('nonsense')` derives `rule-a2b37cba` either way. Because the operator is hashed alongside the boundary, the same pair of boundaries under `op: 'before'` derives `rule-d7804a19` instead. Where the `Number.NaN` rule and the `new Date('nonsense')` rule sit on one feature, `validateConfig` reports `duplicate-rule-id` for the pair on top of the `invalid-instant` it reports for each boundary.
- Every other number is hashed as its own decimal digits, a number past the range a `Date` holds included. `8640000000000001` and `9e15` are two boundaries `createFeatures` refuses for naming no instant, and the two rules carrying them keep two ids.
- To avoid conflicts, the derivation reads the epoch instead of the text `canonical` writes; this is because `canonical` writes `number:NaN` for the number and `null` for the `Date`. Since that `null` is the text a JSON-borne `null` carries, a rule holding an unreadable `Date` and a rule holding `null` would derive one id.
- Because `createFeatures` refuses every string, number and `Date` that names no instant, this path is what a caller reaching `ruleId` directly gets.

To prevent collisions where a field name abuts an operator, every variable-length part of the text, including `op`, carries its length. This ensures that predicates with similar character sequences but different boundaries are written as different texts. For example, `{ field: 'usernot-', op: 'in' }` and `{ field: 'user', op: 'not-in' }` are opposite predicates and are hashed uniquely.

The use of FNV-1a is a performance choice rather than a security one. Evaluation is synchronous, whereas Web Crypto's `digest` returns a promise, and no security property rests on the difficulty of finding a second rule that hashes the same. The hash walks UTF-16 code units to maintain the cross-language contract that implementations in other languages match.

## `configDigest(config)`

To identify a specific configuration state, `configDigest()` returns a 32-character hex string over the text of a `@evanion/feature` document.

```ts signature
function configDigest(config: FeatureConfig): string;
```

Before the text is taken, the function sorts the keys, drops `undefined` properties, and removes the `digest` and `version` members. Four fixed murmur3 seeds widen the 32-bit hash to a 128-bit digest.

This ensures that two documents differing only in key order or whitespace state one configuration and digest the same. Because the digest survives a JSON hop, two processes that computed one digest hold one configuration. It is not a cryptographic digest.

## `parseFeatureConfig(config, options?)`

To build a `@evanion/feature` store from a document while reporting what was refused, you use `parseFeatureConfig()`.

```ts signature
function parseFeatureConfig<
  S extends Record<keyof S, VariantInfo | never> = Record<
    FeatureKey,
    VariantInfo | never
  >,
>(
  config: FeatureConfig<Extract<keyof S, FeatureKey>>,
  options?: FeatureOptions<S>,
):
  | { ok: true; features: Features<S, boolean> }
  | { ok: false; issues: readonly ConfigIssue[] };
```

This function differs from `createFeatures` over the same document in one way: it throws nothing.


Because a document that arrived as JSON carries no literal, the compiler cannot infer variant names from it. Consequently, the caller must name the schema, such as `parseFeatureConfig<ShopFlags>(document)`. The options are the same `FeatureOptions` `createFeatures` takes, including `observe` and `correlateBy`.

## Types

## `FeatureDefinition`

<!-- reference @evanion/feature#FeatureDefinition -->

To define the features available to your application, you use a `FeatureDefinition`. The array of these is what `createFeatures` takes. A definitions literal gives the store its key union and its variant names, because `key` and `variants` carry the type parameters `InferSchema` reads. See [Configuration](/feature/configuration).

To transmit a feature definition over the wire, `@evanion/feature` uses the [`SerializedDefinition`](#serializeddefinition) type. In this wire form, `rules` and `variants` hold the serialized forms of a rule and of a variant.

## `Definitions`

<!-- reference @evanion/feature#Definitions -->

To define the features available in your application, you provide a set of definitions to `@evanion/feature`. The configuration function `createFeatures` takes one `FeatureDefinition` per feature, keyed on `K`.

You should name this type in a `satisfies` clause rather than using a type annotation. For example, `const definitions = [...] as const satisfies Definitions<Flag>` checks the literal against the type while preserving the literal's own type. This allows the inferring overload to read the variant names directly from the literal. The [`createFeatures`](#createfeaturesdefinitions-options) entry states this rule and explains what an annotation costs a caller.

## `DefinitionsOrConfig`

<!-- reference @evanion/feature#DefinitionsOrConfig -->

When calling `createFeatures` in `@evanion/feature`, you can provide either a bare definitions array or a complete document carried by an envelope. The type `DefinitionsOrConfig` is the union that represents these two shapes; the [`createFeatures`](#createfeaturesdefinitions-options) entry covers both call patterns.

A literal definition has no version, schema, or freshness claim, meaning an author writing four flags in a file owes none of them. Conversely, a process whose poller has already fetched a document can hand that document over without unwrapping it.

## `DefinitionsOf`

<!-- reference @evanion/feature#DefinitionsOf -->

To extract the actual definitions regardless of the input format, `@evanion/feature` uses `DefinitionsOf`. This type resolves the union declared by `DefinitionsOrConfig`: `DefinitionsOf<D>` returns `D` if `D` is a definitions array, the `features` member if `D` is a document, and `never` for any other input.

This distinction is necessary because `InferSchema` reads variant names off a definitions array and constrains its own parameter to one. Consequently, `InferSchema<D>` would stop compiling if `D` might be a document, as `D extends DefinitionsOrConfig` fails that constraint. To solve this, every schema position in the [`createFeatures`](#createfeaturesdefinitions-options) signature writes `InferSchema<DefinitionsOf<D>>` instead of `InferSchema<D>`.

## `InferSchema`

<!-- reference @evanion/feature#InferSchema -->

To determine the schema implied by a definitions array in `@evanion/feature`, you use `InferSchema`. It processes each member of the array, keys the result on that member's `key`, and extracts the variant names and value types from the `variants` property.

The resulting schema depends on how the member is defined:

- **Literal variants:** If a member's `variants` property is required and a literal supplies its names, the entry carries the union of those names at `variant` and the union of the declared value types at `value`. A variant that declares no `value` contributes nothing to that union, so a feature whose variants are split between declaring a value and not declaring one carries only the declared ones at `value`.
- **Missing variants:** If a member has no `variants` key at all, it declares no variants and the entry is `never`. [`Decisions`](#decisions) and [`Plan`](#plan) interpret that `never` to mean "this feature has no variants".
- **Generic definitions:** If a member is typed as [`FeatureDefinition`](#featuredefinition), it carries a `variants` key that the compiler cannot read names from because `FeatureDefinition` declares the property as optional. In this case, the entry is [`VariantInfo`](#variantinfo), and `variantOf` returns `string | undefined`. This occurs for every element of a plain array type.

Because an array held in a variable annotated `Definitions<Flag>` is a plain array type, every one of its members falls into this third case; this is why `as const` is required.

## `AsSchema`

<!-- reference @evanion/feature#AsSchema -->

To ensure a schema is in a form that a generic can accept, `@evanion/feature` uses `AsSchema<T>`. This maps every entry of `T` through `T[K] extends VariantInfo ? T[K] : never`, which is the specific test applied by the constraint `S extends Record<keyof S, VariantInfo | never>`.

The `Features` type constrains its schema parameter this way, but the compiler cannot prove that `InferSchema<D>` satisfies this constraint before a call resolves because `InferSchema` remaps keys and `D` is a bare type parameter. `AsSchema` applies the test so the constraint holds, which is why the first signature of [`createFeatures`](#createfeaturesdefinitions-options) writes `AsSchema<InferSchema<DefinitionsOf<D>>>` at every schema position. Each entry retains its type, including the `never` assigned to features with no variants. A caller never writes this type manually.

## `Schema`

<!-- reference @evanion/feature#Schema -->

A `Schema` in `@evanion/feature` is a map from a feature key to its associated variants. You use this to type a store built from configuration that arrives as JSON, where no literal exists for `InferSchema` to read. If a store is built from a literal, the schema is inferred automatically. `DecisionSet` uses this as the default for its own schema parameter.

While this alias can annotate a value, generics that take a schema use a self-referential constraint instead: `S extends Record<keyof S, VariantInfo | never>`, as seen in `Features`, [`Decisions`](#decisions), and [`Plan`](#plan). This is because the `Schema` alias carries an index signature. A hand-written `interface ShopFlags { preorderBanner: { variant: 'wide' | 'tall' } }` satisfies the constraint because `keyof ShopFlags` names its declared keys, but it does not satisfy the `Schema` alias. For example, the annotation `const flags: Schema = handWritten` reports `TS2322: Type 'ShopFlags' is not assignable to type 'Schema'` with `Index signature for type 'string' is missing in type 'ShopFlags'`, whereas `createFeatures<ShopFlags>(document)` accepts that same interface.

This type represents the TypeScript side of a store's typing. The other side is [`FeatureSchema`](#featureschema), which types the `schema` member of a document read by `validateConfig`.

## `Rule`

<!-- reference @evanion/feature#Rule -->

To control when a feature resolves on, `@evanion/feature` uses a `Rule`. Rules are OR-ed: the feature resolves on when any one of them matches. A rule that declares neither `when` nor `rollout` matches every context, so an author narrowing anything writes at least one of the two. See [Rollouts](/feature/rollouts) for `rollout` and [Variants](/feature/variants) for `variant`.

To transmit a rule over the wire, `@evanion/feature` uses the [`SerializedRule`](#serializedrule) type. This wire form ensures that conditions do not contain `Date` objects.

## `RolloutSpec`

<!-- reference @evanion/feature#RolloutSpec -->

To ramp a feature across a share of subjects, a rule in `@evanion/feature` carries a `RolloutSpec`.

- `percent` defines the share of subjects.
- `by` names the context field to bucket on, defaulting to `targetingKey`.
- `seed` overrides the bucketing seed.

Unless overridden, the seed is the feature's own `seed`, and the feature key when the definition names neither, which decorrelates a subject's bucket across different features. You should override it only to correlate two features deliberately, such as keeping a pair of flags rolling out to the same cohort. See [Rollouts](/feature/rollouts).

## `Condition`

<!-- reference @evanion/feature#Condition -->

To specify a requirement within a rule, you use a `Condition`. A rule's `when` is an array of conditions and every one of them has to hold. `op` discriminates the three members, and `field` is `'now'` on the two that read the clock.

To transmit a condition over the wire, `@evanion/feature` uses the [`SerializedCondition`](#serializedcondition) type. This wire form narrows both the instant and the attribute value to types that JSON can hold.

## `WindowCondition`

<!-- reference @evanion/feature#WindowCondition -->

To restrict a feature to a specific time frame, `@evanion/feature` provides the `WindowCondition`. `value` is an [`Instant`](#instant), and `createFeatures` refuses a boundary that names no moment every host reads the same way.

To transmit a window condition over the wire, `@evanion/feature` uses the [`SerializedWindowCondition`](#serializedwindowcondition) type. In this wire form, the `value` is represented as either an ISO 8601 string or epoch milliseconds.

## `DayOfWeekCondition`

<!-- reference @evanion/feature#DayOfWeekCondition -->

To target users based on the day of the week, you use the `DayOfWeekCondition`. The library hands `zone` to `Intl`, so the host's zone database decides the day and its daylight-saving transitions. A condition that names no zone does not type-check.

## `AttributeCondition`

<!-- reference @evanion/feature#AttributeCondition -->

To match a feature against user or system attributes, you use the `AttributeCondition`. `field` names a context member and `value` is the literal it is compared against. `in` and `not-in` read `value` as the array; `contains` reads the context member as the array.

To transmit an attribute condition over the wire, `@evanion/feature` uses the [`SerializedAttributeCondition`](#serializedattributecondition) type. This wire form narrows the `value` to a `JsonValue`.

## `Weekday`

<!-- reference @evanion/feature#Weekday -->

To specify a day of the week in a condition, use the `Weekday` type. These are the seven lower-case short names, which is what `DayOfWeekCondition.value` holds.

## `EvaluationContext`

<!-- reference @evanion/feature#EvaluationContext -->

To provide the data necessary for a decision, `@evanion/feature` requires an `EvaluationContext`. Every call that resolves a decision takes one.

The context uses an index signature to admit any field a condition reads, while `targetingKey` is the field a rollout buckets on when the spec names none. The library reads `stickyVariants` and writes it nowhere; see [Variants](/feature/variants) for where an application keeps it.

To control how the library evaluates time-based conditions, you provide a `now` property. This property accepts an `Instant`, which can be a `Date` object, the ISO 8601 string that `JSON.stringify` writes in a `Date`'s place, or epoch milliseconds.

This flexibility allows a context to maintain consistency across different environments. Because it supports these formats, a context that crossed an RSC payload, an island's props, a response body, or a cookie resolves every window and day-of-week condition the same way the context it was serialized from did. Similarly, a caller handing on a parsed body passes it straight through.

If a `now` property names no instant, every clock condition becomes unevaluable and answers `false`. Note that `snapshot` refuses such a value outright, as a decision set states its instant specifically as an ISO 8601 string.

## `RuleOutcome`

<!-- reference @evanion/feature#RuleOutcome -->

To understand why a rule did or did not match, you can inspect the `RuleOutcome`. `failed` names the first condition that failed. An outcome `plan()` settled drops it when the walk stepped over a condition the build-time context could not read, because a request carrying that field may fail the rule on that one instead. [Build-time plans](/feature/build-time) states the rule.

## `VariantSpec`

<!-- reference @evanion/feature#VariantSpec -->

To declare one variant of a feature in `@evanion/feature`, an author writes a `VariantSpec`.

- `weight` is relative: weights are normalised across the set, so they do not need to sum to 100, and raising one lowers every other share.
- `order` fixes where the variant sits in the bucketing walk. If an author leaves it out, the array index supplies the value.

A control plane writes `order` explicitly so that a serializer that reorders the array still assigns identically. See [Variants](/feature/variants).

To transmit a variant specification over the wire, `@evanion/feature` uses the [`SerializedVariantSpec`](#serializedvariantspec) type. This wire form keeps `value` as `unknown` and leaves the fence to `serializeConfig`.

## `VariantAssignment`

<!-- reference @evanion/feature#VariantAssignment -->

`assignVariant` returns a `VariantAssignment`. This object contains the chosen `VariantSpec`, the `by` field it bucketed on and, in the case of `'weighted'`, the `bucket`.

The `source` is `'weighted' | 'sticky' | 'fallback'`. There is no `'pinned'` case because only `decide` knows which rule matched, and `decide` applies a pin on top of the assignment `assignVariant` returned. A document author never writes one: `decide` reads the assignment into the decision it returns, and `@evanion/react-feature` reads it again when it compares a shipped decision against a local one. See [Variants](/feature/variants).

## `VariantInfo`

<!-- reference @evanion/feature#VariantInfo -->

To track the specific state of a feature, `@evanion/feature` uses `VariantInfo`. This interface records the details of a single feature variant, consisting of a `variant` name typed `string` and an optional `value` typed `unknown`.

While `VariantInfo` defines the general structure of a record, the actual union of declared variant names and the value type associated with each name is determined by `InferSchema` reading a definitions literal.

In `@evanion/feature`, the `Schema` maps every feature key to a `VariantInfo`. Its declaration writes `VariantInfo | never`, and that union collapses so no key of a `Schema` maps to `never`. This `never` mapping belongs to `InferSchema`, with one exception: a member typed `FeatureDefinition<K>` maps to `VariantInfo` and not to `never`.

## `Decision`

<!-- reference @evanion/feature#Decision -->

To understand why a specific feature is on or off, you look at a `Decision`. In `@evanion/feature`, the `enabled` member is the final decision, while every other member provides the supporting explanation.

The engine treats these explanation fields as output only; nothing in `@evanion/feature` consults `reason`, `rule`, `rules`, `blockedBy`, `cause`, `variant`, `value`, or `assignment` to determine enablement, as verified in `reason-is-output-only.spec.ts`.

`V` and `T` default to `string` and `unknown`, and `F` defaults to `string`. The `@evanion/react-feature` context publishes `Decision<FeatureKey>` and not a bare `Decision`: `FeatureKey` is `string | number`, so a store keyed on a numeric enum produces a `Decision<7>` whose `key` does not assign to a bare `Decision`'s. The widening holds at the constraint, which is why `useFeature` returns `Decision<FeatureKey>`.

When a variant is involved, `assignment` records how it was chosen:

- `source`: `'weighted' | 'pinned' | 'sticky' | 'fallback'`
- `by`: The field the engine used for bucketing.
- `bucket`: The bucket value (absent if the context carried no bucketing value).
- `rule`: The name of the pinning rule (present only when `source` is `'pinned'`).

See [Variants](/feature/variants) for more detail.

## `Decisions`

<!-- reference @evanion/feature#Decisions -->

To resolve a full set of features, `@evanion/feature` uses `Decisions`, which maps one decision per feature, each narrowed to the schema entry for its own key. Over the store [Variants](/feature/variants) builds, a lookup like `features.resolve()['checkout-cta'].variant` results in `'control' | 'blue' | undefined`.

If a feature declares no variants, its entry drops the `variant` and `value` fields but retains `rule`, `rules`, `blockedBy`, `cause`, and `assignment` as optional fields.

The signature names a helper, `DecisionOf`, which is internal to the package. It uses a `[E] extends [never]` guard to drop the variant keys. Because `never` is a subtype of every type, a plain `E extends VariantInfo` check would incorrectly take the variant branch for a feature with none and type its `variant` as `never` without reporting an error. The tuple wrap suppresses this distribution to ensure the branch asks the intended question.

`S` defaults to [`Schema`](#schema), so the bare `Decisions` holds what `resolve()` answers on a store built with no observer, at any schema, and on a store typed `Features<Schema, false>`.

To handle the result of a store held in the bare `Features` slot, or built by `parseFeatureConfig`, you must account for how the `Frozen` state affects the return type. Because this configuration leaves `Frozen` at `boolean`, its `resolve()` method answers with `Decisions | DeepReadonly<Decisions>`.

The `DeepReadonly<Decisions>` member types the `Date` a failed window condition in a rule outcome can carry as a `ReadonlyDate`, which the mutable `Decisions` form refuses; consequently, the bare `Decisions` type does not accept that union, and the compiler reports `TS2322`. To resolve this when a loader carries decisions from such a store to a page, the loader returns `snapshot()` and names its return type `DecisionSet`, which holds either freeze. The example under `Features<S>` shows that loader.

## `Cause`

<!-- reference @evanion/feature#Cause -->

When a feature is disabled because of a dependency cascade, you use `Cause` to find the root of the problem. `Cause` represents the first ancestor in the chain that resolved off for its own reason.

A decision with a `reason` of `dependency-off` carries the `Cause` alongside `blockedBy` (which names the immediate parent). This allows a UI to tell an operator which specific feature must be turned back on, while a graph view can draw the dependency edge.

If exactly one rule is responsible, either the matching rule or the single rule that failed, it appears in `rule`. If an ancestor has several rules and no match, the full breakdown is carried on its own decision.

## `Reason`

<!-- reference @evanion/feature#Reason -->

To determine why a feature resolved to its current state, the engine assigns a `Reason`. No rule and no cascade reads the field to decide enablement, which `reason-is-output-only.spec.ts` holds by deleting every explanation field from each parent decision and requiring the same `enabled` for every feature. The engine does read a blocked parent's `reason`, `rule`, `rules` and `blockedBy` to fill the dependant's `cause`, so a caller who caches a decision as `{ key, enabled }` and hands it back keeps every `enabled` and loses the root cause.

- `default-on`: The definition enabled the feature and declared no rules.
- `rule-match`: A rule matched, and the decision names that rule.
- `explicitly-off`: The definition set `enabled` to `false`.
- `no-rule-matched`: The definition enabled the feature, but no rule passed; the decision carries the per-rule breakdown.
- `dependency-off`: A parent resolved off; the decision carries the blocking edge and the root cause.

## `ToggleResult`

<!-- reference @evanion/feature#ToggleResult -->

When you call `features.toggle`, the operation returns a `ToggleResult`.

If the operation is successful (`ok: true`), the result names the key and repeats the `enabled` value the caller wrote. It also includes `willDisable`. The store applies the write before it answers, so `willDisable` names every transitive dependent that resolved on under the previous document and resolves off under the written one, listed in dependency order. By the time the caller holds the result, `features.isEnabled` already answers `false` for every entry on that list. If a caller enables a feature, this list is empty.

If the operation fails (`ok: false`), it indicates a key the store does not hold, and no data is written.

## `DecisionSet`

<!-- reference @evanion/feature#DecisionSet example=snapshot -->

To carry one subject's answers from the process that resolved them to the process that renders them, `@evanion/feature` uses the `DecisionSet` type. You produce one using `features.snapshot(context, options?)`.

The set states four things:

- `version`: The name of the configuration the decisions resolved under. This is absent for a store built from a definitions literal (which carries no version to state). A consumer compares it with `!==` and orders nothing.
- `now`: The instant the decisions were resolved at, as an ISO 8601 string.
- `origin`: A [`DecisionOrigin`](#decisionorigin).
- `decisions`: [`Decisions<S>`](#decisions), which is deeply readonly for a store built with an observer.

While `resolve` answers the decisions alone—leaving a consumer in another process unable to recover the version or the instant—a set states both. This allows a server to state the instant once so that no application must pass `now` by hand.

`snapshot` reads the installed version before it emits its `resolve` event. If an observer calls `reload` on that event, it installs a new document, and `version` names the one the decisions resolved under.

Because the set states its instant as an ISO 8601 string, `snapshot` raises a `FeatureConfigError` naming `context/now` for a `Date` that describes no instant. In contrast, `resolve`, `plan` and `toggle` state no instant; they carry that `Date` into the decision and stay total.

To move a `DecisionSet` over a wire, you serialize it as JSON. Because `JSON.stringify` converts a `Date` to an ISO 8601 string and `JSON.parse` cannot restore the original object, `@evanion/feature` ensures that any instant the store itself supplies—such as `now` or the `Date` bounding a window condition (`field: 'now'`, `op: 'before'` or `'after'`) in a failed rule outcome—is stated as a string, following the same pattern as `serializeConfig`. While a window bounded by a string or epoch milliseconds retains the value the definition wrote, and `resolve` keeps the window `Date` in place, certain literals provided in the definition are not carried across a JSON hop unchanged. A `Date` used by an [`AttributeCondition`](#attributecondition) or a variant's `value` is carried as the definition wrote it, meaning one JSON cycle turns that `Date` into a string. When every value in the set is one that JSON writes and reads back unchanged, `JSON.parse(JSON.stringify(set))` deep-equals the set.

A decision set crosses no service boundary. The process that produced it and the process that consumes it are two halves of one page load, which is the line § 8 of the published policy contracts spec draws between a document and a decision. To cross a service boundary, you use a [`FeatureConfig`](#featureconfig), and you use `configDigest` to prove two processes hold one.

## `DecisionOrigin`

<!-- reference @evanion/feature#DecisionOrigin -->

To state which kind of process resolved a set, `@evanion/feature` uses the `DecisionOrigin` type, which is `'render' | 'build'`.

When a set is `'render'`, it was produced by the request that generated the HTML. Because its instant is only seconds old, the consumer uses it as the default for local resolution. The set records this instant as an ISO 8601 string. Since the `now` property of [`ResolvePlanOptions`](#resolveplanoptions) takes an `Instant`, the consumer passes the value as it is: `resolvePlan(features, plan, context, { now: set.now })`. This call provides the two pieces of information required to answer the resolution logic: the context carries the subject the deferred entry buckets on, and the option carries the instant.

If the context is empty, the entry lacks the `targetingKey` named in `needs`. This triggers a [`'missing-field'`](#divergencereport) divergence report and results in every subject receiving the same variant. By including the subject in the context, a window boundary falling between the server's instant and the client's call will move no part of the tree.

`resolvePlan` settles `now` off the context before it reads the option. If a consumer holds a context that already carries `now`, they should state the set instant there instead: `resolvePlan(features, plan, { ...context, now: set.now })`. When provided with such a context, any `now` value passed in the options argument is discarded.

When a set is `'build'`, it may be days old. In this scenario, the consumer passes no `now` value, allowing the deferred remainder to resolve against the client's own clock.

## `SnapshotOptions`

<!-- reference @evanion/feature#SnapshotOptions example=snapshot -->

To state anything beyond the context, you can pass a `SnapshotOptions` to `features.snapshot`. Its one member is `origin`, which defaults to `'render'`. A build pipeline that writes a set into a bundle passes `'build'`, because it is the party that knows the instant it stated is not a request's.

The member states the provenance and moves no resolution. `snapshot` settles every feature the store holds at the instant the call read, and it reads no `freezeTimeAtBuild`; thus, a build-origin set states an answer for a `now`-dependent rule whose definition opted into no frozen window. If a pipeline wants the client to decide such a rule, it calls `plan` to defer it, and the client calls [`resolvePlan`](#resolveplan).

## `DivergenceObserver`

<!-- reference @evanion/feature#DivergenceObserver -->

To hear about a divergence, you install a `DivergenceObserver`, which takes one [`DivergenceReport`](#divergencereport) and answers `void`. You can provide this at `onDivergence` in `resolvePlan`, or as a prop in both providers of `@evanion/react-feature`.

An observer reads a report and alters no decision. [`reportDivergence`](#reportdivergence) is what calls it, and it discards whatever the observer raises, because an observer that takes down a render is worse than the divergence it was reporting. Because the compiler accepts a function answering anything where a `void` answer is expected, you can install an async function: `async (report) => { await post(report); }`. `reportDivergence` attaches a rejection handler to a thenable answer, which keeps Node from terminating the process over it.

The `F` parameter is the key type the reports name, defaulting to `string`. A caller installing an observer on a typed store gets `keyof S & FeatureKey`.

## `DivergenceReport`

<!-- reference @evanion/feature#DivergenceReport -->

To name what a process could not reproduce, and why, `@evanion/feature` uses the `DivergenceReport` type. A report is output only; nothing in the library reads one back, which is the invariant `reason-is-output-only.spec.ts` already holds for `reason`.

The `kind` member names one of four cases:

- `'config-version'`: the shipped set and the local store name different configuration versions.
- `'unversioned'`: one of the two carries no version, so the comparison cannot be made at all.
- `'missing-field'`: the local context carries no field the shipped answer's rule read, or a deferred plan entry names a field in `needs` that the context does not carry.
- `'decision-differs'`: the local resolution answers a different `enabled`, `reason` or `variant` than the shipped decision.

When a single feature is at fault, the report names that feature at `key`. If the report is a `'missing-field'` type, the context field is named at `field`.

The report tracks where the divergence occurred using the `shipped` and `local` members. Both are optional and hold a [`DivergenceSide`](#divergenceside) if the report has a side to state; a reader guards both before reading through them. To help the developer, the `message` member provides one sentence naming the cause and the fix, written for a developer reading a console.

Different tools generate different reports. Because `resolvePlan` holds only a plan and a context, it reports `'missing-field'` and nothing else, filling neither side. The other three cases come from the `@evanion/react-feature` provider, which holds a shipped set beside a local store.

## `DivergenceSide`

<!-- reference @evanion/feature#DivergenceSide -->

To state one side of a comparison, `@evanion/feature` uses the `DivergenceSide` type.

The `DivergenceSide` type allows `@evanion/feature` to isolate the values provided by a server from those provided by a local process. The `shipped` and `local` members of a [`DivergenceReport`](#divergencereport) are both optional; a report fills a side only where it had one to state. Where it fills both, an observer reads what the server answered beside what the local process answers.

Depending on the reporter, a report may fill these sides differently:

- **`resolvePlan`**: Fills neither side. Because it holds a plan and a context, its `'missing-field'` report names the feature at `key` and the field at `field` and states no answer on either side. An observer written for it reads `key`, `field`, and `message`. If an observer attempts to read `report.shipped.version`, it raises a `TypeError`, which [`reportDivergence`](#reportdivergence) discards, leaving the divergence unreported.
- **`@evanion/react-feature`**: Holds a shipped set beside a local store. It attaches both sides for a `'config-version'`, an `'unversioned'`, and a `'decision-differs'` report. It attaches `shipped` alone on the two `'missing-field'` reports where there is no local answer to state: either the store declares no feature the server shipped a variant for, or it declares that feature with no variants at all.

A report fills the members of a side based on its `kind`. All four members of a side are optional:

- A `'config-version'` report fills `version` on both sides. Each process named a version, and the two differ.
- An `'unversioned'` report attaches both sides and leaves `version` absent on whichever side carried none, which is the condition the report exists to name. Both are absent where neither process holds a versioned document. So an observer that has narrowed a report to a version kind still guards `version` itself before it reads through it, or it raises the `TypeError` [`reportDivergence`](#reportdivergence) discards.
- A variant report fills `variant` and the `source` that assigned it (one of `'weighted'`, `'pinned'`, `'sticky'`, or `'fallback'`, the four a [`Decision`](#decision)'s `assignment` carries).
- A `'decision-differs'` report fills `enabled` as well.

## `Plan`

<!-- reference @evanion/feature#Plan -->

For [Build-time planning](/feature/build-time), `@evanion/feature` uses `Plan`, which contains one plan entry per feature. This uses the same `never` guard as `Decisions`, ensuring a feature declaring no variants receives a plan entry whose decision contains no `variant` or `value` keys.

`S` defaults to [`Schema`](#schema), so the bare `Plan` holds what `plan()` answers on a store built with no observer, at any schema, and on a store typed `Features<Schema, false>`.

To understand how types change when a store is observed, consider how `@evanion/feature` handles the `Frozen` state. A store held in the bare `Features` slot, or built by `parseFeatureConfig`, leaves `Frozen` at `boolean`, and its `plan()` answers `Plan | DeepReadonly<Plan>`.

This creates a type mismatch because the deeply readonly member types the `Date` a failed window condition in a plan entry's decision can carry as a `ReadonlyDate`, which the mutable form refuses; consequently, the bare `Plan` does not accept that union and the compiler reports `TS2322`. To resolve this, a build step that writes the plan of such a store names it `FrozenWhenObserved<boolean, Plan>`, which is the type `plan()` answers there. The example under `Features<S>` shows that build step.

## `PlanEntry`

<!-- reference @evanion/feature#PlanEntry -->

A `PlanEntry` represents a single feature's build-time plan.

The `resolved` member is `true`, `false`, or `'deferred'`. A value of `'deferred'` indicates that a rule or a variant split still requires context that the plan did not have. In this case, `needs` lists the required context fields, sorted; otherwise, `needs` is empty.

A `decision` is present whenever `resolved` is a boolean. It may also be present in a deferred entry if the enablement is settled but the variant split is outstanding. In that case, the decision carries no variant because the context lacked the bucketing field. Consequently, a caller cannot use the presence of a `decision` as proof that `resolved` is a boolean.

## `resolvePlan`

<!-- reference @evanion/feature#resolvePlan example=resolve-plan -->

To turn a build-time plan and a client context into a full decision set, you use the `resolvePlan` function.

The function processes entries based on their resolution state:

- **Settled:** If `resolved` is a boolean and a decision is present, that decision is used as the answer without re-running rules.
- **Deferred (no decision):** The rules are run against the client context.
- **Deferred (with decision):** Enablement is read from the entry and only the assignment is computed. This prevents a second run of the rules against a richer context from flipping the enablement and contradicting the original plan entry.

If a parent resolves off during this pass, it blocks both settled and deferred entries alike. An entry settled the feature's own rules and not the graph above it, and a set that claims a feature is on while its parent is off contradicts itself. The walk follows the dependency order, because a deferred parent puts its `needs` on its dependents.

## `ResolvePlanOptions`

<!-- reference @evanion/feature#ResolvePlanOptions -->

To configure how `resolvePlan` behaves, you pass `ResolvePlanOptions`.

The `now` member specifies the instant the deferred remainder resolves. This prevents a window boundary between server and client from shifting half the tree:

- A `DecisionSet` with `origin: 'render'` states an instant seconds old; the caller passes it here to maintain consistency.
- A `DecisionSet` with `origin: 'build'` may be days old; the caller passes nothing, and `resolvePlan` uses the client's clock.
- If the context passed to `resolvePlan` has its own `now` value, it takes precedence over this option.

To handle missing data during resolution, you provide a callback to the `onDivergence` member. This callback receives a `missing-field` report for every field a deferred entry names in `needs` that the context you pass `resolvePlan` does not carry, with one exception: `now`.

`resolvePlan` always has a `now`. It takes the one on the context, failing that the one on `ResolvePlanOptions`, and failing both the client's own clock. A deferred entry whose `needs` names `now` therefore resolves against a real instant and reports nothing. A window rule on a feature that did not set `freezeTimeAtBuild` defers on `now`, so that entry is the plan working as designed and not a divergence.

## `adoptDecisions`

<!-- reference @evanion/feature#adoptDecisions example=adopt-decisions -->

To sync a process with decisions resolved by another process, you use `adoptDecisions(features, shipped, options?)`. This function takes a [`DecisionSet`](#decisionset) from another process and answers the decisions this process publishes. It imports no framework and runs in any program, though `@evanion/react-feature`'s providers call it.

If `shipped` is left out, `@evanion/feature` answers `features.resolve(options.context)`.

When provided with a set, `adoptDecisions` runs two checks before returning, reporting results through `onDivergence`:

- **Version Check:** It compares the set's `version` with `features.version` using `!==`. If one side carries no version, it reports `'unversioned'`; if two versions differ, it reports `'config-version'`.
- **Field Check:** It reports `'missing-field'` for every shipped decision the local process's context cannot reproduce. This includes features the store does not declare, features declared with no variants, bucketing fields the context lacks, or fields a pinning rule reads that the context lacks. It never names `now`.

The return value depends on the version outcome: on a `'config-version'` mismatch, it returns the shipped decisions under `'use-shipped'` and resolves locally under `'re-resolve'`. An `'unversioned'` outcome always returns the shipped decisions.

If `compare: true` and an observer is installed, `@evanion/feature` resolves locally once and reports `'decision-differs'` for every key where the `enabled`, `reason`, or `variant` differs. Because a store built with `observe` emits a `'resolve'` event, the local resolution happens at most once per call, and only when the comparison or `'re-resolve'` reads the result.

The timing of local resolutions depends on the set type: for a `'render'` set, `now` is the default instant if `options.context` states none; for a `'build'` set, the instant is ignored and the local clock answers.

## `AdoptOptions`

<!-- reference @evanion/feature#AdoptOptions -->

To configure how decisions are adopted, you pass an `AdoptOptions` object to [`adoptDecisions`](#adoptdecisions).

- `context` is the evaluation context held by this process.
- `onVersionMismatch` defaults to `'use-shipped'`.
- `onDivergence` is a [`DivergenceObserver`](#divergenceobserver) and alters no decision.
- `compare` defaults to `false`. Because the core reads no host global to determine this, the caller must state it. For example, `@evanion/react-feature` passes `true` outside a production bundle.

## `VersionMismatchPolicy`

<!-- reference @evanion/feature#VersionMismatchPolicy -->

When the shipped version does not match the store's, you define the behavior using a `VersionMismatchPolicy` (`'use-shipped' | 're-resolve'`).

- `'use-shipped'` publishes the shipped decisions, as the server already rendered from them and recorded an exposure for that variant.
- `'re-resolve'` resolves against the local store.

`@evanion/react-feature` re-exports this type for the `onVersionMismatch` prop of its providers.

## `FeatureEvent`

<!-- reference @evanion/feature#FeatureEvent example=observe-one-key -->

To track how features are evaluated in a running application, `@evanion/feature` provides a way to observe the outcome of store calls via a `FeatureEvent`.

### Reporting Events

The `@evanion/feature` store emits one event for each `resolve`, `isEnabled`, `plan`, `toggle`, and `snapshot` call. No other member reports; `variantOf` and `valueOf` read a field from an internal resolution and emit nothing, and `isEnabled` emits nothing for a key the store was not built with.

The `type` member names the payload, using four values to cover the five reporting calls:

- **`'resolve'`**: Emitted by `resolve`. It carries every decision at `decisions`, the same record `resolve` returned.
- **`'is-enabled'`**: Emitted by `isEnabled`. It carries the `key` requested and, at `decision`, the decision the boolean `isEnabled` returned was read from.
- **`'plan'`**: Emitted by `plan`. It carries at `plan` the partition `plan` returned.
- **`'toggle'`**: Emitted by `toggle`. It carries at `result` the report `toggle` returned.

### Snapshot Events

When `snapshot` is called, the store reports a `'resolve'` event. Because of this, the event does not say which of the two calls ran.

The event carries the set's `decisions` record and nothing else from the [`DecisionSet`](#decisionset) the caller received. It has no `origin`. Its `at` is a `Date` naming the same instant as the set's ISO 8601 `now`.

The `version` handling differs between the event and the set: the event's `version` is the `version` option of `createFeatures`, while the set's `version` is the version of the document the store had installed. Consequently, a store built from a versioned document with no `version` option emits a snapshot event with no `version` at all. An auditor who matches snapshot events to the sets a server shipped has `subject`, the instant and the decisions to join on.

### Type Safety and Metadata

To ensure a consumer who narrows on `key` cannot read a decision belonging to another feature, the `'is-enabled'` member is written as a mapped type the union closes over; this pairs `key: 'checkout-cta'` with the decision that key resolves to, rather than using a flat object typing `key` and `decision` as unions of every possible value.

Common metadata is shared across all events:

- **Context**: No event carries an `EvaluationContext`.
- **Timing**: The `at` member is the instant the call settled on.
- **Identity**: `subject` is the identifier [`correlateBy`](#featureoptions) names, copied out as a primitive.
- **Versioning**: `version` is the `version` option passed to `createFeatures`, absent when the store was given none.

Every payload is deeply readonly, so the compiler refuses a write to it and the engine freezes what it emits. See [Observing](/feature/observing).

## `FeatureOptions`

<!-- reference @evanion/feature#FeatureOptions example=observe-install -->

To install an observer and name the fields an event reports, you pass `FeatureOptions` to [`createFeatures`](#createfeaturesdefinitions-options) as its second argument. The interface declares four optional members:

- `observe`: called once for each call that reports, with the [`FeatureEvent`](#featureevent) that call produced. The engine never awaits it.
- `onObserveError`: replaces the `console.warn` the engine writes when an observer throws or rejects.
- `correlateBy`: the context field whose value identifies the subject on an event. Defaults to `targetingKey`.
- `version`: the configuration version an event reports.

Because `FeatureOptions` declares `observe` optionally, options carrying an observer and options carrying none both satisfy it. [`UnobservedOptions`](#unobservedoptions) is the form that proves the absence.

The overhead of observation is minimal. Measured at forty features on an Apple M1 Pro under Node 24.20.0, the bare call ran at 23 microseconds, a synchronous no-op observer at 41, and an `async` no-op observer (including the thenable check and rejection handler) at 44. The deep freeze a store carrying an observer runs accounts for that difference, and the emit and the thenable check stay within run-to-run noise of the bare call. So the number anyone should care about is what their own hook body does.

### `observe` does not count exposures

You should not use the observer to track feature exposures. Because `resolve` decides every configured feature, an observer fired from it reports a decision for every feature the request never rendered; an experiment computed over those records measures the wrong denominator. The numbers look plausible and are wrong. The application should write an exposure record at its render site, using the fields the decision it already holds carries. See [Observing](/feature/observing#exposure-tracking-is-not-what-this-seam-carries) for the whole argument.

### Records in flight are lost at exit

Because the engine awaits nothing, any buffer the application has not drained is lost when the process exits or when a phone's operating system suspends a process without warning. To prevent this, the application must drain that buffer on `SIGTERM` and on the background transition. Each runtime carries its own transport: a service writes to a log collector, and a browser writes with `navigator.sendBeacon` on `visibilitychange`. See [Observing](/feature/observing#records-in-flight-are-lost-at-exit) for the hook shape.

## `UnobservedOptions`

<!-- reference @evanion/feature#UnobservedOptions -->

To let the compiler prove that a call installs no observer, `@evanion/feature` uses the `UnobservedOptions` type, which is [`FeatureOptions`](#featureoptions) with `observe` pinned to `undefined`.

Only a value whose type proves the absence satisfies it, and that is the type the second [`createFeatures`](#createfeaturesdefinitions-options) signature takes. A call that reaches that signature gets a store whose `resolve`, `plan` and `toggle` answer the mutable form.

An options value typed `FeatureOptions<S>`, and an object literal whose `observe` field holds `Fn | undefined`, both fail this type and therefore answer the frozen form. A wrapper forwarding an optional parameter cannot annotate its way past that, because the forwarded parameter's type is not `undefined`.

## `FrozenWhenObserved`

<!-- reference @evanion/feature#FrozenWhenObserved -->

To type an answer whose readonly-ness the store decides, `@evanion/feature` uses the `FrozenWhenObserved` type.

The store behaves differently under two configurations: a store carrying an observer freezes what it emits and answers the caller with [`DeepReadonly`](#deepreadonly), while a store carrying none freezes nothing and answers the type unwrapped.

The engine takes that asymmetry deliberately to avoid unnecessary overhead. At forty features, the freeze adds 18 microseconds to a 23 microsecond `resolve`; a freeze on every call would penalize every user of the package whether or not they observe anything. Since a store nobody observes hands its record to nobody else, the freeze protects nothing there.

Because `Frozen` is naked in `FrozenWhenObserved`, a store whose observation the compiler cannot settle distributes to the union of both forms, and the reader narrows it.

## `DeepReadonly`

<!-- reference @evanion/feature#DeepReadonly -->

To mark every property readonly through arrays and nested objects, `@evanion/feature` uses the `DeepReadonly` type. In this process, a `Date` becomes a [`ReadonlyDate`](#readonlydate). Functions pass through unchanged, because mapping over their properties would erase the call signature.

## `ReadonlyDate`

<!-- reference @evanion/feature#ReadonlyDate -->

To carry a `Date` a reader cannot move, `@evanion/feature` uses the `ReadonlyDate` type, which drops the mutators.

This is necessary because `Readonly<Date>` marks properties readonly but leaves `setTime`, `setHours` and others callable; each of those writes an internal slot that `Object.freeze` does not cover. To prevent this, the `ReadonlyDate` type uses a template literal to name all mutators starting with `set` and `Omit` to drop them.

## `FeatureKey`

<!-- reference @evanion/feature#FeatureKey -->

To identify a feature in your configuration, you use a `FeatureKey`. A definition may carry `key: 7`. A numeric key union goes in a schema, `Record<Flag, VariantInfo | never>`, and `Decisions` takes that schema. `Decisions<Flag>` over the key union on its own is a compile error, since `Decisions<S>` constrains `S` to `Record<keyof S, VariantInfo | never>`.

```ts twoslash
import { createFeatures } from '@evanion/feature';

enum Flag {
  PreorderBanner = 1,
  TradeInKiosk = 2,
}

const features = createFeatures([
  { key: Flag.PreorderBanner, enabled: true },
  { key: Flag.TradeInKiosk, enabled: false },
] as const);

features.isEnabled(Flag.PreorderBanner);
```

## `Instant`

<!-- reference @evanion/feature#Instant -->

To represent a precise moment in time for conditions, `@evanion/feature` uses the `Instant` type. A number is epoch milliseconds. A string is ISO 8601 and has to name one instant on every host, which two forms do: a date-time carrying `Z` or an offset, and a date with no time, which ECMA-262 fixes to UTC. The offset takes either spelling ISO 8601 gives it.

| Instant string              | Read as                              |
| --------------------------- | ------------------------------------ |
| `2026-01-01T00:00:00Z`      | that instant                         |
| `2026-01-01T09:00:00+09:00` | the same instant                     |
| `2026-01-01T09:00:00+0900`  | the same instant                     |
| `2026-01-01`                | UTC midnight                         |
| `2026-01-01T00:00:00`       | `FeatureConfigError` at construction |
| `2026-13-01`                | `FeatureConfigError` at construction |
| `2026-01-01t00:00:00z`      | `FeatureConfigError` at construction |
| `2026-04-31`                | `FeatureConfigError` at construction |

ECMA-262 reads `2026-01-01T00:00:00` as local time. The rule derives one id on every host and resolves against a different boundary on each, so a browser in Los Angeles and a service in Stockholm disagree about a decision that carries the same name in both logs. The two rows under it sit outside the format ECMA-262 fixes, one naming no calendar date and one written in lower case, and each engine reads them by rules of its own. `2026-04-31` sits inside the format and every engine carries the overflowing day into 1 May, so a string naming April names May on every host, under the one rule id `2026-05-01` also derives. `createFeatures` refuses all four.

| Instant value              | Read as                              |
| -------------------------- | ------------------------------------ |
| `1767225600000`            | that instant                         |
| `new Date(1767225600000)`  | that instant                         |
| `Number.NaN`               | `FeatureConfigError` at construction |
| `Number.POSITIVE_INFINITY` | `FeatureConfigError` at construction |
| `8640000000000001`         | `FeatureConfigError` at construction |
| `new Date('nonsense')`     | `FeatureConfigError` at construction |

A number has to be an epoch a `Date` holds, and a `Date` has to hold an instant. `createFeatures` refuses `Number.NaN`, which is what `Date.parse` and `new Date` answer for a string naming none, so a boundary computed from an unset environment variable is refused where it is written. It refuses a number past either end of the range a `Date` holds, -8640000000000000 to 8640000000000000, since a `before` boundary above that range holds at every instant and an `after` boundary at none.

A `Date` is taken as the instant it holds and is read no further, so `new Date('2026-01-01T00:00:00')` carries the constructing host's zone past every check. Build one from epoch milliseconds, or from a string the table accepts.

To transmit an instant over the wire, `@evanion/feature` uses the [`SerializedInstant`](#serializedinstant) type. This wire form admits strings and numbers but refuses `Date` objects.

## `FeatureConfig`

<!-- reference @evanion/feature#FeatureConfig example=config-document -->

To transport feature definitions across a boundary, you use a configuration document. The `FeatureConfig` interface types that document: a canonical envelope over a list of definitions.

There is no bare-array form, for the reason `Matrix` gives in `@evanion/acl`. By using an envelope, a foreign producer emitting JSON can state the version and the schema, ensuring one document crosses a boundary without needing a wrapper assembled at the call site.

The `version` is compared with `!==`, and it is opaque and unordered. A consumer that could order two versions would act on the order, and both available actions are wrong: declining a lower version blocks a rollback (the operation an operator reaches for at 3am), and accepting only a higher version breaks a control plane serving two shards whose counters diverged. A consumer holding a version different from the one it wants fetches the document that version names.

The `digest` is the `configDigest` of this document, and a holder that finds one verifies it. The `schema` carries the typing contract inline and `schemaVersion` names the schema's own version; a document may name `schemaVersion` alone. The `features` member holds one [`SerializedDefinition`](#serializeddefinition) per feature.

The `maxStale` value indicates how long the publisher believes a holder may keep this document, in milliseconds. This is advisory and no entry point in `@evanion/feature` reads it. The party that fetches is the party that acts on it: whatever reads the document holds the poller, knows the fetch instant because it performed the fetch, and shortens its interval, logs, refuses to start or serves a fallback document. This library holds no clock authority, and no endpoint answers which variant a subject gets, so every holder computes its own answer from the rules the document carries.

The `F` parameter defaults to `FeatureKey`. An entry point that reads a whole document names the bare `FeatureConfig`, and a document keyed on a numeric enum reaches that parameter only while the default admits a number.

See [Distribution](/feature/distribution) for what a document carries.

## `ConfigEnvelope`

<!-- reference @evanion/feature#ConfigEnvelope example=config-document -->

When a serializer writes around a store, it uses `ConfigEnvelope` to define the envelope without its payload. It is `FeatureConfig` with `features` and `digest` dropped, and `digest` written back as `never`. `serializeConfig` takes one as its second argument and defaults to `features.envelope`, the envelope of the document the store installed.

The `digest` is fenced to `never` rather than omitted. Omitting it would drop the member from the type and still admit a whole `FeatureConfig`, because TypeScript refuses an extra property on a fresh object literal and nowhere else. Because a document's `digest` is always the `configDigest` of that same document, a serializer that copied one from its caller would emit a document whose digest covers other bytes. Every holder recomputes it, disagrees, reports `digest-mismatch` and refuses the whole document, and no holder recovers on its own. `configDigest` is the one writer of the member.

## `ValidationResult`

<!-- reference @evanion/feature#ValidationResult example=config-validate -->

To determine if a configuration is valid, you use `validateConfig`, which returns a `ValidationResult`. This result is discriminated on `ok`. The agreement arm is `{ ok: true }` and carries nothing else. The refusal arm carries every issue the walk found, so a caller reporting a bad document names all of its defects in one pass.

## `ConfigIssue`

<!-- reference @evanion/feature#ConfigIssue example=config-validate -->

When `validateConfig` finds a defect, it reports it as a `ConfigIssue`. The `code` names the class of defect and `message` is the same text the thrown counterpart carries, where one exists. The `key` names the feature the issue is about, when it is about one. The `path` is a JSON pointer into the document, so a UI highlights the row.

A `duplicate-feature` or `unknown-dependency` issue names a key, a `cycle` issue names none, and no graph issue names a member.

## `ConfigIssueCode`

<!-- reference @evanion/feature#ConfigIssueCode example=config-validate -->

`ConfigIssueCode` is the closed set of 18 codes, one per class of defect, in four groups: the graph, the variants, the rules and the envelope. The [`validateConfig`](#validateconfigconfig) entry lists them.

## `ReloadResult`

<!-- reference @evanion/feature#ReloadResult example=config-reload -->

To track the outcome of a configuration update, you use `ReloadResult`, which describes what a reload did and is discriminated on `ok`. Both arms carry `version`, and on both arms it names the document that is installed now.

The agreement arm carries `previousVersion`, the version that was installed before, and `changed`, the keys whose stored intent differs from the previous document.

The refusal keeps the previous document, so its `version` is the one that stayed and `rejected` is the candidate's version, which lets a log name what was refused. The `issues` member carries what `validateConfig` found.

## `FeatureSchema`

<!-- reference @evanion/feature#FeatureSchema -->

To define the typing contract of a document, you use the `schema` member, which is typed by `FeatureSchema`. This contract consists of two halves, each with its own vocabulary. The `context` member declares the fields a condition may read and is typed by `ContextSchema`. Conversely, `features[key].variants[name]` declares the shape of a variant's value and is typed by `ValueShape`.

The `@evanion/feature` engine applies distinct logic to these two vocabularies. When handling a context field, `validateConfig` focuses on structure rather than data: it verifies that the schema declares the field and that the condition's operator matches the declared type's `[]` suffix. Because the engine never compares the condition's value against the declared base name, a condition over a field declared `number` will still pass even if it carries the string `'gold'`. In contrast, the engine remains entirely passive regarding variant values, as `valueOf` simply hands the value to the caller untouched.

If a document carries neither `schema` nor `schemaVersion`, it declares no shapes, and the schema walk reports nothing about it. If a document carries an inline `schema` but no `schemaVersion`, it reports `missing-schema-version`, because a holder cannot cache a schema that names no value to cache it at.

## `ContextSchema`

<!-- reference @evanion/feature#ContextSchema -->

To manage the available context fields in `@evanion/feature`, you use `ContextSchema`, where `fields` maps a context field's name to its `FieldType`. The `validateConfig` function reads this map twice over. If a condition is used over a field that the map omits, it reports `unknown-context-field`. If an operator is used that the declared type has no meaning for, it reports `field-type-mismatch`. For example, using `contains` over a field declared `boolean` asks whether a boolean holds a value, which `evaluateCondition` answers `false` for every subject. A document whose schema omits `context.fields` declares no contract, and neither check runs. An empty map declares zero fields, so a condition over any field reports `unknown-context-field`.

## `FieldType`

<!-- reference @evanion/feature#FieldType -->

The `FieldType` used in `@evanion/feature` is a template-literal union over `BaseFieldType`, admitting sixteen strings: each of the four base names on its own, each with `[]`, each with `?`, and each with `[]?` in that order. Consequently, `instant[]?` is a member while `instant?[]` is not.

The `[]` suffix is what `field-type-mismatch` reads, since `contains` asks whether an array holds a value, while `eq`, `ne`, `in` and `not-in` compare a scalar. The check strips a trailing `?` before it tests for `[]`, so `string[]?` names an array to it and `contains` over such a field passes. The `?` suffix also marks a field that a complete context may leave out, and no issue code reports a field a context omitted, so a generator and a reader are what read it for that.

## `BaseFieldType`

<!-- reference @evanion/feature#BaseFieldType -->

`BaseFieldType` defines the four base names that a `FieldType` builds on. Among these, `instant` represents a point in time that the context carries as an ISO 8601 string or as epoch milliseconds.

## `FeatureShape`

<!-- reference @evanion/feature#FeatureShape -->

To record the schema for a specific feature, `@evanion/feature` uses `FeatureShape`, which is held under `schema.features` at the feature's own key. Within this, `variants` maps a variant name to that variant's `ValueShape` in no significant order. The document's own `variants` array holds the order, and `VariantSpec.order` fixes where a variant sits in the bucketing walk.

## `ValueShape`

<!-- reference @evanion/feature#ValueShape -->

To define the shape of a single variant value, `@evanion/feature` uses `ValueShape`, written as a JSON Schema 2020-12 object. The fence admits `type`, `properties`, `required`, `items`, `enum`, `const`, `additionalProperties`, `$defs`, `$ref`, `title` and `description`. A `$ref` resolves only to a `$defs` entry in the same document. Any other keyword reports `unfenced-schema`, including `allOf`, `anyOf`, `oneOf` and `not`. A remote `$ref` leaves a generator with a document it cannot resolve offline, and the four combinators produce Swift and Kotlin a reader cannot map back to the schema. An owner needing a union writes an `enum` over a discriminant.

The `validateConfig` function tests a key only where a shape declares a keyword. Because `properties` and `$defs` hold a map from a name their author chose to a shape, the walk descends into each value and tests no name; thus, a property called `label` and a definition called `Label` are treated as data. Similarly, `items` and `additionalProperties` hold one shape, so the walk descends into the value. Keywords like `type`, `title`, `description`, `required`, `enum` and `const` hold data and the walk stops at them; therefore, a variant value carrying the key `oneOf` under a `const` remains legal.

## `JsonValue`

<!-- reference @evanion/feature#JsonValue -->

When an attribute condition compares against a value as a document carries it, `@evanion/feature` uses `JsonValue`. `SerializedAttributeCondition.value` is this type, and `serializeConfig` writes it.

In this type, an object member written as `undefined` is legal, but an array element is not. Because `canonical` filters an `undefined` member out and `JSON.stringify` omits it, an absent key and a key written as `undefined` digest alike. An `undefined` array element reaches no such agreement, since `canonical` writes it as the text `undefined` while `JSON.stringify` writes it as `null`, and the publisher and the holder would digest two different texts over one array. The `serializeConfig` function refuses that element and raises a `FeatureConfigError` naming the path, so no holder receives the document the two would disagree about.

The object arm is an index signature. Since TypeScript derives one for a type alias and for an object literal, but never for an `interface`, a value annotated with a generated interface does not reach this type. A variant value carries no such fence: `SerializedVariantSpec.value` is `unknown`, which allows a quicktype or openapi-generator interface to land there.

## `SerializedDefinition`

<!-- reference @evanion/feature#SerializedDefinition -->

To represent a feature in a static document, `@evanion/feature` uses the `SerializedDefinition` type. While a live store carries a [`FeatureDefinition`](#featuredefinition), a document carries one `SerializedDefinition` per feature. This type is the element type of `FeatureConfig['features']`, and it is what `serializeConfig` writes.

The `SerializedDefinition` contains every member a live definition declares. The `key`, `enabled`, `dependsOn`, `seed`, `freezeTimeAtBuild`, `variantBy`, and `variantSeed` members carry the types a live definition declares. For a feature that declares variants and leaves the two bucketing members implicit, `serializeConfig` writes `variantBy` and `variantSeed` out. The `rules` member holds [`SerializedRule`](#serializedrule) and the `variants` member holds [`SerializedVariantSpec`](#serializedvariantspec).

Because a serialized definition is a definition a live store could hold, a holder can hand one from a parsed document to `createFeatures` untouched. A live definition does not reach this type, however, because a live condition admits a `Date`.

The `F` parameter defaults to `FeatureKey` (the default used by `FeatureConfig`), allowing a helper annotated with the bare name to read a definition out of a bare document.

## `SerializedRule`

<!-- reference @evanion/feature#SerializedRule -->

To define a rule within a document, `@evanion/feature` uses the `SerializedRule` type, where a live store would carry a [`Rule`](#rule). The `id` provided by a control plane or author travels as written, and the `rollout` and `variant` members travel untouched. The `when` member holds [`SerializedCondition`](#serializedcondition).

Every member a live rule declares is present here. Since `when` stays optional, a document can carry a rule that ramps a percentage and matches on nothing. The condition list is readonly; a holder that rewrote it would match differently from every other process holding the document this digest names.

A serialized rule is a rule a live store could hold. A live rule does not reach this type because its conditions admit a `Date`.

## `SerializedCondition`

<!-- reference @evanion/feature#SerializedCondition -->

To define a condition within a document, `@evanion/feature` uses the `SerializedCondition` type, where a live store would carry a [`Condition`](#condition). This type is a union of three arms: [`SerializedWindowCondition`](#serializedwindowcondition), [`DayOfWeekCondition`](#dayofweekcondition) unchanged, and [`SerializedAttributeCondition`](#serializedattributecondition).

A day-of-week condition needs no wire form of its own because its `zone` is a string and its `value` is an array of [`Weekday`](#weekday); JSON carries both as the store holds them. The other two arms each narrow the one member that admits a value JSON has no form for.

## `SerializedWindowCondition`

<!-- reference @evanion/feature#SerializedWindowCondition -->

To represent a window condition in a document, `@evanion/feature` uses the `SerializedWindowCondition` type, where a live store would carry a [`WindowCondition`](#windowcondition). In this type, the `field` is `'now'`, the `op` is `'before'` or `'after'`, and `value` is a [`SerializedInstant`](#serializedinstant).

A live window condition does not reach this type because `Instant` admits a `Date`. The two forms decide the window alike, since a window condition is read as a point in time and a string, a number, and a `Date` naming one instant all read to one epoch. The function [`serializeConfig`](#serializeconfigfeatures-envelope) converts the `Date` on the way out. Epoch milliseconds are a member of the type, which is what a producer with no ISO formatter writes.

## `SerializedAttributeCondition`

<!-- reference @evanion/feature#SerializedAttributeCondition -->

To represent an attribute condition in a document, `@evanion/feature` uses the `SerializedAttributeCondition` type, where a live store would carry an [`AttributeCondition`](#attributecondition). The `field` and the `op` travel as the store holds them, and `value` narrows from `unknown` to [`JsonValue`](#jsonvalue).

A serialized attribute condition is an attribute condition a live store could hold. A live one does not reach this type because its `value` admits a `Date`.

This narrowing ensures that two processes that agree on a digest resolve alike. `evaluateCondition` compares this value with `===`, and `canonical` writes a `Date` and the ISO string a transport hands the holder as one text. A publisher holding the `Date` and a holder holding the string therefore digest alike and compare apart, and § 2 of the distribution spec reads two agreeing digests as a proof that two processes hold one configuration. `serializeConfig` refuses the `Date` here and names the path.

The `value` is readonly. A holder that rewrote it would decide differently from the document every other process holds under the same digest.

## `SerializedVariantSpec`

<!-- reference @evanion/feature#SerializedVariantSpec -->

To represent a variant in a document, `@evanion/feature` uses the `SerializedVariantSpec` type, where a live store would carry a [`VariantSpec`](#variantspec). The `name` and the `weight` travel as the store holds them, and `serializeConfig` writes an explicit `order` on every variant of a feature whose author left it implicit.

Unlike the attribute condition's value, the `value` here stays `unknown`. § 4 of the distribution spec picks JSON Schema for this member because quicktype and openapi-generator emit TypeScript interfaces from it; since TypeScript gives an interface no implicit index signature, a `JsonValue` here would refuse the generated type the notation was picked to produce. A variant value typed by such an interface lands here and type-checks.

Because the type admits a value JSON cannot carry, [`serializeConfig`](#serializeconfigfeatures-envelope) is what refuses one. Its walk admits a string, a finite number, a boolean, `null`, an array, and a plain object, and it raises a `FeatureConfigError` naming the path for every other leaf, including a `Date`, a `Map`, a `Set`, and a `RegExp`. The `value` is readonly, because `valueOf` would answer one thing here and another in every process holding the document this digest names.

## `SerializedInstant`

<!-- reference @evanion/feature#SerializedInstant -->

To represent an instant in a document, `@evanion/feature` uses the `SerializedInstant` type, which allows an ISO 8601 string or epoch milliseconds, but never a `Date`. This type holds the rule defined in decision 12 of the distribution spec.

A `Date` is not a JSON value. [`Instant`](#instant) admits one (which is what an author writes in a TypeScript literal), and while `JSON.stringify` writes that `Date` as an ISO string, `JSON.parse` hands back a string. A holder reading a parsed document therefore holds a string; a document type that admitted a `Date` would promise the holder a value no parse produces.

A serialized instant is an instant a live store holds, so the type can annotate a live member too. The only member of a definition a `Date` reaches legally is `WindowCondition.value`, and [`serializeConfig`](#serializeconfigfeatures-envelope) handles the conversion: it writes that `Date` as its ISO string, raises a `FeatureConfigError` naming the path for a `Date` that names no instant, and refuses a `Date` at every other member of the document.

## `FeatureConfigError`

<!-- reference @evanion/feature#FeatureConfigError example=config-errors -->

To handle configuration defects in `@evanion/feature`, you can catch a single
base class. The `FeatureConfigError` class serves as the root for the other five
error types described on this page.

### Using FeatureConfigError as a Catch-All

The `createFeatures` function raises `FeatureConfigError` for any defect the
checker reports that is not covered by the five specific subclasses. This
includes a wide range of configuration issues:

- A `when` property that the checker cannot read as an array of conditions.
- A variant weight that is not a usable share.
- A feature that declares an order on none of its variants.
- A document that declares variants but carries no `variantBy` or
  `variantSeed`.
- A document carrying a top-level member that the holder cannot read.
- An inline schema missing a `schemaVersion`.
- A window boundary carrying `Number.NaN`.

Because the error message names the specific feature and the member path, you
should read the message for debugging rather than switching on the class type. A
single `catch` block targeting this base class answers every defect the checker
reports.

### How `@evanion/feature` handles copy errors

To ensure a configuration is safe to use, `@evanion/feature` validates the data
provided to `createFeatures`. Because `VariantSpec.value` is typed as `unknown`,
the checker reports nothing about a variant `value`. If a function or a symbol
is placed there, it clears every check, but is then refused by the copy
`createFeatures` takes before it installs the configuration.

The specific refusal the user receives depends on the host environment.
`@evanion/feature` utilizes `globalThis.structuredClone` where available, such
as in Node, a browser, or a worker, and falls back to its own JSON-shaped copy
walk on a host that defines no such global.

When `structuredClone` fails, it raises the host's own `DataCloneError` (a
`DOMException`) naming the leaf. When the copy walk fails, it raises a
`FeatureConfigError` naming the member path, such as
`"/variants/0/value" carries a function, and a document carries none`.

### Catching errors across different hosts

When operating over a served document, `createFeatures` rethrows either of the
above raises as a `FeatureConfigError` carrying the original text. This allows a
caller to use one catch block over the base class to handle errors on every
host; additionally, a holder catching `FeatureConfigError` to preserve an
existing document will not accidentally catch a `DOMException`.

If `createFeatures` is called over a bare array, the raise travels untouched. In
this scenario, the class the caller catches is the host's native response rather
than the library's. To resolve this, the caller must either read
`error.message` on the literal path or hand `createFeatures` a document and
catch the base class.

## `FeatureCycleError`

<!-- reference @evanion/feature#FeatureCycleError example=config-errors -->

When a `dependsOn` chain closes on itself, the resolution order becomes
undefined. To prevent this, `@evanion/feature` refuses the set via a
`FeatureCycleError`.

The `path` property holds the closed walk and ends where it starts, ensuring the
closing edge is present both on the error object and in the error message.

## `UnknownDependencyError`

<!-- reference @evanion/feature#UnknownDependencyError example=config-errors -->

If a `dependsOn` property names a feature that no definition in the set
declares, `@evanion/feature` raises an `UnknownDependencyError`. The `key`
property identifies the feature that named the missing dependency, and
`dependency` identifies the name that resolves to nothing.

## `DuplicateFeatureError`

<!-- reference @evanion/feature#DuplicateFeatureError example=config-errors -->

When two definitions carry the same `key`, `@evanion/feature` raises a
`DuplicateFeatureError` carrying that key. This typically occurs when a document
is assembled from two different sources; the key named in the error is the one
to investigate in both sources.

## `DuplicateVariantError`

<!-- reference @evanion/feature#DuplicateVariantError example=variant-errors -->

If two variants of one feature declare the same `name`, a rule pinning that name
names both, so `@evanion/feature` refuses the feature via a
`DuplicateVariantError`.

The `feature` and `variant` properties carry the conflicting pair.

## `UnknownVariantError`

<!-- reference @evanion/feature#UnknownVariantError example=variant-errors -->

When a rule's `variant` names a variant that its feature does not declare, the
rule would match and pin nothing, and `variantOf` would answer with a name the
schema does not carry. In this case, `@evanion/feature` raises an
`UnknownVariantError`.

The `feature` and `variant` properties carry the pair. This error is also raised
if a feature declares no variants at all but carries a rule with a `variant`.
