## `FeatureProvider`: Wrapping Your Tree

The `FeatureProvider` from `@evanion/feature/react` wraps your application (or a specific subtree). It takes `features`, the store, plus either a `context` it resolves or a `decisions` record resolved elsewhere. React is an optional peer dependency, so an application that uses only the core does not install it.

### Memoize the Context

Resolution is memoized based on the `context` object's identity. If you pass an object literal inline (e.g., `context={{ targetingKey: id }}`), React will treat it as a new object on every render, forcing the provider to re-resolve the entire feature store.

To avoid this, wrap your context in `useMemo`. The store is the one above, and `Checkout` renders `Express` when express pickup is on and `Standard` when it is off:


Leaving `now` out of the context means "the clock at the moment this context was first resolved". A tree that has to agree with a server render passes `now` explicitly, with the instant the server used.

## Accessing Features via Hooks

Once wrapped in an `@evanion/feature/react` provider, any component can access feature flags using one of four hooks:

| Hook                     | Returns                    | Use Case                                                          |
| :----------------------- | :------------------------- | :---------------------------------------------------------------- |
| `useFeatureEnabled(key)` | `boolean`                  | `useFeature(key).enabled`, for a component that shows or hides.   |
| `useFeature(key)`        | `Decision`                 | When you need the explanation (`reason`) or the assigned variant. |
| `useVariant(key)`        | `{ variant?, value? }`     | When you only care about the variant assigned to the user.        |
| `useFeatures()`          | `Record<string, Decision>` | When a component needs to check multiple flags at once.           |

All four throw outside a `<FeatureProvider>`, naming the provider and the package.

### Strict Key Validation

Unlike `isEnabled()`, the `useFeature`, `useFeatureEnabled` and `useVariant` hooks will **throw an error** if you request a key that is not configured in the provider. This prevents typos from being mistaken for "off" features. `attempt` below renders an element and returns the error message when the render throws:

## Handing the Provider a Resolved Record

The `decisions` prop of `@evanion/feature/react`'s `FeatureProvider` is the way to handle server-side resolution: the server resolves the flags and sends the resulting decisions as a prop, and the client provider uses them as they are without re-resolving.

The provider resolves nothing beside a supplied record, so every key a component reads has to be in it. The compiler refuses a record whose type lacks a key, and a record that arrived as JSON reaches the provider unchecked. `attempt` is the helper from the fence above:

By using a bound context, `useVariant('checkout-cta')` is checked against the keys of your `features` store at compile time, and its `variant` is `'control' | 'blue' | undefined`. If you typo a key, your editor reports a compile error before anything runs. A bound provider also publishes to the shared context, so the package's own `useFeature` reads the same decisions underneath it.

## Server Components and the Client Boundary

Because `FeatureProvider` uses `createContext` and `useMemo`, it must be a Client Component (`'use client'`), so `@evanion/feature/react` is a separate entry point. However, the `@evanion/feature` core is not client code.

The recommended pattern for Next.js/RSC is to resolve the flags in a Server Component and pass the decisions down. `Checkout` is the component above, and express pickup here reaches 25% of customers:

```tsx twoslash file=libs/feature/docs/examples.md region=react-server

```

Decisions are plain objects, so they cross the boundary as serialized props. The store itself does not: it carries functions. This ensures that resolution runs on the server, while the client renders from the record it was handed and stays type-safe.
