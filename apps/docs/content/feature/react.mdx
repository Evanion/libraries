# React

`@evanion/feature` provides a dedicated React adapter to integrate feature flags into your component tree. While the core resolution engine is framework-agnostic, the React adapter handles the distribution of these decisions using a Provider and a set of specialized hooks.

## The Problem: Drilling Decisions Through the Tree

In a complex React app, many components need to know the state of a feature flag. Passing a `features` object down as a prop to every single component (prop-drilling) is tedious and makes your components harder to reuse.

The React adapter solves this by using a `FeatureProvider` to make the resolved decisions available to any component in the tree via hooks.

## Using the `FeatureProvider`

The `FeatureProvider` wraps your application (or a specific subtree) and resolves the feature flags based on a provided context.

```tsx
import { FeatureProvider } from '@evanion/feature/react';

const features = createFeatures([{ key: 'express-pickup', enabled: true }]);
const context = { targetingKey: user.id, now: new Date() };

<FeatureProvider features={features} context={context}>
  <Checkout />
</FeatureProvider>
```

### Performance Tip: Memoize Your Context
Resolution is memoized based on the `context` object's identity. If you pass an object literal inline (e.g., `context={{ userId: id }}`), React will treat it as a new object on every render, forcing the provider to re-resolve the entire feature store.

To avoid this, wrap your context in `useMemo`:

```tsx
const context = useMemo(() => ({ targetingKey: user.id, now }), [user.id, now]);
```

### Decoupling from the Server
You can pass a `decisions` prop to the provider. This is the primary way to handle server-side resolution: the server resolves the flags and sends the resulting decisions as a prop, which the client provider then uses immediately without re-resolving. This is also the hand-off point for the settled half of a [`plan()`](/feature/build-time).

## Accessing Features via Hooks

Once wrapped in a provider, any component can access feature flags using one of four hooks:

| Hook | Returns | Use Case |
| :--- | :--- | :--- |
| `useFeatureEnabled(key)` | `boolean` | The fastest way to toggle a UI element. |
| `useFeature(key)` | `Decision` | When you need the explanation (`reason`) or the assigned variant. |
| `useVariant(key)` | `{ variant?, value? }` | When you only care about the variant assigned to the user. |
| `useFeatures()` | `Record<string, Decision>` | When a component needs to check multiple flags at once. |

### Strict Key Validation
Unlike `isEnabled()`, the `useFeature` and `useVariant` hooks will **throw an error** if you request a key that is not configured in the provider. This prevents typos from being mistaken for "off" features.

## Type-Safe Hooks with `createFeatureContext`

To avoid using string literals for keys and to get full TypeScript autocomplete for variants, you can bind the hooks to your specific feature store.

```tsx
export const { FeatureProvider, useFeature, useVariant } =
  createFeatureContext(features);
```

By using a bound context, `useFeature('express-pickup')` is checked against the keys of your `features` store at compile time. If you typo a key, you get a red squiggly immediately rather than a runtime error.

## Server Components and the Client Boundary

Because `FeatureProvider` uses `createContext` and `useMemo`, it must be a Client Component (`'use client'`). However, the core resolution engine is not.

The recommended pattern for Next.js/RSC is to resolve the flags in a Server Component and pass the decisions down:

```tsx
// app/layout.tsx (Server Component)
export default async function Layout({ children }) {
  const decisions = features.resolve({ targetingKey: await currentUserId() });
  return <Flags decisions={decisions}>{children}</Flags>;
}

// app/flags.tsx (Client Component)
'use client';
import { FeatureProvider } from '@evanion/feature/react';

export function Flags({ decisions, children }) {
  return (
    <FeatureProvider features={features} decisions={decisions}>
      {children}
    </FeatureProvider>
  );
}
```

This ensures that the heavy lifting of resolution happens on the server, while the client remains responsive and type-safe.
