## Planning a Build

A static build of `@evanion/feature` flags can write a flag that is on for everyone into the HTML. A flag that is on for booksellers only waits for the request, which knows who is asking; written into the build as a boolean, it would ship to everyone or to nobody.

`plan()` evaluates your feature store against the part of the context a build has, such as `{ game: 'urn:game:azul' }` for a build that renders one page per game, and returns a `PlanEntry` for every feature.


The new checkout is deferred because its rollout reads `targetingKey`, which a build does not have. Settled entries go through the same decision logic `resolve()` uses, so for a feature that does not set `freezeTimeAtBuild`, a request whose context carries the same fields the build had gets the same `enabled`.

### Understanding the Plan Entry

A feature is categorized into one of two states:

1. **Resolved (`resolved: true | false`)**: The decision is settled, because the fields the build has decide it: the feature is off, a parent is settled off, a rule matched with no rule above it waiting on a missing field, or the build refutes every rule. The `decision` object carries the final result.
2. **Deferred (`resolved: 'deferred'`)**: The decision depends on context not yet available (e.g., the customer's `role` or `targetingKey`). The `needs` array lists, sorted, exactly which fields the request must provide to resolve this feature.

### How Rules are Settled

A rule is settled at build time if it can be decided without the missing context:

- **Refuted Rules**: If a rule's condition is already false regardless of the missing field, the rule is settled off. If the build is Azul's page and a rule requires Spirit Island, that rule is refuted whatever `role` the request carries.
- **Global Defaults**: A feature with `enabled: false` is settled off whatever its rules need. A feature with no rules and `enabled: true` is settled on, unless a parent is deferred or a variant split still needs `targetingKey`.

### Features with Variants

`plan()` settles enablement and the variant split separately. A feature with no rules is settled on, and while its split still needs `targetingKey` the entry is `'deferred'` and carries a `decision` without a variant. A filter that keeps only boolean entries leaves such a feature out of the settled half.

## Handling Time Windows

Time is a special case in `@evanion/feature`. By default, `plan()` withholds `now` from a feature's rules, because whether a date window may be frozen into a build depends on how often you deploy. A window stays deferred even when the build's own clock is past it.

However, you can opt in to freezing a time window at build time using the `freezeTimeAtBuild` property in your configuration. This is useful for sites that rebuild on a strict schedule (e.g., hourly) and can afford a small delay in feature activation. A frozen window disagrees with the request from the moment its boundary passes until the next build.

## Implementing the Plan in your App

The `@evanion/feature` `plan()` function splits your features into two paths:

```mermaid caption="The plan() pipeline: settled decisions ship as static data; deferred rules are resolved at runtime."

  P -->|"resolved: true or false"| S["a decisions record"]
  P -->|"resolved: 'deferred'"| D["a key list, plus needs"]
  S --> B["the build<br>FeatureProvider decisions={…}"]
  D --> R["the request<br>resolve(context)"]
```


### The Workflow

1. **At Build Time**: Run `plan()`. Extract all `resolved` decisions into a `settled` record. Ship this record as a prop to your `<FeatureProvider />`, which takes it as its `decisions`.
2. **At Runtime**: Call `resolve(context)` with the data the request provides; the union of the deferred entries' `needs` is the context it has to assemble. The provider uses a `decisions` record as it is and resolves nothing beside it. A page whose components read only settled keys renders from the build's record, and a page whose components read a deferred key hands the provider the record `resolve(context)` returned, which carries every key.

Your build can leave out the branch behind a flag settled `false`. A deferred flag keeps its branch, because the request that turns it on needs it. Settled flags ship in the HTML, and only deferred keys cost a request-time `resolve`.

[Observing](../observing) reports each `plan`, `resolve` and `toggle` call as an event.
