# Build-time planning

For static sites or server-rendered pages, calculating every feature flag for every possible user at build time is impossible. You don't have the user's context (their role, region, or ID) until the request actually arrives.

`plan()` allows you to partition your features into two groups: those that can be settled now (at build time) and those that must be deferred to the request.

## The Problem: The Build-Time vs. Runtime Gap

If you have a feature that is "Enabled for everyone," you can bake that decision into your HTML during the build. This reduces the amount of logic the client has to run.

However, if a feature is "Enabled only for Staff," you cannot resolve it at build time. You must wait for the request, identify the user, and then decide. If you treat this as a simple boolean in your build, you either ship a feature to everyone or to nobody.

## Solution: The Planning Phase

The `plan()` function analyzes your feature store against a partial context (like the current date) and returns a `PlanEntry` for every feature.

### Understanding the Plan Entry

A feature is categorized into one of two states:

1. **Resolved (`resolved: true | false`)**: The decision is settled. Either the feature is globally off, globally on, or its dependency chain has already failed. The `decision` object carries the final result.
2. **Deferred (`resolved: 'deferred'`)**: The decision depends on context not yet available (e.g., the user's `role` or `targetingKey`). The `needs` array lists exactly which fields the request must provide to resolve this feature.

### How Rules are Settled

A rule is settled at build time if it can be decided without the missing context:
- **Refuted Rules**: If a rule's condition is already false regardless of the missing field, the rule is settled off. For example, if a user is "Free" and a rule requires "Premium," that rule is refuted regardless of the user's region.
- **Global Defaults**: A feature with no rules and `enabled: true` is settled on.

## Handling Time Windows

Time is a special case. By default, `now` is treated as deferred because the clock moves forward. A feature that opens on October 1st cannot be settled on September 30th.

However, you can opt-in to "freeze" a time window at build time using the `freezeTimeAtBuild` property in your configuration. This is useful for sites that rebuild on a strict schedule (e.g., hourly) and can afford a small delay in feature activation.

## Implementing the Plan in your App

The `plan()` function splits your features into two paths:

```mermaid caption="The plan() pipeline: settled decisions ship as static data; deferred rules are resolved at runtime."
flowchart LR
  F["features"] --> P["plan({ now })"]:::accent
  P -->|"resolved: true or false"| S["a decisions record"]
  P -->|"resolved: 'deferred'"| D["a key list, plus needs"]
  S --> B["the build<br>FeatureProvider decisions={…}"]
  D --> R["the request<br>resolve(context)"]
```

### The Workflow:
1. **At Build Time**: Run `plan()`. Extract all `resolved` decisions into a `settled` record. Ship this record as a prop to your `<FeatureProvider />`.
2. **At Runtime**: The `FeatureProvider` uses the settled decisions first. For any `deferred` features, it calls `resolve(context)` using the data provided by the request.

This hybrid approach maximizes the performance of static content while maintaining the precision of dynamic, user-specific feature flags.
