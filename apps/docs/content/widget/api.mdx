# API reference

Everything `@evanion/widget` exports, one heading per symbol. Both renderers
re-export every symbol here except `warnOnce` and `resetWarnings`, so a
renderer's users import these names from the renderer.

## `defineWidgets`

```signature
function defineWidgets<R extends WidgetRegistry>(registry: R): R;
```

Returns the registry it was handed, typed as the literal object passed in.

```ts twoslash file=libs/widget/README.md region=registry

```

The generic parameter is the whole job. Annotating the same object as
`WidgetRegistry` widens its keys to `string`, which takes away the key union a
code editor completes on and the union a renderer types a component against. It has
no effect on `validateItems`, whose `required` map is keyed by plain strings.

## `validateItems`

```signature
function validateItems(
  items: unknown,
  known: KnownWidgetTypes,
  required?: Record<string, string[]>,
): WidgetProblem[];
```

Walks `items`, recurses into each item's `children`, and returns every problem
it found. It throws nothing and it short-circuits nothing, so one call reports
a whole payload.

| Parameter  | What it takes                                                          |
| ---------- | ---------------------------------------------------------------------- |
| `items`    | the payload, typed `unknown` because it usually arrives as parsed JSON |
| `known`    | a registry, or a plain list of type names                              |
| `required` | a widget type mapped to the props that must be present and non-blank   |

```ts twoslash file=libs/widget/README.md region=unknown

```

A type is matched as an own key of `known`, so an item typed `constructor` or
`__proto__` is unknown. Ids are checked for duplicates within one sibling list
only. [What it reports](/widget/problems) lists every message and what produces
it.

## `warnOnce`

```signature
function warnOnce(message: string): void;
```

Writes `message` to `console.warn` the first time it is seen and stays quiet
every time after, for the life of the process. It writes nothing at all when
`NODE_ENV` is `production`, and a bundler folds that comparison and drops the
call.

A renderer warns from render, so one stale type in a payload would otherwise
log on every re-render, and twice over on a page that renders on the server and
then hydrates. Every string in `ERROR_MESSAGES` carries the offending item's
`type` and `id`, which is what makes the text a usable key: each bad item is
reported once, and a second bad item is still reported.

This is the seam between the core and a renderer. A project that draws through
a published renderer has no reason to call it, and neither renderer re-exports
it.
[Print the widget warning from a renderer of your own](/widget/problems#print-the-widget-warning-from-a-renderer-of-your-own)
runs a minimal renderer that calls it.

## `resetWarnings`

```signature
function resetWarnings(): void;
```

Clears the set of messages `warnOnce` has already written. A set that lives as
long as the process is what a dev server wants and what a test file cannot
have, since one case's warning would silence the next case that produces the
same message. Each renderer's test setup calls this before every test, and the
renderer on
[What it reports](/widget/problems#print-the-widget-warning-from-a-renderer-of-your-own)
calls it before its first render.

## `ERROR_MESSAGES`

The text a renderer warns with. Held here so that a stale widget type reads the
same way whether React or Astro drew the page.

```ts twoslash file=libs/widget/README.md region=warning

```

| Key                  | Shape                  | Warned when                                            | Printed by                                                                             |
| -------------------- | ---------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `UNKNOWN_WIDGET`     | `(type, id) => string` | an item's type is not a key of the registry            | both renderers                                                                         |
| `MALFORMED_ITEMS`    | `string`               | the `items` prop is not an array                       | both renderers                                                                         |
| `MALFORMED_ITEM`     | `(id, type) => string` | an entry is not an object, or carries no usable `type` | `@evanion/react-widget`; `@evanion/astro-widget` prints `UNKNOWN_WIDGET` for this item |
| `MALFORMED_CHILDREN` | `(id) => string`       | an item's `children` is present and is not an array    | `@evanion/react-widget`; an Astro widget receives `children` as data                   |
| `UNKNOWN`            | `'unknown'`            | the stand-in a message uses for an id or type it lacks | `@evanion/astro-widget`, inside `UNKNOWN_WIDGET`                                       |

## `VALIDATION_MESSAGES`

The text `validateItems` reports. Compare a problem's `message` against these
to group, count or translate a report, and assert against them in a test. Every
key and what produces it is on [What it reports](/widget/problems).

`MISSING_FIELD` is `(field: string) => string`; the other eight are plain
strings.

## `AnyWidgetItem`

```signature
interface AnyWidgetItem<Type extends string = string, Props = object> {
  id: string;
  type: Type;
  props: Props;
  meta?: WidgetMeta;
  children?: AnyWidgetItem[];
}
```

One item, in the loose form data takes before a registry exists: a content
management system payload, a fixture, a network response. This is the whole
item model, and every renderer draws exactly this.
[The Overview](/widget#how-a-widget-item-array-describes-a-page) walks through
each field. A renderer that can type its components against a registry offers a
checked counterpart, and [`@evanion/react-widget`](/react-widget)'s
`WidgetItem<C>` widens to this one.

## `WidgetRegistry`

```signature
type WidgetRegistry<T = unknown> = Record<string, T>;
```

A widget type mapped to whatever the renderer resolves it to. `T` is the
renderer's component type. `@evanion/react-widget` instantiates it at a
`ComponentType`, which is what drives its compile-time prop check.
`@evanion/astro-widget` leaves it at the default, because an `.astro` module's
default export is an `AstroComponentFactory` carrying no prop types: the props
of a `.astro` file live in its frontmatter `Props` interface, out of the
factory's reach, so `validateItems` covers that ground at build time.

## `WidgetMeta`

```signature
type WidgetMeta = Record<string, unknown>;
```

The `meta` vocabulary of a widget set whose item wrapper declares none. The item
wrapper is the element a renderer draws around each item, `chrome.item` in
`@evanion/react-widget`. `WidgetMeta` accepts any object, so an item carries
whatever placement data it likes and a wrapper that reads `meta` narrows it by
hand.

## `WidgetProblem`

```signature
interface WidgetProblem {
  index: number;
  id: string;
  type: string;
  message: string;
}
```

One line of the report `validateItems` returns. `index` is the item's position
within its own sibling list, and `-1` when the payload itself is not a list.
`id` and `type` are the item's own, or `-` when the item carries none a reader
could use.

## `KnownWidgetTypes`

```signature
type KnownWidgetTypes = WidgetRegistry | readonly string[];
```

The set of widget types a payload may use. A plain list of names is accepted
beside a registry so that a webhook handler or a continuous integration script validates a payload
without importing the components it will never draw.
