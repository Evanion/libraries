# @evanion/widget

A content management system (CMS) saves a page as a list of items, and a
renderer skips any item whose `type` it has no component for.
`@evanion/widget`, the widget core, defines those items and checks them before
a renderer draws them.

## How a widget item array describes a page

A widget item names the component that draws it in `type` and carries that
component's data in `props`. The array below is a listing page in Baize, the

`problems` is an empty array: every item names a type in the list, and every
item carries a `props` object. Each of the other three fields has one job:

- `id` identifies an item among its siblings.
- `meta` holds placement. A renderer hands `span: 2` to the element it wraps
  the listing in, which can make that element two grid columns wide, and the
  listing's own props never see it.
- `children` nests items. Root's listing sits inside the `tonight` shelf, so a
  CMS editor who moves the shelf moves Root's listing with it.

`@evanion/react-widget` draws `children` inside their parent.
`@evanion/astro-widget` hands them to the parent's component as data, and that
component renders them.

## The widget vocabulary

The widget core and both renderers use four terms.

- An **item** is one entry in the array: `id`, `type`, `props`, and optional
  `meta` and `children`. `AnyWidgetItem` is its type.
- A **registry** maps each `type` to the component a renderer draws for it.
  `defineWidgets(registry)` returns the same object, typed so that your code
  editor completes on its keys.
- A **renderer** is the package that turns items into markup, one per
  framework.
- A **problem** is one entry in the array `validateItems` returns, typed
  `WidgetProblem`: the item's `index` among its siblings, its `id` and `type`,
  and a `message`.

## What the widget core can do

| You want to                                        | What the widget core gives you                                                   |
| -------------------------------------------------- | -------------------------------------------------------------------------------- |
| describe a page as data a CMS can write            | `AnyWidgetItem`, plain JSON with no class or builder                             |
| name the types a page may use                      | a registry from `defineWidgets`, or a plain array of type names                  |
| reject a bad payload before it renders             | `validateItems(items, known)`, which returns every problem and throws nothing    |
| demand the props a CMS editor must fill in         | `validateItems` with a `required` map                                            |
| run the check where no renderer is installed       | `validateItems` from a package that imports no framework and has no dependencies |
| print the same warning from a renderer of your own | `ERROR_MESSAGES` for the text, and `warnOnce` to print each message once         |

## What the widget core does not do

- Draw anything. A renderer draws the items.
- Check a prop against its component's type at compile time.
  `@evanion/react-widget` does that, because it knows what a React component
  accepts.
- Run `validateItems` for you. A renderer that meets an unknown `type` skips the
  item, and warns only when `NODE_ENV` is not `production`. The check runs
  where you call it.
- Fetch or store the payload. Where the array comes from is your application's
  code.
