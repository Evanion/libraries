# @evanion/widget

A CMS stores a shop page as a list of sections, and a renderer leaves out any
section whose `type` it has no component for. `@evanion/widget` defines the
items in that list and checks them before a renderer draws them.

## How a widget item array describes a page

A widget item names the component that draws it in `type` and carries that
component's data in `props`. The array below is a listing page in Baize, the
board game shop these examples are set in: a wide listing for Brass:
Birmingham, then a shelf headed "On the table tonight" holding one listing for
Root. `validateItems` checks it against the two types the page may use:

`problems` is an empty array, so every item names a type in the list and
carries its props. `id` identifies an item among its siblings. `meta` is
placement: `span: 2` goes to the markup a renderer wraps the item in, and never
into the listing's own props. `children` nests items, so moving `tonight` moves
Root's listing with it.

A renderer draws this array. `@evanion/react-widget` draws it in React and
`@evanion/astro-widget` draws it in Astro, and both produce the same widgets in
the same order.

## The widget vocabulary

Every later widget page uses these four words.

- An **item** is one entry in the array: `id`, `type`, `props`, and optional
  `meta` and `children`. `AnyWidgetItem` is its type.
- A **registry** maps each `type` to what a renderer draws for it.
  `defineWidgets(registry)` returns one with its keys kept literal, so an editor
  completes on them.
- A **renderer** is the package that turns items into markup, one per
  framework.
- A **problem** is one entry in the array `validateItems` returns, typed
  `WidgetProblem`: the item's position, `id` and `type`, and a message.

## What the widget core can do

| You want to                                        | What the widget core gives you                                                      |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| describe a page as data a CMS can write            | `AnyWidgetItem`, plain JSON with no class or builder                                |
| name the types a page may use                      | a registry from `defineWidgets`, or a plain array of type names                     |
| reject a bad payload before it renders             | `validateItems(items, known)`, which returns every problem and throws nothing       |
| demand the props an editor must fill in            | the optional third argument to `validateItems`, a type mapped to its required props |
| run the check where no renderer is installed       | a package that imports no framework and has no dependencies                         |
| print the same warning from a renderer of your own | `ERROR_MESSAGES` for the text, and `warnOnce` to print each message once            |

## What the widget core does not do

- Draw anything. A renderer does, and each one pins this package exactly and
  re-exports every name on it except `warnOnce` and `resetWarnings`. A project
  that draws its pages through a renderer never installs the core by hand.
- Check a prop against its component's type at compile time.
  `@evanion/react-widget` does that, because it knows what a React component
  accepts.
- Run `validateItems` for you. A renderer that meets an unknown `type` skips the
  item, and warns in development only. The check runs where you call it.
- Fetch or store the payload. Where the array comes from is your application's
  code.
