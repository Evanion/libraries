# Dictionaries

`createLuhn({ dictionary })` builds an instance over an alphabet you choose. The
dictionary is the only thing luhn is configured by, and `createLuhn` checks it
once, when the instance is built.

## The default luhn dictionary

`Luhn` is built over `DEFAULT_DICTIONARY`, the 36 lowercase alphanumerics, and
folds input to lowercase:

```ts twoslash file=libs/luhn/README.md region=default-dictionary

```

`n` is the dictionary's size, which the fold computes modulo. The default holds
no uppercase letters, which is what makes folding sound over it: `O` becomes
`o`, and `o` has one position.

## Build a luhn instance over your own dictionary

Baize's pickup codes draw on 32 characters, the default 36 with `i`, `l`, `o`
and `w` dropped because they are confused when read aloud. `createLuhn` builds
an instance over them:

```ts twoslash file=libs/luhn/README.md region=pickup-dictionary

```

`pickup.generate` and `pickup.validate` are the same calls `Luhn` carries,
bound to the new alphabet. `caseInsensitive` is `false` because a dictionary you
supply is not folded unless you ask, for the reason the case sensitivity
section below gives.

The order of the string decides which position each character holds, and so
every check character the instance produces. `'0123…xyz'` and `'zyx…3210'` are
different alphabets, and a code signed under one is not guaranteed to validate
under the other. Keep the string as a constant, and never sort or deduplicate it at
runtime.

## What createLuhn checks in a luhn dictionary

`createLuhn` throws `InvalidDictionaryError` when the dictionary fails one of
five constraints. The error's `reason` names which:

| `reason`       | Constraint                                                                  |
| -------------- | --------------------------------------------------------------------------- |
| `not-a-string` | the dictionary is a string                                                  |
| `too-short`    | at least 2 code points                                                      |
| `odd-length`   | an even number of code points                                               |
| `duplicate`    | no code point appears twice                                                 |
| `case-pairs`   | no two code points are case variants of each other, when folding is enabled |

`offending` lists the characters the constraint named, so a settings screen can
point at them:

```ts twoslash file=libs/luhn/README.md region=constraints

```

The size has to be even because of the fold. Every second position contributes
`floor(2x / n) + (2x mod n)` for the character at index `x`, and for an odd `n`
two indices can contribute the same amount. Over three characters, indices 1
and 2 both contribute 2, so a 1 typed for a 2 at a doubled position is not
caught.

Nothing is checked when `generate` or `validate` runs. An instance you hold
cannot produce a code its own `validate` rejects.

## How luhn counts a dictionary

`createLuhn` counts code points, not UTF-16 units, so a dictionary of playing
card symbols has the size you see:

`'🂡🂱🃁🃑'.length` is 8 because each symbol is a surrogate pair. `split('')`
would halve every one of them.

## Case sensitivity in a luhn dictionary

`caseInsensitive` folds input to lowercase before looking it up. It defaults to
`true` when you pass no dictionary and `false` when you pass one:

```ts twoslash file=libs/luhn/README.md region=case-sensitivity

```

The pickup instance refuses `A4KP-9MXA` because `A`, `K`, `P`, `M` and `X` are
not in its dictionary and are dropped. Turning folding on makes it accept the
code a customer typed in capitals. `ALTERNATING_CASE_DICTIONARY` is 62
characters, `0` to `9` then `Aa Bb … Zz`, and it reads case: `Order` and
`order` sign differently.

Folding over a dictionary holding both `A` and `a` would send both to one
position and leave the other unreachable, so `createLuhn` refuses it:

```ts twoslash file=libs/luhn/README.md region=case-pairs

```

## Choosing a luhn dictionary's size

A random string passes `validate` one time in `n`, so a larger dictionary
catches more of what is not a code at all. A size that divides 256 is the other
consideration: it is what makes `byte % n` pick each character equally often
when you draw random codes over the dictionary, and `uniformOverBytes` reports
whether it does. 32 satisfies both, which is why the pickup alphabet has 32
characters.
