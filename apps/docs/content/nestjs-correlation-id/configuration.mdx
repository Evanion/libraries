# Configuration

To change the header, the id generator or the check an incoming id passes, pass
a `Partial<CorrelationConfig>` to `CorrelationModule.forRoot()` in your root
module.

| Field       | Default                            | What it does                                   |
| ----------- | ---------------------------------- | ---------------------------------------------- |
| `header`    | `'X-Correlation-Id'`               | read from the request, written to the response |
| `generator` | `randomUUID` from `node:crypto`    | generates an id when none usable arrived       |
| `validate`  | `DEFAULT_CORRELATION_ID_VALIDATOR` | decides whether an incoming id is reused       |

## Pass a configuration to CorrelationModule.forRoot

`forRoot()` fills in every field it is not given, so a provider that injects
`CORRELATION_CONFIG_TOKEN` always gets a complete object. `CorrelationConfig`
still types `validate` as optional, so the fence calls it with `?.`. The last
line checks the generator against the validator: an id the service generates
has to pass its own check when the next service sends it back.

## Choosing the correlation header

No correlation header is registered with the Internet Assigned Numbers
Authority (IANA), so there is no canonical spelling to defer to.
`X-Correlation-Id` and `X-Request-Id` are the two in common use; pick the one
the rest of your stack already sends.

The middleware matches the request header case-insensitively, because Node
lowercases incoming header names. The casing you configure is the casing that
goes out on the response and on calls through `withCorrelation()`.

## Choosing the id generator

The middleware calls the generator only when no usable id arrived, so a counter-
or sequence-backed generator is not advanced for an id that gets discarded.

`randomUUID` produces 36 characters, and the default validator accepts up to 128. Under the default validator, a generator that returns ids longer than 128
characters produces ids the same application rejects when they come back in as
a header.

## Validating an incoming correlation id

An incoming id that passes `validate` goes into the response header and into
whatever the application logs. `DEFAULT_CORRELATION_ID_VALIDATOR` accepts 1 to
128 characters, each a letter from A to Z in either case, a digit, an underscore, a dot, a colon or a
hyphen.


What the default check refuses:

- A carriage return (CR) or a line feed (LF). Node already rejects both in a
  header, incoming and outgoing. The check covers an id from another source,
  such as a queue message, that reaches your log lines, where a CR or LF forges
  a line.
- Anything over 128 characters, which bounds what one request can append to
  every log line it touches.
- A comma. Node joins a repeated request header into one comma-separated string,
  and the middleware joins an array the same way, so one request that carries
  the header twice gets a fresh id.

An id that fails is replaced by a generated one, and `getCorrelationId()`
returns the generated id. `req.headers` keeps the rejected value, because the
middleware writes the request header only when the request carried none.

### Replacing DEFAULT_CORRELATION_ID_VALIDATOR

Tightening `validate` to the exact shape your services generate is safe.
Baize's `/^(storefront|orders|stock)-[0-9a-f]{6}$/` accepts no id the default
refuses. A validator that accepts CR or LF lets an id from a queue message forge
a log line. One with no length bound lets a single request write an arbitrarily
long string into every log line it touches.

## Calling CorrelationModule.forRoot once

`forRoot()` registers the module `global: true`, because
`CorrelationIdMiddleware`, `withCorrelation()` and every provider that reads an
id resolve `CORRELATION_CONFIG_TOKEN` from the root injector. Without that,
every consuming module would import `CorrelationModule` itself.

A second `forRoot()` registers a second configuration under the same token, and
the last import wins. Nest raises no error and prints no warning, so if two
feature modules each call it, the header one of them configured stops applying.

There is no `forRootAsync()`. The configuration is a plain object, fixed when the
root module is declared, so a value from the environment is read from
`process.env` there.
