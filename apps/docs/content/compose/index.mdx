# @evanion/compose

A React app nests its providers one inside the next, so adding one reindents the
tree and moving one means finding its closing tag. `ComposeProvider` takes the
same providers as a flat array.

## How compose reads a provider array

`ComposeProvider` reads the `providers` array as the tree, top to bottom. The
first provider in the array wraps the second, and the last one wraps the
`children` you pass. The two providers below each render a `div`, so the markup
shows where each one sits. `<p>Brass: Birmingham</p>` stands in for a page of
Baize, the board game shop these examples are set in:

```tsx twoslash file=libs/compose/README.md region=render-order

```

`renderToStaticMarkup`, from `react-dom/server`, turns the tree into the HTML
string `markup`. `CartProvider` is first in the array and its `div` is
outermost. `ThemeProvider` needs a `theme`, so `provider()` pairs it with its
props. `ComposeProvider` renders each provider with the next one as its
`children`. It calls no hook and creates no context.

## The compose vocabulary

Every later compose page names the parts of a `providers` array with four
words.

- A **provider** is any component that renders its `children`.
  `ComposeProvider` asks nothing else of one.
- An **entry** is one element of the `providers` array.
- A **bare component** is an entry written as the component alone, like
  `CartProvider`. It fits a provider whose props are all optional.
- A **tuple** is an entry pairing a component with its props,
  `[component, props]`. `provider(component, props)` returns one and checks the
  props at compile time, where you call it.

## What compose can do

| You want to                                  | What compose gives you                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| write a root's providers as one list         | `ComposeProvider`, which nests `providers` around `children`, first outermost                     |
| give a provider its props                    | a tuple, or `provider(component, props)`                                                          |
| catch a prop an entry gets wrong             | a compile error on that entry, in an array written inline or `as const`                           |
| wrap `ComposeProvider` in your own component | `ComposeProviderProps<T>`, the props type, so your component's callers get the same compile error |
| mount the tree from a React Server Component | a component that calls no hook and no `createContext`, so no `'use client'`                       |

The `'use client'` row covers `ComposeProvider` only. A provider you build on
`createContext` is client code and needs its own `'use client'`.

## When compose is the wrong tool

- One or two providers. Two levels of nesting read fine written out.
- Providers that change order or count while the app runs. React reconciles by
  position, so a change to the array remounts everything under it and drops
  that subtree's state.
- A list, a route or a layout. `ComposeProvider` wraps its children in each
  entry and renders nothing of its own.
  [`@evanion/react-widget`](/react-widget) renders components from data.
