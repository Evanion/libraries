# Where the check happens

`provider(component, props)` checks an entry's props where you call it, and
`ComposeProvider` checks a `[component, props]` tuple only while the array stays
a literal tuple.

## Three ways to write a compose entry

A compose entry is a bare component, a `[component, props]` tuple, or a
`provider()` call that returns one. The array below uses each form once:

```tsx twoslash file=libs/compose/examples/entries.tsx region=entries

```

`provider()` infers the component from its first argument, so it checks the
props object at the call and the editor completes `theme` while you type it. A
bare component and a hand-written tuple are checked later, where the array
reaches `ComposeProvider`.

## An inline compose array is checked entry by entry

A JSX attribute gives the array written in it a contextual type, so TypeScript
infers a literal tuple and `ComposeProvider` checks each entry against its own
component. Four broken entries report four errors, one per line:

```tsx twoslash file=libs/compose/README.md region=checked-inline

```

| Entry                                                 | What the compiler reports                         |
| ----------------------------------------------------- | ------------------------------------------------- |
| `ThemeProvider`                                       | `this component requires props`                   |
| `[ThemeProvider, {}]`                                 | `Property 'theme' is missing`                     |
| `[ThemeProvider, { theme: 'baize' }]`                 | `Type 'string' is not assignable to type 'never'` |
| `[ThemeProvider, { theme: 'dark', accent: 'green' }]` | `unknown prop 'accent'`                           |

`markup` is what the same array rendered. `ComposeProvider` checks nothing at
runtime beyond whether `providers` is an array, so `id="baize"` reached the
HTML. The compiler is the only check.

## Reading a compose error

A failing entry resolves to a type your value is not assignable to, and
TypeScript quotes that type in the error. For every failure except a missing or
wrong value, `@evanion/compose` resolves the entry to a type whose property key
carries the message, so the error opens
`Property '"ComposeError: unknown prop 'accent'"' is missing in type …`.

| Message                                                                                        | What it means                                               |
| ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `unknown prop 'x'`                                                                             | the props object has a key the component does not declare   |
| `this component requires props — use provider(Component, props) or a [Component, props] tuple` | a bare component whose props are not all optional           |
| `first tuple element must be a component`                                                      | the pair is the wrong way round, or the first entry is data |
| `second tuple element must be props, not another component`                                    | two components in one tuple                                 |
| `not a valid provider`                                                                         | the entry is neither a component nor a two-element tuple    |

A missing or wrong value gets no message of its own. The entry resolves to the
shape it should have had, and inline a wrong value reports against `never`.
`provider()` reports the same mistake at the call and names both sides:

```tsx twoslash file=libs/compose/README.md region=checked-at-call

```

The error reads `Type '"baize"' is not assignable to type '"light" | "dark"'`.
`entry` is the pair `provider()` returned, unchanged, because the check ran in
the compiler and not when the line ran.

## A named compose array loses the check

TypeScript infers a named array's type at its declaration, where nothing asks
for a tuple. The declaration then decides what `ComposeProvider` checks:

| Declaration                                     | What `ComposeProvider` checks                                  |
| ----------------------------------------------- | -------------------------------------------------------------- |
| `providers={[…]}`, inline                       | every entry                                                    |
| `const providers = […] as const`                | every entry                                                    |
| `const providers = […]`                         | no entry; a tuple entry fails with an error that names no prop |
| `const providers: ProviderArray = […]`          | no entry, and no error                                         |
| `const providers = […] satisfies ProviderArray` | no entry, and no error                                         |

Below, the annotated array compiles and renders `ThemeProvider` with no `theme`.
The same entry declared `as const` reports the missing prop:

```tsx twoslash file=libs/compose/README.md region=named-array

```

A `provider()` entry keeps its check in every row, because `provider()` checked
it at the call. A bare component does not: only `ComposeProvider` refuses a
bare component whose props are required, and only in a literal tuple.

## Wrapping compose in your own component

A wrapper whose `providers` prop is typed `ProviderArray` compiles, and its
callers' entries go unchecked, because a `ProviderArray` has lost the types of
its entries. Make the wrapper generic over `ComposeProviderProps<T>` and the
