# @evanion/astro-widget

A CMS saves a page as a list of items, and the page has to render each item
through the component its `type` names. `Widgets.astro` does that as Astro
renders the page, and sends no JavaScript to the browser.

## How astro-widget renders a list of items

`Widgets.astro` takes two props. `items` is the list the CMS saved, and
`registry` maps each item's `type` to an `.astro` component. For each item in
order, `Widgets.astro` looks up its `type` and renders that component with the
item's `props`. Below, two items from Baize, the board game shop these examples
are set in, render through a registry that holds `ListingHeader.astro` and
`PriceBox.astro`. A page writes `<Widgets items={items} registry={registry} />`,
and the example renders the same component with `AstroContainer`, Astro's
container API, which runs outside a request and returns the HTML:

The `listing-header` item became the `<header>` and the `price-box` item became
the price, in the order the list gives them. The registry is the package's
`examples/src/registry.ts`, and Getting started writes the same file.

## The astro-widget vocabulary

These five terms recur on the astro-widget pages.

- An **item** is one entry in the list the CMS saved: an `id` unique among its
  siblings, a `type`, the `props` its component takes, and optional `meta` and
  `children`, the items nested inside it. Its type is `AnyWidgetItem`.
- A **widget** is the `.astro` component an item renders through. It receives
  the item's `props` as its own props.
- The **registry** maps each `type` to its widget. `defineWidgets` builds one.
- **`ctx`** is page-level data, such as the store's name, that `Widgets.astro`
  passes to every widget as a prop.
- The **chrome** is an optional component, passed to `Widgets.astro` as
  `chrome.item`, that wraps every widget. It reads the item's `meta`, such as a
  background or a column, and never the item's `props`.

The item shape, `defineWidgets` and `validateItems` come from `@evanion/widget`.
astro-widget installs it at one exact version and re-exports those names, so you
import them from `@evanion/astro-widget`.

## What astro-widget can do

| You want to                                  | What astro-widget gives you                            |
| -------------------------------------------- | ------------------------------------------------------ |
| render a page from the items a CMS saved     | `Widgets.astro`, with `items` and `registry`           |
| fail the build on an item nothing can render | `validateItems`, which returns one problem per fault   |
| give every widget the same page-level data   | the `ctx` prop                                         |
| wrap every widget in the same markup         | `chrome.item`, which reads each item's `meta`          |
| render items nested inside an item           | a widget that renders its own `Widgets` over them      |
| keep the registry's type names typed         | `defineWidgets`, which keeps the keys as literal types |

## When astro-widget is the wrong tool

- A page that has to change after it loads. `Widgets.astro` renders once, when
  Astro renders the page. `@evanion/react-widget` renders the same items in
  React, including in an island.
- A check on a widget's props at compile time. An `.astro` module's type
  carries no props, so the compiler has nothing to check an item against.
  `validateItems` checks an item's props from a script you run before the
  build, and `@evanion/react-widget` infers props from its components.
- A page no editor rearranges. Write the components into the page directly.
