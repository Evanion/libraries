# Check CMS items before Astro renders them

`validateItems` checks the items a CMS saved against the widget types you
render, and returns one problem per fault, so a build script can stop before
`astro build` publishes a page with an item missing.

## Check astro-widget items with validateItems

`validateItems` reports each item whose `type` nothing renders and each prop an
item lacks. It takes three arguments: the items; `known`, the widget types as a
registry or a list of their names; and `required`, a map of the props each type
cannot render without:

## Fail astro build on a bad CMS save with validateItems

Run `validateItems` from a script before `astro build`. The script below is the
whole check for the Baize listing page that Getting started renders, and
`items` is the list the CMS saved for it. Save it as
`scripts/check-content.ts`:

```ts file=libs/astro-widget/examples/scripts/check-content.ts region=build-gate

```

`known` lists the type names, because a Node script cannot import the `.astro`
modules the registry holds. The `throw` gives the script a non-zero exit code,
so the command stops before Astro runs. Make it the `build` script in
`package.json`. `tsx` runs a TypeScript file in Node, and `npx` fetches it if
the project does not have it:

```bash
npx tsx scripts/check-content.ts && astro build
```

### A registry or a list of names

The second argument, `known`, takes a registry or a list of type names. From a
registry `validateItems` reads only the keys, and from a list it reads the
names, so both report the same problems. Code that Astro or Vite compiles, such
as a Vitest test or a page's frontmatter, can import the registry and pass it,
and then the check and the render read one list of types:


## Require props on astro-widget items

The third argument, `required`, maps a widget type to the prop names that must
carry a value, and it is the only check an item's props get in Astro.
`undefined`, `null` and a string of only whitespace count as missing, and a CMS
text field an editor opened and left empty arrives as such a string:

```ts twoslash file=libs/astro-widget/README.md region=required-fields

```

`validateItems` checks required props only for an item whose type is known. An
unknown type reports once, as an unknown type, and nothing for each prop it
lacks.

## What validateItems reports for astro-widget items

Six structural rules check the shape of every item, whatever its type. Five of
them fire on this list, where `game-grid` stands for a widget that nests items
in `children`. The sixth, `item type is not a string`, fires on an item whose
`type` is missing or not a string:

```ts twoslash file=libs/astro-widget/README.md region=structural-rules

```

A list with nothing wrong reports nothing, which is the case a build gate meets
on every deploy:

```ts twoslash file=libs/astro-widget/README.md region=clean-payload

```

### A list that is not an array

When `items` is not an array, such as `{ items: [] }`, `validateItems` returns
one problem with `index: -1` and checks nothing else:

```ts twoslash file=libs/astro-widget/README.md region=not-a-list

```

### `index` counts within one level

`validateItems` walks into `children`, the items nested inside an item, so a
problem in a top-level item and a problem inside its `children` can both report
`index: 0`. `id` tells them apart, and the list of problems stays flat:
