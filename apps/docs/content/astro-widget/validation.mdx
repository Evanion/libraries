# Check CMS items before Astro renders them

`validateItems` checks the items a CMS saved against the widget types you
render, and returns one problem per fault, so a build script can stop before
`astro build` publishes a page with an item missing.

## Why astro-widget needs validateItems

`Widgets.astro` skips an item whose `type` the registry does not hold, and warns
only in development. So a CMS save naming a type nothing renders publishes a
page with a gap in it. `validateItems` takes the items, the widget types, and a
map of the props each type cannot render without:

```ts twoslash file=libs/astro-widget/README.md region=validate

```

`answer-wall` is not a type the registry holds, so `validateItems` reports the
third item. Nothing threw, and one call returned every fault in the list.

This check matters more in Astro than in `@evanion/react-widget`, because it is
the only check a widget's props get. An `.astro` module's type carries no props,
so the compiler has nothing to check an item against.

`known` lists the type names, because a Node script cannot import the `.astro`
modules the registry holds. The `throw` gives the script a non-zero exit code,
so the build command stops before Astro runs:

```bash
node scripts/check-content.mjs && astro build
```

A CMS webhook can run the same check when an editor saves, so the editor sees
the problem before anyone deploys.

## Require props on astro-widget items

The third argument maps a widget type to the prop names that must carry a
value. Blank counts as missing, which is what a CMS text field arrives as when
an editor opened it and left it empty:

```ts twoslash file=libs/astro-widget/README.md region=required-fields

```

`validateItems` checks required props only for an item whose type is known. An
unknown type reports once, as an unknown type, and nothing for each prop it
lacks.
