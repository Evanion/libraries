**The concept.** You left a comment on the Brass: Birmingham listing. So did Jo. You
can edit yours. You cannot edit Jo's.

Everyone knows that rule. The interesting part is that no role can express it.
You and Jo are both customers, with exactly the same permissions. What tells you
apart is which comment is yours.

So the rule has to read the comment. That is the whole of this tier.

**What you will have.** A policy that knows whose comment is whose, and a save
that writes only the fields you are allowed to change.

**Why you would want it.** The alternative is the check by hand. It goes in the
handler, as an `if`, next to the code that does the work. It reads fine the day
you write it. Six months later there are forty of them, three are subtly
different, one is missing, and the moderation job that edits comments in bulk
never had one at all.

**How the library gets you there.** One condition reads the comment, and that one
change brings four things with it: a type that catches a misspelled path, a
fourth answer for a comment that arrived half-loaded, a decision that tells you
why it said no, and a field map you hand to the ORM.

## Naming the comment, so acl can check the paths

To ask whether this comment is yours, you name a path into it:
`object.authorId`. That is a string, and strings take typos.

Write `object.authorld` with an L and nothing complains. The matrix builds. The
tests pass. The permission just never says yes, to anybody, and you find out from
a bug report.

So name the shape once and let the compiler hold you to it:

```ts file=libs/acl/README.md region=typed-authoring

```

`policy<Subject>()` names the subject once. Each `.for()` binds one object kind
to its type and hands the condition helpers to a block.

Chain a `.for()` for every kind your app has, so one policy covers the whole
app. A policy per resource is the `if` you came here to delete, in another
file.

The block declares two kinds of rule. `.allow` is the kind you wrote in the
simple tier: the action is granted when the rule's conditions hold. `.deny` is
the kind this page adds. Nobody may delete a published comment, so the block
says so once, and a deny that matches outranks every allow that matched with it.
No permission gates another: a rule that publish shares with update is written
into publish, where a reader of publish sees it.

The typing is smaller than it looks. A helper reads a string beginning
`subject.` or `object.` as a path into that thing, and reads any other string as
a plain value. That is why `p.eq('object.status', 'published')` compares the
status against the text `published`, and why `p.eq('object.authorId',
'subject.idd')` refuses to compile, with the path you fat-fingered in the
message.

`build()` flattens the blocks to a plain matrix, so
`JSON.stringify(access.matrix)` emits the same JSON envelope you wrote by hand in
the simple tier. The types live in your editor and never reach the document.

## The four answers an acl decision can give

All of that assumes you have the comment in hand. Often you do not.

The listing page loads forty comments and selects from each only the fields it
renders. Now ask whether you may edit one. The allow rule reads
`object.authorId`, the deny rule reads `object.status`, the comment in your hand
carries neither, and the honest answer is neither yes nor no.

So a decision here has four outcomes:

```

Three of them you have already met. Nothing matched, so no. An allow rule
matched, so yes. A deny matched, so no, and the deny wins.

The fourth is the new one. The engine could not tell. It says `unevaluable`, and
`missing` names the paths it could not read. Fetch the fields those paths name,
ask again, and you get a real answer.

## Asking an acl decision why

Four answers only help if you can tell which one you got. The decision carries
three more fields for that: `reason`, `rule` and `missing`.

All three are output only. Read them to build an error message, log them, show
them in a tooltip. Never branch on them. Gate on `allowed` and nothing else. A
handler that checks `reason !== 'denied'` grants everything the engine refused.

## Which parts of a comment acl will let you write

Last line of the table, and the one that changes your UI.

You may edit your own comment. Fine. May you still edit it once it is locked?
May you change the text and not the status? "May you edit this" was
never the question the form needed answering. "Which of these inputs do I render"
was.

```

`*` means every field, and `!status` takes one back out.

The fifth argument is the axis. `'read'` asks which fields of the comment you
may see; `'write'` asks which you may set, and takes the proposed comment after
it. The call above names `read` twice, once as the action and once as the axis,
and they are different arguments.

The map covers every field on the comment and every field your rules name. On a
write it also covers every field of whatever the caller sent you, including one
the comment has never had. That last case is why the engine computes the map for
each call rather than reading it off the matrix.

## Applying the field map with `pickAllowedFields`

You have the map. The package applies it for you, and you should let it — here
on a user record, because the two calls narrow every kind alike:

```ts file=libs/acl/README.md region=write-path

```

Pass what it returns to the ORM. Pass only that.

Never filter the map yourself. That is [the one mistake this page most wants you
to avoid](/acl/pitfalls#never-hand-filter-the-field-map). The obvious loop keeps
every field that is not `denied`, which quietly keeps the `unevaluable` ones too,
and those are fields nobody said you could write.

That is the tier. You edit your comment, Jo edits hers, and nobody wrote an `if`.
