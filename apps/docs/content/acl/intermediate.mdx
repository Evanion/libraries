**The concept.** A permission that depends on the row. Not "a bookseller may
edit" but "the bookseller who listed it may edit it" — one condition reads the
thing being acted on, and everything here follows from that single change.

**What you will have.** A policy that answers ownership questions on its own, and
a write path that carries the answer down to the ORM without you filtering
anything by hand.

**Why you would want it.** Role-only rules run out fast. The moment two people
hold the same role and one of them owns the thing, the role cannot tell them
apart — so the check moves into your handler as an `if`, where nobody finds it
again and no second service repeats it. This is where that `if` goes back into
the policy.

**How the library gets you there.** Reading the row costs four things, and they
arrive in order: a type that checks your paths at compile time, a fourth answer
for when the row is not fully loaded, a decision that explains itself, and a
field map you hand to the database rather than apply by hand.

In the simple tier every answer came from the subject. "A bookseller may edit" is
true before you have looked at anything, so the policy could answer without being
handed a listing at all. "The bookseller who listed it may edit it" cannot.
Someone has to fetch the row — and everything below is what that costs.

## What reading the row costs you

| Because a condition reads the object | You now need                                                                       |
| ------------------------------------ | ---------------------------------------------------------------------------------- |
| a path can be misspelled             | [the typed builder](/acl/authoring), which makes it a compile error                |
| the object can be a projection       | [`unevaluable`](/acl/refusals#when-the-answer-is-unevaluable) and one refetch      |
| a list is many instances             | [`canMany`](/acl/asking#asking-about-a-list), one settled clock for the whole list |
| a row has parts                      | [field permissions](/acl/writing) and `pickAllowedFields` on the write             |

Work down that column and you have this page.

## Naming the row, so acl can check the paths

The first line of the table bites first. A condition that reads the object names
a path into it — `object.ownerId` — and a string is a string. Misspell it and
nothing complains. The permission simply never decides.

So name the shape once, and let the compiler hold you to it:

```ts file=libs/acl/README.md region=typed-authoring

```

`policy<Subject>()` names the subject. Each `.for()` binds one object kind to its
type and hands the condition helpers to a block.

What makes that work is smaller than it looks. An operand is read as a path when
its type matches `` `subject.${string}` | `object.${string}` | 'now' ``, and as a
literal otherwise. That one discriminator is the whole mechanism. It is why
`p.eq('object.status', 'published')` compares against a string, and why
`p.eq('object.authorId', 'subject.idd')` is a compile error that names the path
you fat-fingered.

The builder flattens to the canonical matrix on the first query, so
`JSON.stringify(access.matrix)` still emits the document a foreign producer
would. Nothing about the typed path changes what ships.

## The four answers an acl decision can give

Naming the row assumes you have it. Often you do not: a list view holds
`{ id, ownerId }` and little else, and a condition reading `object.status` has
nothing to read.

That is why a decision at this tier has four outcomes rather than two:


Three of them came with you from the simple tier. Default deny is the floor, an
allow rule grants, and a matched deny outranks a matching allow. The fourth is
new here — a projection carrying neither field decides `unevaluable`, and
`missing` names exactly what to fetch.

## Asking an acl decision why

Four answers are only useful if you can tell them apart, and that is what the
rest of the decision is for. Beyond `allowed` it carries `reason`, `rule`,
`blockedBy`, `cause` and `missing`.

```ts file=libs/acl/README.md region=cascade

```

`blockedBy` is the edge this permission died on. `cause` is the first ancestor
off for a reason of its own. In a chain of three those are two different
permissions, which is why both are carried rather than one.

One rule covers all five: they are output only. Nothing in the library reads a
reason back to decide anything, and neither should you. Gating on the reason
string instead of on `allowed` grants what the engine refused.

## Which parts of the row acl will let you write

The last line of the table, and the one that changes the most. Once a condition
can read the row it can read one field of it, and "may this bookseller update
this listing" stops being the only question worth asking. "Which parts of it" is
the one that shapes a form.

```ts file=libs/acl/README.md region=field-permissions

```

`*` is the baseline and `!name` subtracts from it. The map covers every key the
object carries, every name the rules mention, and — on the write axis — every key
of the proposed write, including one the row has never held. That last case is
the one people forget, and it is why the map is computed rather than looked up.

## Applying the field map with `pickAllowedFields`

Holding the map is not the same as applying it correctly, so the package closes
that gap itself rather than leaving it to each caller:

```ts file=libs/acl/README.md region=write-path

```

Pass its result to the ORM, and pass only its result. Filtering the map by hand
is [the defect it exists to prevent](/acl/pitfalls#never-hand-filter-the-field-map):
an `unevaluable` field is not a permitted one, and a hand-written filter that
checks for `denied` lets it through.

That is the tier. One condition read the row, and four things followed — a type
to check the paths, an answer that can be repaired rather than refused, a
decision that says why, and a write that carries the field map all the way to
the database.
