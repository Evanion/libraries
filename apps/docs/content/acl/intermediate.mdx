**The concept.** You left a question on the Brass: Birmingham listing. So did Jo. You
can edit yours. You cannot edit Jo's.

Everyone knows that rule, and no role can express it. You and Jo are both
customers with exactly the same permissions, and what tells you apart is which
question is yours.

So the rule has to read the question. That is the whole of this page.

**What you get.** A policy that knows whose question is whose, and a save
that writes only the fields you are allowed to change.

```mermaid caption="What changes when a condition names an object path. A subject-only condition reads the subject the server resolved whole, so it either holds or fails. A condition naming an object.* path also reads the instance the caller passed, and an instance that does not carry the path leaves the condition unevaluable until a refetch supplies it."
flowchart LR
  S["subject<br>resolved whole"] --> C1["p.contains('subject.roles', 'bookseller')"]
  C1 --> O1["holds<br>fails"]
  S --> C2["p.eq('object.askedBy', 'subject.id')"]:::accent
  O["object<br>the question in hand"] --> C2
  C2 --> O2["holds<br>fails<br>unevaluable"]
```

**Why you want it.** The alternative is the check by hand, in the handler,
as an `if`, next to the code that does the work. It reads fine the day you write
it. Six months later there are forty of them, three are subtly different, and the
bulk close job never had one at all.

**How the library gets you there.** One condition reads the question, and that one
change brings four things with it: a type that catches a misspelled path, a
fourth answer for a question that arrived half-loaded, a decision that tells you
why it said no, and a field map you hand to the ORM.

## Four things you now need

- You name a path into a question, so the typed builder makes a typo a compile
  error.
- A question may be half-loaded, so a decision gains a fourth answer,
  `unevaluable`, and you refetch and ask again.
- A page shows forty questions, so `canMany` decides the array in one call.
- A question has fields, so a decision names which you may write and
  `pickAllowedFields` applies it.

## Naming the question, so acl can check the paths

To ask whether this question is yours, you name a path into it:
`object.askedBy`. That is a string, and strings take typos.

Write `object.askedBv` with a v and nothing complains. The matrix builds, the
tests pass, the permission never says yes to anybody, and you find out from a bug
report.

So name the shape once and let the compiler hold you to it:

```ts file=libs/acl/README.md region=typed-authoring

```

`policy<Subject, Objects, Verbs>()` names the subject, the object kinds, and any
verbs beyond the default four. Each `.for()` hands the condition helpers to a
block. Chain one per kind your app has, so one policy covers the whole app. A
policy per resource is the `if` you came here to delete, in another file.

The block declares two kinds of rule. `.allow` is the kind you wrote against the
subject alone: the action is granted when the rule's conditions hold. `.deny` is
the kind this page adds. Nobody may delete a question the shop has locked, so
the block says so once, and a deny that matches outranks every allow that
matched with it. No permission gates another: a rule that `hide` shares with
`update` is written into `hide`, where a reader of `hide` sees it.

The typing is smaller than it looks. A helper reads a string beginning
`subject.` or `object.` as a path into that thing, and reads any other string as
a plain value. That is why `p.eq('object.status', 'locked')` compares the
status against the text `locked`, and why `p.eq('object.askedBy',
'subject.idd')` refuses to compile, with the path you mistyped in the message.

`build()` flattens the blocks to a plain matrix, so
`JSON.stringify(access.matrix)` emits the same JSON envelope the subject-only
policy flattened to. The types live in your editor and never reach the document.

## The four answers an acl decision can give

All of that assumes you have the question in hand. Often you do not.

The listing page loads forty questions and selects from each only the fields it
renders. Now ask whether you may edit one. The allow rule reads
`object.askedBy` and the deny rule reads `object.status`. The question in your
hand carries neither field, so the honest answer is neither yes nor no.

So a decision here has four outcomes:

```

Three of them you have already met. Nothing matched, so no. An allow rule
matched, so yes. A deny matched, so no, and the deny wins.

The fourth is the new one. The engine could not tell, so it says `unevaluable`
and `missing` names the paths it could not read. Fetch those fields, ask again,
and you get a real answer.

## Asking an acl decision why

Four answers only help if you can tell which one you got. The decision carries
three more fields for that: `reason`, `rule` and `missing`.

All three are output only. Build an error message from them, log them, show them
in a tooltip. Never branch on them: gate on `allowed` and nothing else. A handler
that checks `reason !== 'denied'` grants everything the engine refused.

## Which fields of a question acl lets you write

The last line of the list is the one that changes your UI.

You may edit your own question. Fine. May you change the body and leave the
status alone? The form draws itself from one answer: which of these inputs do I
render.

`canFields` answers it. It decides the action and every field of the write in one
pass, and the shop's lock on `status` is not the customer's:

```ts file=libs/acl/README.md region=write-path

```

`*` means every field, and `!status` takes one back out.

The fifth argument is the axis. `'write'` asks which fields you may set and takes
the proposed question after it. `'read'` asks which you may see and takes nothing
more. The call above names `update` as the action and `write` as the axis, and
they are different arguments.

The map covers every field on the question, every field your rules name, and on a
write every key the caller sent you, including one the question has never had.
That last case is why the engine computes the map on every call: the matrix
cannot hold a field nobody has declared yet.

## Applying an acl field map with `pickAllowedFields`

A field decision is a map, and a map is not a write. `pickAllowedFields` takes
the decision and the proposed question and returns the keys that decided
`allowed`.

```mermaid caption="The guarded save. canFields decides the action and every key of the proposed write in one pass, and each key comes back allowed, denied or unevaluable. pickAllowedFields keeps the allowed keys and drops the other two states, so only those keys reach the ORM."
flowchart LR
  P["the proposed question"] --> D["access.canFields(…, 'write', proposed)"]
  D --> M["fields: one state per key<br>allowed · denied · unevaluable"]
  M --> F["pickAllowedFields(decision, proposed)"]:::accent
  F --> O["the ORM<br>the allowed keys and nothing else"]
```

Pass what it returns to the ORM. Pass only that.

Never filter the map yourself. [Never hand-filter the field
map](/acl/pitfalls#never-hand-filter-the-field-map) is the mistake this API
makes easiest. The obvious loop keeps every field that is not `denied`, which
keeps the `unevaluable` ones too, and nobody said those were writable.

That is the page. You edit your question, Jo edits hers, and nobody wrote an
`if`.
