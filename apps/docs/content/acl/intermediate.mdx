**The concept.** Two booksellers work your shop. Mika and Otto, both with the
`bookseller` role, both looking at the same listing for Brass: Birmingham. Mika
wrote it. Otto did not.

You want Mika to be able to edit it and Otto not to. Their roles are identical,
so no rule about roles can separate them. The only thing that tells them apart is
the listing itself, and that is what this page teaches you to read.

**What you will have.** A policy that knows who owns what, and a write path that
carries the answer from the policy to the database without you filtering
anything in between.

**Why you would want it.** Without it you write the check by hand. It goes in the
handler, as an `if`, next to the code that does the work. It reads fine the day
you write it. Six months later there are forty of them, three are subtly
different, one is missing, and the service that was supposed to repeat the check
never did.

**How the library gets you there.** One condition reads the listing. That single
change costs you four things, and they arrive in this order: a type that catches
a misspelled path, a fourth answer for when you only loaded half the row, a
decision that tells you why it said no, and a field map you hand to the ORM.

Work through them in that order and you have the tier.

## Naming the row, so acl can check the paths

Start at the top of that table. To ask whether Mika wrote the listing, you name a
path into it: `object.ownerId`. That is a string, and strings take typos.

Write `object.ownerld` with an L and nothing complains. The matrix builds. The
tests pass. The permission just never says yes, to anybody, and you find out from
a bug report.

So name the shape once and let the compiler hold you to it:

```ts file=libs/acl/README.md region=typed-authoring

```

`policy<Subject>()` names the subject. Each `.for()` binds one object kind to its
type and hands the condition helpers to a block.

What makes that work is smaller than it looks. An operand is read as a path when
its type matches `` `subject.${string}` | `object.${string}` | 'now' ``, and as a
literal otherwise. That one discriminator is the whole mechanism. It is why
`p.eq('object.status', 'published')` compares against a string, and why
`p.eq('object.authorId', 'subject.idd')` is a compile error that names the path
you fat-fingered.

The builder flattens to the canonical matrix on the first query, so
`JSON.stringify(access.matrix)` still emits the document a foreign producer
would. Nothing about the typed path changes what ships.

## The four answers an acl decision can give

All of that assumes you have the listing in hand. Often you do not.

Your shelf page loads forty listings and takes two columns from each: an id and
an owner. Now ask whether Mika may publish one. The rule wants `object.status`,
the row you loaded has no status, and the honest answer is neither yes nor no.

So a decision here has four outcomes, not two:

```ts file=libs/acl/README.md region=four-outcomes

```

You already know three of them. Nothing matched, so no. A rule allowed it, so
yes. A deny matched, so no, and a deny always wins.

The fourth is the new one. The engine could not tell. It says `unevaluable`, and
`missing` lists the columns to go and fetch. Fetch them, ask again, and you get a
real answer.

## Asking an acl decision why

Four answers only help if you can tell which one you got. The decision carries
five more fields for that: `reason`, `rule`, `blockedBy`, `cause` and `missing`.

```ts file=libs/acl/README.md region=cascade

```

`blockedBy` is the edge this permission died on. `cause` is the first one in the
chain that failed on its own account. In a chain of three those are two
different permissions, which is why you get both.

All five are output only. Read them to build an error message, log them, show
them in a tooltip. Never branch on them. Gate on `allowed` and nothing else — a
handler that checks `reason !== 'denied'` grants everything the engine refused.

## Which parts of the row acl will let you write

Last line of the table, and the one that changes your UI.

Mika may edit her listing. Fine. May she change its price after it has sold? May
she edit the title, or only the description? "May she edit this" was never the
question a form needed answering. "Which fields do I render as inputs" was.

```ts file=libs/acl/README.md region=field-permissions

```

`*` means every field, and `!price` takes one back out.

The map covers every key on the listing and every name your rules mention. On a
write it also covers every key of what the caller sent you, including one the
listing has never had. That last case is the one people forget, and it is why the
map is computed for each call rather than read off the matrix.

## Applying the field map with `pickAllowedFields`

Having the map is not the same as applying it. The package does that part for
you, and you should let it:

```ts file=libs/acl/README.md region=write-path

```

Pass what it returns to the ORM. Pass only that.

Filtering the map yourself is [the one mistake this page most wants you to
avoid](/acl/pitfalls#never-hand-filter-the-field-map). The obvious loop keeps
every field that is not `denied`, which quietly keeps the `unevaluable` ones too,
and those are fields nobody said you could write.

That is the tier. Mika may edit her listing, Otto may not, and the shop never had
to write an `if`.
