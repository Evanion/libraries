**The concept.** A customer edits their own question on the Brass: Birmingham
listing. They may change the body. The shop's lock on `status` is the shop's,
so a form that posts `status` along with the body has to lose that key before it
reaches the database.

**What you get.** One call that decides the action and every field of the
write together, and one call that turns that decision into the object you hand
the object-relational mapper (ORM).

**Why you want it.** The hand-written version is a pick-list in the
handler. It is correct the day you write it, and it stays correct until somebody
adds a column. Then the form posts a field nobody listed, the pick-list has no
opinion about it, and the write goes through.

**How the library gets you there.** `canFields` decides the action and returns a
state per field. `pickAllowedFields` keeps the fields that decided `allowed` and
drops the rest, so the value you pass on is the value the decision approved.

Two calls, and the second one is not optional. `canFields` decides;
`pickAllowedFields` produces the value to write.

## Why hand-filtering the acl field map is the bug

The obvious-looking alternative is to filter the proposed write against the
field map. `fd` and `proposed` below are the two the fence above produced:

```ts
// Do not write this.
const narrowed = Object.fromEntries(
  Object.entries(proposed).filter(([key]) => fd.fields[key] !== 'denied'),
);
```

`FieldState` carries three values, and that filter accounts for two of them. The
third is `unevaluable`: a field config the engine could not check, because the
object handed to `canFields` did not carry that field's current value. A
`transitions` config is the common case, and it needs the current value because
it is a state machine over it. `'unevaluable' !== 'denied'` is `true`, so the
filter writes a value the decision declined to approve. `pickAllowedFields`
keeps the keys that decided `allowed` and withholds everything else, which
leaves you one state to get right.

The same filter also writes any key the decision does not carry at all, because
`undefined !== 'denied'`. On the write axis the decision covers every key of
`proposed`, so that set is normally empty. It is empty by a property of the
engine, and nothing in the filter makes it so.

## What an acl field decision covers

The matrix does not know the object's shape, so the decision covers:

- every field the object carries,
- every field named in the rules,
- every name in the allow-list,
- and on the write axis, every key of the proposed write.

That last one is the mass-assignment case. A key that exists nowhere but the
write still gets a state, so a `!pinned` in the name list decides a posted
`pinned` on a question row that has never carried one. If the decision covered
only the keys already on the object, it would say nothing about the key being
added.

## Naming the fields in an acl policy

`p` is the block helper each `.for()` hands you, the one the fence at the top of
this page called `.allow` and `.fields` on. Three shapes it takes:

```ts
p.fields(['*', '!status']); // everything except status
p.fields(['body']); // exactly this one
p.fields({
  fields: ['*', '!askedBy'],
  status: { transitions: { open: ['locked'], locked: [] } },
});
```

`*` is the baseline and `!name` subtracts from it. Both are authoring syntax and
never field names, wherever they turn up. A `!name` with no `*` is
`DenyWithoutBaselineError`; a `!name` inside an explicit allow-list is
`BangInAllowListError`, because a list naming what is allowed already denies
everything else.

With no name list at all, every unnamed key is writable. A `targets` or
`transitions` config restricts the field it names and no other. Read one of them
as a writable-field list and you leave every other key open.

`targets` allow-lists the proposed value, so `status: { targets: ['open', 'locked'] }`
accepts either of those and refuses anything else. `transitions` is a state
machine over the current value: the key is what the object holds now, the array
is what it may become. An empty array is a terminal state, so the `locked: []`
above refuses every write that moves `status` out of `locked`. The two are
mutually exclusive on one field, which is why the `status` config above takes
`transitions` and cannot also take `targets`.

```mermaid caption="The state machine the status config above declares. The config allows one write, from open to locked; locked names an empty array, so the engine refuses every write out of it. A call that carried no current status decides unevaluable."
flowchart LR
  D["open"] -->|"the one allowed write"| P["locked"]:::accent
  P -. "refused" .-> A["any other value"]
```

On the `write` axis a per-field config decides its own field, and the name list
never sees that field. So `fields: ['*', '!status']` beside a `status` config
leaves `status` to the config, and the `!status` takes back nothing.

| Restricting a field        | On the `read` axis                    | On the `write` axis                                        |
| -------------------------- | ------------------------------------- | ---------------------------------------------------------- |
| the name list              | denies every name it excludes         | denies every name it excludes and no config claims         |
| `targets` on the field     | nothing; `targets` is a write concept | allow-lists the proposed value, ahead of the name list     |
| `transitions` on the field | nothing; a write concept as well      | reads the edge out of the current value, ahead of the list |
| no name list and no config | allowed                               | allowed                                                    |

## The acl action gate

`canFields` returns two booleans named `allowed`, one nested inside the other,
and they can disagree. `fd.allowed` is `true` when the action is allowed and
every field is allowed. `fd.action.allowed` reports the action-level decision on
its own.

The field maps are filled in whatever the action says, deliberately: a blocked
handler still learns which fields become editable once the action is unblocked,
so one call renders the form and explains the block. That is useful and it is a
hazard. Iterate `fd.fields` without checking `fd.allowed` first and you skip the
action entirely. [Caveats and pitfalls](/acl/pitfalls#read-allowed-not-actionallowed)
has both entries.

<Panel heading="`fd.fields` is filled even when the action is refused">
  <Text as="div" size="sm">
    Every field carries a state whatever `fd.action.allowed` says, so a loop
    over `fd.fields` that never reads `fd.allowed` writes the fields of an
    action the engine refused. Read `fd.allowed` first, or call
    `pickAllowedFields`, which reads the action for you.
  </Text>
</Panel>

`pickAllowedFields` throws `ActionNotAllowedError` when the action is refused.
No field of a refused action is writable, and an empty object reads exactly like
a lawful write of nothing. Where the action is allowed and the field rules deny
some of the keys, you have a partial write, which is the case the narrowing
exists for, so the call returns the allowed subset.

## Working the acl field axis

Four failures show up on this axis, and telling them apart means reading the
action decision and the field map together. The sections above take each of the
four in turn. The control below runs one `canFields` call, shows both maps, and
shows the object `pickAllowedFields` returns from them, so you can watch the
action decision and the field map disagree.

It opens signed in as Sam Reyes, who asked the question, over an open row whose
proposed write moves `status` to `locked`. The action is allowed and every
field of that write is writable. Four moves take it elsewhere:

- Sign in as Jo Vainio, who asked no question here. The action decides
  `no-rule-matched`, every field still carries a state, and `pickAllowedFields`
  throws `ActionNotAllowedError`.
- Tick the `pinned` checkbox, which posts a key the policy's name list never
  mentions. `pinned` decides `denied` with the reason `not-listed`, and the
  write that reaches the ORM does not carry it. That is the mass-assignment
  case.
- Set `status now` to `locked`. The `transitions` config names an empty array of
  edges out of `locked`, so `status` decides `denied` with `transition-failed`.
- Tick the checkbox saying the query did not select `status`, which takes the
  field off the row. `transitions` reads the value the row holds now, so
  `status` decides `unevaluable` with `missing-field` and is withheld from the
  write.

## Reading with acl

Every name below comes from the fence at the top of this page: `access` is the
policy, `current` is the question as the database holds it.

```ts
const view = access.canFields(
  { id: 'c1' },
  'question',
  'read',
  current,
  'read',
);
```

The `read` axis takes no proposed write, and per-field `targets` and
`transitions` are write concepts, so on `read` only the name list denies. The
read axis shapes a response the same way the write axis shapes a form.

The call decides a projection and queries nothing. The row was already fetched,
and a field decided `denied` here was still read out of the database.
