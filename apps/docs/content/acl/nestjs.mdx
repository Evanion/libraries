## Baize's acl matrix, built once when the Nest app boots

`@evanion/acl` ships no NestJS module, so `apps/shop-api` calls it directly.
Every fence on this page is a region of that app, run by its own test suite.
`ShopSubject` carries `id`, `roles` and `shop`, and `ShopObjects` maps each of
the four object kinds to its row shape. The policy fence also uses these names:

| Name                     | What it is                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `ShopVerbs`              | the third type argument, `{ game: Action \| 'declare' \| 'reprice' }`; `Action` is `create`, `read`, `update` and `delete` |
| `SHOP_MATRIX_VERSION`    | `'shop-api@1'`, the version a consumer compares against the one it holds                                                   |
| `SHOP_SCHEMA`            | the field types of the subject and each object kind, which every condition is checked against                              |
| `p.always`               | a condition every subject meets                                                                                            |
| `p.contains(path, v)`    | holds when the array at `path` holds `v`                                                                                   |
| `.fields`, `.visibility` | apply to the action the chain declared last                                                                                |
| `AVAILABILITIES`         | the catalogue's availability states, the values a write may set `availability` to                                          |

```ts file=apps/shop-api/src/acl/shop.policy.ts region=shop-matrix

```

Six permissions, and every one but `inventory.read` carries `visibility`, which
marks what the service publishes. `game.declare` lets an operator set
`availability`, and `game.reprice` adds `price` for a manager. Both read
`object.shop === subject.shop`, so an operator in Gothenburg cannot touch a title
Stockholm lists.

`SHOP_MATRIX` is `SHOP_POLICY.matrix`, the JSON document the builder emits,
exported so a test can build a second evaluator over the same bytes.
`buildShopAccess` rebuilds it with `hydratePolicy`, the call for a document this
process authored:

```ts file=apps/shop-api/src/acl/shop.policy.ts region=build-shop-access

```

`hydratePolicy` validates, deep-clones and deep-freezes the document. An unknown
field, or two permissions sharing a key, stops the boot.

## Binding the acl matrix in a global Nest module

`AclModule.forRoot()` returns a `global: true` `DynamicModule` with the matrix as
a `useValue` provider under the token `ACL_ACCESS`, and registers `AclGuard` and
`PolicyController`:

```ts file=apps/shop-api/src/acl/acl.module.ts region=acl-module

```

`APP_GUARD` binds the guard to every route, and the `@Requires` metadata decides
which routes it gates. The token is a package-namespaced string:

```ts twoslash file=apps/shop-api/src/acl/acl.constants.ts region=acl-token

```

A bare `'ACL_ACCESS'` in a global module collides with any other provider of that
name, and nothing reports it. A `Symbol` token is unique per copy of the
package, so two copies mint two tokens and Nest fails to resolve one of them.

`GamesService` and `InventoryClient` among them, rebuilt per request and never
given `onModuleInit`.

## Two seats, the Nest guard and the service

A Nest write passes two places that can call `can`. The guard runs before the
controller method and holds the subject with no row. The service runs after the
read and holds both.

| Seat           | Holds              | Decides                                                        |
| -------------- | ------------------ | -------------------------------------------------------------- |
| `AclGuard`     | the subject        | every permission whose rules read the subject alone            |
| `GamesService` | the subject, a row | `game.declare` and `game.reprice`, on the title it just loaded |

`access.readsObject(key, action)` is true when any allow or deny rule of that
permission reads an `object.*` path, whatever the subject. `AclGuard` refuses on
every permission whose rules read only `subject.*`. On a permission that reads
`object.*` it passes the request on whatever `can` answered, and `GamesService`
decides after the read. The guard's pass is no grant: a guard that took
`unevaluable`, the answer for a rule whose object paths were absent, as a grant
would let a Gothenburg operator edit a Stockholm title.

```mermaid caption="The two seats one write passes through. AclGuard holds the subject and no row, so it refuses a permission whose rules read only subject paths and passes on one that readsObject reports as object-dependent; GamesService decides that one after the read, against the title it loaded."
flowchart TD
  R["a request on a @Requires route"] --> G["AclGuard: can, subject only"]

  G -->|"refused, readsObject false"| F["403 from the guard"]
  G -->|"refused, readsObject true"| C
  C --> S["GamesService loads the title"]

## The Nest guard refuses what the subject decides

`@Requires` writes the permission onto the handler under the metadata key
`REQUIRES_PERMISSION`. `RequiredPermission` is `{ key, action }`, with `key`
typed against `ShopObjects`, so a route naming a kind the matrix does not carry
fails to compile:

```ts file=apps/shop-api/src/acl/requires.decorator.ts region=requires-decorator

```

```ts file=apps/shop-api/src/acl/acl.guard.ts region=acl-guard

```

`order.create` reads the subject's roles alone, so the guard refuses a caller who
is no customer and `OrdersController` never runs. `game.declare` reads the
title's shop, so the guard passes it on.

`action` stays a string, so a `@Requires` naming an action the document lacks
compiles. `hydratePolicy` builds an `Access` in open mode, where `can` on a
permission the document does not carry throws `UnknownPermissionError` and Nest
renders a 500. `requires-coverage.spec.ts` moves that failure to the build: it
reads the metadata off every controller and holds each pair to `SHOP_MATRIX`.

## The Nest service decides on the row

`GamesService.declare` loads the title with `findByUrn`, then decides.
`GameDeclaration` is the body, `{ availability?, price? }`. The action comes from
the body, because `declare` and `reprice` allow different fields:

```ts file=apps/shop-api/src/games/games.service.ts region=row-decision

```

`decision.action.allowed` is checked first, so a refusal is a
`ForbiddenException` and never the `ActionNotAllowedError` that
`pickAllowedFields` throws on a refused action. A `@Body()` carries whatever the
caller put in it, and the write keeps only the keys the decision marked
`allowed`. A whitelisting `ValidationPipe` answers whether a key is a legal field
of the endpoint, and the decision answers whether this subject may set it on this
row, so keep both.

The service spec runs the app's real matrix. `serviceFor` builds `GamesService`
over the real matrix for one subject; `STOCKHOLM_TITLE` is Wingspan and
`GOTHENBURG_TITLE` is Gloomhaven. The same Stockholm operator changes Wingspan
and is refused on Gloomhaven:

```ts file=apps/shop-api/src/games/games.service.spec.ts region=declare-on-the-row

```

## Publishing the matrix from a Nest controller

`PolicyController` answers `GET /api/policy` with the reduced document:

```ts file=apps/shop-api/src/acl/policy.controller.ts region=policy-endpoint

```

`serialize(access, 'reduced')` keeps the permissions marked
`visibility: 'public'`, each whole, and drops `inventory.read`. Baize's three
frontends fetch it and evaluate locally, and shop-api decides again on every
request they send.

## Testing the Nest wiring against the real matrix

`games.controller.spec.ts` builds a testing module over the real matrix and stubs
only the subject, with `useValue` on the class token:


A spec that stubbed `ACL_ACCESS` would test only that the controller called it,

`AppModule` on a real port.
