**The concept.** Nest puts two seats in front of one write. A `CanActivate`
guard runs before the controller method and holds the subject with no row. The
service runs after the read and holds both.

**What you will have.** What `apps/shop-api` runs: one matrix built at boot
behind an injection token, the request's subject in `AsyncLocalStorage`, a
global guard that refuses what it can, and `GamesService` deciding
`game.declare` on the title it has just loaded.

**Why you would want it.** Baize grants `game.declare` to an operator whose own
shop lists the title. A guard called with no title cannot compare `object.shop`
against `subject.shop`, so it answers `unevaluable`, which is not a refusal.
Read that as a grant and an operator in Gothenburg edits a Stockholm listing.

**How the library gets you there.** `access.readsObject(key, action)` is a fact
about the document, and it tells the guard which permissions it can finish. The
guard refuses those and passes the others on. `canFields` and
`pickAllowedFields` then close the write in the service.

## Two seats, and only one of them decides

A guard runs before the row is fetched, so it can ask whether this subject holds
`game.declare` at all and cannot ask whether it holds it on Brass: Birmingham.
An object-dependent rule called with no instance comes back `unevaluable`,
naming the paths it could not read.

## Building Baize's matrix once at boot

`ShopSubject` carries `id`, `roles` and `shop`. `Game`, `OrderDraft`,
`TelemetryEvent` and `Stock` are the four row shapes the four keys decide over,
`SHOP_SCHEMA` states their field types for the document, `AVAILABILITIES` is the
catalogue's four availability tokens, and `SHOP_MATRIX_VERSION` is the string a
frontend compares its copy against.

```ts file=apps/shop-api/src/acl/shop.policy.ts region=shop-matrix

```

Five permissions, each carrying `visibility` except `inventory.read`, which
shop-api keeps to itself. `game.declare` lets an operator set
`availability`; `game.reprice` adds `price` and belongs to a manager. Both read
the ownership axis `object.shop === subject.shop`.

`SHOP_MATRIX` is the document that builder produced and `ShopObjects` maps each
key to its row shape. `hydratePolicy` and not `parseMatrix`, because this process
wrote the document:

```ts file=apps/shop-api/src/acl/shop.policy.ts region=build-shop-access

```

Construction validates, deep-clones and deep-freezes. An unknown field, or two
permissions sharing a key, stops the boot.

## The module that binds the matrix

The registration idiom this repository already runs is `forRoot()` returning a
`global: true` `DynamicModule` with a `useValue` provider under a
package-namespaced string token. `ACL_ACCESS` is that token, `AclGuard` is the
guard two sections below, and `PolicyController` is the endpoint at the end of
this page:

```ts file=apps/shop-api/src/acl/acl.module.ts region=acl-module

```

The token is a namespaced string:

```ts file=apps/shop-api/src/acl/acl.constants.ts region=acl-token

```

The provider sits in a global module, where a bare `'ACL_ACCESS'` collides in
silence, and a symbol is identity-based, so two copies of the package mint two
tokens and Nest fails to resolve one of them. `APP_GUARD` binds the guard to
every route, and the `@Requires` metadata below decides which routes it gates.

## Resolving the subject in a Nest request

This repository holds per-request context in an `AsyncLocalStorage` singleton.
`Scope.REQUEST` propagates _upward_ through the injection graph: every dependent
of a request-scoped provider becomes request-scoped, is rebuilt per request, and
never receives `onModuleInit`. `GamesService` and `InventoryClient` both depend
on the subject, so request scope on it would re-scope the application.

The middleware that fills it types its arguments against `node:http`, so one

`subjectFrom` parses it, and `ANONYMOUS_SUBJECT` is a shopper who works for no
shop:

## The guard refuses what it can refuse

`@Requires` writes the permission onto the handler under the namespaced metadata
key `REQUIRES_PERMISSION`, and the guard reads it back. `RequiredPermission`
types `key` against `ShopObjects`, so a route naming a kind the matrix does not
carry fails to compile:

```ts file=apps/shop-api/src/acl/requires.decorator.ts region=requires-decorator

```

```ts file=apps/shop-api/src/acl/acl.guard.ts region=acl-guard

```

`readsObject` is the load-bearing line. It is a fact about the document rather
than about a subject or a call: true when any allow rule or any deny rule of
that permission reads an `object.*` path, on either operand. `order.create`
reads the subject's roles alone, so a customer-less caller is refused here and
never reaches `OrdersController`. `game.declare` reads the title's shop, so the
guard passes it on for `GamesService` to finish.

One thing this guard does not survive: a `@Requires` naming an `action` the
document has no permission for. `key` is typed and `action` stays a string, and on an
`Access` built open `can` throws `UnknownPermissionError`, which Nest renders as
a 500. A typo in the decorator gives a server error where a refusal was wanted.

## The service decides on the row

`GamesService` holds `SubjectService`, the catalogue and `ACL_ACCESS`.
`GameDeclaration` is the request body, `findByUrn` loads the title, and the
action is chosen from the body because the two write actions carry different
field allow-lists:

```ts file=apps/shop-api/src/games/games.service.ts region=row-decision

```

`decision.action.allowed` is checked first, so the refusal is a
`ForbiddenException` and never an exception thrown out of `pickAllowedFields`.
What survives that check is written, and nothing else: reading the field map by
hand on `!== 'denied'` would write the `unevaluable` fields. A Nest `@Body()` is
the mass-assignment shape, because a caller puts whatever it likes in it.

A whitelisting `ValidationPipe` answers a different question: the pipe says the
key is a legal field of this endpoint, and the decision says this subject may set
it on this row. Keep both.

## Publishing the matrix to the frontends

```ts file=apps/shop-api/src/acl/policy.controller.ts region=policy-endpoint

```

`serialize(access, 'reduced')` emits the permissions marked
`visibility: 'public'`, each kept whole, and drops `inventory.read`. The three
frontends fetch this once and evaluate it locally, so no decision any of them
makes costs a network call. Each of them decides again anyway, and so does this
service on the next request it receives.

## Testing it

`apps/shop-api` stubs the request context with `useValue` on the class token,
the idiom the app already uses elsewhere:

```ts
const module = await Test.createTestingModule({
  controllers: [GamesController],
  providers: [
    GamesService,
    { provide: ACL_ACCESS, useValue: buildShopAccess() },
    { provide: SubjectService, useValue: { current: () => subject } },
  ],
}).compile();
```

The matrix is the real one, because a stubbed decision only asserts that the
controller called something. `acl.guard.spec.ts` covers the refusal seat,
`games.service.spec.ts` the row seat, and `orders.e2e.spec.ts` boots the real
`AppModule` over a real port.
