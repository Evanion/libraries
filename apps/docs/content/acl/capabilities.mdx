**The concept.** Baize's sidebar has six entries on it. Jo signs in and should
see two. The sidebar renders before any listing, order or report has been
fetched, so it has to draw itself from the subject alone.

**What you will have.** One call at the top of a render that answers every
permission in the document at once, and a map the menu filters.

**Why you would want it.** A menu that calls `can` once per entry asks the
clock six times and scans the permission list six times. Worse, it grows a
hand-written list of keys that nobody updates when a permission is added, so the
new section is invisible until somebody notices.

**How the library gets you there.** `capabilities` resolves the whole document
against one subject in one pass and keys the answers by permission. Every entry
is a full decision, so an entry that could not be settled says so.

`capabilities(subject, now?)` resolves every permission in the document against
one subject, keyed, in document order, in one pass.

```

One policy holds every object kind the app has. That one chains a `.for()` for
`report` and another for `listing`, and `capabilities` answers across both from
the single call.

## The no-object contract in acl

`capabilities` passes no object. That is the whole shape of the call, and it
decides what the answer can mean:

- A permission whose rules read only `subject.*` decides definitely. The subject
  was resolved whole before the call, so a field it lacks is a field it does not
  have.
- A permission whose rules read any `object.*` path decides `unevaluable`, with
  `missing` naming the paths. There is no instance to compare against, so the
  question has not been asked yet, and `false` overstates what the engine knows.

```mermaid caption="One subject against the whole document, in one pass. A permission whose rules read only subject.* settles, because the subject was resolved whole. A permission whose rules read object.* has nothing to compare against and comes back unevaluable, with missing naming the paths."
flowchart LR
  S["capabilities(subject)"]:::accent --> P["every permission<br>in the document"]
  P -->|"rules read subject.* only"| A["allowed true or false<br>a settled answer"]
  P -->|"rules read any object.*"| U["unevaluable<br>missing names the paths"]
```

So read the map as the answer to every question that can be answered without a
row. It falls short of the subject's full permissions by exactly the permissions
that need one.

## Driving a menu from an acl capability map

A navigation menu is exactly the object-free question: "is there any point
showing this section". One call at the top of a render, one lookup per item.

The policy below declares `report` and stops there, to keep the fence short.
Chain the app's other kinds onto the same `policy()` call and the map grows the
keys with it; the menu code does not change.

One call answers for every key in the document at once:

```ts twoslash
import { policy } from '@evanion/acl';

const access = policy<{ id: string }, { report: { ownerId: string } }>()
  .for('report', (p) => p.allow('read', p.always))
  .build();

const subject = { id: 's1' };
// ---cut---
const caps = access.capabilities(subject);
//    ^?
```

so the menu is a filter over it:

```ts twoslash
import { parseMatrix } from '@evanion/acl';
import type { Matrix } from '@evanion/acl';

declare const document: Matrix;
const access = parseMatrix(document);
const subject = { id: 's1' };
const caps = access.capabilities(subject);
// ---cut---
const items = [
  { href: '/reports', label: 'Reports', key: 'report.read' },
  { href: '/listings', label: 'Listings', key: 'listing.read' },
].filter((item) => caps[item.key]?.allowed === true);
```

Compare with `=== true`, and reach the entry with `?.`. A key the document does
not carry is absent from the map, and `listing.read` above is that case. A menu
built on `!caps[key]?.allowed` shows every item the matrix has never heard of.

This document arrived as JSON, so its keys are `string` and the miss happens at
runtime. A policy the builder authored carries its keys in the type, and
`caps['listing.read']` is then a compile error and never an absent entry.

You should make one `capabilities` call for the whole menu, because it settles
one instant for the whole document. A loop of `can` settles the clock per
permission, so a `before` boundary can fall between two items of one render.

## What an acl capability map does not replace

A row-level control (the edit button on one question) is a `can` with that
question, or a [`canMany`](/acl/asking#asking-about-a-list) over the page of
rows. A capability map cannot answer it, and an entry that came back
`unevaluable` is the map saying so.

`capabilities` is also not a per-subject projection to ship to a client. Ship
the client `access.matrix` and let the client evaluate it locally, which is the
package's whole premise. A per-subject projection is a second artifact to keep
fresh.
