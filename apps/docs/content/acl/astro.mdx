An `.astro` page's frontmatter runs on the server for every HTTP method at its
URL, so one `access.can` call from `@evanion/acl` at the top of the file gates
both the page and the form that posts back to it.

## One acl decision at the top of `cart.astro`

`apps/storefront` is Baize's shop front, an Astro app that renders on the server
and ships no JavaScript to the browser. Its cart answers `GET` and `POST` at
`/cart`, and both reach the same frontmatter. `decide` returns the `Decision` for
`order.create`, or `undefined` where the app holds no document to decide on:

```ts file=apps/storefront/src/pages/cart.astro region=order-decision

```

A refused `POST` gets status 403 and the wording `refusalText` picks, and the
cart cookie is untouched. Every intent the form carries is decided against
`order.create`, including the three that only edit the cookie, because a cart
is the draft of an order.

A React Router route or a React Server Components (RSC) route reaches its render
and its write through two entry points, so each owes two decisions written in
two places. An `.astro` page owes one.

## Astro server output is what makes a page a boundary

A prerendered build runs a page's frontmatter once, at build time, and serves
the HTML it produced. No process exists at request time to resolve a subject
against, and no handler exists for a form to post to. A server-rendered build
runs the frontmatter on every request, inside a Node process the operator
controls.

`apps/storefront/astro.config.mjs` sets `output: 'server'` and the
`@astrojs/node` adapter in standalone mode. Under a prerendered build, Astro
middleware runs once, at build time, against whoever built the site.

## Astro middleware resolves the subject and the acl document

Astro middleware runs ahead of every page's frontmatter. `readSubject` reads the
visitor's cookie, `ShopApi.forRequest` is the typed client for `apps/shop-api`,
and `policyAccess` answers with the evaluator over shop-api's published
document:

```ts file=apps/storefront/src/middleware.ts region=open-context

```

Every page reads `Astro.locals.subject` and `Astro.locals.access`, resolved once
per request, so two blocks on one page cannot decide against two identities.

`policyAccess` adopts the document with `parseMatrix` and holds it across
requests. It fetches only where the process holds no document or the
revalidation window has closed, so a decision in a frontmatter is a local
function call. [Choosing a framework integration](/acl/choosing-an-integration)
shows the cache, the window, and what a failed poll leaves behind.

## Narrow the roles before the Astro app forwards them

`apps/storefront` states its subject to shop-api on the `X-Shop-Subject` header,
and shop-api believes what it forwards. The cookie it reads is unsigned, so this
hop is the last place that knows which roles this surface may assert. It screens
the claim down to the one role `/session` issues:

```ts twoslash file=apps/storefront/src/lib/subject.ts region=storefront-roles

```

`parseSubject` discards a payload claiming any role outside that list, the whole
payload and never part of it. A hand-edited cookie claiming `manager` reaches the
API as an anonymous shopper.

## An Astro app with no browser copy still has a second decider

`apps/storefront` ships no JavaScript to the browser, so every decision it makes
happens in its Node process. Those decisions still do not guard the catalogue.
`apps/shop-api` owns the data, holds the same document, and decides again on
every request, against a subject it resolves itself. A storefront that disabled
the checkout button does not excuse the service the order is posted to.
