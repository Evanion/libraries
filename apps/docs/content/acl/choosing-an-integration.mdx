## Where the boundary sits

Five platforms put the authoritative call in five places. Which call decides is
the only security question of the three, and the only one that changes from
platform to platform.

| Platform                                         | The call that decides                                   | What is not a boundary                         |
| ------------------------------------------------ | ------------------------------------------------------- | ---------------------------------------------- |
| [Express](/acl/express)                          | the request handler                                     | nothing crosses; the whole app is trusted      |
| [NestJS](/acl/nestjs)                            | the guard, then the service after the read              | the guard alone, which runs before the row     |
| [Astro SSR](/acl/astro)                          | the page's frontmatter, once per request                | the rendered markup, and the form posting back |
| [Next.js (React Server Components)](/acl/nextjs) | the server component, and each Server Action separately | the client component, and the action's caller  |
| [React Router 8](/acl/react-router)              | the loader, and each action separately                  | the component tree, and `clientLoader`         |

Express and NestJS are server-only and have one boundary, the request handler.
Next.js and React Router have two: the render path and the write path, reached
independently by a caller who never renders anything.

The guides' examples are regions of Baize's demo apps in this repository.
`apps/shop-api` is the NestJS service that owns the catalogue and publishes its
matrix. `apps/storefront` (Astro), `apps/storefront-rsc` (Next.js) and
`apps/admin` (React Router) fetch that matrix and decide on it.

[Astro SSR](/acl/astro) is the fifth shape, and server-side rendering (SSR) is
the whole of its trusted runtime. A prerendered Astro site has no runtime at
request time, so it belongs in no row of this table. A server-rendered one runs
a page's frontmatter per request in a process the operator controls, and that
frontmatter is the loader and the action in one module. `apps/storefront`'s
`cart.astro` reaches one `order.create` decision, whether this visitor may place
an order, and its `POST` branch and its checkout button both read it.

[Many services](/acl/federation) closes this band on a topology, where each
service authors and evaluates only the objects it owns.

## What crosses, on the platforms where something does

`Access`, the evaluator type `.build()` and `hydratePolicy` return, holds
functions over a frozen document, and functions do not serialize. `structuredClone` throws on the functions, and `JSON.stringify`
silently drops every method. The document is what crosses a server/client
boundary, and the client rebuilds the evaluator from it:

```ts twoslash file=libs/acl/README.md region=matrix-round-trip

```

`access.matrix` carries its own `version` and `schema`, so the payload needs no
separate version field. A payload of `{ matrix, version, subject }` states the
version twice.

The subject crosses too, because the client needs it to evaluate. The subject is
no credential: the server resolves its own from its own session on the next
request and never reads the client's copy.

### Which function rebuilds depends on where the document came from

`hydratePolicy` rebuilds a document the same process authored, which is the
round trip above. `parseMatrix` rebuilds one that came from somewhere else, and
it is `hydratePolicy` in closed mode: a key the document does not carry answers
`unknown-action`, where `hydratePolicy` throws `UnknownPermissionError`.

```mermaid caption="Which rebuild call a fetched document gets. A document the same process authored rebuilds with hydratePolicy, where a key the document does not carry throws UnknownPermissionError; a document another service published rebuilds with parseMatrix in closed mode, where the same key answers unknown-action and the page keeps serving."
flowchart TD
  D["a matrix document"] --> Q{"which process<br>authored it?"}:::accent
  Q -->|"this one"| H["hydratePolicy"]
  Q -->|"another service"| P["parseMatrix, closed mode"]
  H --> HK["a key it does not carry<br>throws UnknownPermissionError"]
  P --> PK["a key it does not carry<br>answers unknown-action"]
```

When the owner removes a permission, `parseMatrix` refuses the action and keeps
serving, and `hydratePolicy` throws. The three frontends here fetch
`apps/shop-api`'s matrix and adopt it closed.

## Building the matrix once

`hydratePolicy` validates the document, deep-clones it and deep-freezes it, and
every decision after that is a local function call over the frozen copy. Build
the matrix once per process and hold it at module scope. `apps/shop-api` does
that at boot, over the document `SHOP_MATRIX` and the row map `ShopObjects` its
builder produced:

```ts file=apps/shop-api/src/acl/shop.policy.ts region=build-shop-access

```

## Holding a document you fetched

`apps/storefront` has no document of its own at boot, so it fetches shop-api's
and holds it at module scope. `HeldPolicy` is the app's own type, the adopted
`Access` and the version it came from, and `ShopApi` is its typed client for
shop-api. `POLICY_REVALIDATE_MS` is how long the app serves the held document
before it asks again:

```ts file=apps/storefront/src/lib/policy.ts region=policy-cache

```

The window is the ceiling on how long a rule change takes to reach this app's
gates. One minute is safe because shop-api re-decides every request on its own
copy. `refresh` adopts a new version and keeps the held document on every
failure:

```ts file=apps/storefront/src/lib/policy.ts region=policy-refresh

```

An owner can state `maxStale` on its document, the longest a consumer may keep
deciding on a copy it fetched. A consumer that passes `fetchedAt` to
`parseMatrix` then gets `stale-contract` on every key once that time has passed.
shop-api's document states no `maxStale`, and `parseMatrix` throws
`MissingFreshnessBudgetError` on a `fetchedAt` without one, so this app passes
none. [How long a consumer may keep deciding](/acl/publishing#how-long-a-consumer-may-keep-deciding-on-an-acl-contract)
has the arithmetic.

## Resolving the subject

`can(subject, …)` authorizes the bag it is handed and cannot ask where the bag
came from. Each guide resolves it from that platform's own verified session
primitive, server-side, before the first decision. A subject assembled from a
header, a query parameter or a posted field is whatever the caller claims, and
no evaluator detects it.

## Deciding twice is the design

`can` is called twice on a platform with a browser half, once on the server and
once in the browser. Keep both. The browser copy answers "what should this page
look like", for a person looking at it. The server copy answers "may this
happen", for a script posting to the same URL with curl.

```mermaid caption="The same permission decided twice, for two different questions. The browser copy decides what the page draws and enforces nothing; a script that never loads the page reaches the handler anyway, where the server copy decides whether the write happens."
flowchart TD
  P["a person in the browser"] --> BC["can, over the fetched document"]
  BC --> UI["the control is drawn, or hidden"]
  UI --> REQ["the write request"]
  CURL["a script with curl"] --> REQ
  REQ --> SC["can, over the server's own copy"]:::accent
  SC --> OUT["the write happens, or 403"]
```

## The write path

A permission with no `.fields` call decides the whole write with one `can`
call, as `apps/storefront`'s checkout does. A permission with `.fields` needs
`canFields` as well. Its `'write'` argument asks which keys of the proposed body
the subject may set, and the value to write is what `pickAllowedFields` returns.
`.fields(['*', '!status'])` below allows every field but `status`:

```ts twoslash file=libs/acl/README.md region=write-path

```

Check `fd.action.allowed` first. `pickAllowedFields` throws
`ActionNotAllowedError` on a refused action, so the check keeps the refusal off
the exception path. What the call returns is only the keys the decision marked
`allowed`. [Field permissions](/acl/fields#writing) has the rest.
