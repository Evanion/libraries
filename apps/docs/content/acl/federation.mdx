One matrix per service, one `Access` per matrix. Each service authors and
evaluates only what it owns, and no service evaluates another's document to
reach a decision. There is no merged matrix anywhere in the topology.

## Namespace the object kind by origin

Two services that both say `invoice` mean different rows, with different fields,
in different databases. The namespace says so: `orders:invoice`,
`billing:invoice`.

Nothing about the document format changes. `orders:invoice.read` still equals
`` `${object}.${action}` `` character for character, so `KeyMismatchError` is
satisfied by construction, and the typed builder takes the namespaced key
directly:

```ts
policy<Subject>().for<'orders:invoice', Invoice>('orders:invoice', (p) =>
  p.allow('read', p.eq('object.ownerId', 'subject.id')),
);
```

`:` is safe as the separator because `.` is not available. It is the key
delimiter, and a `.` inside `object` or `action` is refused at construction:

```
InvalidPermissionError: permission "orders.invoice.read": "object" carries the
key delimiter ".": an object kind namespaced by origin is spelled "origin:kind"
```

## A gateway holds a map, not a merge


The map key is the origin, so routing a question is a lookup rather than a
search. It is also why nothing collides even without naming discipline: two
documents that both declare `invoice.read` are two entries under two different
map keys, and neither can overwrite the other. A merged matrix has no such
property — the second `invoice.read` wins, silently.

The fold into one view is safe for the same reason. The namespaces are disjoint,
so `Object.assign` over each origin's `capabilities` cannot lose an entry.

## An unreachable upstream needs no flag

Its origin is absent from the map. Under `closed: true` every key it would have
answered is already `{ allowed: false, reason: 'unknown-action' }`, so a
degraded fleet fails closed by absence rather than by a code path somebody has
to remember to write.

This is the reason every entry in the map is constructed closed. On the open
path the same key throws `UnknownPermissionError`, which at an edge means one
unregistered origin takes down the request.

## `dependsOn` does not cross an origin

`orders:order.ship` declaring `dependsOn: ['billing:invoice.paid']` fails at
construction:

```
UnknownDependencyError: permission "orders:order.ship" depends on
"billing:invoice.paid", which is not configured
```

It fails inside orders' own process, at startup, where the author can fix it.
That is the correct outcome rather than a limitation. Resolving that edge would
mean evaluating billing's `object.*` conditions against the order instance the
caller passed — a different kind, with different fields — and the engine would
return a confident wrong answer instead of an error.

When one request genuinely touches two services, the fan-out is the caller's
own `&&`:

```ts
const ok =
  orders.can(subject, 'orders:order', 'ship', order).allowed &&
  billing.can(subject, 'billing:invoice', 'read', invoice).allowed;
```

Deny-overrides, written at a call site by somebody who knows whether they meant
AND or OR. The library does not guess.

## A cross-cutting deny is an overlay the owner applies

A compliance or fraud team publishes deny rules for permissions it does not own.
The owning service fetches them and applies them in its own process, before it
constructs its policy:

```
authored matrix  →  applyDenyOverlay  →  createPolicy  →  access
```

```ts file=libs/acl/README.md region=deny-overlay

```

`applyDenyOverlay(matrix, overlay, { vetoable })` appends each key's rules to
that permission's `denyRules` and returns a new matrix. It is pure
`Matrix → Matrix`, so it composes with anything by ordinary function
composition, and it changes nothing about the topology above: nothing merges at
an edge, nothing but the owner is authoritative, and the service that enforces
the veto is the one that applies it.

### Deny-only is the parameter type, not a check

A contribution is a `readonly Rule[]`, and a `Rule` is `{ id?, when? }`.
`dependsOn` and `fields` live on `Permission`, and an allow rule is a member of
a different array. So a contribution cannot express an allow, a dependency or a
field rule — there is nothing to prohibit, because the shape states none of them.

That is what makes the overlay safe to accept from another team. It can only
subtract: appending deny rules moves the deny side towards a match and never
away, and every decision reached that way is `allowed: false`. A subject the
overlaid matrix allows was allowed by the authored one, for every object and
every instant.

### Three refusals, all at apply time

<Panel heading="Each one names the offending key">
  <Text as="div" size="sm">
    A key the target matrix does not define. A key the target does not list in
    `vetoable`. A condition that does not validate against the target's schema
    for that key's object kind — the same `UnknownFieldError` and
    `FieldTypeMismatchError` construction raises, run over the contribution.
  </Text>
</Panel>

The schema obligation is scoped: a matrix owes a schema for the object kinds of
the keys it lists as `vetoable`, and for nothing else. Opening a key whose kind
has no `schema.objects` entry is itself a refusal, because the contributions to
it would be unchecked. A single-service consumer that opens nothing owes no
schema and never sees any of this — `createPolicy(matrix)` takes no overlay, no
`vetoable` list, and no schema.

### The compliance team runs the same call

`applyDenyOverlay(ordersContract, myOverlay, { vetoable })` in compliance's own
CI, against the document orders publishes, catches compliance's mistake before
the owner's deploy breaks. Nothing in the function reads private state or needs
the full authored matrix: a published subset carrying the vetoable keys and
their schema entries is enough.

Applying comes before serializing. Publishing the authored matrix omits the veto,
and a veto is a deny rule, so omitting one publishes a document that allows what
the owner refuses.

## What this topology does not give you

Integrity of a document in transit belongs to the transport, the same way
resolving a subject does. The library neither signs a matrix nor verifies one:
a document that arrives over an unauthenticated channel is a document an
attacker wrote.
