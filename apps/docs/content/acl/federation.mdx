# Many services

`federatedPolicies` holds one `Access` per service behind a single view and sends
each question to the service whose keys carry it. No document is merged, so each
service stays the only author of its rules.

## Namespace each acl object kind by origin

Baize's storefront and its stock service both hold rows they call a listing, in
two databases with two field sets. A namespace on the object kind says so:
`storefront:listing`, `stock:listing`. The key is still
`` `${object}.${action}` `` character for character, and the typed builder takes
the namespaced kind directly:

```ts twoslash file=libs/acl/README.md region=namespaced-kind

```

`:` is the separator because `.` is the key delimiter. A `.` inside `object` or
`action` throws `InvalidPermissionError` at construction, and the message says
that an object kind namespaced by origin is spelled `origin:kind`.

No app in this repository runs a federated view. `apps/shop-api` is one origin,
and the examples on this page are regions of the `@evanion/acl` README.

## A gateway composes one acl policy per origin

`federatedPolicies` takes one `Access` per origin, keeps every document whole,
and returns a view with three members: `can`, `capabilities` and `get`.

```ts twoslash file=libs/acl/README.md region=federation

```

| Member                        | What it does                                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `can(subject, kind, action)`  | routes by the key to the one origin whose key set holds it; a key no origin holds answers `unknown-action` and reaches no member         |
| `capabilities(subject, now?)` | settles one instant and hands it to every origin, so a `before` boundary falls on the same side of every answer in the view              |
| `get(origin)`                 | returns the `Access` that origin registered, unchanged, which is where `canMany`, `canFields`, `readsObject` and `authorize` are reached |

flowchart LR
  C["fleet.can(subject, key, action)"] --> R{"which origin's key set<br>holds this key?"}:::accent
  R -->|"storefront:…"| O["storefront<br>its own Access"]

```

### One permission never gates another

No permission declares a dependency on another, inside one origin or across two.
A request touching both origins asks both, as `shelf && stock` does in the fence
above, and the caller writes the AND where somebody knows whether they meant AND
or OR.

### Two origins claiming one acl key refuse at construction

`federatedPolicies` throws `OriginCollisionError` when two members declare the
same key, and the message names the key and both origins. Each document is valid
on its own, and two services can each declare `listing.read` with no namespace.
The collision exists only in the process holding both, so the check runs there.

The check reads `permission.key`. A deny rule carries no key, so a key one origin
declares and another only vetoes is no collision.

## A federated acl view at the gateway is advisory

The view `federatedPolicies` returns sits in the same tier as a browser's. Every
service behind the gateway evaluates its own matrix and never trusts the edge's
answer. A gateway that allowed the request does not excuse the service behind
it, which a caller reaches directly whenever it wants to.

```mermaid caption="Where the gateway's answer counts and where it does not. The edge view routes a key to the origin whose key set holds it and answers in the same tier as a browser; each service behind it evaluates its own matrix on every call, including a call that reached it without passing the gateway at all."
flowchart LR
  CL["a caller"] --> GW["the edge view<br>advisory, like a browser's"]
  GW -->|"storefront:…"| S1["storefront<br>decides on its own matrix"]:::accent
  GW -->|"stock:…"| S2["stock<br>decides on its own matrix"]
  CL -->|"directly"| S1
  CL -->|"directly"| S2
```

## An unreachable upstream needs no flag in a federated view

An upstream the gateway cannot reach is absent from the record, so every key it
owns already answers `{ key, allowed: false, reason: 'unknown-action' }` from the
view. No flag records the outage, and no option turns that answer into an error.

Each member is built with `parseMatrix`, for the reason
[A policy from another service](/acl/adopting) gives: every document in the
record came from another process, and closed mode is what turns a key its owner
dropped into a refusal.

## A cross-cutting deny is an acl overlay the owner applies

A compliance or fraud team publishes deny rules for permissions it does not own.
The owning service fetches them and applies them in its own process with
`applyDenyOverlay`, then builds its `Access` with `hydratePolicy`:

```ts twoslash file=libs/acl/README.md region=deny-overlay

```

`applyDenyOverlay(matrix, overlay, { vetoable })` appends each key's rules to
that permission's `denyRules` and returns a new matrix. Nothing merges at an
edge, the owner stays the only authority, and the service that enforces the veto
is the one that applies it.

### A deny overlay can only subtract

A contribution is a `readonly Rule[]`, and a `Rule` is `{ id?, when? }`. `fields`
lives on `Permission`, and allow rules live in a different array, so a
contribution cannot express an allow or a field rule. An appended deny rule moves
the deny side towards a match and never away, so a subject the overlaid matrix
allows was allowed by the authored one, for every object and every instant.

### What `applyDenyOverlay` refuses

`applyDenyOverlay` throws at apply time, naming the key, on three contributions:

- a key the target matrix does not define,
- a key the target does not list in `vetoable`,
- a condition that does not fit the target's schema for that key's object kind,
  which raises the `UnknownFieldError` or `FieldTypeMismatchError` construction
  raises.

A matrix owes a schema for the object kinds of its `vetoable` keys and nothing
else, so a consumer that opens no key owes no schema. The contributing team runs
the same call in its own build, over the owner's published subset, and finds its
own mistake there. Apply before serializing: a published authored matrix allows
what the owner's veto refuses.

## Publishing the rules from one service to a consumer

`serialize(access, 'reduced')` emits the permissions marked
`visibility: 'public'`, each kept whole, and the consumer adopts the result with
`parseMatrix`. `apps/shop-api` serves exactly that at `GET /api/policy`. The
consumer decides locally, and the owner decides again when the call arrives.

## What a federated acl topology does not give you

The transport owns the integrity of a document in transit, the same way the
application owns resolving a subject. `@evanion/acl` neither signs a matrix nor
verifies one, so a document arriving over an unauthenticated channel is a
document an attacker wrote.
