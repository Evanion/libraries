**The concept.** The Edit button on a question is greyed out and the customer
emails support to ask why. Seven answers are possible, and each one wants a
different thing from you: a message, a refetch, a corrected argument, a fresh
copy of the document.

**What you get.** A reading of `reason`, `rule` and `missing` that tells
you which of the seven you got, what to render for it, and which ones a second
call repairs.

**Why you want it.** Render every refusal as "forbidden" and you hide
things the customer can have. Half of these answers mean the engine never got to
decide, and a UI that treats them as a no makes a support ticket out of a
missing database column.

**How the library gets you there.** Every decision carries `reason`. `rule`
names the rule behind a decision a rule made. `missing` names the paths to fetch
when the engine could not read them, so the repair is a query you write from the
decision.

Three fields explain a decision, and each one tells a UI something different to
render. All three are output only: `allowed` is the gate, and nothing else on
the decision should ever reach an `if`.

| `reason`          | Carries   | What the UI has                              |
| ----------------- | --------- | -------------------------------------------- |
| `allow`           | `rule`    | nothing to explain                           |
| `no-rule-matched` | —         | a plain no; this subject, this row           |
| `denied`          | `rule`    | a plain no, and which rule to name in a log  |
| `unknown-action`  | —         | the document has moved on; fail closed       |
| `unevaluable`     | `missing` | a refetch; the engine never decided          |
| `unusable-clock`  | `rule`    | the `now` this call passed is not an instant |
| `stale-contract`  | —         | fetch the document again; this copy is old   |

`unevaluable` and `unusable-clock` both mean the engine could not reach an
answer, and they are two reasons because the repair differs. `unevaluable` names
paths in `missing`, and one refetch settles it. `unusable-clock` says the `now`
the call passed is not an instant, which no refetch changes: fix the argument.

<Panel heading="`unevaluable` is not `denied`">
  <Text as="div" size="sm">
    Both carry `allowed: false`, and only one of them is an answer. A `denied`
    says the rules refused this subject on this row. An `unevaluable` says the
    engine could not read a path it needed, so a UI that draws it as forbidden
    hides a control the customer is entitled to.
  </Text>
</Panel>

`stale-contract` is the third repairable one, and the document is the thing to
fetch. Tell `parseMatrix` when your process last validated its copy, with
`fetchedAt`, and every key answers `stale-contract` once that copy is older than
the `maxStale` the document states. A holder reporting no `fetchedAt` never sees
the reason at all.

## `rule`, which rule decided

`rule` defaults to `#0`, `#1`, … by position, and a rule that states an `id`
reports that `id` instead. Give the rules a UI has to name an `id`, because a
position moves the first time somebody reorders the list.

Treat `rule` as a log line and a support answer ("denied by `locked-question`").
Never branch on it. Two rules can grant the same thing, and which one matched is
not a property the app should depend on.

`allow`, `denied` and `unusable-clock` always carry it. An `unevaluable` carries
it when the deny side raised it, and carries no `rule` when the allow side did,
because the deny side is the only one that names a rule on that path.

## When the answer is `unevaluable`

The engine never reached an answer. `allowed` is already `false`, so nothing
leaks, and the answer is repairable: `missing` names exactly what to fetch.

A caller meets it in two situations, which are the same shortfall:

- No instance at all. `can(subject, 'question', 'create')` against a permission
  whose rules read `object.*`. This is the create toggle: there is nothing to
  compare against yet.
- A projection that does not carry the field. The list query selected `id` and
  `body`; the rule reads `object.askedBy`.

The policy there declares `question` alone, which keeps the fence to the point

answers this way for listings and orders too.

Both sides' unreadable paths come back in one `missing`, so one refetch settles
the permission however many rules read the object. One round trip, never one per
rule:

### What to do with an unevaluable

- On a server, enforcing: treat it as a refusal. Fetch the named paths and
  re-ask, or return a 403. It is never a grant.
- On a client, rendering: draw the control as _pending_. Fetch `missing`, ask
  once more. A UI that draws it as forbidden hides something the customer can
  have; one that draws it as permitted is broken.
- While authoring: an `unevaluable` that no refetch repairs is a bug in the
  document, almost always a mistyped field name. A `schema` turns that class
  into an `UnknownFieldError` at construction.
- Deciding before the row is loaded: ask in front of the fetch and every
  object-dependent permission answers `unevaluable`, every time.
  `access.readsObject(key, action)` tells that case apart from a call that
  happened to lack data. See
  [Deciding before the row is loaded](/acl/decisions#deciding-before-the-row-is-loaded).

Every operator treats an absent `object.*` path as unevaluable, the negative
operators included. "It is not equal to `published`" states no fact about a
field nobody read, so `ne`, `not-in` and `contains` over an absent path come
back as unevaluable as `eq`.

### Why only the object

An absent `object.*` path is unevaluable; an absent `subject.*` path is a plain
miss. Your query chose the object projection, so a field it lacks says nothing
about the row. The app resolves the subject whole before the call and never
projects it, so a subject carrying no `roles` genuinely has none.

## Explaining one field of an acl decision

A read-only input has a `FieldReason` on it, from a vocabulary of its own.
`not-listed` means the rules exclude the name. `targets-failed` and
`transition-failed` point at the value the write proposed, and the field itself
is writable. `missing-field` is the field-level `unevaluable` and wants the same
refetch. [Field
permissions](/acl/fields) has every `FieldReason` in one table, including
`proposed-required`, which the four above leave out.
