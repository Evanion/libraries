## Turning an acl refusal into what the screen says

The Edit button under a question is off, and the customer wants to know why. A
button that says "Not allowed" for every refusal tells a customer whose row is
still loading that they may never edit their own question.

`allowed` is still the only field a handler gates on, as
[Can this user do this?](/acl/asking) sets out. The label is the one thing the
other three fields decide:

```ts twoslash file=libs/acl/README.md region=refusal-label

```

`editLabel` reads `allowed` first and then `reason`. `denied` means a deny rule
matched, and `rule` names it, because `.id('locked-question')` gave the rule
that name. The last call passed a row without `status`, so the deny rule could
not be read: the decision is `unevaluable`, `missing` names `object.status`, and
the button says Checking while the screen fetches that one field.

## The seven reasons an acl decision carries

`reason` takes one of seven values, and each one tells a screen something
different:

| `reason`          | Carries   | What the screen has                            |
| ----------------- | --------- | ---------------------------------------------- |
| `allow`           | `rule`    | nothing to explain                             |
| `no-rule-matched` | none      | a plain no, for this subject on this row       |
| `denied`          | `rule`    | a plain no, and which rule to name in a log    |
| `unknown-action`  | none      | this document carries no such key; fail closed |
| `unevaluable`     | `missing` | a refetch; the engine never decided            |
| `unusable-clock`  | `rule`    | the `now` this call passed is not an instant   |
| `stale-contract`  | none      | fetch the document again; this copy is old     |

`reason`, `rule` and `missing` are output only. No part of the library reads
them back, so a handler that branches on `reason` to allow something has written
a rule of its own beside the policy.

`stale-contract` comes from a document another service published. The consumer
tells `parseMatrix` when it last fetched its copy, as `fetchedAt`, and every key
answers `stale-contract` once that copy is older than the `maxStale` the
document states. A fresh fetch repairs it, and
[How long a consumer may keep deciding on an acl contract](/acl/publishing#how-long-a-consumer-may-keep-deciding-on-an-acl-contract)
sets out the bound.

### When the acl clock decides `unusable-clock`

`can`, `canMany`, `canFields` and `capabilities` take `now` as a trailing
argument: an ISO 8601 string, epoch milliseconds or a `Date`. Omit it and the
call reads the wall clock. A rule built with `p.after` or `p.before` compares
that instant against a boundary:

```ts twoslash file=libs/acl/README.md region=unusable-clock

```

A `now` that does not parse never throws. The permission refuses with
`unusable-clock`, names the rule that compared the clock, and carries no
`missing`, because no refetch repairs it. Fix the value the call passes.

## `rule`, the acl rule that decided

`rule` names the rule behind a decision a rule made. `allow`, `denied` and
`unusable-clock` always carry it. An `unevaluable` carries it when the deny
side was unreadable and carries none when the allow side was, because one deny
rule refuses on its own and the allow rules are alternatives.

The name comes from one of two places:

- A rule the author named reports that name. A typed author writes it with
  [`.id(name)`](/acl/authoring#naming-a-rule-with-pid) after the `allow` or
  `deny` that wrote the rule.
- A rule nobody named reports a derived id, the side it sits on and a hash of
  its conditions, such as `allow-b72dadff`.

Store a name the author wrote, and never store a derived one. A release of this
library that adds a field to `Condition` changes every derived id, so an audit
row holding `allow-b72dadff` stops matching its rule with nothing to report it.

Treat `rule` as a log line and a support answer, such as "denied by
`locked-question`". Never branch on it: two rules can grant the same thing, and
which one matched is not a fact the app should depend on.

## When the answer is `unevaluable`

`unevaluable` says the engine never reached an answer. `allowed` is already
`false`, so nothing leaks, and `missing` names exactly what to fetch. A caller
meets it with no row at all, as a create button does, or with a projection that
lacks a field a rule reads:

```ts twoslash file=libs/acl/README.md region=refetch

```

Both sides' unreadable paths arrive in one `missing`, so one query settles the
permission however many rules read the row. Every operator treats an absent
`object.*` path as unevaluable, `ne` and `not-in` included, because "not equal
to `locked`" states no fact about a field nobody read.

```mermaid caption="The repair loop for one unevaluable. Both sides' unreadable paths arrive in one missing array, so a single query fetches all of them and the second ask decides. An unevaluable that survives the refetch is a mistyped field name in the document."
flowchart LR
  C["can(subject, key, action, projection)"]:::accent --> D{"reason is<br>unevaluable?"}
  D -->|"no"| S["the decision stands"]
  D -->|"yes"| M["missing<br>names every unreadable path"]
  M --> Q["one query<br>for every named path"]
  Q --> C
```

### What to do with an acl `unevaluable`

| Where you meet it        | What you do                                                                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| a server, enforcing      | Treat it as a refusal. Fetch the named paths and ask again, or return a 403.                                                                          |
| a client, rendering      | Draw the control as pending. Fetch `missing` and ask once more. A screen that draws it as permitted is broken.                                        |
| authoring the document   | An `unevaluable` no refetch repairs is a mistyped field name. A `schema` turns that into an `UnknownFieldError` at construction.                      |
| before the row is loaded | Every permission that reads the row answers `unevaluable`. `access.readsObject(key, action)` tells that case apart from a call that lacked one field. |

[Deciding before the row is loaded](/acl/decision-object#deciding-before-the-row-is-loaded)
works the last row through.

### Why only an absent `object.*` path is unevaluable

An absent `subject.*` path is a plain miss. Your query chose the row's
projection, so a field it lacks says nothing about the row. The server resolves
the subject whole before the call and never projects it, so a subject carrying
no `roles` has none.

## Explaining one field of an acl field decision

`canFields` gives every field a state and a `FieldReason`, and a read-only input
names its reason the way a refused button does:

| `FieldReason`       | What it points at                                                     |
| ------------------- | --------------------------------------------------------------------- |
| `allow`             | nothing; the field is writable                                        |
| `not-listed`        | the name, which the rule's list of fields excludes                    |
| `targets-failed`    | the proposed value, which `targets` does not list                     |
| `transition-failed` | the edge from the current value, which `transitions` does not list    |
| `missing-field`     | the current value, which the row lacked; the same refetch as the row  |
| `proposed-required` | the proposed value, which a field with a config needs and did not get |

[Which fields may they write?](/acl/writing) builds a policy that produces the
first five, and [Field permissions](/acl/fields) is the reference.
