passed to `can`, so one rule can tell the customer who asked a question from the

## What an acl object condition reads

You and Jo are both customers of Baize with exactly the same permissions. Only
the `askedBy` field on the question about the Brass: Birmingham listing tells you
apart, so the rule that lets a customer edit their own question has to read that
field off the row in hand.

You write that comparison by hand, as an `if` in the handler beside the code that
does the work. Six months later there are forty of them, three are subtly
different, and the bulk close job never had one at all.

`p.eq('object.askedBy', 'subject.id')` states it once. A subject-only condition
reads the subject the server resolved whole, so it holds or it fails. A condition
naming an object path also reads the instance the caller passed, and that
instance is whatever the query selected.

```mermaid caption="The two inputs a condition can read, and the third outcome the second one adds."
flowchart LR
  S["subject<br>resolved whole"] --> C1["p.contains('subject.roles', 'bookseller')"]
  C1 --> O1["holds<br>fails"]
  S --> C2["p.eq('object.askedBy', 'subject.id')"]:::accent
  O["object<br>the question in hand"] --> C2
  C2 --> O2["holds<br>fails<br>unevaluable"]
```

A fourth answer arrives with that condition, and it is the subject of this page.
The query chose which fields of the question to select, so the row in hand may not
carry the field a rule reads, and a decision that cannot be reached is neither yes
nor no.

Naming a path also opens one way to get it wrong. `object.askedBy` is a string and
a string takes typos: write `object.askedBv` with a v and the matrix builds, the
tests pass, the permission never says yes to anybody, and you find out from a bug
report. Declaring the row shape in `Objects` is what lets the compiler check the
path against it, and [Typed authoring](/acl/authoring) covers the whole of that,
including the third type parameter that names a kind's actions.

## The fourth answer an acl decision can give

A subject-only permission answers `allow`, `denied` or `no-rule-matched`, and
every one of those is a settled answer. A permission reading the object has a
fourth, and it arrives when the row in hand does not carry a path the rules read.

Baize's listing page loads forty questions and selects from each only the fields
it renders. The allow rule reads `object.askedBy` and the deny rule reads
`object.status`, so a question carrying neither field settles as neither yes nor
no. This policy produces all four answers:

The engine could not tell, so it answers `unevaluable`, and `missing` names the
paths it could not read. Fetch those fields and ask again. Both sides' unreadable
paths come back together, so one refetch settles the permission however many
rules read the object.

<Panel heading="`unevaluable` is not `denied`">
  <Text as="div" size="sm">
    `allowed` is already `false`, so nothing leaks. The answer is repairable
    though: fetch what `missing` names and ask once more. A UI that renders it
    as forbidden hides something the user can have. [Why was this

An absent `object.*` path is unevaluable whatever the condition asked of it. A
condition testing that a field differs from something is as unevaluable as
`p.eq` over the same absent field, because a field nobody read says nothing either
way.

### Watching an acl decision move between the four answers

The control below runs the policy above. A field's checkbox says whether the query
selected it and its select says what it holds. A field the query left out never
reaches the engine.

<UnevaluableDemo />

It opens on a projection that selected neither field, so the decision is
`unevaluable` and `missing` names both paths. Three moves take it elsewhere.
Select both fields, and the asker's own draft question decides `allow`. Change
`askedBy` to `s2`, and the allow rule compares two identifiers that differ, which
is `no-rule-matched`. Change `status` to `locked`, and the deny rule matches,
which is `denied` whatever the allow side said.

Clearing a field again shows where the fourth answer comes back and where it does
not. Clear `status` on the asker's own draft question and the deny side has nothing
to read, so `missing` names `object.status`. Clear it on somebody else's question
and the answer stays `no-rule-matched`, because the allow rule already failed on
data the engine did have. A refetch selects exactly what `missing` named and asks
again.

## Where to go next

A rule reading the object changes two things about how you call `access`, and each
change has a page.

- [Can this user do this?](/acl/asking). A row arrives as whatever your query
  selected, and a page renders forty of them. Covers the decision's own shape,
  `readsObject` for the guard that runs before the fetch, and `canMany` for the
  list.
- [Which fields may they write?](/acl/writing). A question has fields and a write
  proposes new values for some of them. Covers `canFields`, which decides the
  action and every key of the write in one pass, and `pickAllowedFields`, which
  applies that decision to the object you hand the database.

Three more pages build on this one.

- [Typed authoring](/acl/authoring). The builder chain in full: the third type
  parameter that names a kind's actions, every condition helper, and what the
  compiler checks.
- [Rules that another service wrote](/acl/advanced). The schema that catches a
  mistyped path at construction, a foreign document, and versioning.
- [Caveats and pitfalls](/acl/pitfalls). The mistakes this API makes easy, and
  what to write in their place.
