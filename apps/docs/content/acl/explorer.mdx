**The concept.** A matrix document states version, freshness, schema and
permissions, and a reader holding one reads all four by eye.
**What you get.** The [matrix explorer](/matrix-explorer), a screen of its own
that takes a document, a subject and an object row, and draws what the document
declares and what it decides.
**Why you want it.** Reading forty permissions to find which ones a subject can
use is the work `capabilities` already does in one call.
**How the library gets you there.** `parseMatrix` adopts, `capabilities`
decides every key against one subject, `readsObject` says which permissions owe
a row first, and `can` decides those against the row.

## Where the acl matrix explorer runs

This site is a static export. There is no server behind these pages, and
`@evanion/acl` imports no framework and evaluates locally, so a document pasted
into the explorer is read by JavaScript in the reader's own browser and has
nowhere to be uploaded to. The tool's own toolbar says the same thing, because
that is where somebody who arrived at it directly is looking.

The tool takes a paste and a file the reader picks. It reads nothing from the
URL. A document reachable at `?matrix=https://…` is a link a third party can
send, and Swagger UI ships the same default off for the same reason. The cost
of that refusal is a matrix nobody can share by pasting a link, and the way to
share one is to send the document.

A pasted document is also invisible to this site's search. Search indexes the
HTML the build emitted, and a reader's document reaches the screen after that.
Everything searchable about the tool is on this page.

## What the acl matrix explorer draws

The explorer adopts with [`parseMatrix`](/acl/api#parsematrix), the closed
path, on the ground that a document arriving from somewhere else is foreign
input: a key it does not carry answers `unknown-action` rather than throwing.
That is the same adoption a consuming service writes, so what the screen shows
is what that service would get.

Two panes. The left one holds what the reader brought: the document, the
subject, and one row box per object kind the document reads. The right one
holds three reports, and each is either the document's own words or one call
into the package.

**Decisions** comes first, because it is what moves when an input changes. Its
`asked` column says which call answered each row: `capabilities` for the one
pass over the whole document, `can` for a permission that reads the object and
has a row to read. **What it declares** is `version`, `maxStale`, the schema's
object kinds and how many permissions carry `visibility: 'public'`, which is
the set [`serialize(access, 'reduced')`](/acl/publishing) would keep. **What
each permission says** is its allow rules, its deny rules and its field rules,
with `needs the row` on every permission `access.readsObject` answers true for.

The sample the tool offers is a shop matrix over `listing` and `order`. Against
the seller `{ "id": "u_31", "roles": ["seller"] }` and no row at all it answers
`allow` for `listing.read`, `no-rule-matched` for `order.refund`, and
`unevaluable` for `listing.update` with `missing` naming `object.status` and
`object.sellerId`. That third answer is the one to watch, because entering
`{ "sellerId": "u_31", "status": "live" }` in the `listing` box turns it into
`allow`, and `{ "sellerId": "u_31", "status": "archived" }` turns it into
`denied` on the rule named `archived`.

This page carries no copy of that document and no preview of the screen. One
document lives in one module, which is the tool's, and a preview here would be
a second empty state to keep in step with the first.

## How the acl matrix explorer asks about an object

A permission whose rules read no `object.*` path decides the same with a row
and without one, so the explorer asks for a row only where
`access.readsObject` answers true, and it asks once per object kind rather than
offering one box and a picker for which kind it holds. The screen's answer is a
table with every permission in it, and a picker would leave half of it stale:
`listing.update` decided against the row in hand while `order.refund` still
carries the answer it gives with none.

A row is optional, and the three states it has are all worth reaching:

- An empty box is no row, and every permission that reads the object answers
  `unevaluable` with `missing` naming every path its rules read.
- A row missing a key the rules read answers `unevaluable` as well, and
  `missing` names only what is short. `{ "sellerId": "u_31" }` against the
  sample leaves `object.status`.
- A key holding an empty value is a value. `{ "sellerId": "", "status": "live" }`
  answers `no-rule-matched`, because the comparison ran and failed.

An absent path and an empty string are different answers, and the box is where
a reader tells them apart. [Why was this refused?](/acl/refusals) has the rest
of that distinction.

A malformed row is reported the way a malformed document is, with the message
`JSON.parse` gave, and the row is not used: the permission stays on the answer
it gives with no row, rather than being decided against half of one.

The tool reads no `relations`. `ObjectSchema` carries it beside `fields`, and
it names the kinds one kind points at for the consumers that resolve them. A
condition compares one field of one scope, so no condition can name a relation,
and a box for one would take a value nothing evaluates.

## What the acl matrix explorer does with a malformed document

Two failures, and the reader's next move differs.

Text that is not JSON never reaches the package. The screen says so and quotes
what `JSON.parse` reported, and no rule has been read at that point.

A document that parsed and that the package refused raises an
[`AclConfigError`](/acl/errors), and the screen renders the class, the message
and the three properties that locate the value. A condition naming
`object.seller_id` against a schema declaring `sellerId` gives this:

| What is shown | What it holds                                                                                                           |
| ------------- | ----------------------------------------------------------------------------------------------------------------------- |
| class         | `UnknownFieldError`                                                                                                     |
| message       | permission "listing.update": condition rules[0].when[0] on "object.seller_id" names a field the schema does not declare |
| `key`         | `listing.update`                                                                                                        |
| `field`       | `object.seller_id`                                                                                                      |
| `where`       | `rules[0].when[0]`                                                                                                      |

`where` is a position inside the permission, so a document with forty rules
still names the one condition to change. [What can throw?](/acl/errors) carries
every class with the input that raises each one.

## What the acl matrix explorer leaves out

Two things a reader might expect, each left out for a reason.

**The field axis.** `canFields` needs a proposed write as well as a row, and it
answers a different question: which fields of this row may be written, rather
than whether the action is allowed at all. That is a third box for a question
[Which fields may they write?](/acl/writing) teaches against a scenario built
for it.

**A diff between two documents.** `diffMatrix` is a second document, a second
adoption and a second refusal path on a screen that has one of each today.
[What did this change do to access?](/acl/changes) has it.
