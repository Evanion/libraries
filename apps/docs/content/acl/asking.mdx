# Can this user do this?

`can(subject, kind, action, object?, now?)`, where `kind` is the object kind —
`'question'`, not `'question.update'`. It answers with a decision.

## Why the answer is not a boolean

A boolean is enough to enforce and not enough to render. Every UI that shows a
disabled control eventually has to say why it is disabled, and the alternatives
to carrying the reason are a second call that re-derives it or a string the app
guesses from context.

So `allowed` is the answer and three more fields are the explanation:

| Field     | Present on                       | What it is                             |
| --------- | -------------------------------- | -------------------------------------- |
| `reason`  | every decision                   | which of the seven answers this one is |
| `rule`    | `allow`, `denied`, `unevaluable` | the rule that decided, by `id` or `#n` |
| `missing` | `unevaluable`                    | the paths that did not read            |

The "Present on" column names `reason` values, so `reason` is the field that
says which row of it applies.

All of them are output only. Nothing in the library reads a `reason` back to
decide anything, which cuts both ways: **gate on `allowed`**, because gating on
the reason string grants what the engine refused. [Why was this
refused?](/acl/refusals) is what to do with the rest.

## The four things that can come back


Default deny is the floor — no rules, an empty rule list and an unknown action
all refuse. Above it, a matched deny outranks a matching allow, and a deny the
engine could not read refuses as well.

## Asking with a projection

The object parameter takes a partial. A list query that selected `id` and
`askedBy` passes what it has, and the typed path checks those field names
against the object type without demanding the rest of the row.

```ts
access.can(subject, 'question', 'update', { askedBy: 's1' });
access.object('question').can(subject, 'update', {});
```

A projection that carries a path some rule reads decides definitely. One that
does not comes back `unevaluable`, with `missing` naming what to fetch. Both are
`allowed: false`, so gating on `allowed` is correct either way — and gating on
`reason` is where a projection turns into permission the engine never granted.
[Caveats and pitfalls](/acl/pitfalls) has that one first.

`access.readsObject(kind, action)` answers, from the document, whether a
permission needs the row at all. A permission that reads only the subject
settles with no object, and a caller holding a projection is the caller that
wants to know which kind it is asking about before it pays for a fetch.

The subject has no partial form. An absent `subject.*` path is a definite miss
rather than a shortfall, so a projected subject would refuse with
`no-rule-matched` and name nothing to fetch. The app resolves the subject whole,
and the type says so.

## Asking about a list

`canMany` takes the instances and answers per instance:

```ts file=libs/acl/README.md region=can-many

```

The array is parallel to the input, so the decision for `rows[i]` is
`decisions[i]`. Nothing is filtered out — a refused row keeps its entry, which
is what lets a table render the refusal beside the row rather than dropping it
and leaving a reader wondering what happened to the record they can see in
search.

### What it costs

`canMany` is not a bulk optimisation. It decides each instance separately,
because a rule reads the object and the objects differ. What it does save over
a loop of `can` is paid once instead of per row:

- **the clock.** `now` is parsed into a single epoch for the whole list. A loop
  of `can` with no `now` reads `Date.now()` per row, so a time window can close
  partway down the page.
- **the object-kind lookup.** Each `can` scans the permission list to check the
  object kind exists. `canMany` scans once.

For a list of rows the clock is the reason to prefer it. One settled instant for
one rendering is a correctness property, not a speed one.

## Binding what does not change

```ts file=libs/acl/README.md region=server-authorize

```

`authorize` binds the subject, and optionally the clock: the call above passes
the subject alone, and `authorize(subject, { now })` pins the instant with it.
Either returns `can`, `canMany`, `canFields` and `capabilities` with what was
bound dropped from each signature. On a typed policy `access.object(kind)` binds
the other axis — one object kind, so it is named once — and the two compose.
