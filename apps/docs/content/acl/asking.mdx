**The concept.** Jo opens the Brass: Birmingham listing and clicks Edit on a
question somebody else asked. One call decides whether that click goes through,
and the same call tells the button what to say when it does not.

**What you get.** One question to ask with the row in hand or over a page
of forty rows, and an answer a handler gates on and a UI renders.

**Why you want it.** Write the check by hand and you write it twice: once
in the handler that refuses the save, once in the component that greys out the
button. The two drift, and the day they disagree the customer sees an enabled
button that 403s.

**How the library gets you there.** `can` answers one question and hands back a
decision. `canMany` answers the same question per row. `authorize` binds the
subject so no handler restates it, and `access.object(kind)` binds the object
kind.

`can(subject, kind, action, object?, now?)` takes the object kind in `kind`, so
you pass `'question'` and never `'question.update'`. It answers with a decision.

```

The policy above declares one object kind because the example has one. Chain a
`.for()` per kind to put the questions and the listings in the same document,
which is the document `can` reads. Do not build a policy per resource.

## Why an acl decision is not a boolean

A boolean tells the handler whether to run the save. It tells the Edit button
nothing. When support asks why that button is greyed out, a component holding
only `true` or `false` answers by calling again to work it out or by guessing a
string from context.

So `allowed` is the answer, and three more fields explain it. One call feeds
both consumers:

```mermaid caption="One call, two consumers. The handler gates on allowed and reads nothing else; the Edit button reads reason, rule and missing to say why it is greyed out. Both read the same decision, so the two cannot disagree."
flowchart LR
  Q["access.can(subject,<br>'question', 'update', row)"]:::accent --> D["a decision"]
  D -->|"allowed"| H["the handler<br>runs the save, or refuses"]
  D -->|"reason, rule, missing"| U["the Edit button<br>label and state"]
```

`reason` comes back on every decision and says which of the seven answers this
one is. `rule` names the rule that decided, by its `id` or by `#n` for its
position; it rides on `allow`, on `denied`, on `unusable-clock`, and on an
`unevaluable` the deny side raised. `missing` lists the paths the engine could
not read, and it rides on `unevaluable`. An `unevaluable` the allow side raised
carries `missing` and no `rule`, because only the deny side names a rule there.

All of them are output only. Nothing in the library reads a `reason` back to
decide anything, and that cuts both ways: **gate on `allowed`**, because a gate
on the reason string grants what the engine refused. [Why was this
refused?](/acl/refusals) is what to do with the rest.

Default deny is the floor. No rules, an empty rule list and an unknown action

That policy declares one kind again. Add a `.for('listing', …)` beside it and
the same `access` answers for listings too, from one document.

## Asking acl with a projection

The object parameter takes a partial. A list query that selected `id` and
`askedBy` passes what it has, and the typed path checks those field names
against the object type without demanding the rest of the row.

`access` below is the policy the quick-start built, and `subject` is the
customer asking:

```ts
const subject = { id: 's1' };

access.can(subject, 'question', 'update', { askedBy: 's1' });
access.object('question').can(subject, 'update', {});
```

A projection that carries every path the rules read decides definitely. One that
does not comes back `unevaluable`, with `missing` naming what to fetch. Both are
`allowed: false`, so gate on `allowed` and both come out right. Gate on `reason`
and a projection turns into permission the engine never granted. [Caveats and
pitfalls](/acl/pitfalls) has that one first.

`access.readsObject(kind, action)` answers, from the document, whether a
permission needs the row at all. A permission that reads only the subject
settles with no object. Ask `readsObject` before the database query when you
hold a projection and want to know which kind of permission you are asking
about.

The subject has no partial form. An absent `subject.*` path is a definite miss.
If you project the subject, the call refuses with `no-rule-matched` and names
nothing to fetch. The app resolves the subject whole, and the type says so.

## Asking about a list

`canMany` takes the instances and answers per instance:

```ts twoslash file=libs/acl/README.md region=can-many

```

The array is parallel to the input, so the decision for `rows[i]` is
`decisions[i]`. Nothing is filtered out. A refused row keeps its entry, so the
table draws the refusal beside the row. Drop the row and the customer wonders
what happened to the record they can still see in search.

The policy behind that call declares one kind. A page that lists questions and
listings together asks one `canMany` per kind against the same `access`.

### What canMany costs

`canMany` is not a bulk optimisation. It decides each instance separately,
because a rule reads the object and the objects differ. Two pieces of work it
does once for the whole list, where a loop of `can` does them per row:

- The clock. `now` is parsed into a single epoch for the list. A loop of `can`
  with no `now` reads `Date.now()` per row, so a time window can close partway
  down the page.
- The object-kind lookup. Each `can` scans the permission list to check the
  object kind exists. `canMany` scans once.

For a list of rows the clock is the reason to prefer it. One settled instant for
one rendering keeps the page consistent with itself, and the speed is a side
effect.

## Binding what an acl call repeats

Every handler in a request passes the same subject, and most of them name the
same object kind. `authorize` and `access.object` take those two out of the
signature once:

```ts twoslash file=libs/acl/README.md region=server-authorize

```

`authorize` binds the subject and one instant. With no `now` the instant is the
moment you call it, and `authorize(subject, { now })` names the instant
yourself. The handle returns `can`, `canMany`, `canFields` and `capabilities`,
each with the subject and the clock dropped from its signature.

`access.object(kind)` binds the other axis. It names one object kind once and
returns `can`, `canMany`, `canFields` and `readsObject`, each of which still
takes the subject first. The two handles are alternatives, so bind the axis the
call site repeats.

That policy declares `report` and `listing`, so `object('report')` and
`object('listing')` are the two handles it offers. A policy chaining four
`.for()` calls offers four, over the one document `authorize` already bound the
subject to.
