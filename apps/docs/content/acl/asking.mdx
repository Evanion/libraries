## The problem one acl call solves

A customer clicks Edit on a question somebody else asked. Two places need the
same answer. The save handler has to refuse, and the Edit button had to be grey
before the click.

One `can` call answers both, because it returns more than a boolean. The handler
reads one field of the decision and the button reads three others, so the two
cannot disagree about whether the edit was allowed.

## The four answers an acl decision comes back in

A decision's `reason` names which branch of the engine answered. Two of them,
`allow` and `no-rule-matched`, came out of the first policy you wrote. There are
four, and one policy produces all four.

`p.deny(action, ...conditions)` is the other half of a block, and it refuses when
its conditions hold. The policy below grants the asker with `p.allow` and refuses
a locked question with `p.deny`:

```ts twoslash file=libs/acl/README.md region=four-outcomes

```

- `allow`. An allow rule matched and no deny rule did.
- `no-rule-matched`. Nothing granted the action. This is default deny and you
  configure nothing to get it: no rules, an empty rule list and an unknown
  action all land here.
- `denied`. A deny rule matched. The engine reads the deny side first, so a
  matched deny answers whatever the allow side would have said.
- `unevaluable`. The engine could not read a path a rule needs, so the
  permission is not answerable yet. `missing` names the paths.

Those four are a teaching order rather than the engine's.
[Why deny, then allow, then deny?](/acl/resolution) carries the precedence the
engine actually walks.

`allowed` is `false` for the last three, so a handler gating on `allowed` alone
is correct for all four.

## Why an acl decision is not a boolean

A boolean tells the save handler whether to write the question and tells the
Edit button above it nothing. A component holding only `true` or `false`
explains a greyed-out button by calling `can` again or by guessing a string from
context.

```mermaid caption="One call, two consumers. The handler gates on allowed and reads nothing else; the Edit button reads reason, rule and missing to say why it is greyed out. Both read the same decision, so the two cannot disagree."
flowchart LR
  Q["access.can(subject,<br>'question', 'update', row)"]:::accent --> D["a decision"]
  D -->|"allowed"| H["the handler<br>runs the save, or refuses"]
  D -->|"reason, rule, missing"| U["the Edit button<br>label and state"]
```

Three fields carry the explanation, and all three are output only.

| Field     | What it carries                                        | When it rides along                 |
| --------- | ------------------------------------------------------ | ----------------------------------- |
| `reason`  | which answer this is, as one of the four strings above | every decision                      |
| `rule`    | the rule that decided, named by its `id`               | `allow` and `denied`, and see below |
| `missing` | the paths the engine could not read                    | `unevaluable`                       |

A permission holds allow rules and deny rules, and the engine reads the deny
rules first. That is why `rule` is sometimes absent on an `unevaluable`. One deny
rule refuses on its own, so the engine can name the one it could not read. The
allow rules are alternatives and any of them grants, so when the engine cannot
read them there is no single rule at fault to name. `missing` arrives either way,
so the refetch is the same.

Three more `reason` strings exist and none of them comes out of the policy on
this page. `unknown-action` answers a permission the document never declared.
`unusable-clock` and `stale-contract` answer a document carrying a time bound.
[Why was this refused?](/acl/refusals) covers all seven and says which situation
produces each.

Gate on `allowed`. A gate on the `reason` string is a second rule you wrote
yourself, and it will let through something `allowed` refused.

## Asking acl when your query selected half the row

A list query selects the columns the list needs, and a rule reads a column the
list did not select. `can` takes a partial object, so pass what you have:

```ts twoslash file=libs/acl/README.md region=refetch

```

A projection carrying every path the rules read decides definitely. One that
does not answers `unevaluable`, and `missing` names exactly what to fetch, so
the second call is the only extra query. Both answers are `allowed: false`, so a
handler gating on `allowed` is right either way.

`access.readsObject(kind, action)` answers from the document whether a permission
reads the row at all. A permission whose rules read only the subject answers
without one, so ask `readsObject` before the query and skip the fetch when it
says `false`.

The subject has no partial form. An absent `subject.*` path is a definite miss,
not something to fetch, so a projected subject refuses with `no-rule-matched` and
names nothing. Your app resolves the subject whole before the call.

## Asking acl about a page of rows

`canMany` takes the rows and answers per row:

```ts twoslash file=libs/acl/README.md region=can-many

```

The array is parallel to the input, so the decision for `rows[i]` is
`decisions[i]`. Nothing is filtered out and a refused row keeps its entry, which
is what lets the table draw the refusal beside the row.

`canMany` is not a bulk optimisation. It decides each row separately,
because the rules read the object and the objects differ. Two things it does once
for the whole list where a loop of `can` does them per row:

- The clock. `now` is parsed into one epoch for the list. A loop of `can` with no
  `now` reads `Date.now()` per row, so a time window can close partway down the
  page.
- The object-kind lookup. Each `can` scans the permission list to check the kind
  exists; `canMany` scans once.

Prefer `canMany` for the clock. One rendering then reads one instant, and the
speed is a side effect.

## Dropping what every acl call site repeats

Every handler in a request passes the same subject, and most of them name the
same object kind. Two calls take one of those axes out of every later signature.
`access.authorize(subject)` binds the subject, and `access.object(kind)` binds the
object kind. They are alternatives, so bind whichever axis your call sites repeat.

[Rules about who the user is](/acl/subject-rules) shows `authorize` bound over a real
policy, which is where the worked example lives.
