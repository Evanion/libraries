## The problem one acl call solves

A customer clicks Edit on a question somebody else asked. Two places need the
same answer: the save handler has to refuse, and the Edit button had to be grey
before the click.

`can` answers both from one call, because it returns a decision rather than a
boolean:

```ts twoslash file=libs/acl/README.md region=quick-start

```

The handler reads `allowed` and the button reads three other fields, so the two
cannot disagree about whether the edit was allowed.

## Why an acl decision is not a boolean

A boolean tells the save handler whether to write the question and tells the
Edit button above it nothing. A component holding only `true` or `false` explains
a greyed-out button by calling `can` again or by guessing a string from context.

```mermaid caption="One call, two consumers reading different fields of the one decision."
flowchart LR
  Q["access.can(subject,<br>'question', 'update', row)"]:::accent --> D["a decision"]
  D -->|"allowed"| H["the handler<br>runs the save, or refuses"]
  D -->|"reason, rule, missing"| U["the Edit button<br>label and state"]
```

`allowed` is the answer. The three fields beside it explain that answer and are
output only.

| Field     | What it carries                               | When it rides along                       |
| --------- | --------------------------------------------- | ----------------------------------------- |
| `allowed` | the answer, and the only field to gate on     | every decision                            |
| `reason`  | which answer this is, as one of seven strings | every decision                            |
| `rule`    | the name `.id()` gave the rule that decided   | `allow`, `denied`, and some `unevaluable` |
| `missing` | the paths the engine could not read           | `unevaluable`                             |

`rule` is the one field whose presence takes explaining, and the reason is an
asymmetry between the two kinds of rule. One deny rule refuses on its own, so when
the engine cannot read a deny it can name exactly which one stopped it. The allow
rules are alternatives and any one of them grants, so when the engine cannot read
them there is no single rule at fault to name. That is why an `unevaluable` carries
`rule` when the deny side was the unreadable one and carries none when the allow
side was. `missing` arrives either way, so the refetch is the same.

### The seven acl reasons, and where four of them were taught

Seven strings can arrive in `reason`. Four of them come out of the rules the two
pages above wrote, and this page takes those four as read:

| `reason`          | What it says                                | Where it was taught                                       |
| ----------------- | ------------------------------------------- | --------------------------------------------------------- |
| `allow`           | an allow rule matched and no deny rule did  | [Rules about who the user is](/acl/subject-rules)         |
| `no-rule-matched` | nothing granted the action                  | [Rules about who the user is](/acl/subject-rules)         |
| `denied`          | a deny rule matched and outranked the allow | [Rules about who the user is](/acl/subject-rules)         |
| `unevaluable`     | a rule read a path the row did not carry    | [Rules about the thing being accessed](/acl/object-rules) |

`allowed` is `false` for the last three, so a handler gating on `allowed` alone is
correct for all four. The remaining three come out of documents neither page above
wrote. `unknown-action` answers a permission the document never declared.
`unusable-clock` answers a rule that compared the clock against a boundary and
received an instant that does not parse. `stale-contract` answers a document that
states how long it stays fresh and has passed that bound, which happens where one
service fetched the document from another.
[Why was this refused?](/acl/refusals) covers all seven and says which situation
produces each, and [Why deny, then allow, then deny?](/acl/resolution) carries the
precedence the engine walks.

## Asking acl when your query selected half the row

A list query selects the columns the list needs, and a rule reads a column the
list did not select. `can` takes a partial object, so pass what you have:

```ts twoslash file=libs/acl/README.md region=refetch

```

A projection carrying every path the rules read decides definitely. One that does
not answers `unevaluable`, and `missing` names exactly what to fetch, so the
second call is the only extra query. Both answers are `allowed: false`, so a
handler gating on `allowed` is right either way.

The subject has no partial form. An absent `subject.*` path is a definite miss
that no fetch repairs, so a projected subject refuses with `no-rule-matched` and
names nothing. Your app resolves the subject whole before the call.

## Skipping the fetch an acl permission does not need

`access.readsObject(kind, action)` answers from the document whether a permission
reads the row at all. A permission whose rules read only the subject answers
without one, so a caller that asks `readsObject` first can skip the query when it
says `false`.

It matters more in the other direction. An HTTP guard that runs ahead of the
handler which loads the row gets `unevaluable` from every object-dependent
permission, every time, and cannot tell that apart from a call that happened to
lack data. `readsObject` tells the guard which permissions it can never settle, so
the guard refuses loudly there. [The Decision object every check
returns](/acl/decision-object#deciding-before-the-row-is-loaded) carries the
worked case.

## Asking acl about a page of rows

`canMany` takes the rows and answers per row:

```ts twoslash file=libs/acl/README.md region=can-many

```

The array is parallel to the input, so the decision for `rows[i]` is
`decisions[i]`. Nothing is filtered out and a refused row keeps its entry, which
is what lets the table draw the refusal beside the row.

`canMany` is not a bulk optimisation. It decides each row separately, because the
rules read the object and the objects differ. Two things it does once for the whole
list where a loop of `can` does them per row:

- The object-kind lookup. Each `can` scans the permission list to check the kind
  exists; `canMany` scans once.
- The clock, for a policy using the `p.before` or `p.after` helpers. `canMany`
  reads one instant for the whole list where a loop of `can` reads the wall clock
  per row, so a time boundary cannot fall partway down one page of rows. Every
  entry point also takes that instant from you, as a trailing argument:
  `access.canMany(subject, 'question', 'update', rows, now)`. [Why was this
  refused?](/acl/refusals) covers what `now` accepts and what an instant that does
  not parse decides.

Prefer `canMany` over a loop of `can`. One rendering then reads one instant, and
the speed is a side effect.

## Dropping what every acl call site repeats

Every handler in a request passes the same subject, and most of them name the same
object kind. Two calls take one of those axes out of every later signature.
`access.authorize(subject)` returns a handle with the subject bound, and
`access.object(kind)` returns one with the object kind bound. Either handle carries
the calls on this page with that argument dropped, which makes the guarded call the
shortest one to write in a middleware, a loader or an action. [Typed
authoring](/acl/authoring#a-bound-handle) shows both and says which calls each one
carries.

Binding the subject is all the library can do about [complete
mediation](/acl/security#complete-mediation), a rule that every path to your data
is checked, because nothing stops a handler calling neither.
