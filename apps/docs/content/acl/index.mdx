**The concept.** Baize is a board game shop. A customer leaves a question under
its Brass: Birmingham listing, and they may edit that question. A bookseller may
edit anybody's. Once the shop locks a question, nobody may edit it at all. Those
three sentences are Baize's authorization rules, and today you write them out
again in the handler and again in the component that greys out the button.

**What you will have.** One document that holds every rule your app has, and one
call that reads it: may this subject take this action on this object? The
subject is whoever is asking, and the object is the one thing they want to
touch. The document is JSON, and the call runs wherever the JSON is, so the
server that enforces the answer and the screen that renders it read the same
rules.

**Why you would want it.** Copies drift. You tighten the handler and forget the
loader. The next endpoint goes out with three of the four checks. A year in, nobody
can say who may edit a locked question without reading four files, and the UI
greys out a button the API would have accepted.

**How the library gets you there.** The rules are a JSON document called the
matrix. `policy()` writes one and hands back an access object over it. That
object answers four questions:

- `can` decides one action and carries the reasons beside the answer.
- `capabilities` decides every action at once.
- `authorize` binds one subject for the length of a request.
- `canFields` names the fields of a write you may set.

Each of those is a local function over the frozen document, so no call waits on
a network round trip.

`can` answers with a decision. `allowed` is the answer; `reason`, `rule` and
`missing` are why.

One `.for()` block declares one object kind, and you chain a block per kind. The
example above declares `question` because `question` is all it asks about. Your
app puts every kind it has in this one policy.

## When to reach for acl

You write one document and you make one call. Reach for acl when your rules
have to look at one of these:

- Permissions that turn on which object is in front of the user as well as on
  the role. "The customer who asked may edit their own question", "an open
  question may be deleted and a locked one may not".
- The same rules needed on a server and in a UI, without writing them twice and
  without an endpoint per question. The document crosses an SSR boundary as
  `access.matrix` and rebuilds on the other side.
- A UI that has to explain a block as well as enforce it: which rule refused,
  which field is read-only, and what is still missing.
- A field-level write, where the answer names which fields are yours.

## When acl is the wrong tool

The document is public and the answer is local. acl does not do these four
jobs:

- Anything the document cannot state in the open. The matrix reaches the
  client in full, so every object kind, action, role string, field name and time
  boundary in it is public. Opaque predicates stay server-side, outside the
  matrix.
- Filtering a collection in the database. A decision is per instance; there is
  no row-scoping query language, and generating a `WHERE` clause from the matrix
  is out of scope.
- Rules that need to call a function. Conditions are declarative because the
  matrix must pass through `JSON.stringify` unchanged.
- A non-JS backend. Only the JSON crosses; a .NET or Go service uses its own
  evaluator.

## What the acl package exports

The entry point exports these beside `policy()` and `can`:

| Export                                  | What it is                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------------ |
| `policy<Subject, Objects, Verbs>()`     | the typed builder; one `.for()` block per kind, `.build()` at the end          |
| `hydratePolicy(matrix, options?)`       | an evaluator over a document you already have                                  |
| `parseMatrix(json, options?)`           | the same, for somebody else's document; fails closed on a key it does not know |
| `access.can` / `canMany` / `canFields`  | one decision, a decision per instance, the field-level decision                |
| `pickAllowedFields(decision, proposed)` | the subset of a proposed write to actually write                               |
| `access.capabilities` / `authorize`     | every decision at once, and a subject bound for the request                    |
| `access.object` / `readsObject`         | one kind bound, and whether a rule reads the row                               |
| `access.matrix` / `version` / `schema`  | the frozen document and its two header fields                                  |
| `serialize(access, mode, options?)`     | the document to hand a consumer                                                |
| `federatedPolicies(policies)`           | one evaluator per origin, behind one handle                                    |
| `applyDenyOverlay(matrix, overlay, …)`  | another team's denies, merged before construction                              |
| `AclConfigError` and its subclasses     | every construction failure; see [Typed authoring](/acl/authoring)              |

The React provider and hooks are a separate package,
[`@evanion/react-acl`](/react-acl).
The `@evanion/acl` entry point imports no framework.
