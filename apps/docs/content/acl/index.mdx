# @evanion/acl

You write your authorization rules twice. The handler checks them, the screen
checks them again, and the two copies drift the first time somebody edits one.

## How acl thinks about a permission

acl keeps every rule in one JSON document, called the matrix. The process that
owns the rules writes the document. Any process holding the document can answer
from it, with no call back to the process that wrote it.

Three names carry that sentence, and the picture below uses all three.
`policy()` writes the document and returns an evaluator over it, which this
documentation always calls `access`. `access.matrix` is the document itself, and
it is a plain value that survives `JSON.stringify`. `hydratePolicy` takes that
value on the other side of a process boundary and returns an evaluator again.

Both sides call can over the same rules, and the service's own answer is the one that guards the write."

```

Every answer is a local function call over a frozen object. Nothing waits on a
network round trip, and nothing keeps a per-subject snapshot in step.

That is the shape of every answer on every page below: a subject, an object
kind, an action, and the row the action is aimed at.

## The acl vocabulary

Five words carry the rest of this section.

- A **subject** is who is acting. The server resolves it before the call.
- An **object** is what is being acted on: a kind, like `question`, and
  optionally the row itself.
- A **permission** is one object kind paired with one action, keyed
  `` `${object}.${action}` ``.
- A **rule** is a set of conditions under a permission. The engine ANDs the
  conditions, and a rule matches when all of them hold.
- The **matrix** is the whole document: a JSON envelope over a flat list of
  permissions, with a version and an optional schema.

A **decision** is what comes back. `allowed` is the answer and nothing else is.
`reason`, `rule` and `missing` say why, and they are output only.

## What acl can do

| The question                                        | The answer                                                         |
| --------------------------------------------------- | ------------------------------------------------------------------ |
| May this subject take this action on this row?      | one decision, with the reason beside it                            |
| May they take it on each of these rows?             | one decision per row, in one call                                  |
| What may they do at all, with no row in hand?       | every permission in the document at once                           |
| Which fields of this write may they set?            | a per-field decision, and the write to actually send               |
| Why was this refused?                               | the rule that refused, or the fields that were missing             |
| I edited the policy. Who gained or lost access?     | a report over the old document and the new one                     |
| May I answer from a document another service wrote? | yes, and an action it never declared is refused rather than thrown |

Every one of those is a local call. The rules behind them are the same rules on
a server and in a browser, because both sides hold the same document.

## When acl is the wrong tool

acl does not do these four jobs, and none of them is on a roadmap.

- Anything the document cannot state in the open. The matrix reaches the client
  in full, so every object kind, action, role string, field name and time
  boundary in it is public. An opaque predicate stays server-side, outside the
  matrix.
- Filtering a collection in the database. A decision is per instance, and
  generating a `WHERE` clause from the matrix is out of scope.
- Rules that call a function. Conditions are declarative, because the matrix has
  to survive `JSON.stringify` unchanged.
- A non-JS backend. Only the JSON crosses, and a .NET or Go service brings its
  own evaluator.
