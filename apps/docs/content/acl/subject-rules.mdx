## What a subject-only acl rule covers

Baize, [the Overview's](/acl) board game shop, lets any bookseller read its stock
report and suspends an account that has been abusing it. Both rules read a role
off the subject, so `can` answers either one with no database read in front of it.

You write that pair of checks by hand and the twentieth copy disagrees with the
first. One handler tests `roles.includes('bookseller')`, another tests
`user.isStaff`, a third was copied before the role was renamed, and the suspended
account is refused in two places out of five. A policy holds the pair once and
every call site reads the same answer.

`policy()` builds one from three calls, which is the chain
[Getting started](/acl/getting-started) used for a single rule:

- `policy<Subject, Objects>()` names the subject type and the object kinds.
- `.for(kind, block)` writes one kind's rules, and `kind` is one of the kinds you
  declared.
- `.build()` hands back the evaluator this documentation calls `access`.

A block holds rules and a rule holds conditions. The engine ANDs the conditions,
so a rule matches when every condition in it holds. `p` is the condition helper
the block hands you, and `p.contains(path, value)` reads the array at
`subject.roles` and asks whether the role is in it.

## Refusing with an acl deny rule

An allow rule is the only thing that grants, and a deny rule is how one
permission states an exception to its own grants. `report.read` carries the allow
for a bookseller and the deny for a suspended one:


`p.deny(action, ...conditions)` takes the same conditions `p.allow` takes and
means the opposite of a grant. Three subjects produce three answers from those
two rules.

The suspended bookseller satisfies both rules, and the decision is `denied`,
because a deny that matched outranks an allow that matched with it. The engine
settles the deny side first. The customer satisfies neither rule, and the
decision is `no-rule-matched`, which is the default deny: nothing is allowed
without an allow rule that matched, and you configure nothing to get that floor.

`.id(name)` names the rule that a decision reports back in its `rule` field. A
rule you do not name still reports an id, and the library derives that one by
hashing the rule's conditions, so a release that changes how a condition is
represented changes the id and a log line holding the old one stops matching its
rule. Name the rules whose ids you store.

```mermaid caption="The order the engine settles one permission in, when every condition reads the subject."
flowchart TD
  Q["can(subject, 'report', 'read')"] --> D{"a deny rule<br>whose conditions<br>all hold?"}
  D -->|yes| X["allowed: false<br>reason: denied"]:::accent
  D -->|no| R{"an allow rule<br>whose conditions<br>all hold?"}
  R -->|yes| A["allowed: true<br>reason: allow"]
  R -->|no| N["allowed: false<br>reason: no-rule-matched"]
```

`allowed` is the answer in all three cases. Gate on it and nothing else. `reason`
and `rule` are output only, and a handler that branches on the reason string
grants what the engine refused.

The diagram shows the two steps a subject-only policy can reach.
[Why deny, then allow, then deny?](/acl/resolution) carries all seven the engine
walks, and the ones this diagram leaves out need a rule reading something other
than the subject.

## Writing an acl exception where a reader will find it

Write the exception into the permission it modifies. One permission never gates
another, so a deny on `report.read` leaves `report.export` untouched even though
a person would call reading a precondition for exporting. Two actions that share
an exception each carry their own copy of it, and a reader of either action sees
every rule that decides it.

One policy holds every object kind your app has. Add a kind by chaining a second
`.for()`, which [Rules about the thing being accessed](/acl/object-rules) shows
over two kinds, and do not build a policy per resource. `access.matrix` is what
those blocks flattened to: the JSON envelope [the Overview](/acl) named, carrying a
flat list of permissions, each keyed `` `${object}.${action}` ``.

## Where subject-only acl rules stop

The engine settles every permission in a subject-only policy, and your code can
rely on two things while that holds.

Your handler always gets a final answer. The server resolves the subject whole
before the call, so every condition has data to read, and a permission here answers
`allow`, `denied` or `no-rule-matched`. None of them answers
[`unevaluable`](/acl/refusals#when-the-answer-is-unevaluable), which is what the
engine answers when it cannot tell yet.

Your caller asks without fetching anything. `can` needs no row, so
[`capabilities`](/acl/listing-permissions) answers every permission in the document
against one subject in a single call, and a navigation menu draws itself from that
one answer.

Baize's next rule is that the customer who asked a question may edit it, and that
rule reads the question. Both properties above stop holding the moment you write
it: an answer can come back undecided, and a question has to be loaded first.
