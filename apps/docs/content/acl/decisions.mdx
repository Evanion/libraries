# Decisions

<WorkshopNotice slug="acl" />

Every entry point answers with a decision. `allowed` is the answer and the rest
is the explanation, so a UI says why a button is disabled without a second call
and a log line carries why a request was refused.

```ts
interface Decision {
  key: string;
  allowed: boolean;
  reason: Reason;
  rule?: string; // the rule that decided; see the table for which reasons carry it
  missing?: string[]; // the paths that did not read, on 'unevaluable'
}
```

What `can` hands back:

```ts twoslash
import { policy } from '@evanion/acl';

type Question = { askedBy: string; status: string };

const access = policy<{ id: string }, { question: Question }>()
  .for('question', (p) =>
    p.allow('update', p.eq('object.askedBy', 'subject.id')),
  )
  .build();

const question = { askedBy: 's1', status: 'draft' };
// ---cut---
const decision = access.can({ id: 's1' }, 'question', 'update', question);
//    ^?
```

That policy declares one kind because the example needs one. Chain a `.for()`
per kind and `question`, `listing` and `report` share the document.

`reason` is output only. Nothing in the library reads a reason back to decide
anything, and gating on the reason string grants what the engine refused.

The seven it can hold are the rows below, and this build says so. A reason added
to the package and not to the table leaves `NotInTheTable` with a member, and a
type constrained to `never` cannot have one:

```ts twoslash
import type { Reason } from '@evanion/acl';

const documented = [
  'allow',
  'no-rule-matched',
  'denied',
  'unknown-action',
  'unevaluable',
  'unusable-clock',
  'stale-contract',
] as const satisfies readonly Reason[];

type Exhaustive<T extends never> = T;
type NotInTheTable = Exhaustive<Exclude<Reason, (typeof documented)[number]>>;
```

| `reason`          | Meaning                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------- |
| `allow`           | an allow rule matched; carries `rule`                                                                                |
| `no-rule-matched` | rules were present and none passed, or there were none                                                               |
| `denied`          | a deny rule matched; carries `rule`                                                                                  |
| `unknown-action`  | the key is not in the matrix; the fail-closed path only                                                              |
| `unevaluable`     | a rule read a path the object did not carry; carries `missing`, and `rule` when the deny side was the unreadable one |
| `unusable-clock`  | a rule read a `now` that is not an instant; carries `rule`                                                           |
| `stale-contract`  | the document is past the freshness budget it states                                                                  |

The deny side settles first, so a `rule` on an `unevaluable` names the deny rule
that could not be read. An allow side left unevaluable carries `missing` alone.

## Default deny, express allow, express deny wins

Nothing is allowed without an allow rule that matched. No rules, an empty rule
list and an unknown action each refuse. Above that, a deny that matched outranks
an allow that also matched, and a deny the engine could not read refuses too.


Seven steps decide one permission, in a fixed order. [Why deny, then allow, then
deny?](/acl/resolution) has the order, the diagram and the argument for it.

## `unevaluable` is a third state

It is neither an error nor a no. The decision cannot be reached with the data it
was handed, and `missing` names exactly what to fetch.

A caller sees it in two situations, both the same shortfall:

- No instance at all. `access.can(subject, 'question', 'create')` against a
  permission whose rules read `object.*`. This is the create toggle: there is
  nothing to compare against yet.
- A projection that does not carry the field. A list query selected `id` and
  `body`, and the rule reads `object.askedBy`.

```ts
const decision = access.can(subject, 'question', 'update', { status: 'draft' });
// { key: 'question.update', allowed: false, reason: 'unevaluable',
//   missing: ['object.askedBy'] }
```

What to do with one depends on where the call is:

- Server, enforcing. Treat it as a refusal. `allowed` is already `false`, so
  fetch the named paths and re-ask, or return a 403. It is never a grant.
- Client, rendering. Render the control as pending, fetch the paths in
  `missing`, re-ask once. Both sides' unreadable paths come back together, so
  one refetch settles the permission.
- Authoring. An `unevaluable` that no refetch repairs is a bug in the matrix,
  usually a mistyped field name. A `schema` turns that class into an
  `UnknownFieldError` at construction.

### Deciding before the row is loaded

An HTTP guard ahead of the handler that loads the row gets `unevaluable` from
every object-dependent permission, every time. That is correct and unhelpful:
the guard cannot tell it apart from a call that happened to lack data, so it
waves the request through and trusts something downstream.

`access.readsObject(key, action)` says which is which, from the document:

```ts file=libs/acl/README.md region=reads-object

```

`listing.read` reads only `subject.roles`. `listing.update` carries a deny on
`object.locked`, so a guard ahead of the fetch only ever holds `unevaluable`:

```ts
if (access.readsObject('listing', 'update')) {
  // Never decidable here. Refuse loudly, or record that the handler still owes
  // the real decision. Do not wave the request through.
}
```

It is true when any allow or deny rule of this permission names an `object.*`
path, on either operand. It takes no subject: it is a fact about the matrix.

Field rules do not count. A `transitions` config reads the object only on the
`canFields` write axis, where the caller holds the row already.

Absence is unevaluable for every operator, negative ones included. "It is not
equal to `published`" says nothing about a field nobody read, so `ne`, `not-in`
and `contains` over an absent path are as unevaluable as `eq`.

### Why only the object

An absent `object.*` path is unevaluable; an absent `subject.*` path is a plain
miss. The object is a projection the caller chose, so a field it lacks says
nothing about the row in the database. The app resolves the subject whole before
the call, so a subject carrying no `roles` genuinely has none.

A condition with one operand in each scope follows the operand that failed: an
absent subject comparand fails the condition, an absent object comparand leaves
it unevaluable.

The branch that needs no data decides a rule that mixes both.
`p.or(p.eq('object.askedBy', 'subject.id'), p.always)` with no instance is
`allow`, because `always` answers without the object.

## Asking more than one question

```ts
access.canMany(subject, 'question', 'update', rows); // one decision per row
access.capabilities(subject); // every permission, keyed
access.authorize(subject); // a handle with the subject bound
```

`canMany` settles the clock once for the whole list. The instances differ, the
instant does not. `capabilities` decides the whole matrix against one context,
and a client hydrates a UI from it. Prefer either over a loop of `can`, which
re-settles the clock each pass.

```ts file=libs/acl/README.md region=server-authorize

```

`authorize` binds the subject, and optionally the clock, so a middleware,
loader, action or RSC server component evaluates without restating either. It
also makes the guarded path the short one to write.

## The clock

`now` is a parameter of every entry point. Omitted, it is the wall clock;
supplied, it is whatever the caller passed, in any `Instant` form: an ISO 8601
string, epoch milliseconds, or a `Date`. The string and number forms survive
JSON, so a client-supplied instant passes straight through.

```ts file=libs/acl/README.md region=clock

```

The engine settles it to one epoch per call, so a matrix with many time windows
parses the clock once. An instant that does not parse never throws and never
grants: every permission whose decision reads it answers
`{ allowed: false, reason: 'unusable-clock' }`, allow side and deny side alike.
Decide deliberately what a caller may supply; [the security
contract](/acl/security#the-clock-a-decision-reads) has it.
