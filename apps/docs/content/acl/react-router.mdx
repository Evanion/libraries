`useCan` from `@evanion/react-acl` and enforces nothing.

## Adopting shop-api's acl document in React Router

`apps/admin` is Baize's back office, a React Router 8 framework-mode app with
`ssr: true`. It authors no rules. `AdminSubject` carries `id`, `roles` and
`shop`, `AdminObjects` maps each key to the row shape it decides over,
`AdminPermission` is the union of the document's keys, and `adoptMatrix` turns
the document `apps/shop-api` publishes into an evaluator:

```ts file=apps/admin/app/access.ts region=adopt-matrix

```

The version keys the memo, because `parseMatrix` validates, deep-clones and
deep-freezes the document on every call.

`access.ts` is not a `.server` module, because the server evaluates the matrix
to enforce and the browser evaluates it to toggle. The fetch lives in
`access.server.ts`, which the Vite plugin keeps out of the browser bundle. A
request that cannot reach shop-api falls back to `NO_ACCESS`, a parsed document
carrying no permissions, so every key answers `unknown-action` and the page
writes nothing.

## The React Router loader and action are two boundaries

A `<Form method="post">` reaches the action, and so does `curl`, for whom the
loader that decided what to render never ran. The action carries none of the
loader's conclusions, so every action re-resolves the subject and decides again.

| Where           | Runtime | Decides?                               |
| --------------- | ------- | -------------------------------------- |
| `middleware`    | server  | answers who is asking; decides nothing |
| `loader`        | server  | yes, for what it returns               |
| Route component | browser | never; it toggles what the user sees   |
| `action`        | server  | yes, independently, for what it writes |
| `clientLoader`  | browser | never                                  |

```mermaid caption="Two server entry points on one route, with the browser tree between them. Middleware answers who is asking and decides nothing further, the loader decides whether that subject may have the page, and a form post and a curl both reach the action, which decides again on the row it re-reads before the revalidating loaders run."
flowchart TD
  N["a navigation"] --> M["middleware: answers who is asking"]
  P["a write request, from a Form or from curl"] --> M
  M -->|"navigation"| L["loader: can, for what it returns"]:::accent
  L --> T["route component<br>useCan toggles, decides nothing"]
  M -->|"write"| A["action: decide again on the re-read row"]
  A --> W["the write happens, or a refusal"]
  A -->|"revalidate"| L
```

A `clientLoader` runs in the browser and is no trust boundary, whatever it
fetches from. `apps/admin` has none and loads everything on the server.

## React Router middleware answers who is asking

Middleware resolves the subject and binds it, so every loader and action on the
route runs against one identity. It calls no `can` itself: a refusal needs a
route to render it, and middleware has none.

React Router 8's stable `middleware` and `createContext` carry the subject.
`demoSubject()` returns `staff:ines`, an operator at the Stockholm shop, or the
subject the `ADMIN_SUBJECT` environment variable states. `readAccess` fetches
and adopts shop-api's document, and `readShelf` fetches the catalogue with its
stock; the contexts defer both:

```ts file=apps/admin/app/page-view.server.ts region=bind-subject

```

`subjectContext` takes a value, and `accessContext` and `shelfContext` take
functions. React Router runs middleware, then the action, then the revalidating
loaders. A memo cell the first caller fills keeps a page view to one fetch, and
that fetch happens after any action.

```ts file=apps/admin/app/page-context.ts region=subject-context

```

The default is a subject with no roles and no shop, so a loader reached without
the middleware decides against an actor Baize's matrix refuses every write.

## What a React Router loader decides

This loader decides whether the bound subject may read the orders page at all.
`access.capabilities(subject)` returns one decision per permission the document
carries, `allows` from `app/access.ts` reads one of them, and `telemetry.read`
belongs to a manager. `defineLedgerItems([])` is the empty ledger the refused
page draws:

```tsx file=apps/admin/app/routes/orders.tsx region=loader-decides

```

The nav entry pointing here is hidden from every other subject and is still a
URL, so this loader decides before it reads anything. The refusal is a returned
`refused: true` member: the component narrows on it and draws a "Not yours to
read" panel where the ledger would be, and the loader never fetches the events.

## What crosses from a React Router loader to the tree

Loader return values are the serialization boundary. The loader returns
`access.matrix`, never `access`, because `Access` holds functions and they do
not serialize.
[Choosing a framework integration](/acl/choosing-an-integration#what-crosses-on-the-platforms-where-something-does)
shows the round trip.

`apps/admin`'s shell loader returns `access.matrix`, the subject and a `now`
string once for the whole tree. The subject is no credential: the server
resolves its own on the next request. The shell component adopts the document
with the same `adoptMatrix` the server used.

`PolicyProvider` and `useCan` are the pair
`createPolicyContext<AdminSubject, AdminObjects>(NO_ACCESS)` returns in
`app/access.ts`, so the key and the row are both checked where a `useCan` call
is written. `ComposeProvider` from `@evanion/compose` nests the providers in
list order; `SessionProvider`, `ThemeProvider` and `CartProvider` are the app's
own:

```tsx file=apps/admin/app/shell.tsx region=mount-provider

```

`now` crosses as a string, because the hooks key their memos on it by value and
a `Date` is a new object each render.

## Every React Router action decides again

The action takes nothing from the loader. It reads the subject and the evaluator
off the context, re-reads the catalogue, and decides on the row it finds.
`proposed.availability` is restated in the catalogue's vocabulary, which is what
the matrix's `targets` list holds, and the write stores the form's own `state`:

```tsx file=apps/admin/app/routes/title.tsx region=action-decides

```

The action checks `decision.action.allowed` first, so a refusal returns the
union member the component narrows with `in`. `pickAllowedFields` throws
`ActionNotAllowedError` on a refused action, so the check keeps the refusal off
the exception path.

A `formData` bag carries whatever the sender put a `name` on, including keys the
title has never held, and the write keeps only what the decision allowed.
Between the render that showed the form and this action arriving, the title can
move to another shop and the ownership rule can stop matching.
