# @evanion/react-widget

A content management system (CMS) sends a page as sections, each naming a
component and its props, and nothing checks them before React renders.
`@evanion/react-widget` renders them. The compiler checks items you write, and
`validateItems` checks a CMS payload.

## How react-widget renders a page from data

`createWidgets` takes a component map, an object from a widget type to the React
component that draws it, and returns a `Widgets` component. `Widgets` takes an
array of items and renders each item's component with the item's props, in the
order the array reads. Baize, a board game shop, maps two types: a listing card
and the strip that books a table for tonight.

```tsx twoslash file=libs/react-widget/examples/listing.tsx region=catalogue

```

`ShopPage` renders the booking strip first and the listing second, because that
is the order of its two items. An item whose `type` is not `listing` or
`booking` is a compile error. So is a `price` written as a string.

The package carries no `'use client'` and no React context, so a page that
renders `<Widgets>` can be a Server Component. A widget can be an async Server
Component that fetches its own data.

## The react-widget vocabulary

Every react-widget page uses the terms below.

- The **component map** is the object passed to `createWidgets` as
  `components`. Its keys are the widget types an item may name.
- An **item** is one entry of the array `Widgets` renders. It is plain data, so
  a CMS can write it and a test can paste it.
- A **widget** is the component the map names for an item's `type`, rendered
  with that item's props.
- A **region** is what one `<Widgets>` renders: every item of one array.
- The **chrome** is the markup around the widgets, passed to `createWidgets` as
  `chrome`. `chrome.wrapper` goes around the whole region, and `chrome.item`
  goes around each widget.
- **`ctx`** is the page-level data `<Widgets ctx={…}>` hands every widget as its
  `ctx` prop.

An item carries five fields:

| Field      | What it holds                                                           |
| ---------- | ----------------------------------------------------------------------- |
| `id`       | a stable string: the React key, and `data-widget-id` on the item chrome |
| `type`     | a key of the component map, naming the component to render              |
| `props`    | that component's props, except `children` and `ctx`                     |
| `meta`     | optional placement data, such as a grid column, read by `chrome.item`   |
| `children` | optional nested items, rendered as the component's `children`           |

`meta` never reaches the widget. An item may carry `children` only when its
component declares a `children` prop. Nesting under any other widget is a
compile error.

## What react-widget can do

| The page needs                                          | What provides it                           |
| ------------------------------------------------------- | ------------------------------------------ |
| A region rendered from an item array                    | `createWidgets`                            |
| An item array held in a variable, typed against the map | `defineItems`, returned by `createWidgets` |
| A CMS payload checked before anything renders it        | `validateItems`                            |
| A wrapper around the region, or around each widget      | `chrome` on `createWidgets`                |
| A grid position that the widget itself never receives   | an item's `meta`                           |
| One value, such as a currency, handed to every widget   | `ctx` on `<Widgets>`                       |
| One `<Suspense>` boundary per widget, or none           | `chrome.suspense`                          |

## What react-widget does not do

- It creates no React context. React's `react-server` build, the one a Server
  Component imports, exports no `createContext`, so page-level data travels as
  `ctx`.
- It ships no error boundary. React only lets a class component be one, and a
  class component inside the package forces all of it into the client bundle.
  Write the boundary into a custom `chrome.item` in your own `'use client'`
  file.
- It does not virtualize a long list. `Widgets` renders every item, off-screen
  ones included.
- It does not render Astro components. `@evanion/astro-widget`, a separate
  package, renders the same items at build time.
- It does not check a payload at render. `Widgets` skips an item it cannot
  render and warns in development, so a stale widget type ships as a gap in the
  page unless `validateItems` runs first.
