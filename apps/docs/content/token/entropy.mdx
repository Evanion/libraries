# Entropy and collisions

To size `length` for the number of codes your shop will issue, read
`entropyBits` on the instance `createToken` returns.

## Read token's entropy off an instance

`length` counts the check character, so a code carries
`(length - 1) * log2(n)` random bits, where `n` is the dictionary's size.
`entropyBits` reports the figure:

```ts twoslash file=libs/token/README.md region=entropy

```

The defaults, `length: 8` and `n: 32`, give 35 bits. A `length` of 12 gives 55.
A `length` of 13 gives 60, and it names `chunkSize: 13` because the default
`chunkSize` of 4 does not divide 13.

## Read a token length as a collision budget

35 bits is 34,359,738,368 values. The birthday bound, and not the size of the
space, decides when two codes collide:

| Issued codes | Chance at least two collide, at 35 bits |
| ------------ | --------------------------------------- |
| 10,000       | about 0.15%                             |
| 100,000      | about 14%                               |
| 218,000      | about 50%                               |
| 1,000,000    | effectively certain                     |

The 50% point is roughly `1.18 × sqrt(2^bits)`. Five more characters add 25
more bits, which moves it from 218,000 to about 1.3 billion:

| `length` | bits | 50% collision at |
| -------- | ---- | ---------------- |
| 6        | 25   | 6,800            |
| 8        | 35   | 218,000          |
| 10       | 45   | 7,000,000        |
| 13       | 60   | 1,300,000,000    |

A `length` of 6, 10 or 13 needs a `chunkSize` that divides it. Pick `length`
from the row above your expected volume, with room for the volume you expect in
three years.

## Token uniqueness is a database constraint

`generate` never retries and never checks for collisions, because the package
does not know which codes you have issued. The orders table does. Put a unique
index on the code and draw again when the insert conflicts:

```ts twoslash file=libs/token/README.md region=issue

```

`issued` stands in for the unique index, and `insertPickupCode` returns `false`
where a database raises a unique violation. In your code, catch that violation
and nothing else. `issuePickupCode` draws up to five times and then throws, so a
table that has run out of codes raises an error.

Index on `body`, not on `value`. `body` is the unchunked, prefix-free,
case-folded form, and it is what `validate` hands back for a lookup, so a
customer who typed the code without its separators finds the same row.

## A token code is not a guess-resistance budget

35 bits is not enough to stop an attacker enumerating codes. If a code is a
capability, such as a password reset link or a download token, where knowing
the string grants access, `@evanion/token` is the wrong package. Use a 128-bit
random value and do not make it readable, because nobody types it.

A token code is one a person handles: a pickup code, a gift card, a support
ticket. It is looked up and not authorised, and what it defends against is a
transcription error.

If a readable code does gate something, rate-limit the lookup and bind it to a
second factor the guesser does not have, such as the email address the code was
sent to.

## Shortening a token code

Two ways spend fewer characters for the same entropy, and each has a cost:

- Raise `n`. 64 characters is 6 bits each against 5, but the alphabet rules
  forbid uppercase, which is where the extra 32 would have to come from.
- Drop the check character. `length: 8` with no check would carry 40 bits
  against 35, and a mistyped code would then cost a database lookup and a "not
  found". `createToken` has no option to drop it.
