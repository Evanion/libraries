# @evanion/urn

A bare `1337` in a message does not say whether it names a game or an order.
`@evanion/urn` writes and reads Uniform Resource Names (URNs), identifiers that
carry their namespace: `urn:game:brass-birmingham`.

## How @evanion/urn reads a URN

`parse` splits a URN into three parts, returned as `urn`, `nid` and `nss`, and
`stringify` joins them. A subclass of `URN` names one namespace by overriding
its `nid` static, and every method it inherits reads that value. These examples
are set in Baize, a board game shop, and `GameURN` is its namespace for games:

```ts twoslash file=libs/urn/README.md region=namespace-class

```

`GameURN.parse` returns a clean `nss` for a URN in its own namespace. The order
URN is foreign to `GameURN`, so `parse` keeps `order` at the front of the `nss`,
and nothing downstream mistakes the order for a game called `order-2026-0042`.

## The @evanion/urn vocabulary

Every later urn page uses these five terms, shown here on
`urn:game:brass-birmingham`.

- The **scheme** is the first part, `urn` in every
  [RFC 8141](https://datatracker.ietf.org/doc/html/rfc8141) URN. `parse` returns
  it under the key `urn`.
- The **namespace identifier** (NID) is the second part, `game`. It says
  what kind of thing the rest names.
- The **namespace-specific string** (NSS) is everything after the NID,
  `brass-birmingham`. It names one thing inside the namespace.
- A **namespace class** is a subclass of `URN` that overrides the `nid` static,
  and optionally `urn` and `separator`. `GameURN`, whose `nid` is `game`, is
  one.
- The **r-, q- and f-components** are optional tails after the NSS, introduced
  by `?+`, `?=` and `#`. RFC 8141 keeps them out of the identifier.

## What @evanion/urn can do

| You want to                                      | What urn gives you                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------------- |
| mint a URN from an id                            | `stringify`, on a namespace class or with the NID as an argument          |
| read a URN into its parts                        | `parse`, which keeps a foreign namespace in the `nss`                     |
| check a string before reading it                 | `isValidFormat`, which never throws                                       |
| get the trailing id, whatever the namespace      | `extractId`                                                               |
| compare two spellings of one URN                 | `equals`, the equivalence RFC 8141 §3.1 defines                           |
| sort URNs by namespace                           | `sameNamespace` and `belongsToNamespace`                                  |
| put a title such as `Brass: Birmingham` in a URN | `encodeNss` and `decodeNss`                                               |
| carry an edition or a section of the rules       | the q- and f-components, read by `parse` and written by `stringify`       |
| tell a malformed URN from one bad part           | `ValidationError`, and `InvalidError`, which names the part in `property` |

## What @evanion/urn does not do

- It does not normalise. `parse` returns every part in the case it was written
  in, with percent-triplets intact, because RFC 8141 §3.1 keeps an encoded octet
  opaque. `equals` is the comparison.
- It does not encode. `stringify` throws on an NSS containing a literal space,
  so nothing is encoded twice by accident. `encodeNss` is the explicit step.
- It does not deduplicate. `stringify('game:azul')` on `GameURN` writes
  `urn:game:game:azul`, which keeps a composite key from another system
  recoverable.
- It does not resolve. A URN names a game, and finding that game's listing is
  the application's job. The r- and q-components carry parameters to whatever
  does the finding.
