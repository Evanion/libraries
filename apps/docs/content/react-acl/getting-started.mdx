## Before you start

- React 18 or 19, the package's only peer dependency.
- Node 20 or newer and an ESM project, since `@evanion/react-acl` has no
  CommonJS build.
- The matrix your server sends to the browser, which is `access.matrix` on an
  `@evanion/acl` policy ([Getting started with acl](/acl/getting-started)
  writes one).
- A subject your server already resolves: the signed-in user, as a plain object.

come from `@evanion/acl`, and the hooks return its `Decision`.

## Mount the react-acl provider

`PolicyProvider` takes three props. `access` is the evaluator, `subject` is
whoever is signed in, and `context` carries `now`, the instant every time
window in the policy is read against. `hydratePolicy` turns the matrix the
server sent into the evaluator:

```tsx twoslash file=libs/react-acl/examples/mount.tsx region=mount

```

Both `useMemo` calls are required. `hydratePolicy` validates, deep-clones and
deep-freezes the document, so it runs once per matrix. `PolicyProvider`
memoises on the identity of `access`, `subject` and `context`, and an object
built during render is a new identity on every pass.

`now` stays a string. The hooks key their memos on it, and a `Date` is a new
object every render, so a `Date` re-evaluates the policy on each pass.

`'use client'` at the top of the file keeps `ShopAccess` in the browser.
`@evanion/react-acl` carries the same directive, so `PolicyProvider` is a client
component wherever you import it.

## Ask react-acl for one decision

`useCan` takes the object kind, the action and the row, and returns the
`Decision` for the subject the provider holds:

```tsx twoslash file=libs/react-acl/examples/decision.tsx region=decision

```

Gate on `allowed` and nothing else. `reason` explains the answer and is output
only, so a component that branches on it is writing a rule of its own.

The row is optional. Leave it off when there is no instance yet, as on a create
form. A rule that reads the row and is asked without one answers `unevaluable`,
which carries `allowed: false`.

`useCan` throws when no `PolicyProvider` sits above it, and the message names
the provider. There is no default policy and no silent deny.

## See what the react-acl provider renders

One rule allows `listing.edit` where the listing's `sellerId` equals the
subject's `id`. `renderToStaticMarkup`, from `react-dom/server`, returns the
HTML React writes for each of two sellers:

```tsx twoslash file=libs/react-acl/README.md region=rendered-decision

```

The seller who owns the listing gets the button. The other seller gets an empty
string, because `EditControl` returned `null` and React renders nothing for it.
If your own tree draws the same two answers, react-acl is working in your
project.

## Drive a whole tree from one react-acl provider

`PolicyProvider` and the controls that read it are three components apart
below, and `ShopPage`, `ListingView` and `ActionBar` pass nothing. Each box
shows the hook call it makes and what came back:

<PolicySpecimen />

Sign in as somebody else and the provider's `subject` changes. The Edit and
Publish badges three boxes down change with it, and Review stays, because the
shop's policy grants it to everybody.

Publish the listing and only `EditControl` moves. One deny rule in the shop's
policy reads the row: it closes `edit` once the listing is published and
outranks every allow that matched. `no-rule-matched` and `denied` are both
refusals, and the badge says which.

## Now that react-acl answers, check again on the server

The Edit button you just drew enforces nothing, because a shopper can post to
the URL behind it. [Which side decides](/react-acl/boundary) puts the same
check in the loader and the action, where the shopper cannot reach it.
