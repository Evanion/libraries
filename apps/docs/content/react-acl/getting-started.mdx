**The concept.** The overview showed a button asking whether to draw itself. On
this page you mount the thing it asks. The provider holds three values for the
whole tree, and a component under it names none of them.

**What you will have.** A shop listing whose action bar is drawn from the
policy, with a role switch at the top that changes every control on it and no
component in between that knows a permission exists.

**Why you would want it.** You thread `access` and `subject` through one
component and nothing objects. Thread them through five and four carry values
they never read. One of those four is the component somebody refactors without
knowing why the props are there, and the branch they drop them from is the branch
where the button stays lit.

**How the library gets you there.** One provider and one hook, and the hook
takes three arguments.

## Install react-acl

```bash
npm install @evanion/react-acl @evanion/acl
```

Both, because the core is where the rules are written and read: the hooks return
its `Decision`, and `hydratePolicy` below is its function. React 18 or 19 is the
only peer dependency, and the package is ESM only.

## Mount the react-acl provider

The provider takes three props. `access` is an evaluator, `subject` is whoever
is signed in, and `context` carries the instant every time window in the policy
is read against.

A server rarely hands a browser an evaluator. It sends
[the matrix](/acl/matrix), the JSON document the server rendered with, and
`hydratePolicy` turns that back into an evaluator:

```tsx twoslash file=libs/react-acl/examples/mount.tsx region=mount

```

The example settles three things.

`'use client'` is on the file because it renders `PolicyProvider`, and the
provider calls `createContext`. The package carries the same directive, so
`PolicyProvider` is a client component wherever you import it. The directive on
the example file settles which side `ShopAccess` runs on.

Both `useMemo` calls are load-bearing. `hydratePolicy` deep-clones the document,
deep-freezes the copy and validates that, so it belongs once per matrix. The
provider memoises its context value on the identity of `access`, `subject` and
`context`, and a value rebuilt during render is a new identity on every pass.

`now` is a string, and it stays one. The hooks key their memos on it, and a
`Date` is a fresh object every render, so a string holds the memo across renders
where a `Date` re-evaluates the matrix on each.

## Ask react-acl for one decision

`useCan` takes the object kind, the action and the row. It returns the
`Decision` that [`can`](/acl/asking) returns, with the same `allowed`, `reason`,
`rule` and `missing` on it:

```tsx twoslash file=libs/react-acl/examples/decision.tsx region=decision

```

Gate on `allowed` and nothing else. `reason` is output only, and a component
that branches on the reason string draws a control the engine refused.

The row is the third argument and is optional. Leave it off for the create case,
where there is no instance yet. A rule that reads the row and is asked without
one answers [`unevaluable`](/acl/refusals#when-the-answer-is-unevaluable), which
has `allowed: false` on it and means something a reader can act on.

Call `useCan` outside a `PolicyProvider` and it throws, naming the provider.
There is no default policy and no silent deny. A tree that lost its provider is
a bug, and the throw is how you find it.

## Watch one react-acl provider drive a whole tree

`PolicyProvider` and the controls that read it are three components apart, and
`ShopPage`, `ListingView` and `ActionBar` in between carry nothing. A code fence
cannot show the absence of a prop, so the tree below writes every hook call onto
the box that makes it.

Sign in as somebody else and the provider's `subject` changes. Three boxes down,
the Edit and Publish badges change with it, and `ShopPage`, `ListingView` and
`ActionBar` were not re-plumbed. Review is granted to everybody, so it stays
where it is:

<PolicySpecimen />

Publish the listing and the other half happens. The provider is untouched, and
the only thing that changed is the row `useCan` was asked about. Only
`EditControl` moves, because one rule in the shop's policy reads the row: a deny
that closes `edit` once the listing is published and outranks every allow that
matched with it. [Rules that read the object](/acl/intermediate) is where denies
are written. `no-rule-matched` and `denied` are both refusals and the badge says
which, because a tooltip on that control would tell the shopper the same reason.

`PolicyProvider` and `useCan` here are the published ones, on the shop policy
behind [One policy behind a screen](/acl/interface). A rule that changed there
changes what these badges say.

## Ask react-acl about a list, a menu and a form

`useCanMany`, `useCapabilities` and `useCanFields` remain, and each one fits a
different shape of screen.

A table of rows needs one decision per row, and React forbids a hook in a loop.
`useCanMany` decides the array in the parent and hands each row its answer:

```tsx twoslash file=libs/react-acl/examples/many.tsx region=many

```

A menu needs everything at once. `useCapabilities` returns every action-level
decision for the current subject, keyed by `` `${object}.${action}` ``:

```tsx twoslash file=libs/react-acl/examples/menu.tsx region=menu

```

`useCapabilities` passes no object, so a rule that reads one cannot be decided
here. The menu draws nothing for that entry.
[What can they do at all?](/acl/capabilities) sets out the no-object contract.

A form needs an answer per input. `useCanFields` takes the axis and returns a
`FieldDecision`, whose `fields` map covers every field name. `'read'` asks which
fields may be shown and `'write'` asks which may be set:

```tsx twoslash file=libs/react-acl/examples/fields.tsx region=fields

```

`!== 'allowed'` is the comparison to write. The obvious one, `!== 'denied'`,
leaves the `unevaluable` fields editable, and those are fields nobody said the
shopper could write. The engine fills the map whatever the action decided, so a
form that a shopper may not edit at all reads `decision.action.allowed` first.
The server applies the same map with
[`pickAllowedFields`](/acl/writing) when the form is posted, because this one
decided nothing.

## Keep the policy's keys through react-acl

`useCan` and its three siblings take the key as a plain string, because the
document arrived as JSON. An application that writes its policy in TypeScript
has more:
[`policy`](/acl/authoring) names the subject once and binds an object type per
block, so `'listing'` is a key the compiler knows.

`createPolicyContext` carries that to the hooks. Hand it the built policy and it
returns a provider and the same four hooks, checking their key against the
policy and their row against the object type:

```tsx twoslash file=libs/react-acl/examples/typed.tsx region=typed

```

That policy declares one object kind because this page works one screen. One
policy holds every kind your app has: chain a `.for()` per kind. You do not
build a policy, or a context, per resource.

`useCan('lsiting', 'edit', listing)` is a compile error there. The imported
`useCan` compiles the same call. The engine then throws `UnknownObjectKeyError`
when the component renders, or answers `unknown-action` where the matrix was
hydrated with `closed: true`.

`Shopper` and `Listing` are named at `policy` and read back off the argument, so
the `createPolicyContext` call writes neither. `createPolicyContext` is a
factory because `createContext` fixes its type where the context is made, and a
hook four components down reads that fixed type whatever the provider was
handed.
