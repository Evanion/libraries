**The concept.** A React Router loader and the route component it renders both
ask whether this shopper may edit this listing. They get the same answer from
the same rules. An attacker can work around one of the two answers and cannot
touch the other, and no line of either file says which is which.

**What you will have.** A clear line through your app: the side that fetches and
writes decides, and the side that renders toggles. A hook never appears on the
first side.

**Why you would want it.** Both calls compile. Both return a `Decision`. The
component that hid the Edit button reads as a permission check to the next
person who opens it, and the action it posts to is a URL that never ran a
loader.

**How the library gets you there.** The package makes the split hard to blur.
`'use client'` sits at the top of its entry point, so a hook cannot be called on
the trusted side at all, and the trusted side calls the core instead.

## One decision, two runtimes

`useCan('listing', 'edit', listing)` and
`access.can(shopper, 'listing', 'edit', listing)` evaluate the same rules over
the same document and return the same `Decision`. The library draws no
distinction between them and cannot. The rules are a JSON document and `can` is
a function over it, and that function does not know where it is running.

The runtime separates them. One call ran where the shopper could not reach the
code, and one ran in the shopper's browser, over a document the shopper can
read, against a subject the shopper's own page supplied.

| Where                                | Runtime | Decides?                                |
| ------------------------------------ | ------- | --------------------------------------- |
| Middleware                           | trusted | yes, for what it lets through           |
| Loader or server component           | trusted | yes, for what it returns or renders     |
| `PolicyProvider` and its tree        | browser | never; it toggles what the shopper sees |
| Action, Server Action, route handler | trusted | yes, independently, for what it writes  |

A caller reaches the last row of that table directly. `curl` posts to the action
without rendering anything, so the handler re-resolves the subject from the
session, re-reads the listing from the database, and decides again. No layer may
lean on "already checked upstream". A gateway that allowed the request does not
excuse the service behind it, and a page that hid the button does not excuse the
handler the button posts to. Every app in the chain runs its own evaluation and
trusts no earlier layer, and that holds between two of your own services as
firmly as it holds between the browser and the server.

Each of those evaluations reads a document already in memory. `can` is a
function over frozen JSON, so nothing in the trusted column waits on a network
call to decide. A policy service that is slow or down cannot turn a deny into an
allow.

## What a server component calls

Nothing on the trusted side imports `@evanion/react-acl`. A loader or a server
component already holds an evaluator and a subject, so it asks the core. The
loader below asks `'read'` before it renders anything, and the Edit button's
question is the same call with `'edit'`:

```tsx twoslash file=libs/react-acl/examples/server.tsx region=server

```

`ListingPage` takes `access` as a prop here so the example runs under a test.
An app builds the evaluator at module scope in a server-only module and calls
`access.authorize(shopper)` once per request, which drops the subject from every
signature after it. [React Router 8](/acl/react-router) and
[Next.js RSC](/acl/next-rsc) each work that through against a real app's file
layout.

`@evanion/react-acl` cannot run in a React Server Component (RSC) at all. Its
entry point carries `'use client'` and calls `createContext`, and the
`react-server` condition Next resolves React under for an RSC exports no
`createContext` and no stateful hook. So an RSC app has one way to ask, and it
is the one above: call `access.can(...)` from `@evanion/acl` directly.

Import the package into an RSC file anyway and the bundler answers before React
does. The `'use client'` directive opens a client boundary around whatever
imported it, and the component you wanted to keep on the server is now sent to
the browser with its props serialized.

## What crosses the render

`Access` is a set of closures over a frozen document, and it does not survive
serialization. `JSON.stringify` drops every method silently, so no loader return
value and no server component prop can carry one.

[The matrix](/acl/matrix) crosses instead: a JSON envelope carrying its own
`version` and `schema`, which is why nothing has to travel beside it. The client
calls `hydratePolicy` on it and gets its own evaluator back, which is the
`access` prop [Getting started](/react-acl/getting-started) mounts.

The subject crosses too, because the browser needs it to evaluate. It is not a
credential and nothing reads it back. On the next request the server resolves
its own subject from the session, and it never trusts the copy it sent.

`now` crosses as a string. Resolve it on the server so the server render and the
client's first render agree on the instant, and so a time window in the policy is
not read against a clock the shopper's machine sets.

## What the browser's copy is worth

The matrix in the browser is as fresh as the render that delivered it. Revoke a
permission and that copy keeps granting until something replaces it, and it has
no way to notice. `access.version` (the revision stamped on
[the matrix](/acl/matrix)) is the surface for detecting the gap. Your app writes
the part that fails closed and refetches.

The server never depends on that copy, so the staleness is survivable. Every
loader, every action and every handler evaluates its own.

Treat the browser's answer as a convenience for toggling what a control looks
like, and nothing else. It keeps the page honest about what the server accepts:
a shopper shown an Edit button that 403s has been misled, and the hooks exist to
prevent that. Everything that actually protects the listing happens on the
trusted side, in every layer, each one deciding for itself.
