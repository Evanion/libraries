# @evanion/compose

**Escape "Provider Hell" with a flat, type-safe way to organize your React context providers.**

`ComposeProvider` takes your providers as a flat array and nests them for you, while TypeScript checks each provider's props.

## The Problem: The "Pyramid of Doom"

Without `@evanion/compose`, your root component grows into a "pyramid of doom" of nested providers as you add features, and manual nesting creates several maintenance burdens:

- **Indentation Drift**: Adding a new provider at the top requires re-indenting every child component.
- **Closing Tag Fatigue**: Finding the matching `</ThemeProvider>` among ten other closing tags is error-prone.
- **Reordering Friction**: Moving a provider (e.g., moving `AuthProvider` above `ThemeProvider`) requires carefully cutting and pasting large blocks of JSX.

## The Solution: Flat Composition

`ComposeProvider`, from `@evanion/compose`, accepts a flat array of providers and handles the nesting for you. It reads the array from top to bottom: the first provider becomes the outermost wrapper, and the last provider wraps the `children`.

The examples on these pages are set in Baize, a board game shop, and `<p>Brass: Birmingham</p>` stands in for one of its pages. The two providers below each render a `div`, and `renderToStaticMarkup`, from `react-dom/server`, turns the tree into the HTML string `markup`, so the markup shows where each one sits:

`CartProvider` is first in the array, and its `div` is outermost. `ThemeProvider` needs a `theme`, so `provider()` pairs it with its props.

By treating your providers as data (a list) and not as structural JSX, you can reorder your entire app's context hierarchy by moving a line in an array.

### RSC Compatibility

Because `ComposeProvider` calls no hooks and creates no context of its own, a React Server Component can render it without a `'use client'` boundary. A provider you pass that calls `createContext` is still client code, and lives in a file marked `'use client'`.

## The Compose Vocabulary

To keep the `@evanion/compose` documentation clear, we use these terms to describe the composition process:

- **Provider**: Any React component that renders its `children`.
- **Entry**: A single element within the `providers` array.
- **Bare Component**: An entry written as the component itself (e.g., `CartProvider`). This is used for providers whose props are all optional.
- **Tuple**: An entry pairing a component with its props, `[component, props]`. The `provider()` helper creates these tuples and checks the props at compile time, where you call it.

## Core Capabilities

| Goal                              | Tool                                                    |
| :-------------------------------- | :------------------------------------------------------ |
| Organize root providers as a list | `ComposeProvider`                                       |
| Assign props to a provider        | A tuple or `provider(component, props)`                 |
| Catch prop errors at compile time | Inline arrays or `as const` declarations                |
| Preserve type checks in wrappers  | `ComposeProviderProps<T>` with a `const` type parameter |
| Use in React Server Components    | `ComposeProvider` (no hooks/context used)               |

## When to Avoid Compose

While powerful, `@evanion/compose` is not the right tool for every scenario:

- **Minimal Nesting**: If you only have one or two providers, manual nesting is often more readable.
- **Dynamic Providers**: If the number or order of providers changes at runtime, React reconciles by position and remounts everything below the change, so that subtree loses its state.
- **Side-by-Side Layouts**: `ComposeProvider` is for _nesting_, not _layout_. If you need to arrange components side-by-side based on data, use [`@evanion/react-widget`](/react-widget).
