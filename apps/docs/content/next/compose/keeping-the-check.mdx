# Keeping the check

`@evanion/compose` checks a bare component or a hand-written tuple only while the array keeps a fixed-length array type. If you move your providers into a named constant or a wrapper component, you might accidentally "silence" the type checker.

## The Danger of Type Widening

When you declare an `@evanion/compose` array in a variable, TypeScript **widens** it: in place of a [fixed-length array type](../type-checking#type-safety-for-inline-arrays) of specific components and props, it infers a general array of any length, such as `(typeof ThemeProvider | { theme: string })[]`, and `ComposeProvider` can no longer pair a specific component with its specific props. `ComposeProvider` checks a widened array only against `ProviderArray`, which two of the package's types define:

- `Provider` is the type of one [entry](../#the-compose-vocabulary), so the name covers a tuple as well as a component: a component, or a `readonly` two-element `[component, props]` tuple.
- `ProviderArray` is `readonly Provider[]`, an array of any length.

## Declaring a Named Array as const

If your `@evanion/compose` constant holds hand-written tuples, declare it `as const`, which tells TypeScript to treat the array as a read-only fixed-length array type with exact values. The example below declares three arrays:

- `annotated` is typed `ProviderArray`, and renders [`ThemeProvider`](../type-checking#validating-providers-at-different-stages), which requires `theme`, with no `theme` and no error.
- `constant` holds the same entry `as const` and reports the missing prop.
- `plain` holds a correct entry with no `as const`, and `ComposeProvider` refuses it.

`markup` is `annotated`, rendered with `renderToStaticMarkup`:


`plain`'s entry `[ThemeProvider, { theme: 'dark' }]` widens to `(typeof ThemeProvider | { theme: string })[]`, which is not a two-element tuple. The error ends `is not assignable to type 'ProviderArray'` and names no prop.

The declaration decides what `ComposeProvider` checks:

| Declaration                                       | Validation Status | Result                                                  |
| :------------------------------------------------ | :---------------- | :------------------------------------------------------ |
| `providers={[...]}`, inline                       | ✅ Fully Checked  | Every entry is validated.                               |
| `const providers = [...] as const`                | ✅ Fully Checked  | Every entry is validated.                               |
| `const providers = [...]`                         | ❌ Widened        | Prop checks are lost; hand-written tuples are rejected. |
| `const providers: ProviderArray = [...]`          | ❌ Silenced       | Type is too general; reports no errors.                 |
| `const providers = [...] satisfies ProviderArray` | ❌ Silenced       | Type is too general; reports no errors.                 |

`satisfies ProviderArray` leaves the array its inferred type, but TypeScript infers that type against `ProviderArray`, whose length is `number`, so the array's length is `number` too.

**Note**: Using the `provider()` helper avoids this entire problem. Because `provider()` checks props at the call site, the check is preserved regardless of how the resulting tuple is stored. A bare component gets no such protection: a bare `ThemeProvider` compiles in the last three rows.

## Preserving Checks in Wrapper Components

It is common to create a custom wrapper component (e.g., `<AppProviders />`) to encapsulate your `@evanion/compose` root. However, if you type the `providers` prop as plain `ProviderArray`, you've silenced the check for anyone using your wrapper.

To fix this, use a **const type parameter**. This forces TypeScript to infer the caller's array as a fixed-length array type. In the example, `CartProvider` renders `<div id="cart">` as on [Where the check happens](../type-checking#validating-providers-at-different-stages). The first `<AppProviders>` exists only for its compile error, and the second renders `markup`:

```tsx twoslash file=libs/compose/README.md region=wrapper

```

### How the wrapper keeps the check

1. **`<const T extends ProviderArray>`**: The `const` modifier tells TypeScript to infer `T` as the most specific literal type possible (a fixed-length array type). Without it, the caller's `[ThemeProvider, {}]` compiles with no error.
2. **`ComposeProviderProps<T>`**: `ComposeProviderProps<T>` is the props type of `ComposeProvider`, imported from `@evanion/compose` with `ProviderArray`. `ComposeProvider` then checks your caller's array entry by entry, because `T` carries its literal type.

Now, if a developer uses your `<AppProviders />` and passes a `ThemeProvider` with missing props, they will get a compile error at the call site.
