# Keeping the check

`@evanion/compose` checks a bare component or a hand-written tuple only while the array keeps a fixed-length type. If you move your providers into a named constant or a wrapper component, you might accidentally "silence" the type checker.

## The Danger of Type Widening

When you declare an `@evanion/compose` array in a variable, TypeScript **widens** it: in place of a [fixed-length array type](../type-checking#type-safety-for-inline-arrays) of specific components and props, it sees a general array of `(Component | Props)[]`, of any length, and `ComposeProvider` can no longer correlate a specific component with its specific props. Two of the package's types name what a named array is checked against:

- `Provider` is the type of one entry: a component, or a `readonly` two-element `[component, props]` tuple.
- `ProviderArray` is `readonly Provider[]`, an array of any length.

### Maintaining Checks in Named Arrays

If your constant holds hand-written tuples, declare it `as const`, which tells TypeScript to treat the array as a read-only tuple with a fixed length and exact values. The example below declares three arrays:

- `annotated` is typed `ProviderArray`, and renders `ThemeProvider` with no `theme` and no error.
- `constant` holds the same entry `as const` and reports the missing prop.
- `plain` holds a correct entry with no `as const`, and `ComposeProvider` refuses it.

```

`plain`'s entry `[ThemeProvider, { theme: 'dark' }]` widens to `(typeof ThemeProvider | { theme: string })[]`, which is not a two-element tuple. The error ends `is not assignable to type 'ProviderArray'` and names no prop.

**Comparing Declaration Styles:**

| Declaration                                       | Validation Status | Result                                                  |
| :------------------------------------------------ | :---------------- | :------------------------------------------------------ |
| `providers={[...]}`, inline                       | ✅ Fully Checked  | Every entry is validated.                               |
| `const providers = [...] as const`                | ✅ Fully Checked  | Every entry is validated.                               |
| `const providers = [...]`                         | ❌ Widened        | Prop checks are lost; hand-written tuples are rejected. |
| `const providers: ProviderArray = [...]`          | ❌ Silenced       | Type is too general; reports no errors.                 |
| `const providers = [...] satisfies ProviderArray` | ❌ Silenced       | Type is too general; reports no errors.                 |

`satisfies ProviderArray` leaves the array its inferred type, but TypeScript infers that type against `ProviderArray`, whose length is `number`, so the array's length is `number` too.

**Pro Tip**: Using the `provider()` helper avoids this entire problem. Because `provider()` checks props at the call site, the check is preserved regardless of how the resulting tuple is stored. A bare component gets no such protection: a bare `ThemeProvider`, which requires `theme`, compiles in the three widened rows.

## Preserving Checks in Wrapper Components

It is common to create a custom wrapper component (e.g., `<AppProviders />`) to encapsulate your `@evanion/compose` root. However, if you type the `providers` prop as plain `ProviderArray`, you've silenced the check for anyone using your wrapper.

To fix this, use a **const type parameter**. This forces TypeScript to infer the exact, fixed-length tuple of the caller's array. In the example, the first `<AppProviders>` exists only for its compile error, and the second renders `markup`:

```

### How it Works:

1. **`<const T extends ProviderArray>`**: The `const` modifier tells TypeScript to infer `T` as the most specific literal type possible (a fixed-length tuple). Without it, the caller's `[ThemeProvider, {}]` compiles with no error.
2. **`ComposeProviderProps<T>`**: By typing the props as `ComposeProviderProps<T>`, the validation logic of `ComposeProvider` is passed through to the caller of your wrapper.

Now, if a developer uses your `<AppProviders />` and passes a `ThemeProvider` with missing props, they will get a compile error at the call site.
