# Where the check happens

`ComposeProvider` renders a wrong or missing prop without complaint, so
`@evanion/compose` checks props at compile time. `provider()` checks at the
call. `ComposeProvider` checks a bare component, or a tuple you write as
`[component, props]`, where the array reaches it.

## Three ways to write a provider entry

`@evanion/compose` takes an [entry](../#four-words-for-a-provider-array) in
three forms: a bare component, a tuple, or a `provider()` call that returns a
tuple. The array below uses each form once, with these providers:

- `CartProvider` takes no prop and renders `<div id="cart">`.
- `ThemeProvider` requires `theme: 'light' | 'dark'` and renders a `div` whose
  `id` is `theme`.
- `CurrencyProvider` requires `currency: 'SEK' | 'GBP' | 'USD'` and renders a
  `div` whose `id` is `currency`.

They take the props the context providers on
[Getting started](../getting-started#compose-the-shops-context-providers) took,
and render a `div` in place of a context so the markup shows which props
arrived. `renderToStaticMarkup` renders `markup`, as on Getting started:

```tsx twoslash file=libs/compose/README.md region=entries

```

`provider()` infers the component from its first argument, so it checks the
props object at the call and the editor completes `theme` while you type it. A
bare component and a hand-written tuple are checked later, where the array
reaches `ComposeProvider`.

## Checking an inline provider array

`@evanion/compose` checks every entry of an array written inline in the
`providers` attribute. A **fixed-length array type** is the type TypeScript
gives an array when it keeps each position apart. TypeScript calls it a tuple
type, and these pages keep "tuple" for an entry. For
`[CartProvider, [ThemeProvider, {}]]`, the fixed-length array type has length 2,
with the type of `CartProvider` first and the type of `[ThemeProvider, {}]`
second.

`ComposeProvider` declares its type parameter `const`, a modifier TypeScript
5.0 added. It makes TypeScript infer an inline array as a fixed-length array
type, so each entry is checked against its own component. Four broken entries
for `ThemeProvider`, which requires `theme: 'light' | 'dark'`, report four
errors, one per line:

```tsx twoslash file=libs/compose/README.md region=checked-inline

```

| Entry                                                 | What the compiler reports                         |
| ----------------------------------------------------- | ------------------------------------------------- |
| `ThemeProvider`                                       | `this component requires props — …`               |
| `[ThemeProvider, {}]`                                 | `Property 'theme' is missing`                     |
| `[ThemeProvider, { theme: 'blue' }]`                  | `Type 'string' is not assignable to type 'never'` |
| `[ThemeProvider, { theme: 'dark', accent: 'green' }]` | `unknown prop 'accent'`                           |

`markup` is what the same array rendered. The two entries with no `theme`
rendered a `div` with no `id`. `ComposeProvider` checks no props at runtime, so
`id="blue"` reached the HTML. The compiler is the only check.

## What a compose error message means

`@evanion/compose` puts its message in the expected type. When an entry fails
a check, the entry's expected type becomes `ComposeError<"message">`, a type no
value matches, so the entry fails to compile. TypeScript names the expected type
in the first line of the error, so the message appears there. `ComposeError` is
internal and not exported. For
`[ThemeProvider, { theme: 'dark', accent: 'green' }]` that line ends
`… & ComposeError<"unknown prop 'accent'">'`.

| Message                                                                                        | What it means                                                  |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `unknown prop 'x'`                                                                             | the props object has a key the component does not declare      |
| `this component requires props — use provider(Component, props) or a [Component, props] tuple` | a bare component whose props are not all optional              |
| `first tuple element must be a component`                                                      | the tuple is the wrong way round, or its first element is data |
| `second tuple element must be props, not another component`                                    | two components in one tuple                                    |
| `not a valid provider`                                                                         | the entry is neither a component nor a two-element tuple       |

## A missing or wrong prop value

`@evanion/compose` has no `ComposeError` message for a missing or wrong prop
value. TypeScript reports it with its own error, which names the prop. For
`[ThemeProvider, { theme: 'blue' }]`, TypeScript gets to its error in three
steps:

1. `ComposeProvider` types `providers` as your array's type intersected with a
   corrected copy of it. In the copy, a failing tuple holds the props its
   component declares: `[ThemeProvider, { theme: 'light' | 'dark' }]`.
2. The intersection requires both types at once, so `theme` must be `'blue'`
   and `'light' | 'dark'` together. No value is both, and TypeScript names that
   empty type `never`.
3. TypeScript prints `'blue'` as `string` in the error. It keeps a literal in
   an error only when the expected type holds literals, and `never` holds none.
   The error reads `Type 'string' is not assignable to type 'never'`.

For `[ThemeProvider, {}]`, the intersection still requires `theme`, and the
error reads `Property 'theme' is missing`.

`provider()` reports the same mistake at the call and names both sides:

```tsx twoslash file=libs/compose/README.md region=checked-at-call

```

The error reads `Type '"blue"' is not assignable to type '"light" | "dark"'`.
`entry` is the tuple `provider()` returned, unchanged, because the check ran in
the compiler and not when the line ran.

## Moving the array out of the JSX

`@evanion/compose` now checks your inline array and every `provider()` call, and
you can read each message it reports. The next step moves the array into a
`const` above the JSX, or into your own wrapper component.
[Keeping the check](../keeping-the-check) shows how each one keeps the check.
