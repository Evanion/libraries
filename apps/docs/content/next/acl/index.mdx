# @evanion/acl

You write your authorization rules twice. The handler checks them, the screen
checks them again, and the two copies drift at the first edit.

## How acl shares one set of rules between server and browser

`@evanion/acl` keeps the rules you write with `policy()` in one JSON document,
called the matrix. The process that owns the rules writes it, and any process holding a
copy answers from that copy with no call back to the owner.

Every example on these pages is set in Baize, a board game shop, where a
customer who asked a question may edit it:

```

Each `// ->` comment is the value its line returns. `policy` takes two types
here: the shape of the user acting, and a map from each kind of object, here
`question`, to the shape of its rows. `.build()` turns the rules into an
evaluator, the object that answers questions from the matrix, which this
documentation always calls `access`.

`access.can(subject, kind, action, row)` asks whether the user acting, the
subject, may take an action on one row, and
`p.eq('object.askedBy', 'subject.id')` compares a field of the row with a field
of the subject. Every question on the pages below has this shape: a subject, an
object kind, an action, and the row the action is aimed at.

`access.matrix` is the matrix itself, a plain JSON value. `hydratePolicy` takes
that value in another process, such as a browser, and returns an evaluator over
it:

Every answer is computed inside the process that asked, with no network call. A
process holding a copy of the matrix keeps answering with the old rules after
you change one, until it fetches the new version.

## The acl vocabulary

- A **subject** is who is acting, as your auth layer resolved it before the
  call.
- An **object** is what is being acted on: a kind, like `question`, and
  optionally the row itself.
- A **permission** is one object kind paired with one action, keyed `` `${object}.${action}` ``.
- A **condition** compares a path into the subject or the row, such as
  `object.askedBy`, with a value or with another path.
- A **rule** is a list of conditions, and it matches when all of them hold. An
  allow rule grants its permission. A deny rule refuses it and outranks every
  allow, and a permission no allow rule matches is refused.
- The **matrix** is the whole document: a JSON object holding a flat list of
  permissions, an optional `version`, and an optional schema that names the
  fields each object kind carries.
- An **evaluator** answers questions from one matrix. `policy().build()` and
  `hydratePolicy` each return one.
- A **decision** is what `access.can` returns. `allowed` is the answer and the
  only field to act on. `reason` names which of seven outcomes decided it,
  `rule` names the rule that decided, and `missing` lists the row fields the
  call needed and did not pass.

## What acl can do

| The question                                          | The answer                                                                      |
| ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| May this subject take this action on this row?        | one decision, with the reason beside it                                         |
| May they take it on each of these rows?               | one decision per row, in one call                                               |
| What may they do at all, with no row in hand?         | every permission in the document at once                                        |
| Which fields of this write may they set?              | a decision per field, and the write with the refused fields removed             |
| Why was this refused?                                 | the rule that refused, or the fields that were missing                          |
| Who gained or lost access when the policy changed?    | a report over the old document and the new one                                  |
| May I answer from a matrix another service published? | yes, from your copy; an action the copy never declares answers `allowed: false` |

Every one of those is a local call. The rules behind them are the same rules on
a server and in a browser, because both sides hold the same document.

## When acl is the wrong tool

acl does not do these four jobs, and none of them is on a roadmap.

- Anything the document cannot state in the open. The matrix reaches the client
  in full, so every object kind, action and field name in it is public, and so
  is every value a condition compares against, such as a role name or a cut-off
  date. A check that has to stay secret runs in your own server code, outside
  the matrix.
- Filtering a collection in the database. A decision is per instance, and
  generating a `WHERE` clause from the matrix is out of scope.
- Rules that call a function. Conditions are declarative, because the matrix has
  to survive `JSON.stringify` unchanged.
- A non-JS backend. Only the JSON crosses, and a .NET or Go service brings its
  own evaluator.

[What `@evanion/acl` does not do](./limits) carries four more questions the
