# @evanion/acl

In most applications, authorization rules are written twice: once in the handler that guards the data, and once in the frontend that hides buttons. `@evanion/acl` lets you write them exactly once.

## One set of rules, shared everywhere

Instead of duplicating logic, `@evanion/acl` keeps your rules in a single JSON document called the **matrix**. Two hand-written copies drift the moment a rule changes, and a user sees a button they aren't allowed to click, or a feature they should have is hidden.

Your server defines the policy and builds the matrix in memory. Any other process, such as a browser or another service, can then hold a copy of that matrix and answer authorization questions locally, with no network call back to the server.

Each `// ->` comment is the value its line returns. `policy()` turns the rules into `access`, the evaluator, and `access.can` answers whether customer-41 may update a question they asked: `true`.

The `access.matrix` property is the raw JSON representation of these rules. By passing this JSON to `hydratePolicy` in another process, you can recreate the exact same evaluator in the browser:


Because the answer is computed inside the process that asked, the UI responds instantly. A copy keeps answering with the old rules after you change one, until it fetches the new matrix.

## The acl vocabulary

These `@evanion/acl` terms appear on every acl page:

- **Subject**: The entity acting (e.g., the logged-in user), resolved by your auth layer before the call.
- **Object**: The resource being acted upon. This consists of a **kind** (like `question`) and optionally a **row** (a specific record). A row's properties are its **fields**.
- **Permission**: A pair of an object kind and an action (e.g., `question.delete`), keyed `` `${object}.${action}` ``.
- **Condition**: A check comparing a path in the subject or row with a value or with another path (e.g., `object.askedBy` must equal `subject.id`).
- **Rule**: A list of conditions, which matches when all of them hold. **Allow rules** grant access; **deny rules** refuse it, and a deny rule that matches outranks every allow rule.
- **Default deny**: If no allow rule matches a request, the permission is refused by default.
- **Matrix**: The complete set of rules serialized as one JSON object, holding a flat list of permissions.
- **Evaluator**: The engine that uses a matrix to answer `can()` requests. `policy().build()` and `hydratePolicy` each return one.
- **Decision**: The result of a `can()` call. `allowed` is the answer and the only field to act on. `reason` says why (e.g., `denied` or `no-rule-matched`), `rule` names the rule that decided, and `missing` lists the row fields the call needed and did not pass.

## What acl can do

`@evanion/acl` handles a wide range of authorization patterns locally, on a server and in a browser alike:

| The question                                          | The answer                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| May this subject take this action on this row?        | a single decision with a specific reason                                     |
| May they take it on each of these rows?               | one decision per row, returned in a single call                              |
| What may they do at all, with no row in hand?         | every permission in the matrix at once                                       |
| Which fields of this write may they set?              | a decision per field, and the write with the refused fields removed          |
| Why was this refused?                                 | the rule that refused, or the fields that were missing                       |
| Who gained or lost access when the rules changed?     | a detailed report comparing the old and new matrices                         |
| May a service answer from a matrix another one built? | yes, from its copy; an action missing from the copy answers `allowed: false` |

## When acl is the wrong tool

`@evanion/acl` does not do these four things:

- **Secret rules**: The matrix is sent to the browser, meaning all object kinds, action and field names, and condition values (such as a role name or a cut-off date) are public. Rules that must remain secret must be written in your server code.
- **Database filtering**: The library makes decisions on individual instances. Generating `WHERE` clauses for database queries is out of scope.
- **Dynamic functions**: Conditions must be declarative so they survive `JSON.stringify` unchanged. You cannot put a JavaScript function inside a rule.
- **Non-JS backends**: Only the JSON is portable. A .NET or Go service brings its own evaluator.

Four more questions stay outside the matrix: how soon a revoked permission reaches a copy, how a rule relates two rows, the full list of subjects who may take an action, and which service's log of decisions is the access record for an audit. [What `@evanion/acl` does not do](./limits) answers each.
