# @evanion/acl

You write your authorization rules twice. The handler checks them and the screen
checks them again. The two copies drift at the first edit.

## How acl shares one set of rules between server and browser

`@evanion/acl` keeps the rules you write with `policy()` in one JSON document,
called the matrix. Your server builds the matrix in memory when it runs
`policy().build()`, and any other process holding a copy, such as a browser or
another service, answers from that copy with no call back to the server.

Every example on these pages is set in Baize, a shop that sells board games and
books, where a customer who asked a question may edit it:


Each `// ->` comment is the value its line returns:

- `policy()` starts the rules, and `.for('question', (p) => …)` writes the rules
  for one kind of object.
- `p.allow('update', …)` grants the action when its condition holds.
  `p.eq('object.askedBy', 'subject.id')` is that condition: the question's
  `askedBy` field equals the `id` of the subject, the user acting.
- `.build()` returns the evaluator, the object that answers questions from the
  matrix. Every page names it `access`.
- `access.can(subject, kind, action, row)` asks whether the subject may take an
  action on one row, a single record such as one question.

Every question on the pages below has the shape of that `can` call: a subject,
an object kind, an action, and the row the action is aimed at.

`access.matrix` is the matrix itself, a plain JSON value. `hydratePolicy` takes
that value in another process, such as a browser, and returns an evaluator over
it:

```mermaid caption="One matrix, two evaluators. Only the server's answer guards the write."
flowchart LR
  P["policy()<br>the rules, written once"] --> M[("access.matrix<br>JSON")]
  M --> S["server<br>can(subject, …)"]:::accent
  M --> B["browser<br>hydratePolicy(matrix)<br>can(subject, …)"]
  S --> W[("the write")]
  B --> U["what the screen draws"]
```

Every answer is computed inside the process that asked, with no network call. A
process holding a copy of the matrix keeps answering with the old rules after
you change one, until it fetches the new version.

## The acl vocabulary

Every `@evanion/acl` page uses these terms.

- A **subject** is who is acting, as your auth layer resolved it before the
  call.
- An **object** is what is being acted on: a kind, like `question`, and
  optionally the row itself, one record of that kind. A row's properties are
  its **fields**.
- A **permission** is one object kind paired with one action, keyed `` `${object}.${action}` ``.
- A **condition** compares a path into the subject or the row, such as
  `object.askedBy`, with a value or with another path.
- A **rule** is a list of conditions, and it matches when all of them hold.
- An **allow rule** grants its permission, and a **deny rule** refuses it. A
  deny rule that matches outranks every allow rule. A permission that no allow
  rule matches is refused, which these pages call **default deny**.
- The **matrix** is every rule you wrote, as one JSON object holding a flat
  list of permissions.
- An **evaluator** answers questions from one matrix. `policy().build()` and
  `hydratePolicy` each return one.
- A **decision** is what `access.can` returns. `allowed` is the answer and the
  only field to act on. `reason` says why, such as `denied` when a deny rule
  matched. `rule` names the rule that decided, and `missing` lists the row
  fields the call needed and did not pass.

## What acl can do

`@evanion/acl` answers each question below with a local call, on a server and in
a browser alike.

| The question                                          | The answer                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| May this subject take this action on this row?        | one decision, with the reason beside it                                      |
| May they take it on each of these rows?               | one decision per row, in one call                                            |
| What may they do at all, with no row in hand?         | every permission in the matrix at once                                       |
| Which fields of this write may they set?              | a decision per field, and the write with the refused fields removed          |
| Why was this refused?                                 | the rule that refused, or the fields that were missing                       |
| Who gained or lost access when the rules changed?     | a report over the old matrix and the new one                                 |
| May a service answer from a matrix another one built? | yes, from its copy; an action missing from the copy answers `allowed: false` |

## When acl is the wrong tool

`@evanion/acl` does not do these four jobs.

- Keeping a rule secret. The matrix reaches the browser in full, so every
  object kind, action and field name in it is public, and so is every value a
  condition compares against, such as a role name or a cut-off date. A check
  that has to stay secret runs in your own server code, outside the matrix.
- Filtering a collection in the database. A decision is per instance, and
  generating a `WHERE` clause from the matrix is out of scope.
- Rules that call a function. Conditions are declarative, because the matrix has
  to survive `JSON.stringify` unchanged.
- A non-JS backend. Only the JSON crosses, and a .NET or Go service brings its
  own evaluator.

Four more questions stay outside the matrix, and
[What `@evanion/acl` does not do](./limits) answers each:

- how soon a revoked permission reaches a copy
- how a rule relates two rows
- the full list of subjects who may take an action
- which service's log of decisions is the access record for an audit
