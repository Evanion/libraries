# The Security Contract

`can` answers **authoritatively** in a trusted environment and **advisory** everywhere else, including every check made in a browser. `@evanion/acl` is a tool, not a complete security system, and using it securely starts with that boundary.

## Authoritative and Advisory Decisions

An `@evanion/acl` decision is **authoritative** only when it is made in a trusted environment (like a server) and used there to guard a write or a sensitive read. In all other cases the decision is **advisory**: a hint to the UI that cannot be trusted as a security boundary. The server's evaluator and the one a browser rebuilds from the same document return the same `Decision` for the same question:

```ts twoslash file=libs/acl/README.md region=one-call-both-sides

```

| Where `can` runs                           | What the answer does                        |
| ------------------------------------------ | ------------------------------------------- |
| a React Router 8 or Next.js server runtime | enforces the decision, and guards the write |
| a Node service                             | enforces the decision, and guards the write |
| the server side of an API boundary         | enforces the decision, and guards the write |
| a browser                                  | toggles controls only, and enforces nothing |

`can` keeps one signature and one return type in every row above, so nothing in the types separates an authoritative answer from an advisory one. The runtime decides.

## The Trust Chain: Every Layer Decides for Itself

A common architectural failure is the "Trusted Gateway" fallacy: the belief that if a gateway or BFF (Backend-for-Frontend) has already authorized a request, the downstream service can trust that `@evanion/acl` decision.

In a secure system, every layer must evaluate the request for itself. A caller can bypass your gateway and reach your service directly; therefore, the service's own decision is the only one that matters. There is no transitive trust and no "already checked upstream" exemption.

```mermaid caption="The multi-layer trust chain. The browser provides a UI hint, the gateway provides a routing hint, but only the final service evaluation guards the actual data mutation."
flowchart LR
  B["Browser<br>can(subject, …)"] --> G["Gateway/BFF<br>can(subject, …)"]
  G --> S["Service<br>can(subject, …)"]:::accent
  S --> W[("Data Write")]
  B -. "direct access" .-> S
```

Each layer evaluates the matrix it already holds in its own process, with no network round trip, which makes "check again" a rule a team can keep.

## Transparency and the Public Matrix

The `@evanion/acl` matrix is a public document, in its names and structure as well as its values. When shipped to a client for UI toggles, the entire document is visible to anyone who opens the browser's developer tools:

- every object kind and every action name
- every role string in a condition
- every field name, including the ones the API never returns
- every state machine and every time window

**Security must not rely on the secrecy of the matrix**, and here it does not, so ship it anyway.

- **Avoid Sensitive Naming**: Do not name actions or roles in a way that discloses internal secrets. An action named `bypass-kyc` or a role named `internal-fraud-reviewer` is disclosed the moment the page loads.
- **Externalize Secrets**: Keep server-only predicates and sensitive business logic outside the matrix, in the application layer.

## Three Tiers of Responsibility

`@evanion/acl` holds itself to [a register of attack classes](../attacks), run under `nx test @evanion/acl`, one row per class, each naming the test that proves it and the tier it sits in:

- **Tier 1**: The library refuses or throws a construction error, from mass assignment to matrix shapes that exhaust the process.
- **Tier 2**: The library supplies the primitive and the consumer calls it: [`pickAllowedFields`](../fields#writing) for a write, `allowed` for a gate.
- **Tier 3**: Structurally out of scope. Every section below sits here, and is yours to own.

## Subject Authenticity (The Confused Deputy)

`@evanion/acl`'s `can(subject, …)` is a pure evaluator; it authorizes the `subject` bag it is handed. It has no way of knowing if that bag is authentic.

If you derive the subject from an untrusted source, such as a request header, a query parameter, an unverified token body, or a client-posted field, you create a "Confused Deputy" vulnerability where an attacker can claim any identity. No evaluator can fix this.

**The Fix**: Always resolve the subject from a verified, server-side session or a verified token before passing it to `@evanion/acl`.

## Complete Mediation

`@evanion/acl` does not automatically guard your application. It is a library, not a framework. Every single entry point into your data must be explicitly guarded.

Forgotten paths, such as a new API route, a new resolver, a background job, or an admin script, remain unguarded until you explicitly call `can`. While `authorize(subject)`, the handle bound to one subject that [Can this user do this?](../asking) teaches, puts the check in middleware on the path a developer already takes, the library cannot make the unchecked path impossible. Your own tests are where you assert that every path is covered.

## Time-of-Check to Time-of-Use (TOCTOU)

An `@evanion/acl` decision is a snapshot of the state provided to it, and the library carries no freshness token and cannot see the gap. Between the moment `can` returns `true` and the moment the write hits the database, the state of the world can change:

- The object may change owners.
- The subject may lose a required role.
- A time-based window may close.

Close this gap: re-read the object and re-check the permission inside the database transaction, or use a conditional write predicate that fails if the state has shifted.

## Time Windows and Clock Trust

The `now` parameter, the fifth argument of `@evanion/acl`'s `can`, is the instant every time-based boundary (`before`/`after`) compares against, and every window moves with the value the caller passes.

| `now` Value                                                   | Engine Behavior              | Result                                                                                                  |
| ------------------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| Omitted                                                       | Uses the process wall clock. | Evaluated against the current time of that process.                                                     |
| Supplied Instant                                              | Uses the provided value.     | Evaluated against the specific instant.                                                                 |
| `null`, `NaN`, an `Invalid Date`, a string that is not a date | Cannot determine time.       | Every permission that needs the clock to decide returns `{ allowed: false, reason: 'unusable-clock' }`. |

Omitted in a browser, `now` is the client's wall clock, and a user can set their system clock back to re-open a closed window.

```ts twoslash file=libs/acl/README.md region=unusable-clock

```

Never trust a `now` value sent from a client payload, such as a request body or a query string: it hands the client every time window in the matrix. Pass `now` only to make a server render and the client's first render agree, and resolve it on the server.

- A refusal on an unusable clock decides nothing, so a deny gated on a time window goes on denying.
- A `before`/`after` boundary in the document that does not parse is refused earlier still, at construction.
- In a browser, a role condition reads the subject a server resolved, while a time condition on the same page reads what the subject's machine produced. A server passing its own `now` is unaffected.

## The Bag a Decision Reads

`@evanion/acl` conditions read `subject` and `object` live, field by field, as the decision walks the rules. The engine reads the deny side before the allow side, and each side reads the fields its own rules name. A bag whose properties are accessors, such as an ORM row, a lazy proxy, or a memoised getter over a cache that can refill, can answer the two sides differently and pass the deny it should have matched.

The matrix the engine evaluates is a frozen deep copy for this reason. The engine copies neither the subject nor the object, because they are the app's data.

**The Fix**: Pass plain, already-resolved objects. [Caveats and pitfalls](../pitfalls#the-live-bag-problem) shows an accessor whose deny rule never matches.

## Avoiding Self-Authorizing Conditions

A security breach occurs when a subject can modify a field that an `@evanion/acl` rule then reads to grant them access. This is known as a "self-authorizing condition."

In the example below, the share dialog writes `sharedWith`, and any customer reaches it. A read rule keyed on `sharedWith` therefore hands the wishlist to whoever shares it with themselves. The engine cannot see this, because it does not know which fields the subject can write, and the write that sets `sharedWith` is a different action from the read.

```

**The Fix**: Ensure that no action a subject holds can write to a field that is used as a key for a read rule. Key your rules on something the subject cannot reach: ownership set at creation (like `ownerId` above), or a field only the server writes.

## Matrix Freshness and Revocation

When a policy is updated on the server, clients holding a cached copy of the `@evanion/acl` matrix will continue to grant permissions based on the old version until they refetch. Nothing pushes an update to a holder.

- **The Version Check**: The library supplies `access.version`, and the comparison is yours. The `revalidate` function below keeps the held evaluator while `access.version` equals the served `version`, and otherwise rebuilds with `parseMatrix`, so a key the new version dropped answers `unknown-action`.
- **The Freshness Budget**: An owner that states `maxStale` bounds how long a consumer that passes `fetchedAt` may keep deciding: past `fetchedAt + maxStale`, or the consumer's own tighter `maxStale`, every key answers `stale-contract` until the consumer fetches again. [How long a consumer may keep deciding](../publishing#how-long-a-consumer-may-keep-deciding-on-an-acl-contract) has the arithmetic.

```

The version comparison is a plain equality, so a digest or a composite covering every input works as well as a counter. A document that states no version leaves `access.version` undefined, so two such documents compare equal and `revalidate` never rebuilds.

While these mechanisms reduce the window of inconsistency, they do not eliminate it. Because the server always evaluates its own matrix on every request, a revoked permission is enforced at the API boundary as soon as the server holds the new rules, even if the client's UI still shows the control.
