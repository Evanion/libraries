# NestJS Integration

When using `@evanion/acl` in a NestJS application, you need a way to bridge the gap between Nest's request lifecycle and the ACL's subject-based evaluation. 

In the Baize shop API (`apps/shop-api`), this is achieved by combining a global `AclGuard` for route-level gating and service-level checks for fine-grained object access.

## Building the ACL Matrix at Boot

Since `@evanion/acl` is framework-agnostic, it doesn't ship a dedicated NestJS module. Instead, the policy is defined as a plain TypeScript file and instantiated when the application boots.

In `apps/shop-api`, the `ShopSubject` defines the identity of the user (id, roles, shop), while `ShopObjects` defines the shapes of the data being accessed.

| Name                     | Role                                                                                                                 |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `ShopVerbs`              | The allowed actions for a resource, such as `create`, `read`, `update`, `delete`, `declare`, or `reprice` |
| `SHOP_MATRIX_VERSION`    | Used by consumers to ensure they are using a compatible version of the policy                                                   |
| `SHOP_SCHEMA`            | Defines the field types for subjects and objects, ensuring conditions are checked against valid data                              |
| `p.always`               | A universal condition that every subject meets                                                                                            |
| `p.contains(path, v)`    | Validates that an array at a specific path contains the value `v`                                                                                   |
| `.fields`, `.visibility` | Refines the result of the last declared action in the chain                                                                                |
| `AVAILABILITIES`         | The valid states a write operation may set for a resource's availability                                          |

```ts file=apps/shop-api/src/acl/shop.policy.ts region=shop-matrix

```

The policy defines specific permissions like `game.declare` (for operators) and `game.reprice` (for managers). These rules typically check that the operator's shop matches the resource's shop, preventing a user in one location from modifying data in another.

To ensure the policy document is valid and immutable, `hydratePolicy` is used during the build process:

```ts file=apps/shop-api/src/acl/shop.policy.ts region=build-shop-access

```

`hydratePolicy` validates the structure, deep-clones the object, and freezes it. If it encounters an unknown field or duplicate permissions, the application will fail to boot.

## Integrating the Matrix via a Global Nest Module

To make the ACL matrix available throughout the application, it is bound into a global `DynamicModule`. This provides the matrix as a provider and registers the necessary guards and controllers.

The `APP_GUARD` binds the `AclGuard` to every route. Which specific routes are gated is determined by the `@Requires` metadata decorator. To avoid collisions with other providers in a global module, a package-namespaced string is used as the token:

## Resolving the Subject from the Request

For `@evanion/acl` to make a decision, it needs a `Subject`. In NestJS, this subject is resolved from the incoming request and stored in `AsyncLocalStorage` via a `SubjectService`.

Using `AsyncLocalStorage` allows the subject to be accessed anywhere in the request chain without forcing every dependent provider to become request-scoped, which would degrade performance and break `onModuleInit` hooks.

```ts file=apps/shop-api/src/acl/subject.service.ts region=subject-service

```

The `SubjectMiddleware` is responsible for populating this service. It is applied to all routes in `AppModule.configure`. The middleware parses the subject from a request header (`X-Shop-Subject`), falling back to a default "shopper" identity if no valid subject is provided:

## Coordinating the Guard and the Service

A typical write request in NestJS passes through two distinct "seats" where ACL checks occur: the Guard and the Service.

1. **The Guard (`AclGuard`)**: Runs before the controller. It only has access to the `Subject`. It can decide on permissions that depend solely on the user's identity (e.g., "Is this user an admin?").
2. **The Service (`GamesService`)**: Runs after the resource has been loaded from the database. It has access to both the `Subject` and the `Object` (the row). It decides on permissions that depend on the data (e.g., "Does this operator belong to the same shop as this game?").

| Seat           | Context               | Decision Capability                                                                                                |
| -------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `AclGuard`     | Subject only          | Permissions whose rules only read `subject.*`                                                                     |
| `GamesService` | Subject + Object row  | Permissions that read `object.*` (e.g., `game.declare` or `game.reprice`)                                              |

The `AclGuard` uses `access.readsObject(key, action)` to determine if a permission requires an object to be evaluated. If a permission is object-dependent, the guard allows the request to proceed to the controller, leaving the final decision to the service.

```mermaid caption="The two-stage authorization flow in NestJS. The Guard handles identity-based checks, while the Service handles data-based checks after the resource is loaded."
flowchart TD
  R["Request on @Requires route"] --> G["AclGuard: Subject-only check"]
  G -->|"Allowed"| C["Controller Method"]
  G -->|"Refused (Identity-based)"| F["403 Forbidden"]
  G -->|"Deferred (Object-dependent)"| C
  C --> S["Service loads resource"]
  S --> D["canFields: Subject + Row check"]:::accent
  D --> W["Filter fields or 403"]
```

## Gating Routes with @Requires

The `@Requires` decorator attaches the required permission to the handler. To ensure type safety, the permission key is typed against `ShopObjects`, meaning a route requesting a permission for a non-existent object kind will fail to compile.

```ts file=apps/shop-api/src/acl/requires.decorator.ts region=requires-decorator

```

The `AclGuard` then evaluates this requirement:

```ts file=apps/shop-api/src/acl/acl.guard.ts region=acl-guard

```

For example, `order.create` may only check the subject's roles. If the user is not a customer, the guard refuses the request immediately, and the controller never executes. Conversely, `game.declare` requires the title's shop ID, so the guard defers the decision.

## Fine-Grained Decisions in the Service

Once the service loads the resource, it performs the final check using `canFields`. This allows the service to not only decide if the action is allowed but also which specific fields the subject is permitted to modify.

```ts file=apps/shop-api/src/games/games.service.ts region=row-decision

```

The service checks `decision.action.allowed` first. If refused, it throws a `ForbiddenException`. If allowed, it uses the decision to whitelist the fields from the request body, ensuring that the user cannot modify restricted fields even if they are present in the payload.

This logic is verified against the real policy matrix in tests, ensuring that an operator from one shop cannot modify a title belonging to another:

```ts file=apps/shop-api/src/games/games.service.spec.ts region=declare-on-the-row

```

## Publishing the Policy Matrix

To allow frontends to implement "optimistic" UI (e.g., hiding a button the user can't use), the `PolicyController` publishes a reduced version of the matrix.

```ts file=apps/shop-api/src/acl/policy.controller.ts region=policy-endpoint

```

`serialize(access, 'reduced')` removes internal-only permissions and keeps only those marked as `visibility: 'public'`. While the frontend uses this for UI hints, the backend always re-evaluates every request to ensure security.
