## Before you install acl

`@evanion/acl` needs the following in the project you install it into:

- **Node 20 or newer.**
- **An ESM project**: Your `package.json` must include `"type": "module"`, as `@evanion/acl` does not ship a CommonJS build.
- **TypeScript 5.5 or newer (Optional)**: While the package runs in plain JavaScript, TypeScript allows the compiler to check your object kinds and actions for errors. The examples below run as JavaScript once you delete their `type` lines and the `<…>` after `policy`.
- **A way to run TypeScript**: We use `npx tsx` in the examples below, which downloads tsx on first use. A project that already compiles its TypeScript runs the file its usual way.
- **Nothing else**: There are no API keys to manage, no external services to run, no environment variables to configure, and no framework to install. `policy()` builds the matrix directly within your own process, and the React provider and hooks are a separate package, [`@evanion/react-acl`](/react-acl).

## Install acl

Run the command for your preferred package manager:

```bash
npm install @evanion/acl
```

```bash
yarn add @evanion/acl
```

```bash
pnpm add @evanion/acl
```

## Create your first policy

Defining an authorization policy in `@evanion/acl` is a three-step chain:

1. **Name your types**: Use `policy<Subject, Objects>()` to define the shape of the user (`Subject`) and the kinds of objects being protected (`Objects`). `{ question: Question }` declares one kind called `question` whose rows are `Question`.
2. **Define the rules**: Use `.for(kind, block)` to write rules for one of the object kinds you declared.
3. **Build the evaluator**: Call `.build()` to create the `access` object, which you will use to check permissions.

Within the `.for()` block, you use a helper (conventionally named `p`) to grant or deny access:

- `p.allow(action, ...conditions)`: Grants access if all provided conditions are true.
- `p.contains(path, value)`: A condition that checks if the array at `path` contains `value`. A path is a string rooted at `subject` or at `object`, so `'subject.roles'` reads `roles` off the user.

To see it in action, wrap each line ending in `// ->` in a `console.log` and run `npx tsx access.ts`. The file prints `true`, `false` and `no-rule-matched`: acl is answering in your project.

The `no-rule-matched` result is the customer's `reason`, the **default deny** behavior explained in the [Overview](../): if no rule explicitly allows an action, it is refused.

## Share your policy with the browser

An `@evanion/acl` evaluator's `access.matrix` property contains the policy as a plain JSON document. You can send this JSON to the browser, where `hydratePolicy` rebuilds a fully functional evaluator.

Change the first line of `access.ts` to `import { hydratePolicy, policy } from '@evanion/acl';`, and add these lines to the end of the file:

```ts twoslash file=libs/acl/README.md region=first-copy

```

Run the file again. The two new lines print `true` and `false`, matching the server's answers exactly. Here the JSON stays inside one process; in a real application, your server writes this JSON string into a page or API response, and the browser parses it and passes the result to `hydratePolicy`.

_Note: When using `hydratePolicy` without type arguments, the evaluator accepts any object kind or action string, meaning the TypeScript compiler can no longer verify them._
