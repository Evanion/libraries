# React Router Integration

A React Router 8 route's `loader` and `action` each call `@evanion/acl`'s `access.can` for themselves, because they run independently on the server. The browser tree between them toggles controls with `useCan` and enforces nothing.

## Adopting a Remote ACL Document

In the Baize admin portal (`apps/admin`, a framework-mode app with `ssr: true`), `@evanion/acl` gates page access via loaders and enforces data mutations via actions, while the browser-side UI only toggles controls based on those same rules. The admin portal does not author its own rules; instead, it "adopts" the policy document published by the `shop-api`. This allows the admin portal to share the same authorization logic as the backend service without duplicating the rules.

The `adoptMatrix` function transforms the published JSON document into a live `@evanion/acl` evaluator:

```ts file=apps/admin/app/access.ts region=adopt-matrix

```

`adoptMatrix` memoizes the evaluator by the document's version. `parseMatrix` validates, deep-clones and deep-freezes on every call, so the memo skips re-parsing a document whose version has not changed. Evaluations never parse.

Because the server evaluates the matrix for enforcement and the browser evaluates it for UI toggles, `access.ts` is a shared module. However, the network call to fetch the document is isolated in `access.server.ts`, which the Vite plugin keeps out of the browser bundle. A request that cannot reach shop-api falls back to `NO_ACCESS`, a parsed document carrying no permissions, so every key answers `unknown-action` and the page writes nothing.

## The Loader and Action: Two Separate Boundaries

An `@evanion/acl` decision a React Router `loader` makes for the page render does not carry over to the `action` that writes the data. In React Router, a `<Form>` submission or a direct `curl` request reaches the `action` without ever triggering the `loader`.

Therefore, every `action` must re-resolve the subject and re-evaluate the permission against the most recent version of the data.

| Phase           | Runtime | Responsibility                                                             |
| --------------- | ------- | -------------------------------------------------------------------------- |
| `middleware`    | Server  | Resolves the identity (Who is asking?)                                     |
| `loader`        | Server  | Decides if the subject may read the resource (Can they see this page?)     |
| Route Component | Browser | Toggles UI elements based on the policy (Should I show this button?)       |
| `action`        | Server  | Decides if the subject may write the resource (Can they change this data?) |
| `clientLoader`  | Browser | Never decides; it is no trust boundary, whatever it fetches from           |

```mermaid caption="The dual-server boundary in React Router. Middleware identifies the user, the loader gates the read, and the action independently gates the write. The browser tree sits between them, merely reflecting the policy for a better user experience."
flowchart TD
  N["Navigation (GET)"] --> M["Middleware: Identity Resolution"]
  P["A write request, from a Form or from curl"] --> M
  M -->|"Read Path"| L["Loader: Read Permission Check"]:::accent
  L --> T["Route Component: UI Toggles via useCan"]
  M -->|"Write Path"| A["Action: Write Permission Check"]
  A --> W["Data Mutation or 403 Forbidden"]
  A -->|"Revalidate"| L
```

## Resolving Identity in Middleware

Middleware is the ideal place to resolve the `@evanion/acl` subject and bind it to the request context. By doing this in the middleware, every subsequent loader and action on the route can assume a consistent identity. The middleware calls no `can` itself: a refusal needs a route to render it, and middleware has none.

`subjectContext` is a React Router 8 `createContext` cell that holds the request's subject. Its default is a subject with no roles and no shop, and Baize's matrix grants that subject no write, so a loader or an action reached without the middleware decides for a subject that may write nothing:

```ts file=apps/admin/app/page-context.ts region=subject-context

```

The admin portal's middleware, `loadPageView`, sets that cell to `demoSubject()`, the demo's stand-in for a session (see the note below). It also sets `accessContext` to a function that fetches the policy document, and fetches nothing itself. React Router runs middleware, then the action, then the revalidating loaders. The first of those to call the function fills a memoized promise, so the action and the loaders of one request decide on one fetched copy. The correlation id and the shelf snapshot the middleware also sets are the app's own plumbing, and decide nothing:

## Gating Reads in the Loader

The admin portal's `loader` asks `@evanion/acl` whether the bound subject may view the page. The orders page requires `telemetry.read`, which only managers hold. `allows` is the app's helper in `access.ts`: it reads one key of `access.capabilities(subject)` and treats an absent key as refused.

```tsx file=apps/admin/app/routes/orders.tsx region=loader-decides

```

If the permission is refused, the loader returns a `refused: true` flag. The route component then narrows on this flag to display a "Not yours to read" panel instead of fetching and rendering the sensitive data.

## Passing the Policy to the Browser

An `@evanion/acl` `Access` evaluator contains functions, so it cannot be serialized and passed from the server to the client. The loader returns the raw `access.matrix` (the JSON document).

The shell loader returns `access.matrix`, the subject and a `now` string once for the whole tree. The subject is no credential: the server resolves its own on the next request. `now` crosses as a string, because the hooks key their memos on it by value and a `Date` is a new object each render. The client-side shell then adopts this matrix using the same `adoptMatrix` logic used on the server. This allows the browser to use the `useCan` hook to toggle UI elements without making a network request for every check.

The shell mounts the policy for the whole component tree with these components:

- `PolicyProvider` comes from `createPolicyContext` in `@evanion/react-acl`, bound in `access.ts` to `NO_ACCESS` until the shell hands it the fetched document.
- `ComposeProvider` and `provider` come from [`@evanion/compose`](/compose) and nest the providers in the order listed.
- `SessionProvider`, `ThemeProvider`, `CartProvider` and `Chrome` are the admin app's own components.

## Enforcing Writes in the Action

The admin portal's `action` is the final `@evanion/acl` trust boundary. It reads no state from the loader and re-evaluates the permission against the row it loads itself.

```tsx file=apps/admin/app/routes/title.tsx region=action-decides

```

The action checks `decision.action.allowed` first. If the write is refused, it returns a failure response, which keeps the refusal off the exception path that `pickAllowedFields` takes with `ActionNotAllowedError`. With `pickAllowedFields`, which [Which fields may they write?](../writing) teaches, the action also ensures that only the fields the subject is permitted to modify are actually written to the database, regardless of what was sent in the `formData`, which carries whatever the sender put a `name` on. Between the render that showed the form and this action arriving, the title can move to another shop and the ownership rule can stop matching.
