# React Router Integration

In a React Router 8 application, the boundary between the user and the server is split across two distinct entry points: the `loader` and the `action`. Because these run independently on the server, each must resolve the subject and make its own ACL decisions to ensure security.

In the Baize admin portal (`apps/admin`), `@evanion/acl` is used to gate page access via loaders and enforce data mutations via actions, while the browser-side UI simply toggles controls based on those same rules.

## Adopting a Remote ACL Document

The admin portal does not author its own rules; instead, it "adopts" the policy document published by the `shop-api`. This allows the admin portal to share the same authorization logic as the backend service without duplicating the rules.

The `adoptMatrix` function transforms the published JSON document into a live `@evanion/acl` evaluator:

```ts file=apps/admin/app/access.ts region=adopt-matrix

```

To optimize performance, the document is memoized using a version key. Since `parseMatrix` performs deep-cloning and freezing on every call, memoization prevents unnecessary overhead during repeated evaluations.

Because the server evaluates the matrix for enforcement and the browser evaluates it for UI toggles, `access.ts` is a shared module. However, the network call to fetch the document is isolated in `access.server.ts`, ensuring that the API credentials and fetch logic are kept out of the browser bundle.

## The Loader and Action: Two Separate Boundaries

A common mistake in framework integration is assuming that a decision made during the page render (the `loader`) persists until the data is written (the `action`). In React Router, a `<Form>` submission or a direct `curl` request reaches the `action` without ever triggering the `loader`.

Therefore, every `action` must re-resolve the subject and re-evaluate the permission against the most recent version of the data.

| Phase           | Runtime | Responsibility                                                             |
| --------------- | ------- | -------------------------------------------------------------------------- |
| `middleware`    | Server  | Resolves the identity (Who is asking?)                                     |
| `loader`        | Server  | Decides if the subject may read the resource (Can they see this page?)     |
| Route Component | Browser | Toggles UI elements based on the policy (Should I show this button?)       |
| `action`        | Server  | Decides if the subject may write the resource (Can they change this data?) |

```mermaid caption="The dual-server boundary in React Router. Middleware identifies the user, the loader gates the read, and the action independently gates the write. The browser tree sits between them, merely reflecting the policy for a better user experience."

  M -->|"Write Path"| A["Action: Write Permission Check"]

  A -->|"Revalidate"| L
```

## Gating Reads in the Loader

The `loader` decides if the bound subject has the necessary capabilities to view the page. For example, the orders page requires `telemetry.read` permissions, which are restricted to managers.

```tsx file=apps/admin/app/routes/orders.tsx region=loader-decides

```

If the permission is refused, the loader returns a `refused: true` flag. The route component then narrows on this flag to display a "Not yours to read" panel instead of fetching and rendering the sensitive data.

## Passing the Policy to the Browser

Because the `Access` evaluator contains functions, it cannot be serialized and passed from the server to the client. Instead, the loader returns the raw `access.matrix` (the JSON document).

The client-side shell then adopts this matrix using the same `adoptMatrix` logic used on the server. This allows the browser to use the `useCan` hook to toggle UI elements without making a network request for every check.

The `PolicyProvider` and `ComposeProvider` are used to make the policy available to the entire component tree:

## Toggling the UI with useCan

The browser-side components use the `useCan` hook to decide whether to show specific controls. This is purely for user experience; it does not provide any actual security.

## Enforcing Writes in the Action

The `action` is the final trust boundary. It ignores any state from the loader and re-evaluates the permission against the actual data row retrieved from the database.

```tsx file=apps/admin/app/routes/title.tsx region=action-decides

```

The action checks `decision.action.allowed` first. If the write is refused, it returns a failure response. By using `pickAllowedFields`, the action also ensures that only the fields the subject is permitted to modify are actually written to the database, regardless of what was sent in the `formData`.
