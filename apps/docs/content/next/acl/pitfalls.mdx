# Caveats and Pitfalls

Each section below names a mistake the `@evanion/acl` API invites, where a small coding slip can open a significant security hole, and explains what to write instead.

## Misinterpreting the Decision Object

Every call to `can` returns an `@evanion/acl` `Decision` object. The most common mistake is gating logic on the `reason` field rather than the `allowed` boolean.

### Gate on `allowed`, not on `reason`

The `allowed` property is the only authoritative gate. The `reason` field says _why_ the engine decided, and no authorization logic should read it. The example below adopts a matrix with `parseMatrix`, where `maxStale` is how many milliseconds after `fetchedAt` the holder may keep deciding on it, and each `can` call refuses for a different reason:

```ts twoslash file=libs/acl/README.md region=gate-on-allowed

```

`reason` has seven values. `allow` grants, and `denied` means a deny rule matched. A gate written as `reason !== 'denied'` grants in five cases the engine refused:

- `no-rule-matched`: No allow rule matched the subject/object.
- `unknown-action`: The matrix does not contain this permission.
- `unevaluable`: The call lacked an object field required by the rules.
- `unusable-clock`: The instant passed to `can` did not parse.
- `stale-contract`: The local copy of the matrix is older than its `maxStale` allows.

Gate with `if (decision.allowed) { ... }`.

### Handling `unevaluable` Decisions

An `unevaluable` decision means the object you passed lacked a field a rule reads. A missing `subject.*` field never decides `unevaluable`: its condition fails like any other, because the app resolves the subject whole.

The decision's `missing` property names the fields to fetch. Fetch them, call `can` again, and the decision settles as `allow`, `denied` or `no-rule-matched`:

```ts twoslash file=libs/acl/README.md region=refetch

```

`allowed` is already `false`, so a server that refuses on it is safe. A UI that renders the control read-only hides something the user can have: render it as pending, fetch what `missing` names, and ask once more.

A decision still `unevaluable` after a refetch points at a mistyped field name in the policy document. Declare a `schema` in the document, and these mistakes become `UnknownFieldError` when the evaluator is built. [Why was this refused?](../refusals#when-the-answer-is-unevaluable) covers the refetch and the schema.

### A Key the Document Does Not Carry Is Absent, Not False

`access.capabilities(subject)` returns a map with an entry per permission in the document, as [What may this user do at all?](../listing-permissions) teaches. A key the document does not carry reads `undefined`, and `undefined !== false` is `true`:

```ts twoslash file=libs/acl/README.md region=capabilities-menu

```

A menu filtered with `!== false` grows an item whenever somebody renames a permission. Filter with `=== true`.

## Common Mistakes with `canFields`

`@evanion/acl`'s `canFields` is used to determine which specific fields of an object a subject is permitted to modify, as [Which fields may they write?](../writing) teaches. Because it returns a map of field states, it is easy to misread the result.

### Never Hand-Filter the Field Map

When applying a write, do not manually filter the field map to remove only `denied` keys. Here the handler loaded the question without `status`, so the `transitions` config cannot read the edge it guards:

```ts twoslash file=libs/acl/README.md region=hand-filter

```

A filter that only drops `denied` keys will accidentally write keys that are `unevaluable` (`'unevaluable' !== 'denied'`) or entirely absent from the map (`undefined !== 'denied'`). Instead, use the provided `pickAllowedFields` utility, which explicitly keeps only the keys that were decided as `allowed`.

### A Missing Name is Not a Denial

The map returned by `canFields` only contains keys the engine actually evaluated: the union of the object's own keys, the proposed write's keys, the names the rules configure, and the names in the permission's `fields` list. Hand `canFields` a row the query selected only some fields of, and the map shrinks:

```ts twoslash file=libs/acl/README.md region=projection-fields

```

If a field name is missing from the map, it doesn't mean it was denied; it means it was never asked about. To maintain a "fail-closed" security posture, always rely on `pickAllowedFields` to allow-list the final write payload, rather than assuming that a missing key in the map is a grant.

### Distinguishing Action-level vs. Field-level Grants

The `canFields` result contains two `allowed` booleans: one for the action itself and one for the overall field set.

```ts twoslash file=libs/acl/README.md region=field-decision

```

- `fd.allowed`: True only if the action is allowed **and** every evaluated field is allowed.
- `fd.action.allowed`: True if the action itself is permitted, regardless of individual field states.

`canFields` fills the field maps whatever the action decides, so a subject refused the action still gets a complete map of which fields would be editable once the action is unblocked. A caller who reads that map as the gate skips the action entirely, and the map looks identical either way. Check `fd.allowed` before iterating `fd.fields`, or let `pickAllowedFields` read the action for you.

### A `targets` or `transitions` Config Is Not an Allow-List

`targets` lists the values a field may be set to, and `transitions` lists the moves from its current value. Either config restricts the field it names and no other:

```ts twoslash file=libs/acl/README.md region=config-not-allow-list

```

With no `fields` list beside the config, every unnamed key is writable. A caller who reads the config as the writable-field list leaves the rest of the row open, here `sellerId`.

## Policy Authoring Traps

Some `@evanion/acl` mistakes exist within the policy matrix itself and cannot be caught at the call site.

### Self-Authorizing Conditions

A "self-authorizing condition" occurs when a subject can write to a field that a rule then reads to grant them access. Below, the share dialog writes `sharedWith`, so a read rule keyed on `sharedWith` hands the wishlist to whoever shares it with themselves:

```ts twoslash file=libs/acl/README.md region=self-authorizing

```

The evaluator cannot see this: it does not know which object fields the subject can write, and the write that sets `sharedWith` is a different action from the read.

**The Fix**: Ensure that no action a subject holds can write to a field used in a read rule. Key the rule on something out of reach instead, such as ownership set at creation (`ownerId` here) or a field only the server writes.

### Disclosure via Public Names

The policy matrix is shipped to the client in full. This means every object kind and action name, every role string, every field name (including the ones the API never returns), and every instant a `p.before` or `p.after` condition compares against is public.

Naming an action `refund-without-receipt` or a role `shrinkage-auditor` discloses internal business logic the moment the page loads. Name your elements as if a reader has the document open, and keep secrets and server-only predicates in the application layer.

## Runtime and Boundary Pitfalls

These `@evanion/acl` pitfalls sit at the boundary between the evaluator and the code that calls it, where the engine cannot see the mistake.

### Forged Subjects (The Confused Deputy)

`can(subject, ...)` authorizes the bag it is handed. If you derive the subject from a header, a query parameter, an unverified token body, or a field the client posted, an attacker can claim any identity they want.

**The Fix**: Resolve the subject from a verified, server-side session or token before calling `can`.

### Trusting the Client-Side Decision

A browser-side `can` call only decides what the user sees. It is not a security boundary. The call has the same signature and return type on a server, so nothing in the types marks an answer as authoritative.

A common mistake is assuming that because a button was hidden in the UI, the API endpoint it posts to is also secure. Every server-side handler must re-evaluate the permission using its own matrix. The same holds for a gateway: a gateway that already allowed the request does not excuse the service behind it, because a caller reaches that service directly whenever it wants to.

### The TOCTOU Gap

There is always a gap between the moment `can` returns `true` and the moment the write is committed to the database. During this gap, the subject's roles, the object's owner, or a `p.before` cut-off could change, and a decision carries no record of when its inputs were read.

```mermaid caption="The TOCTOU (Time-of-Check to Time-of-Use) gap. A decision based on a snapshot can become invalid before the write occurs."
flowchart LR
  C["can(subject, …)<br>allowed: true"] --> G["The Gap<br>State Changes"]:::accent
  G --> W[("The Write")]
  G -.-> R["Re-read & Re-check<br>inside transaction"]
  R --> W
```

To close this gap, re-read the object and re-check the permission inside a database transaction, or use a conditional update (e.g., `WHERE owner_id = X`).

### A Caller-Supplied Clock

`now` is the instant every `p.before` and `p.after` condition compares against, so it decides which time windows are open. The evaluator has no way to ask where the instant came from:

```ts twoslash file=libs/acl/README.md region=clock

```

`crossed.now` went through JSON, so the `Date` arrives as an ISO string, and `can` reads the string as the same instant. A `now` from a request body lets the caller open every time window in the matrix.

**The Fix**: Pass `now` only to make a server render and the client's first render agree, and resolve it server-side. The one guarded case is a clock that does not parse (`null`, `NaN`, an `Invalid Date`, a non-date string): every permission that needs the clock to decide answers `{ allowed: false, reason: 'unusable-clock' }`, in an allow rule or a deny rule, so a time-gated deny goes on denying.

## The "Live Bag" Problem

`@evanion/acl` reads `subject` and `object` fields live as it evaluates rules, and it reads the deny side before the allow side. If you pass a "live" object, such as an ORM row with lazy-loading getters or a proxy, the value of a field might change between the time the engine reads it for a `deny` rule and the time it reads it for an `allow` rule:

```ts twoslash file=libs/acl/README.md region=live-bag

```

This can allow a subject to bypass a deny rule they should have matched. The matrix itself is a frozen deep copy, so nothing can change it between two reads; the subject and the object are your app's data, and the evaluator copies neither.

**The Fix**: Pass plain, already-resolved JavaScript objects to the evaluator.
