# Rules about the thing being accessed

Many authorization decisions depend not just on who the user is, but on the specific resource they are trying to access. For example, while any customer can *view* a question in the Baize shop, only the customer who *asked* that specific question should be allowed to *edit* it.

To handle this, `@evanion/acl` allows you to write conditions that read properties directly from the object being accessed.

## Authorizing based on the resource

When a condition begins with `object.`, the evaluator looks at the row passed to the `can()` call. This allows you to create dynamic rules based on the data in your database.

Instead of writing manual `if` checks in every handler—which inevitably drift and lead to bugs—you can declare the relationship once in your policy:

```ts twoslash file=libs/acl/README.md region=object-condition

```

By using `p.eq('object.askedBy', 'subject.id')`, you've created a rule that only matches if the user's ID matches the `askedBy` field of the question.

### The "Unevaluable" state

Unlike subject-only rules, object-based rules depend on the data you provide to the `can()` call. If your database query didn't select the field that a rule needs to read, the evaluator cannot decide if the rule holds or fails.

In this case, the decision returns a fourth state: `unevaluable`.

```mermaid caption="The two inputs a condition can read, and the third outcome the second one adds."
flowchart LR
  S["subject<br>resolved whole"] --> C1["p.contains('subject.roles', 'bookseller')"]
  C1 --> O1["holds<br>fails"]
  S --> C2["p.eq('object.askedBy', 'subject.id')"]:::accent
  O["object<br>the question in hand"] --> C2
  C2 --> O2["holds<br>fails<br>unevaluable"]
```

If a decision is `unevaluable`, the `missing` field will list the exact paths that were missing from the object. Your application can then use this list to perform a targeted refetch of the missing data and ask the evaluator again.

<Panel heading="`unevaluable` is not `denied`">
  <Text as="div" size="sm">
    An `unevaluable` result still results in `allowed: false`, so your app remains secure. However, it is fundamentally different from a `denied` result. A denied request is a permanent refusal; an unevaluable request is a temporary lack of information. Treating an unevaluable result as "forbidden" might hide features from a user who actually has permission.
  </Text>
</Panel>

## Ensuring path safety

Because `object.askedBy` is just a string, it's easy to make a typo (e.g., `object.askedBv`). In a large policy, these typos can be hard to find because the matrix still builds, and the rules simply never match.

To prevent this, `@evanion/acl` allows you to declare the shape of your objects in the `Objects` type parameter of `policy<Subject, Objects>()`. This enables the TypeScript compiler to check your paths against your data model at compile time.

For a deep dive into using types to secure your policy, see [Typed authoring](../authoring).
