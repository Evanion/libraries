## Authorizing based on the resource

When an `@evanion/acl` condition begins with `object.`, the evaluator looks at the row passed to the `can()` call. This allows you to create dynamic rules based on the data in your database.

Declare the relationship once in your policy, and the handlers stop carrying `if` checks that drift apart. Sam and Jo below are both customers with exactly the same roles, so nothing on the subject tells them apart:

By using `p.eq('object.askedBy', 'subject.id')`, you've created a rule that only matches if the user's ID matches the `askedBy` field of the question. Sam asked the question and may edit it; Jo may not.

## The `unevaluable` answer

An `@evanion/acl` rule that reads the object depends on the row you pass to `can()`. If your query didn't select a field the rule reads, the evaluator cannot decide whether the rule holds, and the decision is a fourth answer beside `allow`, `denied` and `no-rule-matched`: `unevaluable`.

```mermaid caption="The two inputs a condition can read, and the third outcome the second one adds."
flowchart LR
  S["subject<br>resolved whole"] --> C1["p.contains('subject.roles', 'bookseller')"]
  C1 --> O1["holds<br>fails"]
  S --> C2["p.eq('object.askedBy', 'subject.id')"]:::accent
  O["object<br>the question in hand"] --> C2
  C2 --> O2["holds<br>fails<br>unevaluable"]
```

Baize's listing page loads forty questions and selects from each only the fields it renders. In the policy below, the allow rule reads `object.askedBy` and the deny rule reads `object.status`, so it produces all four answers:


An `unevaluable` decision's `missing` field lists the paths the object lacked, so your application can refetch exactly those and ask again. The allow rules and the deny rules are a permission's two sides, and the paths neither side could read come back together, so one refetch settles the permission however many rules read the object.

An absent `object.*` path is unevaluable whatever the condition asked of it. `p.ne('object.status', 'locked')` (not equal) over an absent `status` is as unevaluable as `p.eq` over it, because a field nobody read says nothing either way.

### Watching a decision move between the four answers

The control below runs the `@evanion/acl` policy above. A field's checkbox says whether the query selected it, and its select says what it holds.

<UnevaluableDemo />

It opens on a row with neither field, so the decision is `unevaluable` and `missing` names both paths. Three moves take it elsewhere:

- Select both fields, and the asker's own draft question decides `allow`.
- Change `askedBy` to `s2`, and the allow rule compares two different identifiers: `no-rule-matched`.
- Change `status` to `locked`, and the deny rule matches, which is `denied` whatever the allow side said.

Clear `status` on somebody else's question and the answer stays `no-rule-matched`: fetching `status` cannot make that allow rule match, so the engine answers the failed allow side first. A deny it could not read still outranks an allow that matched. [Why deny, then allow, then deny?](../resolution) has the whole order.

## Ensuring path safety

An `@evanion/acl` path such as `object.askedBy` is a string, so it's easy to make a typo (e.g., `object.askedBv`). In a large policy, these typos can be hard to find because the matrix still builds, and the rules never match.

To prevent this, `@evanion/acl` allows you to declare the shape of your objects in the `Objects` type parameter of `policy<Subject, Objects>()`. This enables the TypeScript compiler to check your paths against your data model at compile time.

For a deep dive into using types to secure your policy, including the third type parameter that names a kind's actions, see [Typed authoring](../authoring).
