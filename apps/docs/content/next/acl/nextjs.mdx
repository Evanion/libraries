# Next.js (React Server Components)

In a Next.js application, authorization happens at the trust boundary. When a request hits the server, your server components and Server Actions act as the final gatekeepers. Because they run in a trusted Node.js process, they can call `@evanion/acl`'s `access.can` to enforce rules before any data is rendered or any write is performed.

## Adopting a shared policy document

In a microservices architecture, your frontend doesn't usually author the rules; it adopts a document published by a backend service.

In the Baize storefront (`apps/storefront-rsc`), the app fetches a `PolicyDocument` (containing a version and the matrix) from the `shop-api`. It then uses `parseMatrix` to create an evaluator.

```ts file=apps/storefront-rsc/app/access.ts region=version-keyed-memo

```

### Why `parseMatrix` instead of `hydratePolicy`?

When you adopt a document from another process, you use `parseMatrix` to enter **closed mode**. In closed mode, if a request asks about a permission key that the document doesn't carry, the engine returns `unknown-action` and refuses. Using `hydratePolicy` in this scenario would cause the app to throw an error mid-render, which would crash the page.

### Efficiency through versioning

To avoid the cost of validating and deep-freezing the matrix on every single request, the app keys its evaluator by version. If the fetched version matches the held version, the app re-uses the existing evaluator, skipping the expensive setup process.

## Request-scoped authorization

To ensure that every component on a page uses the same subject and the same instant in time, the app scopes the evaluator to the request.

By wrapping the logic in React's `cache`, the app ensures that `GET /api/policy` is called only once per render, regardless of how many components (like `Catalogue` or `Spotlight`) need to check permissions.

## Gating the render and the fetch

In a Server Component, you can decide whether to render a piece of UI before you even fetch the data it needs.

For example, the `Activity` component might list recent events, but only for managers. By calling `can()` before the fetch, you prevent the server from pulling sensitive data from the API if the user isn't authorized to see it:

## The two boundaries: Render and Action

A Next.js route has two independent trusted entry points: the **Render** (Server Component) and the **Server Action**.

| Boundary         | Runtime | Role                                                                 |
| ---------------- | ------- | -------------------------------------------------------------------- |
| Server Component | Trusted | Decides what is rendered; hides buttons or sections.                 |
| Client Component | Browser | Advisory only; toggles UI based on the render's verdict.             |
| Server Action    | Trusted | Decides independently if a write is allowed before committing to DB. |

```mermaid caption="The dual-gate architecture. A page view runs the server component to decide what to render. A direct post to a Server Action skips the render entirely, requiring the action to re-resolve the subject and re-evaluate the rules."
flowchart TD
  V["a page view"] --> SC["server component: can"]:::accent
  SC --> CC["client component<br>toggles, decides nothing"]
  CC --> SA["the Server Action endpoint"]
  CURL["a caller posting directly"] --> SA
  SA --> AD["the action: re-resolve the subject,<br>re-read the row, decide again"]
  AD --> W["the write happens, or it throws"]
```

### Why Server Actions must decide again

Even if the render hid a "Delete" button from the user, a malicious actor can post directly to the Server Action endpoint using `curl` or a script. Therefore, the Server Action must never trust the render's verdict; it must re-resolve the subject, re-read the row, and decide again.

## Client-side UI toggles

To provide a snappy UI, you can pass the `access.matrix` (but never the `access` evaluator itself, as functions cannot be serialized) to the client.

The client rebuilds the evaluator using `parseMatrix` and wraps the tree in the `@evanion/react-acl` provider. This allows client components to use the `useCan` hook to hide or show elements instantly. However, this is purely advisory; the actual enforcement always happens on the server.
