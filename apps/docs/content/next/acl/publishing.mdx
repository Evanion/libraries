# Publishing ACL Contracts

In a distributed system, one service often owns the authorization rules for a specific resource, but other services need to know those rules to provide a consistent user experience. For example, an `orders` service owns the rules for issuing refunds, but the `storefront` needs to know those rules to decide whether to show a "Request Refund" button.

If the storefront were to maintain its own copy of these rules, it would inevitably diverge from the source of truth. To prevent this, `@evanion/acl` allows a service to publish a "contract"—a reduced version of its policy matrix—that other services can adopt and evaluate locally.

## Creating a Public Contract with `serialize`

A service defines which parts of its policy are intended for public consumption using the `.visibility('public')` mark. Any permission not marked as public is considered internal and is stripped away during serialization.

The `serialize` function produces the contract. A "reduced" serialization keeps only the public permissions and their associated rules, while a "full" serialization returns the entire document.

```

The resulting reduced document is the formal contract. It contains only the permissions the owner intended to share (e.g., `orders:order.refund`) and excludes internal-only permissions (e.g., `orders:ledger.read`). The consumer adopts this contract using `parseMatrix`, allowing them to make local decisions without making a network call to the owner for every check.

## The Integrity of Published Permissions

When a permission is published, it is exported in its entirety. This includes all allow rules and all deny rules.

If a permission's logic depends on a deny rule (e.g., "Allow refund unless the user is on probation"), that deny rule must be part of the published contract. If it were stripped, a consumer might incorrectly grant a permission that the owner would refuse.

Because the contract includes the full set of rules for the published permission, the consumer's local decision will exactly match the owner's decision for that specific key.

## Managing Contract Freshness

Since consumers evaluate a local copy of the contract, there is a risk that the copy becomes stale. `@evanion/acl` manages this through a "freshness budget."

The owner defines a `maxStale` value (in milliseconds) in the document, which sets the maximum allowed age of a copy. The consumer tracks when the document was last updated using `fetchedAt`.

| Bound                 | Source       | Purpose                                                                               |
| --------------------- | ------------ | ------------------------------------------------------------------------------------- |
| `maxStale` (Document) | The Owner    | Sets the absolute ceiling for how long a copy may be considered fresh.                |
| `maxStale` (Consumer) | The Consumer | Allows the consumer to tighten the owner's ceiling (e.g., for higher-security areas). |
| `fetchedAt`           | The Consumer | The timestamp of the last successful synchronization.                                 |

If the current time exceeds `fetchedAt + min(ownerMaxStale, consumerMaxStale)`, any attempt to use the contract results in a `stale-contract` response. This forces the consumer to refetch the document to repair the budget.

## Enabling Third-Party Vetoes

In some organizations, a separate team (such as Compliance or Fraud) must be able to override the permissions of a service. This is handled via **Deny Overlays**.

To allow another team to veto specific permissions, the owner must explicitly list those keys as `vetoable` during serialization. If a key is not published in the contract, a third party cannot write a valid overlay for it, as they would have no schema to validate their rules against.

`serialize(access, 'reduced', { vetoable })` will throw an `UnpublishedVetoableError` if the `vetoable` list includes a key that would otherwise be dropped from the reduced contract.
