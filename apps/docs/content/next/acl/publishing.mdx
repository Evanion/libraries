# How do I give my rules to another service?

`serialize(access, 'reduced')` publishes a "contract", a reduced version of your policy matrix, that another service adopts with `parseMatrix` and evaluates locally.

## Creating a Public Contract with `serialize`

In a distributed system, one service often owns the `@evanion/acl` rules for a resource that other services need to know. Baize's `orders` service owns the rules for issuing refunds, but the `storefront` needs them to decide whether to show a "Request Refund" button. If the storefront maintained its own copy of these rules, it would inevitably diverge from the source of truth, and the button would stay hidden against a server that would have allowed the call.

A service marks the parts of its policy intended for public consumption with `.visibility('public')`, which applies to the action declared most recently in the chain. Any permission not marked as public, including one whose author forgot the mark, is internal and is stripped away by `serialize(access, 'reduced')`, while `serialize(access, 'full')` returns the entire document:

```

The resulting reduced document is the formal contract. It contains only the permissions the owner intended to share (`orders:order.refund`) and excludes internal-only permissions (`orders:ledger.reconcile`). The consumer adopts this contract using `parseMatrix`, as [How do I use rules another service published?](../adopting) covers, allowing it to make local decisions without a network call to the owner for every check. The `orders:` prefix names the service that owns the object kind, which [Many services](../federation) explains.

## The Integrity of Published Permissions

When an `@evanion/acl` permission is published, it is exported in its entirety. This includes all allow rules and all deny rules. The document below is written as JSON, which is what a service in another language emits: a permission lists its allow rules under `rules` and its deny rules under `denyRules`, and a rule with an empty `when` grants everyone.

```ts twoslash file=libs/acl/README.md region=contract

```

A deny rule (here, "allow a refund unless the user is on probation") stays in the published contract. Stripped, it would let a consumer grant what the owner refuses; a stripped allow rule would turn an allow into a refusal. The price is disclosure: every consumer reads `subject.tier` and the word `probation`. Publish a permission whose deny rules read an internal concept and accept the disclosure, or leave it unmarked.

The schema keeps only the object kinds a kept permission names, so the ledger's entry is gone. Because the contract carries every rule of a published permission, the consumer's decision on that key matches the owner's. A contract trimmed to refuse more often would hide buttons the owner allows, and the user could not tell those from buttons a rule hid.

## How Long a Consumer May Keep Deciding on an ACL Contract

Since `@evanion/acl` consumers evaluate a local copy of the contract, there is a risk that the copy becomes stale. The library bounds this through a "freshness budget."

The owner defines a `maxStale` value (in milliseconds) in the document, which sets the ceiling. The consumer reports the instant of its last successful check that its copy is current as `fetchedAt`, as the storefront does with `Date.now()` above.

| Bound                 | Source       | Purpose                                                                                                |
| --------------------- | ------------ | ------------------------------------------------------------------------------------------------------ |
| `maxStale` (Document) | The Owner    | Sets the absolute ceiling for how long a copy may be considered fresh.                                 |
| `maxStale` (Consumer) | The Consumer | Allows the consumer to tighten the owner's ceiling (e.g., for higher-security areas), never extend it. |
| `fetchedAt`           | The Consumer | The instant of the last successful freshness check, which the bound measures from.                     |
| no `fetchedAt`        | The Consumer | Turns the bound off, so the copy never expires.                                                        |

If the current time exceeds `fetchedAt + min(ownerMaxStale, consumerMaxStale)`, every key answers `stale-contract`, and a fetch of the document repairs it. Measuring from the last check is what expires a consumer whose poll silently stopped.

State `maxStale` on the document before any consumer reports `fetchedAt`. A consumer reporting one against a document with no ceiling gets `MissingFreshnessBudgetError` at construction, because the owner's bound is the only one that expires a copy. A consumer that reports no `fetchedAt` runs under no bound. A service evaluating a matrix it authored in its own process is that case, since its copy cannot fall behind.

A copy inside its bound can still be out of date: it draws a control the owner has since revoked, and the write fails at `orders`, because `orders` evaluates its own matrix on every call.

## Enabling Third-Party Vetoes

In some organizations, a separate team (such as Compliance or Fraud) must be able to refuse some of a service's `@evanion/acl` permissions with deny rules of its own. This is handled via **Deny Overlays**: [`applyDenyOverlay`](../federation#cross-cutting-denials-via-overlays) merges the team's rules into your document before the evaluator is built, and may touch only the keys you list as `vetoable`.

The vetoing team tests its overlay against your published contract, so every vetoable key has to be in it. When a vetoable key is left out of the contract, its object kind's schema entry goes too, and the team's check then refuses every rule it wrote for that key.

`serialize(access, 'reduced', { vetoable })` will throw an `UnpublishedVetoableError` if the `vetoable` list includes a key that would otherwise be dropped from the reduced contract.
