# Policy Federation

In a microservices architecture, authorization logic is often fragmented across different services. If a single request needs to be validated against rules owned by multiple services, you need a way to compose these separate policies without merging them into a single, monolithic document.

`federatedPolicies` allows you to create a unified view over multiple ACL evaluators. It routes requests to the appropriate service-specific evaluator based on the object kind, ensuring that each service remains the sole authority over its own rules.

## Namespacing Object Kinds by Origin

When multiple services manage similar types of data, they may use the same names for their object kinds. For example, both a `storefront` service and a `stock` service might have a `listing` object.

To avoid collisions in a federated view, object kinds should be namespaced by their origin using a colon separator (e.g., `storefront:listing` and `stock:listing`). This tells the federated evaluator exactly which service owns the permission.

```

The key for these permissions remains `${object}.${action}`. If a `.` is used inside the object or action name itself, the library throws an `InvalidPermissionError` during construction, as the dot is reserved as the key delimiter.

## Composing a Federated View

`federatedPolicies` takes a map of `Access` evaluators (each created via `.build()`, `hydratePolicy`, or `parseMatrix`) and returns a unified view. This view preserves the integrity of each original document—nothing is merged or altered.

```ts twoslash file=libs/acl/README.md region=federation

```

The unified view provides three primary members:

| Member                        | Responsibility                                                                                                                          |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `can(subject, kind, action)`  | Routes the request to the single origin whose key set contains the target key. If no origin holds the key, it returns `unknown-action`. |
| `capabilities(subject, now?)` | Captures a single point in time and evaluates capabilities across all origins, ensuring a consistent "snapshot" for the entire request. |
| `get(origin)`                 | Returns the original `Access` evaluator for a specific origin, allowing access to advanced methods like `canFields` or `authorize`.     |

```mermaid caption="The routing logic of a federated view. A request for a permission is routed to the specific service evaluator that owns that key. If the key is not found in any registered evaluator, the view returns a refusal."
flowchart LR
  C["fleet.can(subject, key, action)"] --> R{"Which origin's key set<br>holds this key?"}:::accent
  R -->|"storefront:…"| O["storefront<br>its own Access"]
  R -->|"stock:…"| B["stock<br>its own Access"]
  R -->|"no origin"| U["unknown-action"]
```

If a request requires permissions from multiple origins, the caller simply performs multiple checks and combines the results (e.g., `can(storefront_key) && can(stock_key)`).

### Handling Origin Collisions

To prevent ambiguous authorization, `federatedPolicies` throws an `OriginCollisionError` if two different origins declare the same permission key. This check happens at the time the federated view is constructed.

A "deny overlay" (see below) does not cause a collision because it appends rules to an existing permission rather than declaring a new one.

## The Federated View as an Advisory Layer

It is critical to understand that a federated view at a gateway or edge level is **advisory**. It is functionally equivalent to a browser-side ACL check: it provides a hint to the system, but it is not the final trust boundary.

Every downstream service must still evaluate the request against its own matrix. A gateway that allows a request does not excuse the service behind it, which may be reached directly by a caller.

```mermaid caption="The trust boundary in a federated topology. The edge view is advisory and routes requests for efficiency; the actual enforcement must happen within each service using its own independent matrix."
flowchart LR
  CL["a caller"] --> GW["the edge view<br>advisory, like a browser's"]
  GW -->|"storefront:…"| S1["storefront<br>decides on its own matrix"]:::accent
  GW -->|"stock:…"| S2["stock<br>decides on its own matrix"]
  CL -->|"directly"| S1
  CL -->|"directly"| S2
```

## Managing Unreachable Upstreams

If a service is offline or unreachable, simply omit it from the object passed to `federatedPolicies`. The view will treat any keys owned by that missing service as `unknown-action`.

Each member of the federation is built using `parseMatrix`, ensuring that if a service is dropped from the federation, its rules are not mistakenly treated as grants in "closed mode."

## Cross-Cutting Denials via Overlays

Sometimes a specialized team (e.g., Compliance or Fraud) needs to enforce global restrictions that override the rules of a specific service. Instead of asking the service owner to change their rules, the "owner" service can apply a **Deny Overlay**.

An overlay is a set of deny rules for permissions the service already owns. The service applies this overlay to its own matrix before building the final evaluator:

```ts twoslash file=libs/acl/README.md region=deny-overlay

```

`applyDenyOverlay` appends these rules to the `denyRules` of the target permissions. Because only deny rules are added, an overlay can only subtract permissions—it can never grant a permission that the original author denied.

### Validation of Overlays

`applyDenyOverlay` validates the overlay against the target matrix's schema. It throws errors if:

- The overlay refers to a permission key that doesn't exist in the target.
- The object kind of a vetoable key lacks a corresponding entry in the target's `schema.objects`.
- The overlay attempts to modify a permission not marked as `vetoable`.

## Publishing and Consuming Policies

To share a policy with another service or a frontend, use `serialize(access, 'reduced')`. This emits only the permissions marked as `public`, allowing consumers to adopt the result via `parseMatrix`.

## Security Considerations

`@evanion/acl` does not provide built-in signing or verification for policy documents. You must transport your matrices over an authenticated and encrypted channel (e.g., HTTPS with mutual TLS). A document received over an unauthenticated channel should be considered untrusted.
