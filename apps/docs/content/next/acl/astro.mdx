# Astro SSR Integration

An `.astro` page's frontmatter runs on the server for every HTTP method at its URL, so a single `@evanion/acl` check can gate both the page render and any form submissions posting back to it.

## Single-Point Authorization in Astro

In the Baize storefront (`apps/storefront`), `@evanion/acl` ensures that users can only interact with the shopping cart if they have the required permissions. In frameworks like Next.js or React Router, a page render and a data write often happen through two different entry points (e.g., a Page component and a Server Action). In Astro, both a `GET` request to view a page and a `POST` request to submit a form reach the same frontmatter.

In `apps/storefront`, the `/cart` page handles both. `access` and `subject` are what the storefront's middleware put on `Astro.locals` (see [Resolving the subject and policy in middleware](#resolving-the-subject-and-policy-in-middleware)), and `decide` calls `access.can(subject, 'order', 'create')`, returning `undefined` where the app holds no document to decide on. By deciding at the very top of the frontmatter, the application resolves the permission once and uses the verdict for both the UI and the enforcement.

```ts file=apps/storefront/src/pages/cart.astro region=order-decision

```

If a `POST` request is refused, the application returns a 403 Forbidden response and leaves the cart cookie untouched. The `refusalText` is derived from the ACL decision's reason, providing the user with a clear explanation of why the action was blocked.

The form posts one of four intents: `add`, `update` and `remove` edit the cookie, and `checkout` places the order. All four are decided against `order.create`, because a cart is the draft of an order.

## Syncing the UI with the Enforcement

In `cart.astro`, one `@evanion/acl` decision governs both the render and the write, so the page cannot display a control that its own handler would refuse.

The checkout button in `cart.astro` is enabled or disabled based on the `mayOrder` variable, which is the result of the `order.create` check performed in the frontmatter:

```astro file=apps/storefront/src/pages/cart.astro region=checkout-gate

```

While the disabled button provides a better user experience, the actual enforcement happens in the `POST` branch of the frontmatter. A direct script posting to `/cart` with `intent=checkout` will still be blocked by the same ACL check, regardless of the UI state.

## Establishing the Server Boundary

An `@evanion/acl` decision in Astro frontmatter needs the app configured for Server-Side Rendering. In a prerendered (static) build, the frontmatter runs only once at build time, meaning there is no request-time context to resolve a subject against.

The `apps/storefront/astro.config.mjs` file sets `output: 'server'` and uses the `@astrojs/node` adapter in standalone mode. This ensures the frontmatter runs on every request inside a Node.js process controlled by the operator. Under a prerendered build, Astro middleware also runs once, at build time, against whoever built the site.

## Resolving the Subject and Policy in Middleware

The storefront's Astro middleware resolves the subject and the `@evanion/acl` document before any page's frontmatter runs, so no page repeats that setup.

The middleware reads the visitor's identity from a cookie and fetches the latest policy document from `apps/shop-api`. The resulting `access` evaluator and `subject` are then attached to `Astro.locals`, making them available to every page.

```ts file=apps/storefront/src/middleware.ts region=open-context

```

Every page reads `Astro.locals.subject` and `Astro.locals.access`, resolved once per request, so two blocks on one page cannot decide against two identities. The `policyAccess` evaluator adopts the document with `parseMatrix`, caches it across requests, and only fetches where the process holds no document or the revalidation window has closed. This ensures that ACL decisions in the frontmatter are local function calls rather than network requests.

## Sanitizing Roles at the App Boundary

The storefront sits between the user and the `shop-api`, and states the subject its `@evanion/acl` decisions read on the `X-Shop-Subject` header. The API trusts that header, so the storefront is the last point where the application can check which roles it asserts on behalf of the user. A subject read from a header is the forged subject the [security contract](../security#subject-authenticity-the-confused-deputy) warns about, and shop-api accepts one only because Baize is a demo. The cookie it reads is unsigned, a demo identity that a deployment replaces with a verified session.

To prevent a user from manually editing their cookie to claim a `manager` role, the `parseSubject` function screens the subject against `STOREFRONT_ROLES`, which holds `customer`, the one role the app's `/session` sign-in route issues. If any role outside it is claimed, the whole payload is discarded and the subject becomes `ANONYMOUS_SUBJECT`, an anonymous shopper.

## The Backend Decides Again

The storefront's `@evanion/acl` decisions all run in its Node process, because it ships no JavaScript to the browser, and the data still lives in `apps/shop-api`. `apps/shop-api` re-evaluates every order against the same policy document, as [the security contract](../security#complete-mediation) requires.
