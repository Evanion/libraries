# Astro SSR Integration

In an Astro application using Server-Side Rendering (SSR), the boundary between the user's request and the server's response is the page's frontmatter. Because this code runs on the server for every HTTP method at its URL, a single ACL check can gate both the page render and any form submissions posting back to it.

In the Baize storefront (`apps/storefront`), `@evanion/acl` is used to ensure that users can only interact with the shopping cart if they have the required permissions.

## Single-Point Authorization in Astro

In frameworks like Next.js or React Router, a page render and a data write often happen through two different entry points (e.g., a Page component and a Server Action). In Astro, both a `GET` request to view a page and a `POST` request to submit a form reach the same frontmatter.

In `apps/storefront`, the `/cart` page handles both. By calling `access.can` at the very top of the frontmatter, the application resolves the permission once and uses the verdict for both the UI and the enforcement.

```ts file=apps/storefront/src/pages/cart.astro region=order-decision

```

If a `POST` request is refused, the application returns a 403 Forbidden response. The `refusalText` is derived from the ACL decision's reason, providing the user with a clear explanation of why the action was blocked.

## Syncing the UI with the Enforcement

Because the same decision governs both the render and the write, it is impossible for the page to display a control that its own handler would refuse.

The checkout button in `cart.astro` is enabled or disabled based on the `mayOrder` variable, which is the result of the `order.create` check performed in the frontmatter:

```astro file=apps/storefront/src/pages/cart.astro region=checkout-gate

```

While the disabled button provides a better user experience, the actual enforcement happens in the `POST` branch of the frontmatter. A direct script posting to `/cart` with `intent=checkout` will still be blocked by the same ACL check, regardless of the UI state.

## Establishing the Server Boundary

For this pattern to work, the Astro app must be configured for Server-Side Rendering. In a prerendered (static) build, the frontmatter runs only once at build time, meaning there is no request-time context to resolve a subject against.

The `apps/storefront/astro.config.mjs` file sets `output: 'server'` and uses the `@astrojs/node` adapter. This ensures the frontmatter runs on every request inside a Node.js process controlled by the operator.

## Resolving the Subject and Policy in Middleware

To avoid repeating setup logic on every page, the storefront uses Astro middleware to resolve the subject and the ACL document before the frontmatter ever executes.

The middleware reads the visitor's identity from a cookie and fetches the latest policy document from `apps/shop-api`. The resulting `access` evaluator and `subject` are then attached to `Astro.locals`, making them available to every page.

```ts file=apps/storefront/src/middleware.ts region=open-context

```

The `policyAccess` evaluator caches the document and only refreshes it when the revalidation window closes. This ensures that ACL decisions in the frontmatter are local function calls rather than network requests.

## Sanitizing Roles at the App Boundary

The storefront acts as a bridge between the user and the `shop-api`. While the API trusts the subject it is given, the storefront is the last point where the application can verify which roles it is asserting on behalf of the user.

To prevent a user from manually editing their cookie to claim a `manager` role, the `parseSubject` function screens the subject, discarding any roles not included in `STOREFRONT_ROLES`. If an invalid role is claimed, the subject is downgraded to an anonymous shopper.

## The Backend as the Final Arbiter

Even with a perfectly implemented frontend, the Astro app is not the final authority on security. Because the storefront ships no JavaScript to the browser, all decisions happen in the Node process, but the data still lives in `apps/shop-api`.

The backend service always re-evaluates the request using the same policy document. This adheres to the principle of complete mediation: a storefront that disables a button does not excuse the service that receives the order.
