## Handling exceptions with deny rules

A **subject-only rule** in `@evanion/acl` depends only on the user's properties, like their roles or account status, so it is evaluated without any database reads. While `p.allow` grants permission, `p.deny` explicitly revokes it. If a deny rule matches, the permission is refused, even if an allow rule also matches.

Consider the Baize shop's stock report: any staff member with the `bookseller` role may read it, unless their account has been suspended. Replace the contents of `access.ts` with this file, which keeps the question rule from [Getting started](../getting-started) and adds the report:


In this policy, the `report.read` permission is decided by two rules:

1. An **allow rule** that grants access to anyone with the `bookseller` role.
2. A **deny rule** that refuses access to anyone with the `suspended` role. Baize suspends an account by adding that role, and the account keeps `bookseller`.

`p.deny(action, ...conditions)` takes the same conditions `p.allow` takes. `p.allow`, `p.deny` and `.id` each return `p`, so the calls chain one after another. One policy holds every object kind your app has: `report` joins `question` in the `Objects` type, and the second `.for()` chains onto the same `policy()`, so `access.matrix` holds both kinds' permissions in one list.

Wrap each line ending in `// ->` in a `console.log` and run `npx tsx access.ts`. When `can()` is called, the engine checks deny rules first. If a user is both a `bookseller` and `suspended`, the deny rule wins: `allowed` is `false` and the `reason` is `denied`. If they are only a `bookseller`, `allowed` is `true` and the `reason` is `allow`. If they are neither, the `reason` is `no-rule-matched` (the default deny).

### Identifying rules with `.id`

`.id(name)` gives the rule written by the `.allow` or `.deny` call just before it a human-readable name, and a decision reports that name in its `rule` field. The suspended bookseller's refusal above reports `suspended-reads-nothing`, the third line the file prints.

A rule you do not name reports an id derived from its conditions. The id stays put when a rule is inserted above it, and changes only when a release of `@evanion/acl` changes how a condition is represented. A stored derived id stops matching its rule after such a release, and nothing reports it. Name the rules whose ids you store, such as in a log.

### One permission never gates another

An `@evanion/acl` deny rule goes into the permission it refuses. A deny on `report.read` leaves `report.export` untouched, even though a person would call reading a precondition for exporting. Two actions that share a deny rule each carry their own copy of it in the matrix, so a person reading either permission there sees every rule that decides it.

## The scope of subject-only rules

A subject-only `@evanion/acl` rule is completely decoupled from the resource. This leads to two major advantages:

1. **Final answers**: The server resolves the subject (the user) whole, once per request, so every condition has data to read. A permission here always answers `allow`, `denied` or `no-rule-matched`, without triggering additional database queries.
2. **Pre-flight checks**: You can ask about these permissions before you've fetched any object. For example, a navigation menu can decide whether to show the "Stock report" link without loading a single row.

However, once you need to check a relationship, such as "Can this user edit _this specific_ question?", you have moved beyond the subject. You now need to read the object itself, and the handler has to load it before it asks. A question loaded without the field the rule reads gets `allowed: false` with the reason `unevaluable`: the evaluator could not decide, and fetching that field settles it.

[Rules about the thing being accessed](../object-rules) explains how to write conditions that compare the user to the resource, and how to handle `unevaluable`.
