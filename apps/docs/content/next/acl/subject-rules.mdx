## What a subject-only rule covers

A subject-only `@evanion/acl` rule reads nothing but the subject, so `can`
answers it with no database read in front of it. Baize lets a bookseller, the
staff role that [Getting started](../getting-started) allowed to delete
questions, read the shop's stock report unless the shop has suspended that
bookseller's account.

When each handler writes the rule and its exception by hand, the copies drift:
one tests `roles.includes('bookseller')`, another tests `user.isStaff`, and the
suspended account is refused in two places out of five. A policy holds the pair once, in
one `.for('report', …)` block.

## Refusing with a deny rule

An `@evanion/acl` deny rule refuses what the allow rules for the same action on
the same object kind, here `report.read`, would grant. Replace the contents of
`access.ts` with this file, which keeps the question rule and adds the report:

```ts twoslash file=libs/acl/README.md region=subject-deny

```

One policy holds every object kind your app has. `report: Report` joins
`question` in the `Objects` type, and a second `.for()` chains onto the same
`policy()`, so `access.matrix` holds both kinds' permissions in one list.

`p.deny(action, ...conditions)` takes the conditions `p.allow` takes and refuses
when they all hold. Baize suspends an account by adding the `suspended` role,
and the account keeps `bookseller`, so the deny tests
`p.contains('subject.roles', 'suspended')`. `p.allow`, `p.deny` and `.id` each
return `p`, so the calls chain one after another and the block returns the
chain.

Wrap each line that ends in a `// ->` comment in `console.log` and run
`npx tsx access.ts`. Four lines print. The three `.reason` lines give the three
subjects three answers:

- The bookseller gets `allow`, the reason a granted decision reports.
- The suspended bookseller satisfies both rules and gets `denied`, because a
  deny that matched outranks an allow that matched with it. `can` checks the
  deny rules first.
- The customer satisfies neither rule and gets `no-rule-matched`, the default
  deny.

### Naming a rule with `.id`

`.id(name)` names the rule written by the `.allow` or `.deny` call just before
it, and a decision reports that name in its `rule` field. The suspended
bookseller's refusal above reports `suspended-reads-nothing`, the fourth line
the file prints. A rule you do not
name reports an id hashed from its conditions, and a release of `@evanion/acl`
can change that hash. Name the rules whose ids you store, such as in a log.

## Where a deny rule belongs

An `@evanion/acl` deny rule goes into the permission it refuses. One permission
never gates another, so a deny on `report.read` leaves `report.export` untouched
even though a person would call reading a precondition for exporting. Two
actions that share a deny rule each carry their own copy of it, and a reader of
either action sees every rule that decides it.

## Where subject-only rules stop

While every condition in an `@evanion/acl` policy reads only the subject, your
code can rely on two things:

- Your handler always gets a final answer. The server loads every field of the
  subject before the call, so every condition has data to read, and a permission here
  answers `allow`, `denied` or `no-rule-matched`.
- Your caller asks without fetching anything. `can` needs no row, so a
  navigation menu can ask about every permission before it loads one.

The rule [the Overview](../) opened on, that the customer who asked a question
may edit it, reads the question. Both properties stop holding the moment you add
it. The handler has to load the question before it asks, and a question loaded
without the `askedBy` field gets `allowed: false` with the reason `unevaluable`:
the evaluator could not decide, and fetching `askedBy` settles it.
[Rules about the thing being accessed](../object-rules) writes that rule and
handles `unevaluable`.
