# Chrome, meta, ctx and Suspense

`chrome` on `createWidgets` sets the markup around a region and around each
widget, and `chrome.suspense` sets the `<Suspense>` boundaries inside it. `meta`
places one item in that markup, and `ctx` hands every widget page-level data.

## Wrap a react-widget region and each widget

A region needs an `aria-label`, or each widget a class for the grid. The
markup that takes them is the chrome: `chrome.wrapper` renders around the whole
region and `chrome.item` renders around each widget. The package exports both
defaults. `DefaultWrapper` renders a `<section>`, and `DefaultItem` renders a
`<div>` carrying the `data-widget-*` attributes. A custom chrome spreads its
props into one of them:

```tsx twoslash file=libs/react-widget/README.md region=chrome

```

| Chrome           | Receives                                                             |
| ---------------- | -------------------------------------------------------------------- |
| `chrome.wrapper` | `children`, and `items`: the region's items, aligned with `children` |
| `chrome.item`    | `children`, `data-widget-id`, `data-widget-type` and `meta`          |

Keep the `data-widget-*` attributes on the element. CMS click-to-edit overlays,
analytics and end-to-end selectors key off them. `DefaultWrapper` drops `items`
and `DefaultItem` drops `meta`, because React warns about an unknown attribute
for each prop that reaches the DOM.

## Place a react-widget item with `meta`

An item's `meta` goes to `chrome.item` and never into the widget's props, so a
listing renders the same at column 1 and at column 7. Annotate `chrome.item`
with the keys it reads, and `createWidgets` checks every item's `meta` against
them. `defineItems`, which `createWidgets` returns, types the array:

```tsx twoslash file=libs/react-widget/README.md region=meta-grid

```

`WidgetItemComponent<GridMeta>` types `GridCell`, and `createWidgets` infers
`GridMeta` from it with no type argument to pass. Root spans columns 2 and 3.
The Hive item names `col`, a key `GridCell` does not read, so it compiles only
under `@ts-expect-error` and renders through the `auto` fallback.

`meta` is optional on every item. Write a fallback in the chrome for an item
that omits a key it reads. A `createWidgets` call with no `chrome.item`, or with
an unannotated one, accepts any object as `meta`.

## Pass page-level data to every widget in a react-widget region

`<Widgets ctx={…}>` passes one object to every widget as its `ctx` prop.
React's `react-server` build exports no `createContext`, so the package hands
page-level data down as a prop:

```tsx twoslash file=libs/react-widget/README.md region=ctx

```

`ListingCard` declares `ctx` required, and the Root item still carries only a
`title`: `ctx` is left out of an item's `props`, the way `children` is.
`Widgets` passes `ctx` after the item's props, so an item from untrusted data
cannot override it. `<Widgets>` types its `ctx` prop as
`Record<string, unknown>`, so the compiler does not check it against the `ctx`
a widget declares.

## Choose where react-widget's Suspense boundaries go

`Widgets` wraps every widget in its own `<Suspense>` boundary, so one slow
widget does not hold up its siblings. That is `chrome.suspense: 'per-item'`, the
default. `chrome.suspenseFallback` is what renders while a widget suspends, and
it defaults to nothing:

```tsx twoslash file=libs/react-widget/README.md region=suspense-fallback

```

`StockLevel` is an async Server Component. `renderToStaticMarkup` does not wait
for a widget that suspends, so its HTML carries `Counting stock` in that
widget's place. A streaming render sends the same fallback first and replaces it
when the count resolves. The boundary lives in `Widgets`, so a custom
`chrome.item` cannot remove it.

## Render a synchronous react-widget region: `chrome.suspense: 'none'`

By default `Widgets` wraps each widget in its own `<Suspense>` boundary. A
streaming render, through `renderToPipeableStream`, sends the shell first. Once
the shell passes `progressiveChunkSize`, an option that defaults to 12,800
bytes, React stops writing `<Suspense>` boundaries into it and outlines every
remaining one, whether or not anything in it suspended. An outlined boundary
leaves a placeholder in the shell and sends its content later, in a trailing
`<div hidden>`. An inline `<script>$RC(…)</script>` then moves the content into
place.

A client that runs no inline script never sees an outlined widget, which covers
scripts turned off and a Content-Security-Policy that blocks inline scripts. A
text extraction, a reader-mode pass or a snapshot test reads placeholders where
the widgets should be. Measured over 150 synchronous items of about 1,000
bytes:

| `chrome.suspense` | Bytes   | Outlined boundaries | Items in the shell |
| ----------------- | ------- | ------------------- | ------------------ |
| `'per-item'`      | 139,233 | 145                 | 5 of 150           |
| `'none'`          | 122,069 | 0                   | 150 of 150         |

Set `'none'` on a region whose widgets never suspend. `renderToString`, from
`react-dom/server`, writes a `<!--$-->` marker pair per boundary, which shows
where they went:

```tsx twoslash file=libs/react-widget/README.md region=suspense-none

```

`Widgets` does not detect which widgets suspend: `use(promise)` looks
synchronous at runtime, and `memo()` hides an async component. If you set
`'none'` on a region holding a widget that does suspend, that widget suspends
the nearest boundary above the region. Wrap `<Widgets>` in `<Suspense>` to stop
it there.

## Catch an error thrown inside a react-widget region

The package ships no error boundary. A boundary is a class component, and React
exports no `Component` under `react-server`, so a class inside the package
forces `'use client'` onto all of it. Write the boundary in your own
`'use client'` file, with the directive as its first line, and render it inside
`DefaultItem`:

```tsx twoslash file=libs/react-widget/README.md region=error-boundary

```

Export `SafeItem` from that file, import it into the server file that calls
`createWidgets`, and pass it as `chrome: { item: SafeItem }`. The boundary is
then client code, and the widgets inside it stay server components.

## Render a long react-widget region

`Widgets` renders every item and has no windowing option. For server-rendered
content, the CSS property `content-visibility: auto` on the item chrome lets the
browser skip layout and paint for off-screen items, and every item stays in the
HTML:

```tsx twoslash file=libs/react-widget/README.md region=content-visibility

```

For a client-side list long enough to need windowing, virtualize in your own
`'use client'` `chrome.wrapper`. It receives `items` in the same order as
`children`, one entry per top-level item, so it can measure and window by item.

The [Playground](../playground) runs `Widgets` in the browser, with
nested items and chrome you can edit.
