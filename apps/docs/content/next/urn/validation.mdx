## The Problem: Untrusted Input

When receiving URNs from external sources—API requests, URL parameters, or user input—you cannot assume they are well-formed. Attempting to `parse` a string that isn't a URN will throw an error, which, if uncaught, can crash your request handler.

Checking every input with a `try...catch` block is verbose and computationally expensive for high-volume endpoints.

## Solution: Pre-screening with `isValidFormat`

`isValidFormat` allows you to screen input without the overhead of exception handling. It internally calls `parse` but returns a boolean instead of throwing, ensuring that your validation logic and parsing logic never disagree.

## Avoiding the "Unbound Static" Pitfall

A common JavaScript error occurs when passing static methods as callbacks. Every static method of an `@evanion/urn` class reads `this` to determine the current namespace. If you pass a static method as a bare callback, it loses its class binding.

`stringify`, `parse` and `extractId` will throw a `TypeError` in this scenario. However, `isValidFormat`, `sameNamespace` and `equals` are designed to fail gracefully and return `false` instead.

## Distinguishing Malformed URNs from Bad Parts

`@evanion/urn` provides two distinct error classes to help you provide better feedback to your users.

- **`ValidationError`**: The string is not a URN at all (e.g., it is missing the `urn:` scheme or the NID).
- **`InvalidError`**: The string is a URN, but a specific part (like the NSS) broke its grammar.

```ts twoslash file=libs/urn/README.md region=error-handling

```

Every `InvalidError` is also a `ValidationError`. An `InvalidError` carries detailed fields to explain exactly what failed:

| Field         | What it holds                                                                                   |
| ------------- | ----------------------------------------------------------------------------------------------- |
| `property`    | The failed part: `'URN'`, `'NID'`, `'NSS'`, `'R-COMPONENT'`, `'Q-COMPONENT'` or `'F-COMPONENT'` |
| `value`       | The part as it was written                                                                      |
| `invalidChar` | The first character outside the grammar (absent if the whole part is fundamentally broken)      |
| `reason`      | The rule broken when characters are valid (e.g., the NID is too short)                          |

## URN Part Grammars

To ensure strict RFC 8141 compliance, `@evanion/urn` validates each part against specific grammars:

- **Scheme**: A letter, followed by letters, digits, `+`, `-` and `.`.
- **NID**: Letters, digits and interior hyphens. `stringify` requires 2-32 characters; `parse` accepts 1-32.
- **NSS**: Letters, digits, `-._~!$&'()*+,;=:@`, percent-encoded characters, and `/` after the first character. Spaces, `?` and `#` are prohibited.

`schemeGrammar`, `nidGrammar` and `nssGrammar` hold the patterns `stringify` checks. Note that the NID is the only part read and written differently: `parse` accepts a one-character NID (per RFC 2141), while `stringify` refuses to write it.
