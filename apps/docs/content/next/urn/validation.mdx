## Untrusted Input

When receiving URNs from external sources—API requests, URL parameters, or user input—you cannot assume they are well-formed. Attempting to `parse` a string that isn't a URN will throw an `@evanion/urn` error, which, if uncaught, can crash your request handler.

Wrapping every call in a `try...catch` block is verbose.

## Pre-screening with `isValidFormat`

`isValidFormat` in `@evanion/urn` lets you screen input without writing a `try` block. It calls `parse` and returns `false` where `parse` would throw, so your validation logic and parsing logic never disagree. It checks that a URN is well-formed, not which namespace it belongs to.

## Avoiding the "Unbound Static" Pitfall

Passed as a bare callback, an `@evanion/urn` static such as `GameURN.extractId` loses its class binding. Every static reads `this` to determine the current namespace.

`stringify`, `parse` and `extractId` will throw a `TypeError` in this scenario. However, `isValidFormat`, `sameNamespace` and `equals` are designed to fail gracefully and return `false` instead.

```ts twoslash file=libs/urn/README.md region=unbound

```

`catalogue.filter(GameURN.isValidFormat)` returns an empty list because the binding is lost. To fix this, wrap the call in an arrow function to preserve the class context, as the first `map` and the last `filter` do.

`belongsToNamespace` takes the scheme as an optional third argument, and throws the `TypeError` only when that argument is left out. `filter` and `map` pass a third argument, so under either it returns `false` for every URN.

## Distinguishing Malformed URNs from Bad Parts

`@evanion/urn` provides two distinct error classes to help you provide better feedback to your users.

- **`ValidationError`**: The string is not a URN at all (e.g., `azul`, which has no scheme and no NID).
- **`InvalidError`**: The string is a URN, but a specific part (like the NSS) broke its grammar.

```ts twoslash file=libs/urn/README.md region=error-handling

```

Every `InvalidError` is also a `ValidationError`, so `problemWith` checks `InvalidError` first. An `InvalidError` carries detailed fields to explain exactly what failed:

| Field         | What it holds                                                                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `property`    | The failed part: `'URN'` for the scheme, `'NID'`, `'NSS'`, `'R-COMPONENT'`, `'Q-COMPONENT'` or `'F-COMPONENT'`, or `'COMPONENT'` on a class whose separator contains `?` or `#` |
| `value`       | The part as it was written                                                                                                                                                      |
| `invalidChar` | The first character outside the grammar, `undefined` when no single character is at fault                                                                                       |
| `reason`      | The rule broken when every character is allowed (e.g., the NID is too short), `undefined` otherwise                                                                             |

An empty part leaves both `invalidChar` and `reason` `undefined`, and its message says the part must not be empty. `rejection` reads the fields off two refusals from `stringify`:

## URN Part Grammars

`@evanion/urn` checks the NID and the NSS against RFC 8141, and the scheme against RFC 3986, so it accepts schemes other than `urn`:

- **Scheme**: A letter, followed by letters, digits, `+`, `-` and `.`.
- **NID**: Letters, digits and interior hyphens. `stringify` requires 2-32 characters; `parse` accepts 1-32.
- **NSS**: Letters, digits, `-._~!$&'()*+,;=:@`, percent-encoded characters, and `/` after the first character. Spaces, `?` and `#` are prohibited.

`schemeGrammar`, `nidGrammar` and `nssGrammar` hold the patterns `stringify` checks. The NID is the only part read and written differently: `parse` accepts a one-character NID (per RFC 2141, the URN standard before RFC 8141), so `isValidFormat` accepts `urn:g:azul` while `stringify` refuses to write it.
