# Encoding and comparing URNs

`encodeNss` in `@evanion/urn` turns a human-readable title, such as `Brass: Birmingham`, into a valid NSS, and `equals` compares two URNs according to the RFC 8141 §3.1 standard.

## "Messy" Titles and Inconsistent Spelling

`@evanion/urn` checks a Namespace Specific String (NSS) against RFC 8141, which refuses the space in `Brass: Birmingham`. A title put directly into a URN runs into two problems:

1. **Grammar Violations**: Characters like spaces are prohibited in the NSS.
2. **Equivalence Drift**: Different services might spell the same URN differently (e.g., `URN:GAME:azul` against `urn:game:azul`, or `%3a` against `%3A`), making string equality (`===`) fail.

## Percent-Encoding with `encodeNss`

`@evanion/urn` accepts a character outside the NSS grammar only once it is percent-encoded.

`encodeNss` leaves letters, digits and `-._~` alone and percent-encodes every other character, writing each of its UTF-8 bytes as a `%` and two hex digits. `decodeNss` reverses this process.

`stringify` and `parse` do not perform encoding automatically:

```

`encodeNss` also encodes the `:`, even though the NSS grammar allows it unencoded. It encodes everything outside the RFC 3986 `unreserved` set, so its output is valid anywhere in an NSS. `equals` treats `%3A` and `:` as different characters, so `Brass%3A%20Birmingham`, encoded in full, and `Brass:%20Birmingham`, with only its space encoded, name two different games.

## Comparing URNs Across Services

When URNs arrive from multiple services, you cannot rely on string equality. `equals` in `@evanion/urn` implements RFC 8141 §3.1 equivalence.

It treats URNs as equal if:

- The scheme and NID match (case-insensitively).
- The NSS matches character for character, case included, except the hex digits of a percent-encoded character, which match ignoring case. A percent-encoded character is never decoded for the comparison.

```

Use `equals` wherever you need to verify that two differently spelled URNs refer to the same resource.

## Carrying a URN in a URL Path

To carry a URN from `@evanion/urn` as a segment in a URL path (e.g., `/games/urn:game:brass-birmingham`), you must handle two layers of encoding.

The NSS must be encoded first, and then the entire URN must be encoded to ensure that characters like `:` and `%` do not interfere with the browser or the router.

```ts twoslash file=libs/urn/README.md region=url-segment

```

The `%3A` inside the NSS becomes `%253A` in the path. A single `decodeURIComponent` restores the URN. A router that decodes path parameters has already made that one decode, so call `parse` on its value directly. A second decode would turn `%3A` into `:` and `%20` into a space, and `parse` throws on the space.

## Mint URNs outside RFC 8141

You can now carry any title in an `@evanion/urn` NSS, compare URNs that two services spelled differently, and pass a URN through a URL path. Every namespace class so far keeps the `urn` scheme and the `:` separator. A class that overrides both writes a dotted key such as `baize.game.azul`, which [Schemes and separators](../separators) builds.
