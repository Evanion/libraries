# r-, q- and f-components

`@evanion/urn`'s `parse` splits the r-, q- and f-components off a URN into fields of their own, and `stringify`, given the parts as an object, writes them back.

## Identifying Specific Versions or Sections

`@evanion/urn` keeps a resource's identity in the NSS, so `urn:game:brass-birmingham` names the game and no _specific version_ or _subset_ of it. A link to the 2018 edition, or to one section of the rules, needs more than that bare identifier.

The edition cannot go into the NSS: `urn:game:brass-birmingham-2018` would name a different game.

## URN Components

RFC 8141 §2.3 defines three components that `@evanion/urn` can append to a URN. Each component starts with an **introducer**:

| Component | Introducer | RFC 8141 | Purpose                                          | Example Use Case                            |
| :-------- | :--------- | :------- | :----------------------------------------------- | :------------------------------------------ |
| **r**     | `?+`       | §2.3.1   | Parameters for the service that looks the URN up | `?+lang=en` (Request English listing)       |
| **q**     | `?=`       | §2.3.2   | Parameters for the named resource                | `?=edition=2018` (Specific edition)         |
| **f**     | `#`        | §2.3.3   | A fragment within the resource                   | `#setup` (The "Setup" section of the rules) |

## Writing Components with `stringify`

To write components with `@evanion/urn`, you must pass the parts to `stringify` as an object: `{ nss, urn?, nid?, rComponent?, qComponent?, fComponent? }`.

The library ensures the introducers appear in the correct order (r, then q, then f), regardless of the order of keys in your object. An empty `fComponent` writes a bare `#`.

## How Components are Identified

Because the identifier itself (the NSS) cannot contain `?` or `#`, `@evanion/urn` uses these characters as delimiters. It parses components in the following order:

1. **f-component**: Everything after the first `#`. This is the final part of the URN.
2. **r- and q-components**: In the remaining string, the first `?` after the NSS starts the component. If `+` follows, it's an r-component; if `=` follows, it's a q-component. Any other character following `?` throws a `ValidationError`.
3. **r-component bounds**: An r-component continues until it hits `?=`, which marks the start of the q-component.

## What a URN component may contain

`@evanion/urn` allows the r- and q-components the characters of the NSS, which [Checking URN input](../validation) lists, plus `?` anywhere but the first character, and each needs at least one character. The f-component allows the same set with no first-character rule and may be empty, so `urn:game:azul#` parses to `fComponent: ''`. `URN.rComponentGrammar`, `URN.qComponentGrammar` and `URN.fComponentGrammar` hold the three patterns:

## Components and URN Equivalence

In `@evanion/urn`, components sit outside the resource's identity: RFC 8141 §3.1 excludes all three from URN equivalence.

`@evanion/urn`'s `equals` checks each component's grammar but does not compare components, and `extractId` drops them. This means a URN with metadata is considered equivalent to the bare URN it describes.

`sameNamespace` and `belongsToNamespace` do not compare components either, as they compare only the scheme and NID. All three return `false` for a URN whose component breaks its grammar.

## Encoding and Comparison

A title such as `Brass: Birmingham` holds a space, which no `@evanion/urn` grammar allows in an NSS or a component. `encodeNss` makes such a title valid, and [Encoding and comparing URNs](../encoding) encodes one before it compares two spellings of a URN with `equals`.
