# URNs from several namespaces

In a large system, you often deal with multiple types of identifiers. For example, an e-commerce shop needs to handle both **Game URNs** (identifying board games) and **Order URNs** (identifying customer orders).

While both are URNs, they belong to different namespaces. If you try to read an order URN as a game URN, your application should be able to identify it as "foreign" rather than simply failing or, worse, treating it as a game with a very strange ID.

## The Problem: Namespace Collision and Confusion

When your system handles multiple resource types, using a single generic parser can be dangerous. If you pass `urn:order:123` into a function that expects a `GameURN`, a naive implementation might just strip `urn:` and treat `order:123` as the game's ID.

This leads to:

- **Database Pollutants**: Accidentally searching for a game with the ID `order:123`.
- **Silent Failures**: Logic that assumes any valid URN is of the "correct" type.
- **Brittle Logic**: Manual string slicing to check if an ID "looks like" an order.

## Solution: Namespace-Specific Classes

The safest way to handle different identifier types is to declare a separate namespace class for each one. This allows you to treat namespaces as first-class types in your application.

By creating `GameURN` and `OrderURN`, you can use the `belongsToNamespace` helper to filter a mixed list of identifiers instantly:


`belongsToNamespace` compares the scheme and NID of the URN without regard to case. This means `URN:GAME:azul` is correctly recognized as a game URN. If a string is not a valid URN at all (like `'hive'`), the function simply returns `false` without throwing an error.

## Handling "Foreign" URNs Safely

What happens when you use a specific namespace class—like `GameURN`—to parse a URN that belongs to a different namespace?

`GameURN.parse` is designed to be "safe." It will strip its own NID if it finds it, but if it encounters a foreign NID, it simply leaves it at the front of the Namespace Specific String (NSS).

Because the foreign NID (e.g., `order:`) remains part of the `nss`, it will never accidentally match a game slug in your database, effectively isolating your namespaces.
