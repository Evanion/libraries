# URNs from several namespaces

`belongsToNamespace` in `@evanion/urn` tells one kind of identifier from another, so a board game shop can handle both **Game URNs** (identifying board games) and **Order URNs** (identifying customer orders) in one list.

## Namespace Collision and Confusion

`@evanion/urn` reports the NID of every URN it parses, so your application can tell an order URN from a game URN before it looks anything up. When your system handles multiple resource types, using a single generic parser can be dangerous. If you pass `urn:order:123` into a function that expects a `GameURN`, a naive implementation might just strip `urn:` and treat `order:123` as the game's ID.

This leads to:

- **Database Pollutants**: Accidentally searching for a game with the ID `order:123`.
- **Silent Failures**: Logic that assumes any valid URN is of the "correct" type.
- **Brittle Logic**: Manual string slicing to check if an ID "looks like" an order.

## Namespace-Specific Classes

The safest way to handle different identifier types in `@evanion/urn` is to declare a separate namespace class for each one. `GameURN.stringify('azul')` then needs no NID argument, and the class adds no TypeScript type: `stringify` returns a plain `string`, and `IFullURN` in the [API reference](../api) types a URN literal.

`belongsToNamespace` takes the NID as its second argument, even on `GameURN`: the class supplies only the scheme and the separator. It compares the scheme and NID of the URN without regard to case. This means `URN:GAME:azul` is correctly recognized as a game URN. If a string is not a valid URN at all (like `'hive'`), the function returns `false` without throwing an error.

## Handling "Foreign" URNs Safely

What happens when you use an `@evanion/urn` namespace class such as `GameURN` to parse a URN that belongs to a different namespace?

`GameURN.parse` strips its own NID if it finds it, compared without regard to case. A foreign NID comes back in `nid` and also stays at the front of the Namespace Specific String (NSS). A foreign scheme keeps the whole identifier in the NSS. Every part comes back in the case it was written in.


A game lookup by that `nss` still runs, and an NSS may itself contain a `:`, so `urn:game:order:123` is a game whose `nss` is also `order:123`. Check `nid`, or call `belongsToNamespace`, before you use `nss` as a game key.

## Dynamic Namespaces with the Base URN Class

If your application supports a dynamic or unknown number of namespaces (e.g., a gateway service), you can use the base `URN` class of `@evanion/urn` instead of creating subclasses.

The base `URN` class provides a generic `stringify` method that takes the NSS, then the NID, then the scheme. The object form, `{ nss, nid?, urn? }`, names each part and matches what `parse` returns, so it is the form to prefer. The scheme `baize` in the third call puts that URN outside RFC 8141, which fixes the scheme at `urn`.

## Comparing Namespaces Across URNs

Sometimes you just need to know if two URNs belong to the same category, regardless of what that category is. `sameNamespace` in `@evanion/urn` compares the scheme and NID of two URNs. If they match (case-insensitively), the URNs are in the same namespace. Like `belongsToNamespace`, it returns `false` for a string that is not a URN.

## Validating input

A URN from outside the shop can be malformed as well as foreign, and `GameURN.parse` throws on a malformed one before `@evanion/urn` reports any NID. To screen such input with `isValidFormat`, and to tell a malformed URN from one with a single bad part, read [Checking URN input](../validation).
