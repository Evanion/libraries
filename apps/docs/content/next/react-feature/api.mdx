# API reference

`@evanion/react-feature` exports one provider, four hooks, a factory that binds them to a store, and six types of its own. It re-exports 33 `@evanion/feature` types, names unchanged, from [`BaseFieldType`](#basefieldtype) down. The core's values, such as `createFeatures`, `parseFeatureConfig` and `serializeConfig`, come from `@evanion/feature` and are documented in [the core API reference](/feature/api).

## `FeatureProvider`

<!-- reference @evanion/react-feature#FeatureProvider example=react-provider -->

To publish decisions to your component tree, you use the `FeatureProvider`. This provider takes a store and publishes decisions at the erased types; every hook below it reads `Decision<FeatureKey>` per key, regardless of the schema the store carried. For a form that keeps the schema, use [`createFeatureContext`](#createfeaturecontext).

## `createFeatureContext`

<!-- reference @evanion/react-feature#createFeatureContext example=react-bound -->

To keep your store's schema and allow for nested stores, you can use `createFeatureContext`. Each call makes its own React context, so two stores can nest and each set of hooks will read its own provider. The returned provider also publishes to the shared context, meaning a component calling this package's own [`useFeature`](#usefeature) underneath it reads the same decisions.

## `useFeature`

<!-- reference @evanion/react-feature#useFeature example=react-decisions -->

To read a decision for a specific flag, use the `useFeature` hook. If you call it for a key the provider does not publish, it throws an error naming the key and the provider. The decision's `reason`, `rule` and `assignment` are what [the core's Decisions page](/feature/decisions) describes.

## `useFeatures`

<!-- reference @evanion/react-feature#useFeatures example=react-decisions -->

When a component needs to check several flags at once, you use the `useFeatures` hook rather than calling [`useFeature`](#usefeature) per key. This hook returns every decision the provider published, organized by key.

## `useFeatureEnabled`

<!-- reference @evanion/react-feature#useFeatureEnabled example=react-provider -->

For a component that simply shows or hides based on a flag, use the `useFeatureEnabled` hook. This is a convenience wrapper for `useFeature(key).enabled`.

## `useVariant`

<!-- reference @evanion/react-feature#useVariant example=react-decisions -->

To determine which variant of a feature is active, use the `useVariant` hook. Both fields are absent for a feature that resolved off and for a feature declaring no variants, so calling code should handle the "off" state before switching on a name.

## `AnyDecisions`

<!-- reference @evanion/react-feature#AnyDecisions -->

The `AnyDecisions` type represents what [`FeatureProvider`](#featureprovider) publishes and what [`useFeatures`](#usefeatures) answers. Because a React context fixes its type when created and cannot hold a schema the compiler has not resolved, a provider widens to this type once and the bound hooks narrow back.

## `FeatureProviderProps`

<!-- reference @evanion/react-feature#FeatureProviderProps -->

The `FeatureProviderProps` type defines the requirements for the provider. The `features` prop is required here, whereas it is optional on [`BoundFeatureProviderProps`](#boundfeatureproviderprops). The `context` prop is memoised on identity, and `decisions` takes the set `Features.snapshot` produced elsewhere.

## `BoundFeatureProviderProps`

<!-- reference @evanion/react-feature#BoundFeatureProviderProps -->

The `BoundFeatureProviderProps` type is what the provider returned by [`createFeatureContext`](#createfeaturecontext) takes. It includes `Frozen` from the factory's own store; this turns a mount that would publish frozen decisions to hooks promising the mutable form into a compile error.

## `BoundVariant`

<!-- reference @evanion/react-feature#BoundVariant -->

The `BoundVariant` type is what `useVariant` answers for one key when using [`FeatureContext`](#featurecontext). Both fields come off `Decisions<S>[K]`, ensuring this and the decision for the same key cannot drift apart.

## `FeatureContext`

<!-- reference @evanion/react-feature#FeatureContext -->

The `FeatureContext` type represents the provider and four hooks that [`createFeatureContext`](#createfeaturecontext) returns. Each hook names `keyof S`, meaning a misspelled key is a compile error and the variant a reader switches on is the union that store declares.

## `VersionMismatchPolicy`

<!-- reference @evanion/react-feature#VersionMismatchPolicy -->

The `VersionMismatchPolicy` determines what a provider renders when the shipped set states one config version and the store states another. The default is `'use-shipped'`, while `'re-resolve'` is intended for applications that run no experiment and care about revocation latency. An `'unversioned'` outcome never re-resolves, because one of the two sides carrying no version proves nothing about the other.

## `BaseFieldType`

<!-- reference @evanion/feature#BaseFieldType -->

To categorize the data allowed in a context field, you use `BaseFieldType`. This type defines the four fundamental types a declared context field may hold: `'string'`, `'number'`, `'boolean'`, and `'instant'`.

This serves as the foundation for [`FieldType`](#fieldtype). In practice, a React application that defines its own document schema will name this type there, and [Distribution](/feature/distribution) is where that schema is described.

## `ConfigEnvelope`

<!-- reference @evanion/feature#ConfigEnvelope -->

When you need to handle a document without its associated payload, you use the `ConfigEnvelope` type. This is particularly useful for servers that serialize a store for the page they ship; the server will name this type during the call to `serializeConfig` on the core entry, which takes an envelope and writes it around a store.

Note that the `digest` member is fenced to `never` because `configDigest` is the sole writer of that member. For more details on the serializer, see [the core API reference](/feature/api).

## `ConfigIssue`

<!-- reference @evanion/feature#ConfigIssue -->

The `ConfigIssue` type describes what a failed `validateConfig` lists. A component that validates a document it fetched names this in the branch that reports the failure.

## `ConfigIssueCode`

<!-- reference @evanion/feature#ConfigIssueCode -->

To programmatically determine why a document was refused without relying on fragile message text, you can branch on a `ConfigIssueCode`. This type represents the `code` found on a [`ConfigIssue`](#configissue), with one unique code assigned per class of defect.

These codes are produced by `validateConfig`, which is documented in [the core API reference](/feature/api).

## `ContextSchema`

<!-- reference @evanion/feature#ContextSchema -->

A document describes its requirements through a schema. The `ContextSchema` type represents the half of the [`FeatureSchema`](#featureschema) dedicated to declaring the rules for context fields, with each field assigned a [`FieldType`](#fieldtype).

The two vocabularies stated by a document are further described in [Distribution](/feature/distribution).

## `FeatureConfig`

<!-- reference @evanion/feature#FeatureConfig -->

The `FeatureConfig` type is the served document a store is built from. A React application that reloads its store from a poller writes the handler beside the component, and that file names this type. [Distribution](/feature/distribution) is where a document is served and reloaded.

## `FeatureSchema`

<!-- reference @evanion/feature#FeatureSchema -->

The `FeatureSchema` type acts as the typing contract that a document states, carried at the `schema` property. It manages two distinct vocabularies:

1. [`ContextSchema`](#contextschema): For fields the engine reads and compares.
2. [`FeatureShape`](#featureshape): One per feature, for variant values the engine never reads.

The division between these two vocabularies is described in [Distribution](/feature/distribution).

## `FeatureShape`

<!-- reference @evanion/feature#FeatureShape -->

To record the specifics of a single feature within a schema, you use the `FeatureShape` type. It maps feature variants by name, with each mapping to a [`ValueShape`](#valueshape). Because the document itself maintains the order that a rollout follows, this map carries no inherent order.

## `FieldType`

<!-- reference @evanion/feature#FieldType -->

The `FieldType` type defines the declared type of a single context field. To ensure a producer in any language can emit the entire schema via reflection, this is written as a flat string.

You can modify the base type using these markers:

- `[]`: Indicates an array of the base type.
- `?`: A trailing question mark marks a field that a complete context may leave out.

## `JsonValue`

<!-- reference @evanion/feature#JsonValue -->

For the values held by a condition, the system uses the `JsonValue` type, which [`SerializedAttributeCondition`](#serializedattributecondition) uses to narrow its `value` property.

Crucially, `JsonValue` refuses `Date` objects wherever they appear. This is because a `Date` reaches the next process as an ISO string, and `canonical` writes the two the same way: the publisher and the holder then digest alike, which a reader takes as proof that the two hold one configuration, while `evaluateCondition` compares the two values with `===` and finds them unequal.

## `ReloadResult`

<!-- reference @evanion/feature#ReloadResult -->

The `ReloadResult` type is what `features.reload` answered. The poller's handler names it, and its `changed` list is keyed on [`FeatureKey`](#featurekey).

## `SerializedAttributeCondition`

<!-- reference @evanion/feature#SerializedAttributeCondition -->

To evaluate a feature based on custom data, the system uses attribute conditions. When these conditions are carried within a document, they are represented as `SerializedAttributeCondition`, where the `value` is narrowed to [`JsonValue`](#jsonvalue). The engine performs a strict equality check (`===`) when comparing this value.

## `SerializedCondition`

<!-- reference @evanion/feature#SerializedCondition -->

A feature's activation often depends on a variety of triggers, such as time windows, days of the week, or specific attributes. `SerializedCondition` represents a single condition as it is carried in a document across these different arms. The instant a window names and the value an attribute condition compares are the two members that narrow against the form held by a store built from a literal.

## `SerializedDefinition`

<!-- reference @evanion/feature#SerializedDefinition -->

A document carries its feature configurations in a `features` array, where each element is a `SerializedDefinition`. Because its key parameter defaults to [`FeatureKey`](#featurekey), the same default carried by a document, a helper annotated with the bare name can read a definition directly out of a bare document.

## `SerializedInstant`

<!-- reference @evanion/feature#SerializedInstant -->

While the core `Instant` type admits a `Date` (which is what an author uses in a literal), data passing through JSON must be represented differently. `SerializedInstant` is an instant that survives JSON transport, appearing as either an ISO 8601 string or epoch milliseconds. A document narrows to this type so that a document making one hop through a transport is digested the same way as the one that authored it.

## `SerializedRule`

<!-- reference @evanion/feature#SerializedRule -->

Rules define the logic for feature assignment. When a rule is carried in a document, it is typed as `SerializedRule`, which keeps the control-plane `id` untouched but narrows the `when` property to an array of [`SerializedCondition`](#serializedcondition). These rules are written within [Rollouts](/feature/rollouts).

## `SerializedVariantSpec`

<!-- reference @evanion/feature#SerializedVariantSpec -->

Each possible outcome of a feature is a variant. `SerializedVariantSpec` represents one such variant as it is carried in a document. The `value` remains `unknown` because the engine never reads a variant value, and a generated TypeScript interface does not reach [`JsonValue`](#jsonvalue).

## `SerializedWindowCondition`

<!-- reference @evanion/feature#SerializedWindowCondition -->

To restrict a feature to a specific timeframe, the system uses time windows. As carried in a document, a `SerializedWindowCondition` defines this window by setting the `field` to `'now'`, the `op` (operator) to either `'before'` or `'after'`, and the `value` to a [`SerializedInstant`](#serializedinstant).

## `ValidationResult`

<!-- reference @evanion/feature#ValidationResult -->

The `ValidationResult` type is what `validateConfig` answered about a document, as one of two arms.

## `ValueShape`

<!-- reference @evanion/feature#ValueShape -->

To ensure variant values adhere to a specific structure, [`FeatureShape`](#featureshape) carries a `ValueShape` for each variant. This type is a JSON Schema 2020-12 object, fenced to the subset that `validateConfig` accepts. While a code generator and an optional validator read this shape, the engine hands the variant value to the caller untouched.

## `DecisionOrigin`

<!-- reference @evanion/feature#DecisionOrigin -->

The `DecisionOrigin` type describes which kind of process resolved a shipped set. A provider handed a set from a per-request render adopts that set's own instant, and a set from a build leaves the client's clock to answer.

## `DecisionSet`

<!-- reference @evanion/feature#DecisionSet -->

The `DecisionSet` type is what `decisions` takes on both providers. The set states the config version it was resolved under and the instant as an ISO 8601 string, which is what lets a provider tell whether the two processes hold one configuration.

## `DivergenceObserver`

<!-- reference @evanion/feature#DivergenceObserver -->

The `DivergenceObserver` type is what `onDivergence` takes on both providers. It is notified for every divergence a provider detects and alters no decision.

## `DivergenceReport`

<!-- reference @evanion/feature#DivergenceReport -->

The `DivergenceReport` type represents one report an observer receives. A provider sends one per pass of its checks, and React invokes a render twice under `StrictMode`, so an observer that counts sees each report of that pass twice.

## `DivergenceSide`

<!-- reference @evanion/feature#DivergenceSide -->

When comparing decisions made by different environments, the system identifies which side of the comparison is being referenced. `DivergenceSide` represents one of these sides via four members. Because a [`DivergenceReport`](#divergencereport) carries both `shipped` and `local` sides, an observer can read what the server decided beside what the local process decided.

## `Decision`

<!-- reference @evanion/feature#Decision -->

To handle the outcome of a feature check, the library uses the `Decision` type. This represents the specific decision made for a single feature.

When you use [`useFeature`](#usefeature), the hook returns the erased form of this type, represented as `Decision<FeatureKey>`. Similarly, [`AnyDecisions`](#anydecisions) acts as a container that holds one of these decisions per key.

It is important to note the distinction between the bare `Decision` type and `Decision<FeatureKey>`. Because the first parameter defaults to `string` but its constraint allows for a `number`, these are treated as two distinct types. If you use the bare name as a type annotation, it will refuse the value returned by the hook.

## `Decisions`

<!-- reference @evanion/feature#Decisions -->

The `Decisions` type is what [`FeatureContext`](#featurecontext)'s hooks answer at the factory's schema, and [`BoundVariant`](#boundvariant) reads `variant` and `value` off it.

## `EvaluationContext`

<!-- reference @evanion/feature#EvaluationContext -->

The `EvaluationContext` type is what `context` takes on both providers. It is an argument the store is read against and has nothing to do with React context.

## `FeatureKey`

<!-- reference @evanion/feature#FeatureKey -->

The `FeatureKey` type is used as every hook's `key` parameter, and the key type [`AnyDecisions`](#anydecisions) is keyed on. It is `string | number`, so a store keyed on a numeric enum types its hooks on numbers.

## `Features`

<!-- reference @evanion/feature#Features -->

The `Features` type is what `features` takes on both providers, and what [`createFeatureContext`](#createfeaturecontext) takes. One `@evanion/feature` in the dependency graph is what makes the store an application built assign to the prop.

## `FrozenWhenObserved`

<!-- reference @evanion/feature#FrozenWhenObserved -->

The `FrozenWhenObserved` type defines how [`FeatureContext`](#featurecontext)'s `useFeatures` and `useFeature` type their answer. A store built with an observer freezes what it resolves and its hooks answer the deeply readonly form; a store built without one answers the mutable form.

## `Schema`

<!-- reference @evanion/feature#Schema -->

The `Schema` type is the default schema parameter given by [`FeatureProviderProps`](#featureproviderprops), meaning `FeatureProviderProps` needs no type argument.

## `VariantInfo`

<!-- reference @evanion/feature#VariantInfo -->

The `VariantInfo` type is the constraint every schema parameter in this package is written against: `S extends Record<keyof S, VariantInfo | never>`, where `never` is the entry a variant-free feature carries.
