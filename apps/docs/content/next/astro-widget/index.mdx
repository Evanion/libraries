# @evanion/astro-widget

**Render CMS-driven pages with zero-JS overhead using Astro.**

A content management system (CMS) saves a page as a list of items, and each item's `type` names the `.astro` component that renders its `props`.

## The Problem: The "Static Content" Bottleneck

In many Astro projects, developers place components on a page by hand, and astro-widget is for the page where that stops working: when a CMS drives the page, you don't know which components are needed until the data is fetched.

Writing a `switch` statement on the `type` string by hand is repetitive and error-prone. An `.astro` module's type also carries none of its component's props, so it's easy to miss a required prop in the CMS data and publish a broken page.

## Solution: Data-Driven Component Mapping

`@evanion/astro-widget` solves this with a **registry**, a map from each widget type, such as `'listing-header'`, to the `.astro` component that renders it. The `Widgets.astro` component takes your item array and the registry, and renders each item in order through its mapped component when Astro renders the page, so it sends no JavaScript to the browser.

## The astro-widget Vocabulary

These terms are used throughout the astro-widget documentation:

- **Item**: A single entry in the CMS list. It contains an `id` unique among its siblings, a `type`, and the `props` for its component. It can also carry `meta` (placement data) and `children` (nested items). Its type is `AnyWidgetItem`.
- **Widget**: The `.astro` component that renders an item. It receives the item's `props` as its own props.
- **Registry**: The map linking each `type` to its widget. `defineWidgets` builds one and keeps its type names as literal types, so your editor completes them.
- **Problem**: A fault identified by `validateItems`, such as a type that isn't in the registry. `validateItems` returns every problem in one list, and never throws.

The item shape, `defineWidgets` and `validateItems` come from `@evanion/widget`, the framework-free core of the package family. astro-widget installs it at one exact version and re-exports those names, so you import them from `@evanion/astro-widget`.

## When astro-widget is the Wrong Tool

- **Dynamic Content**: `Widgets.astro` renders once, when Astro renders the page. If a page needs to change after it has loaded in the browser, use `@evanion/react-widget` within an Astro island.
- **Strict Prop Checking**: If you need the compiler to verify every prop of every item, use `@evanion/react-widget`, which infers props from its components. An `.astro` module's type carries no props, so astro-widget checks the props you list from a script, with `validateItems`.
- **Static Pages**: If your page structure never changes and is not driven by a CMS, write the components directly into your `.astro` page.
