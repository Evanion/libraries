# What a bad CMS save reports and renders

`validateItems` reports every fault in a list of items, and `Widgets.astro` renders what it can of the same list. This guide examines the relationship between a validation error and its resulting effect on the rendered page.

## Faults in an Item's Shape

Alongside checking for a specific widget type, `validateItems` checks if an item is structurally sound. If a CMS save contains broken entries, the engine identifies the faults based on six structural rules.

```ts twoslash file=libs/astro-widget/README.md region=structural-rules

```

| Entry | Structural Fault                         | Resulting Message         |
| :---- | :--------------------------------------- | :------------------------ |
| 0     | Saved as `null` instead of an object     | `item is not an object`   |
| 1     | Missing the `id` field                   | `item id is not a string` |
| 2     | `children` is a string instead of a list | `children is not a list`  |
| 3     | `id` repeats a sibling's `id`            | `duplicate sibling id`    |
| 3     | Missing the `props` object               | `props is not an object`  |

### Special Case: Payload is not a list

If the entire payload is not an array (e.g., it's an object `{ items: [] }`), `validateItems` returns a single problem with an index of `-1` and a message of `items is not a list`.

```ts twoslash file=libs/astro-widget/README.md region=not-a-list

```

### Nested Indexing

Because `validateItems` performs a depth-first walk, it reports problems for nested children using an index relative to their own siblings. A top-level item and its first child can both report `index: 0`. Use the `id` field to identify the faulty item; it tells the two apart only when your CMS keeps ids unique across the whole tree.


## How `Widgets.astro` Renders a Bad Item

`Widgets.astro` follows a "fail-soft" strategy: it renders every item it can and throws on none. This means a bad save publishes with a gap in the UI.

Unless `NODE_ENV` is `production`, the renderer prints a warning to the console using `ERROR_MESSAGES`.

| Fault                 | Render Result                                      | Console Warning                                      |
| :-------------------- | :------------------------------------------------- | :--------------------------------------------------- |
| Unknown `type`        | Nothing renders                                    | `ERROR_MESSAGES.UNKNOWN_WIDGET`                      |
| No string `type`      | Nothing renders                                    | `ERROR_MESSAGES.UNKNOWN_WIDGET` (type: "unknown")    |
| Not an object         | Nothing renders                                    | `ERROR_MESSAGES.UNKNOWN_WIDGET` (type/id: "unknown") |
| Missing prop          | Widget renders, but with `undefined` for that prop | None                                                 |
| `items` is not a list | Nothing renders                                    | `ERROR_MESSAGES.MALFORMED_ITEMS`                     |
| Missing/Repeated `id` | Widget renders (if type is known)                  | None                                                 |
| `children` not a list | Widget renders; its internal `<Widgets />` warns   | `ERROR_MESSAGES.MALFORMED_ITEMS`                     |

## The "Double-Validation" Gap

A common point of confusion is when an item passes the global `validateItems` check but still renders incorrectly. This usually happens with nested registries.

Imagine a `GameGrid` widget that only renders `game-card` types. If the global build gate checks the page with one `known` list, it might pass a `listing-header` inside a grid. However, when `GameGrid` tries to render its children using its own `cardRegistry`, the `listing-header` is unknown and will be skipped.

```ts twoslash file=libs/astro-widget/README.md region=nested-registry

```

To prevent this, you should run `validateItems` against the specific registries used by your container widgets.
