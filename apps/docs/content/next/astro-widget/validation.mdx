# Check CMS items before Astro renders them

`validateItems` checks the items a CMS saved against the widget types you
render. A script that runs it before `astro build` stops the build on a save
that `Widgets.astro` would publish with an item missing.

## Check items with validateItems

astro-widget's `validateItems` reports each item whose `type` nothing renders
and each prop `required` names that an item lacks. It takes the items and
`known`, the widget types you render as a registry or a list of their names. An
optional third argument, `required`, maps a type to the props it cannot render
without:

```ts twoslash file=libs/astro-widget/README.md region=validate

```

Each problem names the item's `index` in its list, its `id` and `type`, and a
`message`, and its type is `WidgetProblem`. `answer-wall` is not in the list of
known types, and the `price-box` item has no `price`. A problem's message calls
a prop a field, so this one reads `missing field price`. Nothing threw, and one
call returned both faults.

## Stop astro build on a bad save

The astro-widget build gate for the listing page is one script. It checks
`items`, the list [Getting started](../getting-started) typed from the CMS's
JSON, and throws on any problem. Save it as `scripts/check-content.ts`:

```ts file=libs/astro-widget/examples/scripts/check-content.ts region=build-gate

```

`known` lists the type names, because a script Node runs cannot import the
`.astro` modules the registry holds. `@evanion/astro-widget`'s main entry holds
only the widget core's names and no `.astro` file, so Node imports
`validateItems` from it. The `throw` gives the script a non-zero exit code, so
the command stops before Astro runs. Set your `package.json`'s `build` script to
this command. `tsx` runs a TypeScript file in Node, and `npx` fetches it if the
project does not have it:

```bash
npx tsx scripts/check-content.ts && astro build
```

### A registry or a list of names

`validateItems` takes a registry or a list of type names as `known`. From a
registry it reads only the keys, so both report the same problems. Code that
Astro or Vite compiles, such as a page's frontmatter or a Vitest test run
through Astro's `getViteConfig`, can import the registry and pass it, and then
the check and the render read one list of types:

## Require props on an item

astro-widget's `validateItems` takes `required`, a map from a widget type to the
prop names that must carry a value, and it is the only check an item's props
get in Astro. `undefined`, `null` and a string of only whitespace count as
missing, and a CMS text field an editor opened and left empty arrives as such a
string:

```ts twoslash file=libs/astro-widget/README.md region=required-fields

```

`validateItems` checks required props only for an item whose type is known. An
unknown type reports once, as an unknown type, and nothing for each prop it
lacks.
