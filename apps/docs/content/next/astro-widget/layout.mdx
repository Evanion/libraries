## Providing Page-Level Data with `ctx`

astro-widget hands page-level data (such as the store's name, the current currency, or a user's locale) to every widget through the `ctx` prop on `<Widgets />`. An Astro component renders once, top down, and Astro has no context API a widget could read while it renders.

`Widgets.astro` passes this object to every widget as a prop named `ctx`. Save this widget as `src/widgets/Stock.astro`. It renders a `stock` item's `copies` and reads the store's name from `ctx`:

```astro file=libs/astro-widget/examples/src/widgets/Stock.astro region=stock

```

In your page, you pass the data once: `<Widgets ctx={{ store: 'Gothenburg' }} items={items} registry={registry} />`. Every widget that `<Widgets />` renders now has access to the store name without it being duplicated in the CMS data for every single item.

To try it on the listing page:

1. Add `stock: Stock` to the registry in `src/registry.ts`, and import `Stock` from `./widgets/Stock.astro` there.
2. In `src/pages/brass-birmingham.astro`, pass `ctx={{ store: 'Gothenburg' }}` to `<Widgets>`.
3. Add a `stock` item to `src/data/brass-birmingham.json`, with `"id": "stock"`, `"type": "stock"` and `"props": { "copies": 3 }`.

## Wrapping Widgets with `chrome`

astro-widget's `chrome` prop takes a shared wrapper component that surrounds every widget. The wrapper handles layout concerns, like adding a `<section>` tag, applying a background color, or setting a grid span.

The `chrome.item` component receives the item's `type`, `id`, and `meta`, but **none of its `props`**. Save this chrome as `src/chrome/Section.astro`. It puts each widget in a `<section>` whose class names the item's background:

```astro file=libs/astro-widget/examples/src/chrome/Section.astro region=section

```

### The Chrome Renders `<slot />`

A chrome component must render a `<slot />`. This is where Astro injects the actual widget. If you omit the `<slot />`, the widget inside the wrapper disappears from the page, and Astro reports no error and no warning.

### Seeing `ctx` and `chrome` Together

In `src/pages/brass-birmingham.astro`, import `Section` from `../chrome/Section.astro` and pass `chrome={{ item: Section }}` to `<Widgets>` beside `ctx`. Give the `stock` item in the JSON `"meta": { "background": "felt" }`. The test below renders that `stock` item through `Widgets.astro` and the container API:


The `<section>` and its `id` came from the chrome, `bg-felt` from the item's `meta`, and `Gothenburg` from `ctx`. On your page the header and the price each get a `<section>` too.

## Rendering Nested Items

In some cases, an astro-widget widget holds other widgets, such as an "Also on the shelf" grid containing game cards.

Unlike `@evanion/react-widget`, which renders children automatically, `Widgets.astro` passes the `children` items to the parent component as raw data, in a prop named `children`. An Astro component takes rendered child content only through `<slot />`. To render them, the parent widget must render its own `<Widgets />` component using its own registry.

### Why `cardRegistry` Has a Module of Its Own

`cardRegistry` has a module of its own to avoid a circular import. `src/registry.ts` imports `GameGrid`, so a `cardRegistry` inside it would have `GameGrid` import a module that imports `GameGrid`.

### Passing `ctx` to the Cards

The nested `<Widgets />` gets no `ctx` and no `chrome` unless the grid passes them on. `GameGrid` receives `ctx` like every widget. For cards that read it, add `ctx` to the destructuring of `Astro.props` in `GameGrid.astro`, then render `<Widgets items={children} registry={cardRegistry} ctx={ctx} />`.

### The Registry Hierarchy

Because the nested `<Widgets />` uses its own registry, it only renders children that match that specific registry. If a child item's type is not in the `cardRegistry`, astro-widget skips it, even if that type is supported by the page's main root registry.

## Syncing the Build Gate

If you add new widget types or nested containers, update `known` and `required` in the build gate [Check CMS items before Astro renders them](../validation#integrating-into-the-build-process) wrote. `validateItems` scans the entire tree, including all nested children, against the one `known` list it is handed.

In your `scripts/check-content.ts` file, add your new types (`'stock'`, `'game-grid'` and `'game-card'`) to the `known` list, or the build stops on the new items as unknown types. Add `'game-grid': ['title']` to the `required` map as well, so the build stops on a grid with no `title`.
