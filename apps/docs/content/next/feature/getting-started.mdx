# Getting started

The examples on this page are regions of `libs/feature/docs/examples.md` and
run under `nx test @evanion/feature`.

By the end of this page, you will have a store of features resolving for a customer, a rollout check, and a toggle that reports its transitive impact.

## Prerequisites

To start using `@evanion/feature`, you need a compatible runtime and the package installed in your project.

```bash
npm install @evanion/feature
```

## How to define features

To manage rollouts and dependencies, you first define the intent of your features in `@evanion/feature`. A feature consists of `enabled` (the shop's intent), `rules` (which determine if that intent reaches a customer), and `dependsOn` (the flags that must resolve first).


The `createFeatures` function validates this graph and returns a store. To determine if a feature is active for a specific user, you use `isEnabled`. This function requires a `targetingKey` to bucket the customer and a `now` timestamp to evaluate time windows.

For example, `cust-0042` and `cust-0107` receive different results because a 25% rollout places them in different buckets. These answers remain consistent across subsequent requests.

## How to debug why a flag is off

While `isEnabled` returns a boolean, the `resolve` function in `@evanion/feature` provides a detailed decision for each flag. ## How to toggle a feature

The `toggle` function is the only call in `@evanion/feature` that writes. It updates the `enabled` state of a stored definition and reports which dependent features are disabled as a result.

```ts twoslash file=libs/feature/docs/examples.md region=toggle

```

The `willDisable` list is transitive and follows dependency order: for example, demo night booking depends on express pickup, which depends on the new checkout. This list can be used to power a confirmation dialog or be ignored by a script.

No other functions write to the store. `resolve` and `plan` are pure functions of the configuration, the context, and the clock; thus, a time window closing will change an answer without modifying any stored data.

You now have two dependent flags resolving for a customer and a toggle that reports its impact. To learn how to write your own definitions, including every field, the precedence between them, and the conditions a rule can match on, see [Configuration](../configuration).
