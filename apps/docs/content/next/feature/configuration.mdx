# Configuration

To move your feature flags out of component logic and into a central store, you use `createFeatures`. This function takes your feature definitions, validates them, and returns the store every other call reads. A rule in a definition replaces the `role === 'bookseller'` check each component would otherwise repeat.

## Declarative Feature Definitions

`@evanion/feature` uses a declarative configuration so you can define the intent (is it enabled?) and the rules (when is it active?) in a single place. `createFeatures` validates the dependency graph, deep-clones and freezes your definitions, and returns the store.


The store holds a frozen copy of each definition. Your own array stays editable, and an assignment to the copy `definition()` returns throws a `TypeError`, so the store never diverges from what it resolves.

### The Configuration Schema

| Field               | Meaning                                                                                  |
| :------------------ | :--------------------------------------------------------------------------------------- |
| `key`               | The unique identifier for the feature. A string or a number.                             |
| `enabled`           | The kill switch. If `false`, the feature is off for everyone.                            |
| `dependsOn`         | A list of other features that must resolve on for this one to activate.                  |
| `rules`             | Activation rules (OR-ed). If any rule matches, the feature is active.                    |
| `seed`              | A bucketing seed for rollouts. Defaults to the `key`.                                    |
| `freezeTimeAtBuild` | If true, `plan()` resolves time windows at build-time for static sites.                  |
| `variants`          | The named variants this feature splits across (see [Variants](../variants)).             |
| `variantBy`         | The context field used to bucket variants. Defaults to `targetingKey`.                   |
| `variantSeed`       | Bucketing seed for the variant split. Defaults to the `seed` (or `key`) plus `:variant`. |

A rule carries an optional `id`, a `when` list of conditions, an optional `rollout`, and an optional `variant` it pins. A condition names a context `field`, an `op` and a `value`.

## Resolution Precedence

When you call `resolve()`, `@evanion/feature` follows a strict hierarchy to determine if a feature is active.

1. **The Kill Switch**: If `enabled === false`, the feature is off. No rules are evaluated.
2. **The Dependency Chain**: If any feature in `dependsOn` resolves to `false`, this feature is off. No rules are evaluated.
3. **The Default State**: If `enabled === true` and there are no rules, the feature is on.
4. **The Rules**: If rules exist, they are OR-ed. If any rule matches, the feature is on. Inside a rule, conditions are AND-ed.

`enabled` does not depend on rule order. `rule` names the first rule that matched, and that rule's `variant` pin is the one applied, so moving a rule up can change which rule a decision names.

The kill switch works in one direction only. Setting `enabled: true` on a feature whose rules do not match changes the stored intent, and the feature still resolves off.

## Dependency Cascades

`@evanion/feature` cascades dependencies transitively and one way. With demo night booking behind express pickup, and express pickup behind the new checkout, express pickup being off takes demo night booking off and leaves the new checkout on.

`createFeatures` evaluates in dependency order, so the cascade works at any depth and you can declare your features in any order.

### Configuration Errors

`createFeatures` validates the dependency graph at construction. It throws a subclass of `FeatureConfigError` if it detects:

- **Cycles**: `FeatureCycleError`, e.g., `A` depends on `B`, and `B` depends on `A`. Its `path` property holds the cycle's keys, from the first key back to itself.
- **Unknown Dependencies**: `UnknownDependencyError`, when a feature depends on a key that isn't configured.
- **Duplicates**: `DuplicateFeatureError`, when two features share the same key.

```ts twoslash file=libs/feature/docs/examples.md region=config-errors

```

Variants are checked at the same point: `DuplicateVariantError` for two variants sharing a name, and `UnknownVariantError` for a rule pinning a variant its feature does not declare. Once `createFeatures` returns, `resolve`, `plan` and `toggle` never throw.

A decision names the rule in `rule`, and in its breakdown when no rule matched. The hash leaves out `rollout.percent`, so two rollout rules on one feature that differ only in their percentage share a name. Give a rule you expect to read in a log an explicit `id`.

### Condition Operators

The store uses these operators to compare context fields against target values.

| `op`                    | Effect                                                           | Example                                      |
| :---------------------- | :--------------------------------------------------------------- | :------------------------------------------- |
| `before` / `after`      | Checks if an instant field is strictly before/after a boundary.  | `value: '2026-10-01T00:00:00Z'`              |
| `day-of-week`           | Checks if `now` falls on specific weekdays in a zone.            | `zone: 'Europe/Stockholm'`, `value: ['mon']` |
| `eq` / `ne`             | Strict equality or inequality.                                   | `value: 'bookseller'`                        |
| `in` / `not-in`         | Checks if the value is in/not in an array.                       | `value: ['bookseller', 'owner']`             |
| `contains`              | Checks if the field (which must be an array) contains the value. | `value: 'bookseller'`                        |
| `exists` / `not-exists` | Checks whether the context carries the field at all.             | (no `value` required)                        |

A `day-of-week` condition requires an IANA zone (e.g., `Europe/Stockholm`) because UTC day-of-week calculations are often incorrect for local business hours.

### Missing Context Fields

In `@evanion/feature`, a condition over a field the context does not carry never holds, and that includes `ne` and `not-in`. Treating `ne` on an absent field as true would switch features on for exactly the contexts that carry the least information.

### Time Windows

To read the same on every host, a date-time string must include an offset (e.g., `+09:00`, `+0900` or `Z`). A date with no time is read as UTC midnight. `createFeatures` rejects a date-time without an offset, and a date the calendar does not have, at construction.

```ts twoslash file=libs/feature/docs/examples.md region=instant-strings

```

A window's `value` can also be epoch milliseconds or a `Date`. `createFeatures` refuses `NaN` and a number outside the range a `Date` holds, and it takes a `Date` as the instant it holds, so `new Date('2026-01-01T00:00:00')` carries the zone of the host that built it.

The answer depends only on the instant you ask about, so a server and a browser that ask about the same instant always agree, and nobody deploys or flips a switch at launch.

### Field Paths

To retrieve data from the context, a condition uses a `field` path. Segments are joined by dots; for example, `subject.role` reads the `role` member of the `subject` object. This same path logic is used by a rollout's `by`, a feature's `variantBy`, and the store's `correlateBy`.

```ts twoslash file=libs/feature/docs/examples.md region=nested-context

```

Each segment is read as an own data property of a plain object (one whose prototype is `Object.prototype` or `null`). The store never calls getters. A field is considered absent if:

- A segment is missing.
- A parent in the path is an array, a `Date`, a class instance, a primitive, or `null`.
- The property is an accessor.

The top level of the context is read normally. Paths are limited to 32 segments and cannot contain empty segments or reserved names like `__proto__`, `constructor`, or `prototype`. Literals `.` or `\` must be escaped as `\.` or `\\`; any other use of `\` is forbidden. If a path breaks these rules, `createFeatures` throws a `FeatureConfigError` and `validateConfig` reports `invalid-field-path`. The reserved name `now` always refers to the clock.

If you have a flat context key that contains a literal dot, escape it. In a context like `{ 'subject.id': 'flat', subject: { id: 'nested' } }`, the path `subject.id` reads `'nested'`, while `subject\.id` reads `'flat'`. You can use `escapeField` to handle this formatting.

```ts twoslash file=libs/feature/docs/examples.md region=escape-field

```

In version 0.1, `field: "subject.id"` targeted a flat key. In 0.2, it targets the nested `id` within `subject`. This is the primary change for documents not using new constructs. See [Distribution](../distribution#publishing-to-mixed-sdk-versions) for rewriting guidance.

### Absent and Present Fields

A field is **present** if the path resolves to any value, including `null`, `''`, `0`, or `false`. It is **absent** if the path reads nothing or if the property holds `undefined`.

Following the rule for [Missing Context Fields](#missing-context-fields), any comparison over an absent field is false. This applies to paths as well as top-level names: `ne` over `subject.role` is false if the context has no `subject`.

The `exists` operator holds if the field is present; `not-exists` holds if it is absent. Neither operator accepts a `value`; providing one results in an `unknown-member` report from `validateConfig`. Note that `null` is present, so `not-exists` is false for `{ realm: null }`. However, if a parent in the path is `null` or an array, the field is absent and `not-exists` holds.

```ts twoslash file=libs/feature/docs/examples.md region=exists-ops

```

`exists` and `not-exists` fit any declared field type. A document that carries a schema still declares the field, and `validateConfig` reports `unknown-context-field` for one it leaves out. When a condition fails, the decision's `failedField` reports the path read and whether a value was present.

### Instant Fields

The `before` and `after` operators work on any field, not just `now`. The store parses these values as ISO 8601 strings with offsets, epoch milliseconds, `Date` objects, or dates without times (interpreted as UTC midnight). A value that names no instant makes the condition false. The decision's `failedField` still reports the field as present, because the context carried a value there. Both comparisons are strict. When the document carries a schema, it must declare the field as `instant` or `instant?`.

Boundaries can be relative to the context's `now` using `fromNow`. For example, `{ fromNow: '-P30D' }` represents 30 days ago, allowing you to target "accounts created in the last 30 days" via the `after` operator.

```ts twoslash file=libs/feature/docs/examples.md region=instant-fields

```

Relative durations are ISO 8601 in capitals, and the sign is optional: `PT12H`, `P1D`, `+P1D` and `-P30D` all read. A duration may include weeks (`W`), days (`D`), hours (`H`), minutes (`M`), and seconds (`S`). Seconds support up to three decimal places. Years and months are forbidden because their variable lengths would cause inconsistent resolution across different ports.

Additionally, relative boundaries cannot be used on `field: 'now'`, as this would compare the clock to a shifted version of itself. If the context's `now` is present but is not a valid instant, the condition is false. If `now` is omitted from the context, the store provides its own clock value.


### What an Instant Field Accepts

To ensure consistent behavior across your application, `@evanion/feature` uses a single grammar to read context values as instants—the same logic applied to `now` and any other instant field. This allows a port to implement the reading logic uniformly.

#### Strings

To define a point in time via a string, you provide an ISO 8601 date, optionally followed by a time and an offset.

Dates are accepted in three formats:

- A four-digit year (e.g., `2026`).
- A year and month (e.g., `2026-01`).
- A full date (e.g., `2026-01-01`).

Extended years are supported using a sign and six digits, though `-000000` is refused. All full dates must exist on the calendar; for example, `2028-02-29` is accepted, but `2026-02-29` is refused. If a date is provided without a time, it is treated as UTC midnight. A year alone names the start of that year in UTC (`2026` is `2026-01-01T00:00:00Z`), and a year and month name the start of that month (`2026-05` is `2026-05-01T00:00:00Z`).

A time must follow a `T` separator and be formatted as `HH:mm`, `HH:mm:ss`, or `HH:mm:ss.fraction`. A time requires an offset: `Z`, `+HH:mm`, or the basic form `+HHmm`.

The following are refused:

- Times without an offset.
- A lower-case `z` offset or a lower-case `t` separator.
- Offsets missing minutes.
- A space used in place of `T`.
- An offset attached to a date with no time.

For the fractional component, one or more digits are accepted and then cut to milliseconds without rounding. Hour `24` is accepted only as `24:00` (or `24:00:00` with a zero fraction) to represent the midnight that ends the day.

#### Other Values

Beyond strings, `@evanion/feature` accepts the following as valid instants:

- Numbers: Treated as epoch milliseconds. The value must fall within the range a `Date` object can hold (±8.64e15).
- Date Objects: Read as the instant they hold.

A context `now` of `null` or a boolean names no instant either. Values that do not name an instant—such as strings of digits, `null`, objects, booleans, or arrays—result in a false condition.

### Paths in Rollouts

A rollout's `by` property is a path. The store buckets based on the value found at that path. If the path reads no value, the context is not bucketed (matching the behavior of top-level `by`). A `targetingKey` cannot substitute for a missing `by`. The `rollout.bucket` in the outcome is set only when the value at the path is a string or a number. A `null`, a boolean or any other type leaves the context unbucketed, and the outcome carries no `bucket`.


### Schema Keys for Paths

The `context.fields` map in a schema remains flat, but its keys use the path syntax: `{ "subject.id": "string", "subject.createdAt": "instant" }`. A condition's path must exactly match a schema key.

Declaring `subject.id` does not automatically declare `subject`. Furthermore, you cannot have a key that is a proper prefix of another (e.g., `subject` and `subject.id`) because a field cannot be both a scalar and an object; this triggers a `conflicting-context-fields` error.

When using `plan()`, a path is considered available if its first segment is available; otherwise, it is deferred. `PlanEntry.needs` will specify the full path.
