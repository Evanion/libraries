# @evanion/feature

**Independent feature flags let a child feature reach a customer its parent is off for.** `@evanion/feature` resolves a feature off whenever a feature it depends on resolves off.

## Why Independent Flags Diverge

Most feature flag systems treat every flag as an independent switch, which creates a risk of broken user experiences when features have implicit dependencies. For example, express pickup only exists inside the new checkout; a flag that turns express pickup on for a customer who is not on the new checkout shows that customer a broken page.

To prevent this, you would typically have to:

- **Write manual checks** in every component: `if (features.newCheckout && features.expressPickup)`.
- **Manage state manually**: Update every child flag whenever a parent changes.

With either approach, every component repeats the parent check, and the one that leaves it out ships the broken page.

## Dependency-Aware Resolution

To solve this, `@evanion/feature` moves the dependency logic into a hierarchical decision engine. Asking whether a feature is enabled checks the entire dependency chain, transitively, with no manual updates to any child flag.

In `@evanion/feature`, a feature's definition holds its intent, `enabled`, and its `rules`. A rule matches fields of the context you pass, such as a customer's `role`. A feature resolves on when it is enabled, every feature in its `dependsOn` resolves on, and one of its rules matches or it has none.

In the example above, express pickup is offered only to customers who are already on the new checkout. The new checkout's one rule matches a bookseller and nobody else, so for a customer it resolves to `false`, and express pickup resolves to `false` with it, even though its own definition has no rules and would resolve on alone.

## The Core and the React Package

`@evanion/feature` imports no framework. It runs in a Node.js API, a build script or a serverless function, and it resolves flags and plans which of them a build can settle. Every page in this section is about that package.

`@evanion/react-feature` is the React binding, and it is a package of its own because `'use client'` is a per-module directive. It carries a `FeatureProvider` and four hooks that read its decisions anywhere in a React tree, and it decides nothing. [The react-feature pages](/react-feature/) are where it is documented.

## What a Decision Carries

To provide more than a simple boolean, `@evanion/feature` returns a **decision** object for every feature when you call `resolve()`:

- **`enabled`**: The final answer (true/false).
- **`reason`**: A code naming _why_ the feature is on or off: `default-on`, `rule-match`, `explicitly-off`, `no-rule-matched` or `dependency-off`.
- **`blockedBy`**: On a `dependency-off` decision, the parent that blocked it.

The `reason` field is for the person debugging a flag. If a feature is unexpectedly off because of a parent, its reason is `dependency-off` and `blockedBy` names the parent to look at. Nothing in the library reads `reason` back, so it explains a decision and never changes one.

## The Store Never Writes

Resolving in `@evanion/feature` is a pure function of the configuration, the context you pass and the current time. The only writer is `toggle()`, which sets a feature's `enabled` intent.

The engine never writes resolved values back into the configuration. This ensures:

- **Audit Integrity**: Your configuration remains a record of _intent_, not a log of results.
- **Temporal Consistency**: A rule can close at an instant. Once it closes, `resolve()` returns `false` for the feature and every dependant without a database update.
- **Statelessness**: Multiple processes resolving the same context against the same configuration will always agree.

## What It Leaves to You

`@evanion/feature` evaluates flags in your process and stops there:

- It fetches no configuration. `createFeatures` takes the definitions your application loaded.
- It stores no variant assignment. A context can hand back one your application saved.
- It records no exposure. A component records it where it renders.
- It declares no `drain()`. An observer's own transport flushes what it buffered.
- [What it does not do](./limits) lists all nine boundaries and the file that fixes each.
