# What validateItems reports

`validateItems(items, known)` allows you to scan a whole payload in one pass, identifying every fault—including those nested deep within other widgets—without throwing exceptions.

## Every fault in one pass

`validateItems` from `@evanion/widget` catches the [silent failures](../#silent-failures-in-a-cms-page) a CMS payload carries by performing a depth-first walk of your widget tree. It reports an item's own problems first, then recursively validates its `children` before moving to the next sibling.

Consider a payload with three distinct faults: a missing `props` object, a duplicate ID, and a typo in a widget type.


In this case, `validateItems` identifies the missing props on the first item and the duplicate ID on the second. Finally, it descends into the `tonight` shelf and finds that its child, Hive's listing, has an unknown type.

Because it walks the tree depth-first, Hive's problem is reported last, and its `index` is `0` because it is the first child of the shelf, not the fourth item in the overall payload. That is the position a CMS editor sees inside the shelf they opened.

An `id` repeated at two depths is not reported. `@evanion/react-widget` passes an item's `id` to React as its key, and React compares keys only among siblings, so two items with one `id` at different depths never collide.

### What a `WidgetProblem` carries

Every fault found by the library is returned as a `WidgetProblem` object:

| Field     | Description                                                                        |
| :-------- | :--------------------------------------------------------------------------------- |
| `index`   | The item's position among its siblings. Returns `-1` if the payload is not a list. |
| `id`      | The item's `id` string, or `-` if the item has no string `id`.                     |
| `type`    | The item's `type` string, or `-` if the item has no string `type`.                 |
| `message` | A human-readable error string from `VALIDATION_MESSAGES`.                          |

## Standardized Error Messages for Automation

To make it easier to translate or group errors, `@evanion/widget` exports `VALIDATION_MESSAGES`. Instead of comparing raw strings, you should compare the `message` against these constants. `MISSING_FIELD` is a function of the field name, so compare against `VALIDATION_MESSAGES.MISSING_FIELD('title')`.

| Constant           | Message                     | Cause                                                                     |
| :----------------- | :-------------------------- | :------------------------------------------------------------------------ |
| `NOT_A_LIST`       | `items is not a list`       | The payload is not an array.                                              |
| `NOT_AN_OBJECT`    | `item is not an object`     | An entry is a string, a number, `null` or an array instead of an object.  |
| `INVALID_ID`       | `item id is not a string`   | The `id` field is missing or is not a string.                             |
| `INVALID_TYPE`     | `item type is not a string` | The `type` field is missing or is not a string.                           |
| `UNKNOWN_TYPE`     | `unknown widget type`       | The `type` is not present in the `known` list.                            |
| `INVALID_PROPS`    | `props is not an object`    | The `props` field is missing, or is an array, `null` or a primitive.      |
| `INVALID_CHILDREN` | `children is not a list`    | The `children` field is present but is not an array.                      |
| `DUPLICATE_ID`     | `duplicate sibling id`      | Two items in the same sibling list share the same `id`.                   |
| `MISSING_FIELD`    | `missing field <name>`      | A field marked as `required` is absent, `null`, empty or whitespace only. |

A renderer prints its own warnings from a different set, `ERROR_MESSAGES`.

A common mistake places data at the top level of the item (e.g., `{ id: 'wingspan', type: 'listing', title: 'Wingspan' }`). This triggers an `INVALID_PROPS` error because the item has no `props` object. Both renderers read a widget's data only from `props`, so they would draw that listing empty and print nothing.

## Enforcing Required Fields in CMS Data

Beyond checking if a widget type is known, `@evanion/widget` can enforce that certain props are present and not blank (where "blank" means `undefined`, `null`, an empty string, or a string of only whitespace).

In the example above, even though `title` is a string, it is blank. `validateItems` reports `missing field title`, and the gate from [Getting started](../getting-started) fails the run before the page publishes.

`required` checks only happen for known types. If a widget's `type` is unknown, it is reported as an `UNKNOWN_TYPE` fault, and its required props are ignored.

The keys of `required` are plain strings, which TypeScript does not check against your widget types. A misspelled type there is an entry nothing reads, so no item is ever checked against it.

## Syncing Validation with Your Renderer

`validateItems` from `@evanion/widget` accepts the registry your renderer draws from as its `known` argument. The gate then rejects exactly the types the renderer would skip.

`validateItems` reads only the registry's keys and never calls a value. If you are running a validation check in a continuous integration (CI) script that cannot import your React components, you can pass a plain array of the same type names.

`defineWidgets` returns the object it was handed, and its generic parameter keeps the keys `listing` and `shelf` as a union your code editor completes on. Annotating the object as `WidgetRegistry` instead widens the keys to `string`.

### Inherited Names Are Unknown Types

`validateItems` matches a `type` only against keys set on the registry object itself, which it tests with `Object.prototype.hasOwnProperty`. An item typed `constructor`, `toString` or `__proto__` is therefore reported as `unknown widget type`, and never resolves to something every object inherits. Both published renderers look a type up with the same test, so a type `validateItems` rejects is one they skip.
