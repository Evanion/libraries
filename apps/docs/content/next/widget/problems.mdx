# What validateItems reports

To find everything wrong with a content management system (CMS) payload before
a renderer draws it, call `validateItems(items, known)` once over the whole
payload. It walks nested items too, throws nothing, and returns one
`WidgetProblem` per fault.

## Check a whole widget payload in one call

`validateItems` from `@evanion/widget` reports every fault in a payload from one
call, including faults in nested items. `check.mts`, the script
[Getting started](../getting-started) builds, found one renamed type. The payload
below has three faults, and the `.map` keeps each problem's `index` and
`message`:

```ts twoslash file=libs/widget/README.md region=sweep

```

The first item, Wingspan's listing, has no `props`. The second item repeats its
`id`, `wingspan`, in the same sibling list. The shelf `tonight` is valid, and
its one child, Hive's listing, names the type `listting`, which is not in the
list of known types.

`validateItems` walks the payload depth first. It reports an item's own
problems, then walks that item's `children`, then moves to the next sibling.
Hive's problem comes last because `tonight` is the last top-level item, and its
`index` is 0, its position inside the shelf.

An `id` repeated at two depths is not reported. `@evanion/react-widget` passes
an item's `id` to React as its key, and React compares keys only among siblings,
so two items with one `id` at different depths never collide.

## The fields of a widget problem

Each `WidgetProblem` that `@evanion/widget`'s `validateItems` returns carries
four fields.

| Field     | What it holds                                                                                   |
| --------- | ----------------------------------------------------------------------------------------------- |
| `index`   | the item's position in its own sibling list, and `-1` when `items` is not a list                |
| `id`      | the item's `id`, or `-` when the item has no string `id`                                        |
| `type`    | the item's `type`, or `-` when the item has no string `type`                                    |
| `message` | a string from `VALIDATION_MESSAGES`, the exported object that holds every message it can return |

A child's `index` counts from its own parent, so the first item nested in a
shelf reports `index: 0` whatever its position in the whole payload. That is the
position a CMS editor sees inside the shelf they opened.

## The messages validateItems returns

`VALIDATION_MESSAGES`, exported from `@evanion/widget`, holds every string
`validateItems` reports.

| Constant           | Message                     | What produced it                                         |
| ------------------ | --------------------------- | -------------------------------------------------------- |
| `NOT_A_LIST`       | `items is not a list`       | the payload itself is not an array                       |
| `NOT_AN_OBJECT`    | `item is not an object`     | an entry is a string, a number, `null` or an array       |
| `INVALID_ID`       | `item id is not a string`   | `id` is absent, or is something other than a string      |
| `INVALID_TYPE`     | `item type is not a string` | `type` is absent, or is something other than a string    |
| `UNKNOWN_TYPE`     | `unknown widget type`       | `type` is not one of the known types                     |
| `INVALID_PROPS`    | `props is not an object`    | `props` is absent, or is an array, `null` or a primitive |
| `INVALID_CHILDREN` | `children is not a list`    | `children` is present and is not an array                |
| `DUPLICATE_ID`     | `duplicate sibling id`      | two items in one sibling list carry the same `id`        |
| `MISSING_FIELD`    | `missing field <name>`      | a prop `required` demands is absent or blank             |

A renderer warns with a different set, `ERROR_MESSAGES`, which
[Your own renderer](../renderer#the-warning-a-widget-renderer-prints) covers.
Compare a problem's `message` against `VALIDATION_MESSAGES` to group, count or
translate a report. `MISSING_FIELD` is a function of the field name, so compare
against `VALIDATION_MESSAGES.MISSING_FIELD('title')`. A CMS editor who reads
`missing field title` knows which box to fill.

`INVALID_PROPS` also catches an item that carries its data at the top level,
such as `{ id: 'wingspan', type: 'listing', title: 'Wingspan' }`. Both renderers
read a widget's data only from `props`, so they would draw that listing empty
and print nothing.

## Required props, and what blank means

`validateItems` from `@evanion/widget` takes an optional third argument,
`required`, which maps a widget type to the props that must be present and not
blank. Blank is `undefined`, `null`, an empty string, or a string of only
whitespace. A CMS text field arrives blank when an editor opened it and typed
nothing:

```ts twoslash file=libs/widget/README.md region=required

```

`title` is present and is a string. A check for presence alone would pass it,
and the renderer would draw a listing with no name, so `validateItems` also
rejects a blank value.

Two limits apply to `required`. Its keys are plain strings, which TypeScript
does not check against your widget types. A misspelled type there is an entry
nothing reads. An item whose `type` is unknown is reported once, as
`unknown widget type`, and its required props are not checked.

## Check against the registry a renderer draws from

`validateItems` in `@evanion/widget` takes a registry as its second argument,
`known`, as well as a plain array of type names. Passing the registry your
renderer draws from keeps the check and the renderer agreeing on which types
exist. `defineWidgets` types it:

```ts twoslash file=libs/widget/README.md region=registry

```

`defineWidgets` returns the object it was handed. Its generic parameter keeps
the keys `listing` and `shelf` as a union, which a code editor completes on.
`WidgetRegistry` is the type of any registry, and annotating the object as
`WidgetRegistry` widens the keys to `string`. `validateItems` reads only the
registry's keys and never calls a value. A continuous integration (CI) job that
cannot import the components therefore passes a plain array of the same names.

`validateItems` matches a `type` only against keys set on the registry object
itself, which it tests with `Object.prototype.hasOwnProperty`. So an item typed
`constructor`, `toString` or `__proto__` is reported as `unknown widget type`.
Both published renderers look a type up with the same test, so a type
`validateItems` rejects is one they skip.

## Draw a payload that passes the widget check

A payload that `validateItems` from `@evanion/widget` passes goes to a
renderer, which draws the items in the order the array holds them.
[Order and nesting](../layout) shows how each published renderer draws nesting
and placement, on the dashboard Baize's staff read each week, and lets you move
its items.
