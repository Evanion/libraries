# Write your own widget renderer

If you are using a framework without a published renderer, you can implement your own and synchronize its warnings with `@evanion/widget`, so they match the published renderers' warnings. React and Astro projects already have one.

## One warning for one stale type

When a renderer encounters a widget `type` it doesn't have a component for, it must skip that item. Both published renderers build the warning with `ERROR_MESSAGES.UNKNOWN_WIDGET(type, id)` from `@evanion/widget`, so the same stale type prints the same line in React and Astro.

### Using `warnOnce`

Renderers run during the render loop. Without protection, a single unknown widget would trigger a warning on every single re-render, flooding your console.

`@evanion/widget` provides `warnOnce`, which prints a message the first time it is encountered in a process and then silences it. It also automatically suppresses all warnings when `NODE_ENV` is set to `production`.

## Implementing the Render Loop

A basic renderer for `@evanion/widget` items iterates over them, looks up the `type` in a registry, and renders the corresponding component. ### Key implementation details:

- **Registry Lookup**: Use `Object.prototype.hasOwnProperty` to check for the type, the same own-key test [`validateItems` applies](../problems#inherited-names-are-unknown-types). `item.type in registry` or `registry[item.type]` alone finds what every object inherits: a function for `constructor` and `toString`, and `Object.prototype` itself for `__proto__`.
- **Warning Reset**: In your tests, call `resetWarnings` before each case to ensure that one test's warning doesn't silence the next.
- **Production Silence**: In production, `warnOnce` prints nothing. So run `validateItems` as a separate quality gate (as shown in [Getting started](../getting-started)) to catch content errors before they hit production.

## Extending the Renderer for Complex Layouts

A production-ready renderer for `@evanion/widget` items handles four additional responsibilities:

1. **Children**: Decide how to handle nested items. You can either draw them inside the parent (like `@evanion/react-widget`) or pass them as data to the parent's component (like `@evanion/astro-widget`).
2. **Meta**: Pass the `meta` property to the [item chrome](../#item-fields), never to the widget's `props`.
3. **Structural Warnings**: Use `warnOnce` to report structural failures:
   - `MALFORMED_ITEMS`: The items provided are not an array.
   - `MALFORMED_ITEM(id, type)`: An entry is not an object or lacks a string `type`.
   - `MALFORMED_CHILDREN(id)`: The `children` field is present but is not an array.

   A message that lacks an item's `id` or `type` uses `ERROR_MESSAGES.UNKNOWN` in its place.

4. **Separation of Concerns**: Draw what you can and warn about what you can't, and leave `validateItems` to [the gate](../getting-started) that runs where the payload first enters your system.

## Every widget core export

You now have a renderer that draws `@evanion/widget` items, skips an unknown type with the shared warning, and stays quiet in production. The [API reference](../api) lists every export of `@evanion/widget` with its signature and the shape of each `ERROR_MESSAGES` key.
