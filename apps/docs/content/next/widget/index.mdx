# @evanion/widget

**Stop "Silent Failures" in your CMS-driven pages.** `@evanion/widget` checks the widget items a page is saved as, and reports every widget a renderer would skip or draw empty before the page reaches the browser.

## Silent failures in a CMS page

When a content management system (CMS) saves a page for `@evanion/widget`, it stores the content as a list of "items," each with a `type` (which component should be used) and `props` (the data for that component).

The danger is a **Silent Failure**:

- If a CMS saves an item with a type that your frontend doesn't recognize, the renderer skips that item, leaving a mysterious gap in your page where a widget should have been.
- If a required prop is blank, the renderer draws the widget with that field empty.
- In production, the renderer throws no error and logs no warning, so you might not notice either until a user reports it.

`@evanion/widget` allows you to catch these content errors during the save process, in a webhook, or as a blocking step in your continuous integration (CI) pipeline.

## A page as an array of widget items

`@evanion/widget` describes a page with three terms:

- A **widget** is a single structural block of a page—such as a game listing, a hero banner, or a featured shelf.
- A **widget item** is the data representation of that block.
- A **renderer** (such as `@evanion/react-widget` or `@evanion/astro-widget`) is the framework-specific package that actually turns these data items into UI components.

### Item fields

Every item consists of a few key fields that standardize how your CMS talks to your frontend:

- `id`: A required string, unique among the item's siblings. `@evanion/react-widget` uses it as the item's React key, and its default item chrome writes it to the `data-widget-id` attribute. `@evanion/astro-widget` passes it to the widget as the `id` prop.
- `type`: The name of the component used to render the widget.
- `props`: The actual data passed to the component.
- `meta`: Optional placement data (like `span: 2` for a grid). A renderer hands it to the **item chrome**, the component that surrounds each widget, and never to the widget's `props`. Your application supplies the item chrome to the renderer as `chrome.item`, and the item chrome decides what `span: 2` does. Without item chrome of yours, `meta` changes nothing.
- `children`: An optional array of nested items, allowing you to create complex layouts like shelves containing listings. A CMS editor who moves the `tonight` shelf moves Wingspan's listing with it.

## The Widget Vocabulary

`@evanion/widget` and its renderers use these terms:

- **Known Types**: The list of widget types that your renderer actually has components for. `validateItems` takes them as its second argument, `known`.
- **Registry**: A map that links each known type to its corresponding component. `defineWidgets(registry)` types it so your editor completes on its keys, and `validateItems` accepts it as `known`.
- **Problem**: An error report generated by `validateItems`, typed `WidgetProblem`: the faulty item's `index` among its siblings, its `id` and `type`, and a `message`.

## Core Capabilities

`@evanion/widget` provides the logic for validating your CMS payloads without requiring a frontend framework:

| Goal                                 | Tool                                                                                                                                |
| :----------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------- |
| Describe a page as JSON data         | `AnyWidgetItem`, a type for items that can be written by a CMS                                                                      |
| Define supported types               | A registry from `defineWidgets`, or a simple list of type names                                                                     |
| Reject bad payloads before rendering | `validateItems(items, known)`, which reports all problems without throwing                                                          |
| Enforce required props in the CMS    | A `required` map for `validateItems`, which reports a prop that is missing, `null`, empty or whitespace only                        |
| Framework-agnostic checks            | `validateItems`, from a package that imports no framework and has no dependencies                                                   |
| Consistent renderer warnings         | `ERROR_MESSAGES`, the warning text both renderers print, and `warnOnce`, which prints each warning once, for a renderer of your own |

## Design Boundaries

`@evanion/widget` checks items and draws nothing. `@evanion/react-widget` and `@evanion/astro-widget` draw them.

- **No UI Rendering**: The core does not draw anything on the screen; that is the job of the renderer.
- **No Compile-time Prop Checks**: The core checks an item's shape, its `type` and the props `required` names at runtime. It cannot check if the `props` match a component's TypeScript definition (though `@evanion/react-widget` can).
- **No Automatic Execution**: Neither renderer calls `validateItems`; you must call it in your own code (e.g., in a webhook or build script).
- **No Data Fetching**: The core only validates the data it is given; it doesn't know where the data comes from.

## Gate a saved page

You now have the model `@evanion/widget` checks: an array of items, and the list of types your renderer draws. [Getting started](./getting-started) installs the package and turns `validateItems` into a script that fails a run when a saved page names a type outside that list.
