# Generating and validating

`Luhn.generate` computes the check character for an identifier, and `Luhn.validate` checks if a code carrying one is well-formed. Both return the "phrase" (the cleaned input) they read, allowing you to map a customer's input back to a database record.

### The Result Object

| Field      | What it holds                                       | Example (`order-2026-0042`) |
| :--------- | :-------------------------------------------------- | :-------------------------- |
| `phrase`   | The cleaned input used for the calculation.         | `'order20260042'`           |
| `checksum` | The computed check character.                       | `'l'`                       |
| `filtered` | The number of characters dropped (separators, etc). | `2`                         |

Because `generate` reads the **phrase**, inputs like `order-2026-0042` and `ORDER 2026/0042` produce the same checksum. This ensures that the identity of the resource is preserved regardless of how it was written.

## Handling Empty Inputs

`Luhn.generate` throws an `EmptyInputError` when no characters in the input belong to the dictionary.

If every character is dropped, the resulting phrase is empty. Since every empty phrase would produce the same check character, a blank form field or a string of hyphens (`'--'`) would be "valid." To prevent this, the library requires at least one valid character.

## Validating a Code with `Luhn.validate`

`Luhn.validate` treats the last character of the input that belongs to the dictionary as the check character.

```

### Key Validation Rules:

- **The Phrase**: `validate`'s `phrase` includes the check character.
- **Minimum Length**: `isValid` is `false` if the phrase contains fewer than two characters (an ID plus its check character is the minimum).
- **Case and Separators**: Like `generate`, `validate` ignores case and non-dictionary characters.

## Mapping a Code Back to an Order

To look up an order using a customer's input, you should store the **phrase** generated by `Luhn.generate` in your database.

When a code comes back, use `validate` to verify it, then slice off the last character (the check character) to get the original phrase.

```

This approach ensures that `ORDER 2026 0042 L` and `order-2026-0042-l` both resolve to the same database key: `order20260042`.

## Strict Input with `filtered`

While allowing separators is great for humans, it can be a problem for automated systems. For example, a barcode scanner should not be adding random separators.

You can use the `filtered` count to enforce strict input. If `filtered` is greater than 0, you know the input contains characters that weren't part of the original identifier.

```ts twoslash file=libs/luhn/docs/examples.md region=strict-input

```

By checking `filtered === 0`, you can distinguish between a manually typed code (which allows separators) and a scanned code (which must be exact).

## Customizing the Alphabet

By default, all calls run on a 36-character dictionary. If you need to use a different set of characters—such as the 32-character alphabet used by `@evanion/token`—you can build a custom instance. [Dictionaries](../dictionaries) shows how to use `createLuhn`.
