# Standards and modulo bias

`@evanion/luhn` provides a faithful implementation of the Luhn algorithm. Depending on the dictionary you choose, it either matches a global industry standard or implements a general-purpose "mod-N" checksum.

## Luhn mod-10 and Its Standards

When you use the dictionary `'0123456789'`, `@evanion/luhn` implements **Luhn mod-10**. This is the standardized check digit used worldwide for credit card numbers, payment cards, and various government identifiers.

`createLuhn({ dictionary: '0123456789' })` reproduces the published mod-10 test vectors:


Luhn's patent [US 2,950,048](https://patents.google.com/patent/US2950048A/en) defines the algorithm, and these standards specify the same check digit:

- **ISO/IEC 7812-1 Annex B**: The specification for issuer identification numbers on payment cards.
- **3GPP TS 23.003 Annex B.2**: The check digit of the IMEI, the identifier of a mobile device.
- **CMS National Provider Identifier (NPI)**: The [check-digit specification](https://www.cms.gov/Regulations-and-Guidance/Administrative-Simplification/NationalProvIdentStand/Downloads/NPIcheckdigit.pdf) for US healthcare providers.

## Luhn mod-N Over Any Other Dictionary

When you use any other dictionary, `@evanion/luhn` implements **Luhn mod-N**.

**There is no formal RFC, ISO, ITU or ANSI standard for mod-N Luhn**. The doubling formula used by this library (and many others), `floor(2x / n) + (2x mod n)` for index `x`, traces back to [Wikipedia revision 74161899](https://en.wikipedia.org/w/index.php?title=Luhn_mod_N_algorithm&oldid=74161899) of 2006-09-06, which was unsourced then and is unsourced now.

If you are integrating with another system that claims to use "Luhn mod-N," do not assume their implementation matches. Always verify their output against your own test vectors, as the dictionary order and the doubling formula may differ.

## The "Blind Spot" of the Luhn Algorithm

As the [Overview](../#what-a-check-character-catches-and-what-it-doesnt) notes, the `@evanion/luhn` check character misses exactly one adjacent swap: a swap of the dictionary's first and last characters.

For any even-sized dictionary, swapping the characters at index `0` and index `n - 1` (e.g., `0` and `z` in the default dictionary, `0` and `9` in mod-10) leaves the Luhn sum unchanged. This is a mathematical property of the algorithm's doubling step and cannot be "fixed" without changing the algorithm itself.

## Modulo Bias in Random Generation

`@evanion/luhn` does not generate random values, but a shop that draws its codes at random over a Luhn dictionary meets **modulo bias**.

If you draw a random byte (0-255) and use `byte % n` to pick a character, every character is equally likely **only if `n` divides 256**.

The default 36-character dictionary is not uniform: $256 \bmod 36 = 4$. This means the first four characters in the dictionary will appear roughly 14.3% more often than the others.

### How to Avoid Bias

1. **Use a dictionary whose size divides 256**: This is why `@evanion/token` refuses any other dictionary size, and why its default dictionary holds 32 characters.
2. **Rejection Sampling**: Draw a byte, discard it if it falls in the "biased tail" (e.g., values 252-255 for $n=36$), and draw again.

Your random number generator, such as `crypto.getRandomValues`, supplies the bytes, and `uniformOverBytes` says nothing about their quality.
