# Getting started

In this guide, you will build a pickup code flow with `@evanion/token`: issue a human-readable code at checkout, and use `validate` to check the code read back at the counter before searching your database.

## What token Needs

`@evanion/token` needs:

- **Node 20 or newer**, or any modern browser. `generate` uses `crypto.getRandomValues`, which is available in both environments without additional imports.
- **An ESM project**: Your project must be an ES module. If you are starting in an empty folder, run `npm init -y` followed by `npm pkg set type=module`.
  _(A CommonJS project needs a Node whose `require()` loads ES modules: 20.19 or later on Node 20, or 22.12 or later. An older `require()` fails with `ERR_REQUIRE_ESM`.)_
- **A way to run a TypeScript file**: The examples are TypeScript. `npx tsx file.ts` runs one, and downloads tsx on first use. A project that already compiles its TypeScript runs the file its usual way.

## Install token

Run the command for your preferred package manager:

```bash
npm install @evanion/token
```

```bash
yarn add @evanion/token
```

```bash
pnpm add @evanion/token
```

`@evanion/token` automatically installs `@evanion/luhn`, which handles the check-character calculations.

## Configure your token instance

The first step is to create an `@evanion/token` instance with `createToken`. `createToken` checks the options once and freezes the instance, so every code it mints has the same length and dictionary. Define it at module scope, so that check runs at start-up.

If you call `createToken()` without options, it uses the defaults: a length of 8 (including the check character), split into chunks of four by a hyphen. This results in a `value` that is 9 characters long (e.g., `a4kp-9mxa`).

## Implement the checkout and pickup flow

Issue an `@evanion/token` code at checkout and validate it at the counter.

The workflow has two steps:

1. **At Checkout**: Call `generate()`. This returns both the `value` (which you print on the receipt) and the `body` (which you store in your database).
2. **At Pickup**: Pass the customer's spoken or typed code to `validate`.

A `Map` stands in for the orders table:

```ts twoslash file=libs/token/README.md region=checkout

```

The code `generate` minted finds `order-2026-0042`. `a4kp-9mxa` is well formed, so `validate` accepts it, and the table answers `'no such order'` because it holds only the code just minted. `a4kp-9nxa` is the same code with `m` misheard as `n`, and `validate` refuses it with `'check-failed'`.

In this example, `validate` acts as a gate. It refuses a misheard code before your system performs a database lookup for a code `generate` could never have minted, so you can tell the customer their code is mistyped rather than a bare "not found."

## Adding a prefix

Your counter now tells a misheard `@evanion/token` code from one the shop never issued. To make your codes more recognizable, you can add a prefix like `ORD-`, which helps users and staff identify the code's purpose at a glance.

You can mint prefixed codes by passing a `prefix` option to `generate`. [Generating and validating](../usage) mints one and redeems it however the customer types it.
