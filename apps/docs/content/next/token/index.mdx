# @evanion/token

When a customer reads a pickup code over the phone or types it into a form, a single misheard character can turn a valid code into a "no such order" error. This is frustrating for the user and makes it impossible for the staff to know if the code was truly invalid or just mistyped.

`@evanion/token` solves this by minting codes with built-in error detection. Its `validate` function can identify a misheard character before your application ever touches the database, allowing you to tell the user "That code looks slightly wrong" instead of "Order not found."

## How misheard codes are caught

A default `@evanion/token` code consists of random characters followed by a single **check character**. For example, in the code `a4kp-9mxa`, the final `a` is the check character, computed from the preceding seven characters.


When you call `validate`, the library recalculates the check character from the body. If a customer reads `a4kp-9mx8` (where the `a` was misheard as `8`), `validate` immediately returns `reason: 'check-failed'`. 

This means your system can refuse the code without performing a costly database lookup, instantly distinguishing a typo from a non-existent order.

## The token vocabulary

To help you use the API, here are the core terms we use:

- **Code**: The full string the user sees, such as `a4kp-9mxa`.
- **Body**: The random characters of the code, excluding separators and the check character. This is the part you store in your database.
- **Check Character**: The final character used for error detection. It is computed using the Luhn algorithm (the same system used by credit cards).
- **Dictionary**: The set of characters used to generate the code. The default dictionary leaves out confusing characters like `i`, `l`, `o`, and `w` to prevent misreads.
- **Chunk**: A group of characters (four by default) used to make codes easier to read.
- **Separator**: The character between chunks (a hyphen by default).
- **Prefix**: An optional identifier, such as `ORD`, added to the front of a code for categorization.

## What token can do

`@evanion/token` provides a simple set of tools for managing these codes:

| You want to                                        | What token gives you                                                                                   |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| mint a human-readable code                        | `generate()`, using cryptographically strong random values                                               |
| refuse a mistyped code before the database lookup  | `validate()`, which returns a specific reason for failure                                               |
| support flexible user input (no hyphens/caps)     | `validate`, which automatically cleans the input before checking                                      |
| categorize codes with a prefix (e.g., "ORD-")     | `generate({ prefix: 'ORD' })`                                                                           |
| customize length, chunks, or separators           | `createToken({ length, chunkSize, separator })`                                                           |
L| use a custom set of allowed characters           | `createToken({ dictionary })`                                                                           |
| calculate the risk of collisions                  | `entropyBits`, to ensure your code length matches your expected volume                                |

## What token does not do

It's important to note that `@evanion/token` is an error-detection library, not a full identity system:

- **Uniqueness**: `generate` does not check your database for collisions. You should use a unique index on your database column to ensure uniqueness.
- **Existence**: A `valid: true` result only means the code is *well-formed*. It does not mean the code was actually issued.
- **Security**: These codes are designed for convenience (like pickup codes), not as high-security credentials. An attacker could enumerate random strings to find a valid check character.
- **Prefix Validation**: The check character only covers the body. You must strip the prefix (e.g., `ORD-`) manually before calling `validate`.
- **Retrofitting**: It cannot add a check character to an existing ID. For that, use the `@evanion/luhn` package directly.
