## Collisions and the Birthday Paradox

When `@evanion/token` generates random codes, you don't just worry about running out of possible values: you worry about **collisions**. A collision occurs when `generate()` produces a value that has already been issued to another user.

Because of the "Birthday Paradox," collisions happen much sooner than you'd expect: with 35 bits of entropy, you don't need 34 billion codes to see a collision; there's a 50% chance of a collision after only 218,000 codes.

## Calculating Entropy

The entropy of an `@evanion/token` code is the total number of random bits it carries. Since the check character is computed from the body and isn't random, the formula is:

$$\text{Entropy Bits} = (\text{length} - 1) \times \log_2(\text{dictionary size})$$

The default `length` of 8 and 32-character dictionary provide 35 bits. A `length` of 12 provides 55 bits, and a `length` of 13 provides 60. The example passes `chunkSize: 13` because the default chunk size of 4 does not divide 13, which `createToken` refuses.

### Collision Probability

The 50% collision point is roughly $1.18 \times \sqrt{2^{\text{bits}}}$. The last column is the number of issued codes at which the next insert's chance of a conflict reaches 1 in 1,000, the figure the sizing rule below uses. Both grow fast with the length:

| `length` | Bits | 50% Collision Point | 1 in 1,000 per Insert |
| :------- | :--- | :------------------ | :-------------------- |
| 6        | 25   | 6,800               | 34,000                |
| 8        | 35   | 218,000             | 34,000,000            |
| 10       | 45   | 7,000,000           | 35,000,000,000        |
| 13       | 60   | 1,300,000,000       | 1,200,000,000,000,000 |

## Handling Collisions with Unique Indexes

`@evanion/token` does not check your database for collisions because it has no access to your issued codes, and `generate` never retries. The responsibility for uniqueness lies with your database.

Put a `UNIQUE` index on the `body` column and redraw the code if the insert fails:


In this pattern, `issued` stands in for the unique index, and `insertPickupCode` returns `false` where a database raises a unique violation. In your code, catch that violation and nothing else, then call `generate()` again. `issuePickupCode` draws up to five times and then throws, so a table that has run out of codes raises an error. Once `length` keeps each insert's chance of a conflict under 1 in 1,000, the sizing rule in the next section, five consecutive collisions happen about once in $10^{15}$ inserts.

## Sizing Your Code Length

To choose the right `length` for an `@evanion/token` code, calculate the chance that the _next_ insert will conflict: $\frac{\text{Codes Issued}}{2^{\text{bits}}}$.

Keep this probability below 1 in 1,000 for your expected volume over the next three years. For a default 35-bit code, the probability reaches 1 in 1,000 at about 34 million issued codes. The 50% collision point of 218,000 codes measures something else: the point where some two codes have an even chance of matching, and the retry loop redraws that one match.

## Security Warning: Guessing vs. Typo-Detection

**`@evanion/token` codes are not secure credentials**.

A 35-bit code is designed to protect against _transcription errors_ (typos), not _adversarial guessing_. An attacker can enumerate 35 bits, so a code that grants access by being known, such as a password reset link, needs a different tool.

- **Wrong tool**: Do not use `@evanion/token` for session IDs, password resets, or any code where knowing the string grants access. Use a 128-bit random value for those, and do not make it readable, because nobody types it.
- **Right tool**: Use it for pickup codes, support tickets, or any identifier a human must handle.

If a readable code _must_ gate a resource (like a gift card), you must implement additional security:

1. **Rate-limiting**: Prevent attackers from guessing thousands of codes per second.
2. **Second-factor binding**: Bind the code to a known identity, such as the customer's email address.

## Why Codes Are Not Shorter

`@evanion/token` could get the same bits from fewer characters with a larger dictionary or without the check character, and does neither:

1. **Alphabet Limits**: `createToken` refuses uppercase, so a 64-character dictionary would require punctuation or non-ASCII characters. Even expanding to a full alphanumeric set (36 chars) would bring back characters like `o` and `l`, which are confused with `0` and `1`, and 36 does not divide 256.
2. **The Value of the Check**: Dropping the check character would increase entropy (e.g., 40 bits instead of 35), but it would mean every mistyped code triggers a database lookup and a "Not Found" error. `createToken` has no option to drop it.

The check character is what `@evanion/token` adds to a random string. [The API reference](../api) lists every option, field and error these pages use.
