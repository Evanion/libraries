# acl 0.2.0

Status: draft, 2026-11-05. Extends
[2026-09-14-acl-design.md](2026-09-14-acl-design.md), which is released (acl
0.1.1). Ships after 0.1.2, which refuses at construction every field-rule
entry and every `targets`/`transitions` key that contains `.` or `\`.

0.2.0 carries four changes:

1. nested field paths, which close the field-rule leak for good;
2. `validateAll`, every validation issue without throwing (#542);
3. `explain`, each condition's result behind a decision (#543);
4. `canEach`, one permission over many subjects (#544).

Changes 2 to 4 come from Portcullis, a policy editor built on acl. It needs a
problems list, a "why was this refused" view and a "who can do this" view, and
must not re-implement validation or condition evaluation to get them.

## Part 1: nested field paths

### Why

Field rules match top-level keys only. `decideFields` keys its maps by
`Object.keys(object)`, and `allowed()` in `libs/acl/src/fields.ts` compares
each key against the list as written. A rule that names a nested path is
accepted at construction and never matches:

- `['*', '!address.street']` marks `address` as `allowed`, and
  `pickAllowedFields` returns the whole address with the street in it. The
  author asked to hide the street and the response carries it.
- `['id', 'address.city']` never allows `address`, so the city the author
  allowed is withheld.
- `{ 'address.country': { targets: ['SE'] } }` configures a decision key that
  no proposed write carries. Without a name list `address` is writable, so a
  write of `address.country: 'US'` passes.

The first and third cases leak. The published docs page
`apps/docs/content/next/acl/filtering.mdx` ("Nested objects") and the
`nested-fields` region of `libs/acl/docs/examples.md` document the first case
as current behaviour and tell readers to give the nested shape its own object
kind.

The owner chose the long-term fix: field rules name nested paths and the
engine enforces them.

### Goals

- A field rule can name any key at any depth of a plain object, on both axes.
- An exclusion below a key hides exactly that subtree, and
  `pickAllowedFields` returns the rest of the parent.
- A policy that names no nested path decides exactly as it does today: same
  map keys, same states, same reasons.
- Every case the engine cannot walk fails closed.
- Construction refuses a path list whose intent is contradictory or
  undefined, as conditions already do.

### Non-goals

- Nested condition paths. `pathFault` keeps refusing `object.a.b`. Conditions
  decide whether the action is allowed and field rules decide which data
  passes, so the two can move separately. Nested conditions get their own
  spec if users ask.
- Nested types in `MatrixSchema`. The schema stays flat and keeps not checking
  field-rule names, as `types.ts` documents.
- Wildcards inside a path (`items.*.price`, `*.secret`). `*` stays a top-level
  baseline.
- Index paths into arrays (`items.0.price`).
- A deep-merge helper for applying a nested write (see "Applying a nested
  write").

### Anti-goals

The work fails, even if every test passes, if:

- any policy without a dotted entry changes its decision output;
- a value the engine cannot walk is returned by `pickAllowedFields` while a
  rule names something below it;
- `__proto__`, `*` or `!name` turns up as a key at any depth of a decision map,
  or in any object `pickAllowedFields` builds (a subtree no rule descends into
  is copied by reference, as today);
- a decision throws on hostile data (accessors, null prototypes, cycles).

### Path syntax

A path is one or more segments joined by `.`: `address`, `address.street`,
`lines.price`. A segment that contains `.` or `\` escapes it with `\`, so a
flat key literally named `a.b` is written `a\.b` (in JSON `"a\\.b"`). Every key
a JSON object can carry is nameable.

The same encoding keys the decision maps. `fields['address.street']` is the
nested street; `fields['a\\.b']` is the flat key `a.b`. This changes the map
key for an existing flat key containing `.` or `\`. It is the only change to a
policy without a dotted entry, and the changelog names it.

A list entry is `*`, a path, or `!` followed by a path.

### Semantics

The tree of named paths decides. For a path `p`:

1. An entry `!q` where `q` is `p` or an ancestor of `p` denies `p`.
2. Otherwise `*`, or an entry naming `p` or an ancestor of `p`, allows `p`.
3. Otherwise `p` is denied with reason `not-listed`.

An exclusion needs a baseline: `*`, or a listed ancestor. This replaces the
current rule ("a `!` entry needs `*`"), so `['id', 'address',
'!address.street']` is valid and means "id and the address, without its
street". `['id', '!address.street']` is still refused, with
`DenyWithoutBaselineError`.

#### Which keys a decision carries

Today the maps carry every key of the object (and of the write, on the write
axis), every rule key, and every list name. With paths, the engine expands a
key into its children when, and only when, a rule that applies on that axis
names a path below it and the key is not excluded. On the read axis only list
entries apply. On the write axis list entries and `targets`/`transitions` keys
apply. The expanded key leaves the map and its children enter it,
recursively, so the map holds the leaves the rules reach. A key and one of its
descendants are never both in a map.

- `['*', '!address.street']` over `{ id, address: { city, street } }` gives
  `id: allowed`, `address.city: allowed`, `address.street: denied`.
- `['*', '!address']` over the same object gives `id: allowed`,
  `address: denied`. Nothing descends below an excluded key, so it is not
  expanded.
- `['id']` gives `id: allowed`, `address: denied`, as today.

A named path that the data does not carry still enters the map, as a named
top-level field does today.

`allowed` stays "every key in the map is allowed", so a policy that hides a
nested key answers `allowed: false`, as `['*', '!status']` does today.

#### Arrays

A segment that reaches an array applies to every element. `!lines.cost` hides
`cost` on every line. The map key carries no index (`lines.cost`), and the
children of an expanded array are the union of its elements' keys.

On the read axis this is exact, because a read decision depends on the name
alone. On the write axis the engine has no element identity between the
stored and the proposed array. A write that drops or reorders elements would
erase or move values in keys the caller may not write. So on the write axis
an array that a rule descends into is `not-traversable` (below) as a whole,
and the caller writes it through its own per-element action. (My call: the
same fail-closed rule as a subtree replacement.)

#### Values the engine cannot walk

The engine walks plain objects (prototype `Object.prototype` or `null`) and
arrays. Anything else that a rule needs to walk (a `Date`, a `Map`, a class
instance such as an ORM row, a primitive, `null`) is a leaf it cannot see
into. A rule that names a path below such a value denies that value with a
new `FieldReason`, `not-traversable`. On the read axis that hides the whole
value. On the write axis it refuses the write of it.

A write that replaces a subtree the rules descend into is the same case.
Proposing `address: null` under `!address.street` would erase a street the
caller may not write, so `address` is `not-traversable`.

On the write axis the object and the write are both walked. When either side
holds a value at a key that cannot be walked, the key stays one map entry,
`denied` with `not-traversable`, and none of its children enter the map. (My
call: fail closed, and the "key and descendant never both" rule holds.)

An array whose elements are not all walkable is denied whole. The engine
does not drop single elements, because a shorter array reads as complete
data.

A cycle in the data is `not-traversable` at the point it repeats. Depth is
bounded by the deepest path the rules name, so the walk never goes deeper
than the rules.

#### Write configs on paths

A `targets` or `transitions` key may be a path through plain objects:
`'address.country': { targets: ['SE', 'NO'] }`. The current value is read at
that path on the object, the proposed value at that path on the write, with
own-property reads at every step. The existing reasons (`missing-field`,
`proposed-required`, `targets-failed`, `transition-failed`) apply unchanged.

A config decides its own path, as a config decides its key today
(`['*', '!status']` plus `status: { targets }` makes `status` writable to
those targets). A config under an excluded ancestor (`['*', '!address']` plus
`'address.country': { targets }`) is refused at construction, because it
states two intents for one path.

#### `pickAllowedFields`

`pickAllowedFields` rebuilds the allowed tree. It walks the proposed value
along the decision's keys, copies every allowed leaf, and builds each parent
as a new object or array with own data properties (`put`). An object parent
appears in the result only when at least one of its children does. An array
keeps every element and its indexes, so an element whose children were all
withheld becomes `{}` (my call: a shorter array reads as complete data). It
never returns a value from the input whose subtree held a denied key, and it
never copies a key the decision does not carry. A subtree no rule descends
into is copied by reference, as `pickAllowedFields` does with every value
today.

### Construction checks

`validateMatrix` (and therefore `policy().build()` and `hydratePolicy`)
refuses:

- an empty segment: `a..b`, `.a`, `a.`, a trailing `\`;
- a segment that is `__proto__`, or that is `*` or begins with `!` (`a.*`,
  `a.!b`);
- an exclusion with no baseline above it (`DenyWithoutBaselineError`);
- an entry and its own exclusion (`['a', '!a']`), and an allow under an
  excluded ancestor (`['*', '!address', 'address.city']`). Both state two
  intents for one path. This replaces `BangInAllowListError`, whose case
  (`!x` inside an explicit list without its ancestor) is now the
  missing-baseline case. `BangInAllowListError` is removed from the exports
  in 0.2.0 and the changelog names it (my call: 0.2.0 is a breaking release
  already, and a class nothing throws misleads an `instanceof` check);
- a `targets`/`transitions` key under an excluded ancestor.

A redundant entry (`['*', 'title']`, `['address', 'address.city']`) is
accepted, as `['*', 'title']` is today.

The error classes and messages are the builder's call, provided each names
the permission key and the offending entry.

### Typed authoring

`.fields()` on the typed builder (`policy<Subject, Objects>()`) accepts the
paths of the object kind's type: top-level keys, nested keys through plain
object properties, array element keys, `*`, and `!` of any of those. An
unknown path is a compile error. Recursion stops at a fixed depth (the
builder picks it, at least 4), past which the type accepts any string so
deep types never fail to compile. The untyped builder and `hydratePolicy`
take any string and rely on the construction checks.

### Other consumers

- `diffMatrix`: two lists without `*` stay decidable, now as path sets with
  ancestor coverage and nested exclusions. `widened` and `narrowed` report
  paths. A list with `*` stays `undetermined` as today.
- `serialize`, `parseMatrix`, `canonical`: no change beyond the paths being
  strings.
- `react-acl`: types are unchanged. `useCanFields` returns path keys.
- The security register (`libs/acl/SECURITY.md`) gains entries with tier-1
  tests for: a nested exclusion leaking through the parent, a subtree
  replacement on write, a value that cannot be walked, and `__proto__` / `*`
  / `!name` at depth. SEC-007 and SEC-008 extend to every depth.

### Docs

- Rewrite "Nested objects" on `filtering.mdx` and the `nested-fields` example
  region for path rules. Prose goes through the Gemma workflow.
- `canFields` and `pickAllowedFields` reference pages: path keys, arrays,
  `not-traversable`.
- "Applying a nested write": the picked value is a partial tree.
  `Object.assign(row, picked)` replaces `row.address` with the allowed part of
  it and drops the keys the write did not carry. The page shows a deep merge
  for a document row and the nested update form of an ORM. The deep merge
  skips `__proto__`, because a subtree copied by reference can carry one from
  `JSON.parse`.

## Part 2: `validateAll` (#542)

### Why

`validateMatrix` throws on the first fault, so an editor shows one problem at
a time and the author fixes them one save at a time.

### API

```ts
validateAll(matrix: unknown, options?: ValidateOptions): ValidationIssue[]

interface ValidationIssue {
  code: string;           // the error class name, e.g. 'DenyWithoutBaselineError'
  message: string;        // the message the throwing path raises
  path: string;           // JSON pointer into the document, e.g. '/permissions/3/fields/fields/1'
  permissionKey?: string; // `${key}.${action}` when the issue sits in a permission
}
```

An empty array means the document is valid. `validateAll` never throws, for
any input, including a non-object.

`ValidateOptions` holds the `AccessOptions` that change what construction
checks (today `fetchedAt` and `maxStale`, behind `MissingFreshnessBudgetError`
and `InvalidFreshnessError`), so `validateAll`
reports exactly what `hydratePolicy` with the same options would refuse.
Runtime errors (`UnknownObjectKeyError`, `UnknownPermissionError`) are calls,
not documents, and stay out.

### One validator

The checks get one implementation that collects issues. `validateMatrix`
runs it and throws the first issue as the error it throws today, so every
existing throw keeps its class, message and order. `AclConfigError` gains
`code`, `path` and `permissionKey`, so a thrown error and a collected issue
carry the same data, and the issue is a plain object that crosses a worker or
the network.

A fault stops only the checks that depend on the faulty node. `permissions`
not being an array stops everything. A permission whose `fields` is malformed
still gets its rules checked. A condition with an invalid shape skips the
schema checks for that condition, as the schema pass skips it today. The
builder lists these dependencies in the plan.

"Every existing throw keeps its class" is measured against main after Part 1
lands, so Part 1 merges first.

The typed builder's chain errors (`authoring.ts`) are authoring mistakes the
compiler mostly catches, and stay throwing.

## Part 3: `explain` (#543)

### Why

A decision names the rule that matched and nothing about the rules that did
not. "Wrong role", "missing grant" and "a deny matched" all read as
`allowed: false`. An editor's "Can X do Y?" checker needs every condition's
result, from the engine.

### API

```ts
access.explain(subject, key, action, object?, now?): Explanation
access.authorize(subject).explain(key, action, object?)   // bound form, one clock

interface Explanation {
  decision: Decision;            // equal to what can() returns for the same call
  step: 1 | 2 | 3 | 4 | 5 | 6 | 7; // the precedence step in decideResolved that decided
  deny: RuleExplanation[];
  allow: RuleExplanation[];
}

interface RuleExplanation {
  rule: string;                  // ruleId(rule, side)
  state: 'matched' | 'not-matched' | 'unusable-clock' | 'unevaluable';
  conditions: {
    condition: Condition;        // as stored in the document
    state: 'holds' | 'fails' | 'unusable-clock' | 'unevaluable';
    missing?: readonly string[];
  }[];
}
```

`explain` evaluates every condition of every rule. It does not short-circuit
the way `ruleMatches` does, because a UI wants to show each failing condition.
Conditions are pure, so this changes nothing but cost. `decision` comes from
the same `decideResolved` that `can` calls, and a property test asserts
`explain(...).decision` deep-equals `can(...)` over generated matrices and
contexts.

A stale document and an unknown action return their `can` decision with empty
`deny` and `allow` lists and no `step`.

`explain` carries no values read from the subject or the object, only states
and the paths that were missing. (My call: the explanation then holds nothing
the document does not already publish, per SEC-206, and a client may log it.)

Field decisions already carry per-field reasons on `canFields`, so `explain`
covers the action decision only.

## Part 4: `canEach` (#544)

### Why

"Who can approve a refund?" needs subjects, and acl holds none. Portcullis
keeps saved scenarios and sample subjects, so the scoped ask is one permission
over a list of candidate subjects.

### API

```ts
access.canEach(subjects, key, action, object?, now?): Decision[]
```

It mirrors `canMany` with the roles swapped: one permission, one object, many
subjects, one settled clock for the whole list. Each entry is the `Decision`
`can` returns for that subject, so `allowed`, `reason`, `rule` and `missing`
already give "allowed", "denied with the deciding rule" and "undetermined
until the object is loaded". Grouping is the caller's.

The symbolic subject predicate in #544 ("subjects where role is support and
team is billing") is out of 0.2.0. It needs a predicate algebra over allow
minus deny with negation, and is its own design.

`federatedPolicies` gets neither `canEach` nor `explain`. It omits `canMany`
and `canFields` because each answers about one permission and `get(origin)`
reaches it, and the same holds for both new methods.

Each new export gets its reference section under the per-export rule

## Release

`nx.json` sets `adjustSemverBumpsForZeroMajorVersion`, so a plain `feat` on
0.1.x bumps the patch. Part 1's commit is `feat(acl)!` with a
`BREAKING CHANGE` footer, which gives 0.2.0. All four PRs merge to main
first, then the owner dispatches one release.

`react-acl` re-exports `FieldReason`, which gains a member, so it releases as
0.2.0 too, with its own changelog line and its `@evanion/acl` pin moved to
0.2.0. The plan names the commit that carries its bump.

One changelog for acl names:

- the map key change for flat keys containing `.` or `\`;
- the new `FieldReason` `not-traversable` (an exhaustive switch needs an arm);
- the newly refused field lists;
- the removal of `BangInAllowListError`;
- the three new APIs.

`react-acl` gains `useExplain` and `useCanEach` only if Portcullis asks.

0.1.2 makes construction refuse dotted entries. A 0.1.2 reader therefore
refuses a 0.2 document that uses paths, where 0.1.1 would read it as flat keys
and leak. The 0.2.0 changelog states that every evaluator reading a 0.2
document must run 0.1.2 or later.
