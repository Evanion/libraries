# feature 0.2.0: richer conditions

Status: draft, 2026-11-07. Covers Evanion/libraries #569, #570 and #571,
requested by Portcullis for its console flag context. Extends
[2026-09-23-feature-variants.md](../../specs/2026-09-23-feature-variants.md)
and the released `@evanion/feature` 0.1.1.

## Why

Portcullis keeps its flag context grouped (`{ subject: { id, role, realms },
page }`). Today a condition reads one top-level own property, so it cannot
target `subject.id`. It cannot compare a context instant other than `now`. It
cannot say "the context has no realm". Callers flatten fields, copy instants
into synthetic booleans and add marker fields, and the rules then name the
caller's workarounds instead of the data.

## Goals

- Every place the engine reads a context field by name takes a path: a
  condition's `field`, a rollout's `by`, a definition's `variantBy`, the
  observer's `correlateBy`, and the field checks `adopt` runs for its
  `missing-field` divergence report. (My call: one meaning for a field name
  everywhere in a definition.)
- `before` and `after` compare any instant field, and optionally an instant
  relative to `now`.
- `exists` and `not-exists` test whether the context carries a field.
- Every port decides each new case the same way, through conformance cases.
- A document that uses none of these decides exactly as on 0.1.1.

## Non-goals

- Nested types in `ContextSchema` as nested objects. The schema stays flat
  JSON (see "Schema").
- Paths into arrays (`realms.0`), wildcards, or array element matching beyond
  the existing `contains`.
- Comparisons between two context fields.
- Months and years in relative instants.

## Path syntax

A path uses the escaping `@evanion/acl` 0.2.0 uses
(`libs/acl/src/field-path.ts`): segments joined by `.`, a literal `.` or `\` in
a segment escaped with `\`. Construction refuses an empty segment, a trailing
`\`, a `\` before any other character, a segment that is `__proto__`,
`constructor` or `prototype`, and more than 32 segments. `now` stays the bare
name of the clock.

The path parser and formatter move out of `libs/acl` into a place both
packages read without one depending on the other. The builder picks the place
(a shared internal module copied into each package's source is acceptable; a
new published package is not, for this release). Only the parser is shared:
`@evanion/acl` keeps its own validity rules unchanged, and the extra refusals
above (`constructor`, `prototype`, the 32-segment cap where acl lacks it) are
`@evanion/feature`'s. (My call: acl needs no release for this.)

A flat context key containing `.` is named by escaping it (`subject\.id`).
This changes the meaning of an existing `field: "subject.id"`: in 0.1.1 it
named a flat key, in 0.2.0 it names `subject` → `id`. That is the one change to
a document that uses none of the new features, and the changelog names it.

## Reading a path

Each segment is read as an own data property of a plain object (prototype
`Object.prototype` or `null`). A getter is not invoked: the walk reads the
property descriptor, and an accessor counts as absent. A missing segment, a
non-plain parent (array, `Date`, class instance, primitive, `null`) or an
accessor makes the field absent.

An absent field keeps today's rule: every comparison over it is false,
`ne` and `not-in` included. `exists` and `not-exists` are the only ops that
answer for an absent field.

`plan()` treats a path as available when its first segment is available, and
defers it otherwise, as it defers a top-level field today. `PlanEntry.needs`
names the full path (`subject.id`), not the first segment, so a reader knows
which field to supply. (My call.)

## `exists` and `not-exists` (#571)

`{ field, op: 'exists' }` holds when the path reads a value other than
`undefined`. `not-exists` holds otherwise. `null` is present. The condition
carries no `value`; a document that gives one is refused at validation.

## Instant fields (#570)

`before` and `after` take any `field`. For `field: 'now'` they behave as
today. For any other field, the context value is read and parsed like `now`
(the `contextEpoch` rules: an ISO 8601 string with an offset, epoch
milliseconds, or a `Date`). A value that does not parse is absent, so the
condition is false. A present schema requires the field to be declared
`instant` or `instant?`.

### Relative boundaries

The value may also be `{ "fromNow": "<duration>" }`: the boundary is the
context's `now` plus a signed ISO 8601 duration restricted to weeks, days,
hours, minutes and seconds (`-P30D`, `PT12H`, `-P2W`, `-PT90M`). A duration
with years or months is refused at validation, because their length depends
on the calendar and the ports would disagree. A relative boundary with
`field: 'now'` is refused at validation (it compares the clock with itself
shifted). If `now` does not parse, the condition is false.

Example: "accounts created in the last 30 days" is
`{ field: 'subject.createdAt', op: 'after', value: { fromNow: '-P30D' } }`.

## Rollout `by`

`by` is a path, read the same way. An absent value means the context is not
bucketed, as today. `RuleOutcome.rollout.bucket` (#539) is set from the value
the path reads.

## Schema

`ContextSchema.fields` keys are paths, in the same escaped syntax:
`{ "subject.id": "string", "subject.createdAt": "instant", "page": "string" }`.
The schema stays a flat map of strings, so a producer in any language still
emits it by reflection. Validation checks a condition's path against the keys
exactly; a schema that declares `subject.id` does not declare `subject`. A
schema key that is a proper prefix of another (`subject` and `subject.id`) is
refused, because one would be a scalar and the other an object.

The `exists`/`not-exists` ops need no type. `before`/`after` over a non-`now`
field need `instant` or `instant?`. The other ops keep today's checks.

## Conformance

`libs/feature/conformance/config-decisions.json` and `plan-decisions.json` keep
their shape. A new file, `libs/feature/conformance/condition-cases.json`, holds
a list of cases, each `{ name, config, context, decisions }`, so one file
carries many contexts. Only JSON-expressible inputs go in the shared file:
absent vs present, `null`, ISO strings, epoch numbers, nested objects, arrays
as non-plain parents, escaped flat keys, unparseable instants. Inputs JSON
cannot carry (`undefined` distinct from a missing key, `Date`, accessors,
class instances) are tested in `@evanion/feature`'s own specs and do not bind
other ports. (My call.) The new file covers: nested paths
(present, missing segment, non-plain parent, accessor, escaped flat key, flat
key that a path would also spell), `exists`/`not-exists` (absent, `undefined`,
`null`, present), instant fields (string, epoch, `Date`, unparseable),
relative boundaries (each unit, sign, `now` unparseable) and rollout `by` paths
with `bucket`. Every port runs the same files.

## Docs

The feature docs' conditions page and reference gain the path syntax, the new
ops and the relative form, with checked examples. Prose goes through the Gemma
workflow.

## Release

`feat(feature)!` with a `BREAKING CHANGE:` footer naming the changed meaning of dotted names in `field`, `by`, `variantBy` and `correlateBy`,
released as 0.2.0. The packages that depend on
`@evanion/feature` release as dependents; any that re-export `Condition` or
`ContextSchema` types carry their own `feat!` so they reach 0.2.0 too.
