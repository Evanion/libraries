# @evanion/baize-ui: the Baize design system as a shared library

Status: proposed
Depends on: `2026-09-10-demo-apps.md` (the approved visual design),
`2026-09-10-react-widget-rsc.md` (the RSC constraint),
`2026-09-11-feature-toggles.md` (the two-entry packaging precedent)

## Why

The visual design in the demo-apps spec is approved and settled. Four apps are
meant to render it: `storefront`, `admin`, `rsc-example` and `docs`. Built per
app, the six ground hexes exist in four places, the stat line is written four
times with four different radii, and the first app to ship becomes the
specification by accident.

This is the same failure the repo already fixed once for documentation: the
README examples drifted from the code until `tools/doc-examples` made them
execute as tests. A colour value in four stylesheets drifts the same way and has
no compiler to catch it.

Three of the four apps are being built concurrently with this spec. It therefore
describes where the library is going, and names what each app has to adopt,
rather than describing what any app currently has.

## Decisions

1. `libs/baize-ui`, package `@evanion/baize-ui`, `private: true`.
2. Four entries: `.` (server-safe React primitives), `./client` (primitives that
   need client React), `./tokens` (the token values as TypeScript), and
   `./tokens.css` (the same values as custom properties).
3. The TypeScript token module is the source. `tokens.css` is generated from it
   and committed, with a test holding the two in step.
4. The RSC constraint is enforced on the packed output, not documented. `.` may
   import no React API that the `react-server` condition omits.
5. The library holds the design system. It holds no domain data access, no
   routing and no app state.
6. Fonts are not shipped. Tokens name the families; each app loads them.
7. The docs app is in scope, in two steps: tokens first, primitives second.
   Replacing `nextra-theme-docs` is not proposed.

Decision 6 and the docs sequencing in 7 are the ones most likely to be wrong.
Both are cheap to reverse.

## 1. Where it lives, and whether it is published

`nx.json` `release.projects` is `["libs/*", "nest/*"]`. A project at `libs/*` is
in release scope: nx versions it, tags it `baize-ui@x.y.z`, and writes it a
changelog. `private: true` is what stops the publish step, which is exactly the
position `@evanion/feature` is in today — versioned and tagged, never pushed to
npm.

`tools/*` is outside release scope entirely and would avoid all of that.
`@evanion/doc-examples` lives there: `main` points straight at `src/index.ts`,
there is no build, no exports map and no packed form.

`libs/` is the right home anyway, and the reason is mechanical rather than
taxonomic. This library needs every piece of machinery that `libs/*` carries and
`tools/*` does not:

- A build. It emits a bundle per entry, a generated stylesheet, and
  declarations. `@evanion/doc-examples` emits nothing.
- An exports map with conditions, because the RSC split is expressed in it.
- A packed form, because `scripts/verify-packaging.mjs` is where the RSC
  constraint is proven, and it asserts on tarball contents.

Excluding it from release scope by naming the other projects in
`release.projects` is not available: the repo's rule is that adding a package
must not require editing an unrelated file. `private: true` in the package's own
manifest keeps the decision local to the package.

Cost of being in release scope, stated rather than discovered later: the
implementation PR must add `baize-ui` to `scope-enum` in `commitlint.config.js`,
or `tools/repo-checks/src/commitlint-scope-enum.test.ts` fails. That test exists
precisely so this is not forgotten.

### The name

`libs/baize-ui`, and the reason is not aesthetic.

`libs/ui` is wrong because the package name would be `@evanion/ui`, which claims
to be the UI library for everything published under `@evanion/`. It is one
design system, and a second one later would have nowhere to go.

`libs/baize` is wrong because `baize` is the name the shop domain wants. A
future package holding the catalogue model, the mechanism taxonomy or the order
types is `baize`. Spending the bare name on the stylesheet forces the domain
package into a worse name.

`tools/baize-ui` is wrong per the section above.

That leaves the tension the user named: the design identity is Baize, the shop,
and the docs site is "Evanion Libraries", which sells no games. The answer is in
the entry split. `./tokens`, `./tokens.css` and the `.` primitives carry the
foundation — ground, type, radii, tracking, elevation. The mechanism hue scale
and the availability states are the shop's informational colour systems and are
namespaced as such (`--baize-mechanism-*`, `--baize-availability-*`). The docs
app consumes the foundation and never references either. The package name is
then the name of the design system, which is genuinely Baize, and the shop
vocabulary is opt-in within it.

`baize-ui` also survives nx's scope matching. `nx release` matches a commit
scope against project names with a word-boundary regex where `-` is a word
character, so `baize-ui` resolves to this project and a future `baize` resolves
to that one, with no fragment collisions.

## 2. Entry points

```jsonc
{
  "exports": {
    "./package.json": "./package.json",
    ".": {
      "@evanion/source": "./src/index.ts",
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js",
    },
    "./client": {
      "@evanion/source": "./src/client/index.ts",
      "types": "./dist/client/index.d.ts",
      "import": "./dist/client/index.js",
      "default": "./dist/client/index.js",
    },
    "./tokens": {
      "@evanion/source": "./src/tokens/index.ts",
      "types": "./dist/tokens/index.d.ts",
      "import": "./dist/tokens/index.js",
      "default": "./dist/tokens/index.js",
    },
    "./tokens.css": "./dist/tokens.css",
  },
}
```

Four entries, and each exists because something cannot reach the others.

| Entry          | Contents                                           | Consumers                                        |
| -------------- | -------------------------------------------------- | ------------------------------------------------ |
| `.`            | React primitives using only server-safe React      | `admin`, `rsc-example`, `docs`, `storefront` JSX |
| `./client`     | primitives needing state or events, `'use client'` | `admin`, `docs`; `rsc-example` via a boundary    |
| `./tokens`     | the token values and their types, no React import  | tests, build scripts, any JS that needs a value  |
| `./tokens.css` | the same values as custom properties on `:root`    | every app, including `.astro` and MDX            |

The split between `.` and `./client` is the `@evanion/feature` precedent applied
unchanged: a single bundle cannot carry per-module directives, so a client layer
needs its own build entry. `@evanion/feature` reached that conclusion because
its React adapter genuinely is client code; `@evanion/react-widget` reached the
opposite one because it has no client code at all. This library has both kinds,
so it needs both answers.

`./tokens` is separate from `.` rather than re-exported through it, because a
build script or a Nest response that needs the availability hue should not pull
React into its graph. That is the same reason `@evanion/feature`'s core is not
reachable only through its React entry.

`./tokens.css` is the only entry `.astro` style blocks and MDX can use. Astro
scoped styles and MDX prose have no module graph to import a TypeScript object
into; they have `var(--baize-chalk)`. `@evanion/astro-widget` already sets the
precedent for a package exporting non-JS source through its exports map with
`"./components/*": "./src/components/*"`.

`./client` may start with a single export, or none. If it starts with none, the
entry is not created and the exports map carries three. The directory split in
decision 4 holds regardless, so adding the entry later changes no existing
import.

## 3. How tokens reach a consumer

One source, one generator, two artefacts.

`src/tokens/*.ts` is the source. The generator emits `src/tokens.css`, which is
committed. A vitest test regenerates and compares byte-for-byte.

```ts
// src/tokens/ground.ts
export const ground = {
  ink: '#0C1714', // page
  felt: '#142521', // panels
  rule: '#2A3F39', // hairlines
  chalk: '#F2EDE3', // primary text
  lichen: '#8FA69E', // secondary text
  moss: '#5E736C', // tertiary text
} as const;
```

```css
/* src/tokens.css -- generated from src/tokens/, do not edit */
:root {
  --baize-ink: #0c1714;
  --baize-felt: #142521;
  --baize-rule: #2a3f39;
  --baize-chalk: #f2ede3;
  --baize-lichen: #8fa69e;
  --baize-moss: #5e736c;
}
```

Why this direction rather than CSS-first or CSS-only:

- A stylesheet cannot be type-checked. `var(--baize-chlak)` compiles, renders
  nothing, and inherits whatever the parent had. A TypeScript union of token
  names fails the build.
- A TypeScript object cannot be used from an `.astro` style block or from MDX
  prose, which is most of two of the four consumers.
- Two hand-maintained copies drift, silently, in the direction of whichever file
  the last contributor happened to open. The repo has already paid for this once
  in its READMEs.

Generated-and-committed rather than generated-at-build, which is the one real
choice here. Generating into `dist/` only would make drift impossible, but it
also means nothing in the repo can read a token value without a build having
run, and a reviewer cannot see a colour change in a diff. Committing the
generated file and testing it against the generator is the pattern
`commitlint.config.js` plus `commitlint-scope-enum.test.ts` already uses: a
static artefact that something cheap can read, with a dynamic test holding it in
step. The build copies `src/tokens.css` to `dist/tokens.css` unchanged.

Fonts are named but not shipped:

```ts
export const type = {
  title: "'Bricolage Grotesque', 'Arial Narrow', sans-serif",
  text: "'Public Sans', system-ui, sans-serif",
} as const;
```

`tokens.css` also sets `font-variant-numeric: tabular-nums` on the stat-figure
class, because the design makes numeric alignment a requirement rather than a
preference. The font files themselves are loaded per app — `next/font` in `docs`
and `rsc-example`, Astro's font handling in `storefront`, a Vite-resolved
`@font-face` in `admin`. A library that shipped `@font-face` with its own URLs
would fight all three. This is the decision I am least sure of: it means four
apps each get font loading right separately, and a fifth could load Inter by
accident, which the design explicitly rules out. Mitigation: the token value
names the families, so a test can assert what the system asks for even though it
cannot assert what each app loaded.

### Values this spec does not invent

The demo-apps spec settles the six ground hexes, the two families, the three
radii, the tracking direction, and the absence of a house colour. It does not
give hex values for the five mechanism hues, the four availability states or the
five weight ramp stops.

This spec specifies their shape and not their values:

- Mechanism: five categorical hues, each legible as a title colour on `felt`.
- Availability: four state colours, each legible as pill text on `felt`.
- Weight: a five-stop sequential ramp, because weight is ordinal.

The values land in the implementation PR with a stated contrast floor. I am
guessing that a 4.5:1 floor against `felt` is achievable for five distinguishable
hues on that ground; if it is not, the title hue drops to a 3:1 large-text floor
and the tags keep 4.5:1. Either way the number goes in the token file as a
comment and a test asserts it.

## 4. The RSC constraint

`apps/rsc-example` imports from a React Server Component. React 19.2.8's
`react-server` condition provides no `createContext`, `useContext`, `Component`,
`PureComponent` or stateful hook, so any primitive reachable from `.` that
touches one is `undefined` at module evaluation. The build succeeds, the jsdom
tests pass, and it fails only in the app.

Three guards, layered so that each catches what the others cannot.

**Source separation.** Everything under `src/client/` may use client React.
Nothing reachable from `src/index.ts` may import from `src/client/`. A
repo-check asserts this on the module graph, so a contributor who adds `useState`
to a card gets a failure naming the import path rather than a runtime
`undefined` three apps away.

**A pinned-condition vitest project.** `libs/widget/vite.config.ts` already does
this: a second project with `resolve.conditions: ['react-server']`, `ssr.resolve`
matching, `server.deps.inline: [/^react(\/|$)/]` so the condition is not lost to
Node's resolver, and `*.server.test.tsx` as its only includes. Copy it. The
first test in `libs/widget/src/rsc.server.test.tsx` asserts the condition is
actually active before asserting anything about the package — keep that, because
without it a misconfigured project passes while proving nothing.

**The packed output.** `scripts/verify-packaging.mjs` gains
`['libs/baize-ui', '@evanion/baize-ui']` in `LIBS`. `private: true` is no
obstacle: `@evanion/feature` is private and is packed and checked there already.
A package absent from that list is packed by nothing and checked by nothing, and
the script asserts the tarball count after packing so a failed pack cannot pass
as a shorter list.

What it checks, following the `@evanion/feature` block almost exactly:

```
dist/index.js        first line is not 'use client'
dist/index.js        the `react` import's specifiers include none of
                     createContext, useContext, useState, useEffect,
                     useReducer, useRef, Component, PureComponent
dist/client/index.js first line IS 'use client'
package.json         exports map still carries every entry it promises
dist/tokens.css      resolvable as '@evanion/baize-ui/tokens.css' and
                     containing the six ground hexes
```

Specifiers rather than call sites, for the reason the react-widget spec
established: rolldown renames imported bindings, so a real context compiles to
`import { createContext as t }` and a call to `t(...)`, and
`grep "createContext("` returns zero on a build that genuinely has one. #81
confirmed that empirically.

Each entry is bundled, so checking the entry module is sufficient and the
file-per-file walk `@evanion/feature` needs does not apply. If the build ever
emits `.` unbundled, the walk comes back — note it next to the rolldown config
rather than leaving it to be rediscovered.

A consumer cannot import the wrong one by accident because there is no path
from `.` to a client primitive and no deep-import path into the package: the
exports map lists its entries and nothing else, so `@evanion/baize-ui/src/...`
does not resolve.

## 5. What belongs in it

The test a contributor applies, in order. A primitive belongs if all three pass.

1. **Does it render the same markup with the same meaning in two different
   apps?** The stat line does: `admin` shows it on an inventory row,
   `storefront` on a game card, and it is the same component with the same
   data shape. A storefront category grid does not — `admin` has no categories.
2. **Does it reach for data, a route or app state?** If it fetches, imports a
   router, or reads a cart, it is app code. Props only.
3. **Is its vocabulary in the design spec?** "Stat line", "mechanism hue",
   "availability pill", "chip", "card" are in the design. "Cart summary",
   "order row", "search result" are in the domain.

Applied:

| In                                        | Why                                                  |
| ----------------------------------------- | ---------------------------------------------------- |
| Tokens                                    | the reason the library exists                        |
| `StatLine` / `Stat`                       | the design calls it the hero and structural device   |
| `AvailabilityPill`                        | informational colour system, one tiny component      |
| `MechanismTag`, and the title hue binding | the other informational colour system                |
| `Card`, `Panel`                           | 12px radius and the `felt` ground, one definition    |
| `Button`                                  | 6px radius, ink/parchment inversion, no house colour |
| `Chip`                                    | 3px radius                                           |
| `Title`, `Text`                           | the two families and the tracking-by-size rule       |

| Out                             | Why                                                                   |
| ------------------------------- | --------------------------------------------------------------------- |
| Category grid, cart, checkout   | fails 1 and 3                                                         |
| Navigation, breadcrumbs, search | needs a router; fails 2                                               |
| Anything named after an entity  | fails 3                                                               |
| Page layouts                    | fails 1; each app's chrome differs                                    |
| A data table                    | fails 1 today; revisit when `admin` and `docs` both want the same one |

`StatLine` takes `{ players, playtime, weight }` as formatted strings plus the
ramp stop for weight, not a game object. That is what keeps it in the library
rather than making it a view of the domain model.

The line is drawn explicitly because a library whose boundary is vague accretes
app code, and the first piece of app code in it is the one that makes the next
piece an obvious precedent.

## 6. The docs app

In scope, and the user's intent is that it adopts the library. It cannot do so
in one step, for reasons specific to Nextra.

`apps/docs/app/layout.tsx` imports `nextra-theme-docs/style.css` and renders
Nextra's `Layout`, `Navbar` and `Footer`. `app/global.css` is one line,
`@import 'tailwindcss'`. The theme owns the shell, the sidebar, the search UI
and the colour scheme, which `next-themes` writes onto `<html>` from a blocking
script. None of that is ours to restyle component by component.

Three steps, of which the first two are proposed now.

**Step 1 — tokens, no primitives.** `apps/docs` depends on
`@evanion/baize-ui`, imports `@evanion/baize-ui/tokens.css` in
`app/global.css` after the Tailwind import, and maps Nextra's theme variables
onto Baize tokens in a small override block. What this replaces: nothing in our
code, because there is nothing; it overrides the theme's defaults. The site
gains the baize ground and the two families and keeps every Nextra behaviour.

I am guessing at the exact variable names Nextra 4 exposes for its theme
colours. They are read out of the installed `nextra-theme-docs` stylesheet
during implementation, not from memory, and if the theme turns out not to expose
a mappable set, step 1 becomes a scoped override on the content area only and
the chrome stays as it is. Say which one happened in the PR.

**Step 2 — primitives in MDX.** `mdx-components.js` and the playground
components use `Card`, `StatLine`, `Chip` and `Button` from
`@evanion/baize-ui`. This replaces the ad-hoc styling inside
`components/PlaygroundExamples.tsx` and `WidgetPlayground.tsx`, and it makes the
docs app a real consumer of the library the same way the demo-apps spec makes it
a real consumer of `@evanion/react-widget`.

**Step 3 — not proposed.** Replacing `nextra-theme-docs` with our own shell
would mean reimplementing the sidebar, the page map rendering, the pagefind
search UI and the `output: 'export'` behaviour. That is a separate spec, if
ever.

Two mechanical notes for whoever does step 1.

`apps/docs/tsconfig.json` sets `customConditions: []` to override
`tsconfig.base.json`'s `["@evanion/source"]`. The app deliberately resolves
`@evanion/*` through `types`/`import` to built `dist/`, because `next build`
type-checks with a plain `tsc` that does not build project references and would
hit TS6305 on a source file redirected to a declaration output nothing emitted.
So: add `{ "path": "../../libs/baize-ui" }` to the app's `references`, as it
already does for `libs/widget`, and `@evanion/baize-ui` must be built before the
docs app. nx's `build-deps` ordering handles that, the same way it already does
for `react-widget`.

Second: under `customConditions: []` the docs app's TypeScript imports resolve to
`dist/`, while in-repo consumers resolve to `src/` through `@evanion/source`.
`dist/tokens.css` is a copy of `src/tokens.css`, so a stale `dist/` is the only
way the two can disagree. Build ordering is what prevents it, and the generator
test is what catches a `src/tokens.css` that was edited by hand.

## 7. Testing

What proves it works rather than compiles. Each guard has a sabotage that makes
it fail, because a guard that has never failed is not a guard.

**The RSC import constraint.** Three layers from section 4.

- Sabotage the source split: import `useState` into a module reachable from
  `src/index.ts`. The repo-check fails, naming the path.
- Sabotage the condition: add `createContext` to a `.` primitive without a
  directive. `*.server.test.tsx` fails at module evaluation, and
  `verify-packaging.mjs` fails on the import specifiers. The `'use client'`
  check alone would pass, which is why both exist.
- Sabotage the client entry: let the build collapse `./client` into `.`.
  `dist/client/index.js`'s first-line check fails.
- Sabotage the project config: remove `resolve.conditions` from the
  `react-server` vitest project. Its first test — the one asserting
  `React.createContext` is `undefined` — fails, so a misconfigured project
  cannot pass silently.

**Token values against the approved design.** A test asserts the six ground
hexes literally, against the values quoted in the demo-apps spec, with the spec
path in the failure message. Sabotage: change `#142521` to `#142520`; the test
names the token.

**No house colour.** The design's structural divergence is that Baize has none.
A test asserts the exported token set contains no name matching
`/brand|accent|primary-colo|theme-colo/`. Sabotage: add `--baize-accent`; the
test fails. This is the one guard against the design eroding back toward the
pattern it was defined against.

**Tokens and stylesheet in step.** Regenerate `src/tokens.css` in a test and
compare byte-for-byte. Sabotage in either direction: edit a hex in the CSS, or
edit the TS and do not regenerate. Both fail.

**Contrast floors.** Each mechanism hue and each availability colour is checked
against `felt` at the floor stated in the token file. Sabotage: darken one hue
one step past the floor.

**Primitives not drifting from the apps.** Two mechanisms, because neither alone
is sufficient.

- `verify-packaging.mjs`'s `consumer.ts` names every public export and assigns
  it to an annotated binding, so a removed export or an export whose type became
  unreachable fails `tsc`. Extend it with the primitives and the token types.
  Sabotage: stop exporting `StatLine`.
- The README's examples execute, through `docExamples()` and
  `docExampleSources()`, and the docs pages render those same regions through
  `@evanion/doc-examples/mdx-region-loader`. A documented prop that stopped
  existing fails the library's own test run, and a renamed region fails the docs
  build. Sabotage: rename a region; `next build` fails.

**Render output.** A stat line renders three figures in document order with the
tabular-numerals class on each, and a card renders the 12px radius token rather
than a literal. These are the assertions that catch a refactor that keeps the
API and loses the design.

**What is not tested, and is accepted.** That each app actually loaded Bricolage
Grotesque and Public Sans. The token names them; nothing in this library can
observe an app's font loading. If that turns out to matter, the check belongs in
each app's own render test, not here.
