# @evanion/baize-ui: the Baize design system as a shared library

Status: proposed
Depends on: `2026-09-10-demo-apps.md` (the approved visual design),
`2026-09-10-react-widget-rsc.md` (where the import-specifier guard comes from),
`2026-09-11-feature-toggles.md` (the packaging precedent this one does not need)

## Why

The visual design in the demo-apps spec is approved and settled. Four apps are
meant to render it: `storefront`, `admin`, `storefront-rsc` and `docs`. Built per
app, the six ground hexes exist in four places, the stat line is written four
times with four different radii, and the first app to ship becomes the
specification by accident.

This is the same failure the repo already fixed once for documentation: the
README examples drifted from the code until `tools/doc-examples` made them
execute as tests. A colour value in four stylesheets drifts the same way and has
no compiler to catch it.

Three of the four apps are being built concurrently with this spec. It therefore
describes where the library is going, and names what each app has to adopt,
rather than describing what any app currently has.

`apps/storefront-rsc` is the Next App Router app the demo-apps spec calls
`apps/rsc-example`.

## Decisions

1. The library is stateless. No hooks of any kind, no state, no context, no
   effects, no async components, no Suspense, no data fetching.
2. It has no awareness of a rendering model. There is no RSC accommodation in it,
   because a stateless presentational component needs none.
3. Three entries: `.` (the components), `./tokens` (the token values as
   TypeScript), `./styles.css` (the custom properties and the component classes).
4. The TypeScript token module is the source. The custom-property block is
   generated from it and committed, with a test holding the two in step.
5. Props are already-formatted values. No domain objects, no formatting, no
   locale decisions.
6. `libs/baize-ui`, package `@evanion/baize-ui`, `private: true`.
7. Fonts are not shipped. Tokens name the families; each app loads them.
8. The docs app is in scope, in two steps: tokens first, components second.
   Replacing `nextra-theme-docs` is not proposed.

Decisions 1 and 2 are the architectural constraint the rest of this document
follows from, and they are not mine to trade away. Decision 7 and the docs
sequencing in 8 are the ones most likely to be wrong, and both are cheap to
reverse.

## 1. Stateless, and what that buys

Every component here takes props and returns elements. That is the whole
contract.

The consequences are worth stating separately, because each one removes a
decision this spec would otherwise have had to make.

**No per-framework entry and no per-framework caveat.** Astro, React Router SSR,
Next App Router and Nextra all render a presentational component identically.
There is no `'use client'` anywhere in the package, so there is no second build
entry, no directive to keep on the right module, and no consumer-side question
about which import to reach for. `@evanion/feature` needs two entries because its
React adapter genuinely is client code; this library is in
`@evanion/react-widget`'s position instead, and more strictly so.

**Where an `await` happens.** In the consuming app. `apps/storefront-rsc` owns
its async Server Components; they fetch, they format, and they render library
components with the results. The library is what they render into. A component
here never awaits, so it never needs `Suspense`, and the suspense-fallback
plumbing in `@evanion/react-widget` has no counterpart here.

**The RSC question does not arise.** A component that imports no hook cannot
reach for an API the `react-server` condition omits, so Server Component
compatibility is a consequence of the rule rather than a feature to maintain.
Section 4 covers how that is enforced, and why the enforcement is not built
around the `react-server` condition.

### The boundary rule for stateful primitives

A primitive that needs client state — a disclosure, a tab set, a quantity
stepper, a theme toggle, anything with an `onClick` that changes what is
rendered — belongs to the app that needs it, not here. It is written in the app's
own `'use client'` file, styled with the tokens and the component classes this
library ships.

Stated as a rule rather than left implicit, because the reflex when the second
app wants a disclosure is to add a `./client` entry. That entry is not coming.
The moment it exists, the statelessness rule has an exception, and the next
stateful component has a precedent instead of a boundary.

Cost, honestly: two apps that both want a disclosure write it twice. That is the
accepted price, and it is bounded — a disclosure is a dozen lines once the
styling is a class name from `./styles.css`. If it turns out not to be bounded,
the answer is a separate package with its own name, not a second entry on this
one.

## 2. Where it lives, and whether it is published

`nx.json` `release.projects` is `["libs/*", "nest/*"]`. A project at `libs/*` is
in release scope: nx versions it, tags it `baize-ui@x.y.z`, and writes it a
changelog. `private: true` is what stops the publish step, which is exactly the
position `@evanion/feature` is in today — versioned and tagged, never pushed to
npm.

`tools/*` is outside release scope entirely and would avoid all of that.
`@evanion/doc-examples` lives there: `main` points straight at `src/index.ts`,
there is no build, no exports map and no packed form.

`libs/` is the right home anyway, and the reason is mechanical rather than
taxonomic. This library needs every piece of machinery that `libs/*` carries and
`tools/*` does not:

- A build. It emits a bundle, a stylesheet and declarations.
  `@evanion/doc-examples` emits nothing.
- An exports map, because three entries with conditions is how the CSS and the
  components stay separable.
- A packed form, because `scripts/verify-packaging.mjs` is where the statelessness
  rule is proven, and it asserts on tarball contents.

Excluding it from release scope by naming the other projects in
`release.projects` is not available: the repo's rule is that adding a package
must not require editing an unrelated file. `private: true` in the package's own
manifest keeps the decision local to the package.

Cost of being in release scope, stated rather than discovered later: the
implementation PR must add `baize-ui` to `scope-enum` in `commitlint.config.js`,
or `tools/repo-checks/src/commitlint-scope-enum.test.ts` fails. That test exists
precisely so this is not forgotten.

### The name

`libs/baize-ui`, and the reason is not aesthetic.

`libs/ui` is wrong because the package name would be `@evanion/ui`, which claims
to be the UI library for everything published under `@evanion/`. It is one design
system, and a second one later would have nowhere to go.

`libs/baize` is wrong because `baize` is the name the shop domain wants. A future
package holding the catalogue model, the mechanism taxonomy or the order types is
`baize`. Spending the bare name on the stylesheet forces the domain package into
a worse name.

`tools/baize-ui` is wrong per the section above.

That leaves the tension the user named: the design identity is Baize, the shop,
and the docs site is "Evanion Libraries", which sells no games. The answer is in
the token namespacing. The foundation — ground, type, radii, tracking, elevation
— is `--baize-*` with no domain vocabulary in it. The mechanism hue scale and the
availability states are the shop's informational colour systems and are
namespaced as such (`--baize-mechanism-*`, `--baize-availability-*`). The docs app
consumes the foundation and references neither. The package name is then the name
of the design system, which is genuinely Baize, and the shop vocabulary is opt-in
within it.

`baize-ui` also survives nx's scope matching. `nx release` matches a commit scope
against project names with a word-boundary regex where `-` is a word character,
so `baize-ui` resolves to this project and a future `baize` resolves to that one,
with no fragment collisions.

## 3. Entry points

Three.

```jsonc
{
  "exports": {
    "./package.json": "./package.json",
    ".": {
      "@evanion/source": "./src/index.ts",
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "default": "./dist/index.js",
    },
    "./tokens": {
      "@evanion/source": "./src/tokens/index.ts",
      "types": "./dist/tokens/index.d.ts",
      "import": "./dist/tokens/index.js",
      "default": "./dist/tokens/index.js",
    },
    "./styles.css": "./dist/styles.css",
  },
}
```

| Entry          | Contents                                          | Consumers                                       |
| -------------- | ------------------------------------------------- | ----------------------------------------------- |
| `.`            | the components, stateless, no CSS import          | every app that renders React                    |
| `./tokens`     | the token values and their types, no React import | tests, build scripts, any JS that needs a value |
| `./styles.css` | the custom properties and the component classes   | every app, imported once in its root            |

**Why the CSS is a separate entry rather than imported by the components.**
`dist/index.js` must contain no CSS import. Next resolves a CSS import inside a
package's module graph; Astro and plain Vite SSR do not do so uniformly, and a
non-bundler consumer — `node --import tsx`, a test runner, a build script — fails
outright on one. So the app imports `@evanion/baize-ui/styles.css` once in its
root, and the components ship class names only. This carries forward unchanged
from the `storefront-rsc` findings.

**Why `./tokens` is separate from `.`.** A build script, a Nest response, or a
test that needs the availability hue should not pull React into its graph. The
token module imports nothing.

**Why one CSS file rather than `tokens.css` plus `styles.css`.** The custom
properties and the class rules that consume them are always wanted together by
anything rendering a component, and an app wanting only the properties — the docs
app at step 1 — gets a few hundred bytes of class rules that match no element in
its markup. That is cheaper than a second entry and a documented rule about which
to import when. Internally they stay separate files so the generated half can be
tested against its generator; section 4 covers that.

`./styles.css` is also the only thing `.astro` style blocks and MDX prose can
use: neither has a module graph to import a TypeScript object into, and both have
`var(--baize-chalk)`. `@evanion/astro-widget` already sets the precedent for a
package exporting non-JS through its exports map with
`"./components/*": "./src/components/*"`.

There is no deep-import path into the package. The exports map lists these
entries and nothing else, so `@evanion/baize-ui/src/...` does not resolve.

## 4. How tokens reach a consumer

One source, one generator, two artefacts.

`src/tokens/*.ts` is the source. The generator emits
`src/tokens.generated.css`, which is committed. `src/styles.css` is
hand-written, and its first line imports the generated file:

```css
/* src/styles.css */
@import './tokens.generated.css';

.baize-card {
  background: var(--baize-felt);
  border: 1px solid var(--baize-rule);
  border-radius: var(--baize-radius-card);
}
```

```ts
// src/tokens/ground.ts
export const ground = {
  ink: '#0C1714', // page
  felt: '#142521', // panels
  rule: '#2A3F39', // hairlines
  chalk: '#F2EDE3', // primary text
  lichen: '#8FA69E', // secondary text
  moss: '#5E736C', // tertiary text
} as const;
```

```css
/* src/tokens.generated.css -- generated from src/tokens/, do not edit */
:root {
  --baize-ink: #0c1714;
  --baize-felt: #142521;
  --baize-rule: #2a3f39;
  --baize-chalk: #f2ede3;
  --baize-lichen: #8fa69e;
  --baize-moss: #5e736c;
}
```

The build inlines the `@import` and emits one `dist/styles.css`.

Why the TypeScript side is the source, rather than CSS-first or CSS-only:

- A stylesheet cannot be type-checked. `var(--baize-chlak)` compiles, renders
  nothing, and inherits whatever the parent had. A TypeScript union of token
  names fails the build.
- A TypeScript object cannot be used from an `.astro` style block or from MDX
  prose, which is most of two of the four consumers.
- Two hand-maintained copies drift, silently, in the direction of whichever file
  the last contributor happened to open. The repo has already paid for this once
  in its READMEs.

Generated-and-committed rather than generated-at-build, which is the one real
choice here. Generating into `dist/` only would make drift impossible, but it
also means nothing in the repo can read a token value without a build having run,
and a reviewer cannot see a colour change in a diff. Committing the generated
file and testing it against the generator is the pattern `commitlint.config.js`
plus `commitlint-scope-enum.test.ts` already uses: a static artefact that
something cheap can read, with a dynamic test holding it in step.

Fonts are named but not shipped:

```ts
export const type = {
  title: "'Bricolage Grotesque', 'Arial Narrow', sans-serif",
  text: "'Public Sans', system-ui, sans-serif",
} as const;
```

`styles.css` sets `font-variant-numeric: tabular-nums` on the stat-figure class,
because the design makes numeric alignment a requirement rather than a
preference. The font files themselves are loaded per app — `next/font` in `docs`
and `storefront-rsc`, Astro's font handling in `storefront`, a Vite-resolved
`@font-face` in `admin`. A library that shipped `@font-face` with its own URLs
would fight all three. This is the decision I am least sure of: it means four apps
each get font loading right separately, and a fifth could load Inter by accident,
which the design explicitly rules out. Mitigation: the token value names the
families, so a test can assert what the system asks for even though it cannot
assert what each app loaded.

### Values this spec does not invent

The demo-apps spec settles the six ground hexes, the two families, the three
radii, the tracking direction, and the absence of a house colour. It does not
give hex values for the five mechanism hues, the four availability states or the
five complexity ramp stops.

This spec specifies their shape and not their values:

- Complexity: a five-stop sequential ramp, saturated, each stop legible as a
  title colour on `felt`. Five tier names, one per stop.
- Availability: four state colours, each legible as pill text on `felt`.
- Mechanism: categorical hues, each legible as chip text on `felt`, used where a
  mechanism is the subject and never on a game's title or tags.

The values land in the implementation PR with a stated contrast floor. A 4.5:1
floor against `felt` holds for all three: the ladder paints a card title at 18px
bold, which is under the 14pt-bold threshold for the 3:1 large-text allowance, so
normal-text AA is the floor it is held to. The number goes in the token file as a
comment and a test asserts it per stop.

## 5. Enforcing statelessness

The rule is that the library imports no hook and no stateful React API at all.
That is what is asserted, and it is a stronger and simpler statement than
surviving the `react-server` export condition.

The difference matters concretely. `useMemo`, `useCallback`, `useId` and
`useDebugValue` all exist under the `react-server` condition, so a guard built
around that condition passes a component that memoises. A memoising component is
not stateless, it is not framework-agnostic, and it is a hook this library has no
use for. This distinction came out of the `storefront-rsc` work and is the reason
the guard is reframed rather than copied from
`2026-09-10-react-widget-rsc.md`.

### An allowlist, not a denylist

`scripts/verify-packaging.mjs` gains `['libs/baize-ui', '@evanion/baize-ui']` in
`LIBS`. `private: true` is no obstacle: `@evanion/feature` is private and is
packed and checked there already. A package absent from that list is packed by
nothing and checked by nothing, and the script asserts the tarball count after
packing so a failed pack cannot pass as a shorter list.

What it checks:

```
dist/index.js   every specifier imported from 'react' is in the allowlist
                { createElement, Fragment }
                -- anything else fails, including a hook added next year
dist/index.js   imports nothing from 'react-dom' or 'react-dom/*'
dist/index.js   contains no CSS import
dist/index.js   first line is not 'use client'
package.json    exports map still carries '.', './tokens' and './styles.css'
dist/styles.css resolvable as '@evanion/baize-ui/styles.css' and containing the
                six ground hexes
```

An allowlist rather than a denylist because a denylist has to be maintained
against React's surface. `/^use[A-Z]/` would catch every current hook and miss
`createContext`; naming the eight client-only APIs, as the react-widget guard
does, misses `useMemo`. Two names are allowed, the list is short enough to read,
and a React API this library has no business importing fails by default.

Specifiers rather than call sites, for the reason the react-widget spec
established: rolldown renames imported bindings, so a real context compiles to
`import { createContext as t }` and a call to `t(...)`, and
`grep "createContext("` returns zero on a build that genuinely has one. #81
confirmed that empirically. The import specifier list is what survives the build.

The entry is bundled, so checking it is sufficient. If the build ever emits `.`
unbundled, the check becomes a file-per-file walk the way
`@evanion/feature`'s does — note that next to the rolldown config rather than
leaving it to be rediscovered.

### The same check at source

Pack time is too late to be the only place this fails. A vitest test in the
library scans every module under `src/` for its `react` import specifiers and
applies the same allowlist, so a contributor who adds `useMemo` to a card gets a
failure in the library's own test run naming the file.

Two checks of the same rule, because they catch different things: the source scan
catches the author, and the packed-output check catches a build, a bundler
upgrade or a transitive dependency that reintroduced an import the source does
not show.

### The `react-server` project, demoted

A vitest project pinning `resolve.conditions: ['react-server']`, copied from
`libs/widget/vite.config.ts`, with one test that renders a representative tree.
It is kept, and it is explicitly not the contract: it is evidence that the
consequence holds in a real resolver, and it would pass a library that memoises.
Keep the first-test-asserts-the-condition-is-active pattern from
`libs/widget/src/rsc.server.test.tsx`, because without it a misconfigured project
passes while proving nothing.

## 6. What belongs in it

The test a contributor applies, in order. A component belongs if all four pass.

1. **Is it stateless?** No hook, no state, no effect, no `await`. If it needs
   one, it is app code — see the boundary rule in section 1.
2. **Does it render the same markup with the same meaning in two different
   apps?** The stat line does: `admin` shows it on an inventory row,
   `storefront` on a game card, same component, same props. A storefront
   category grid does not — `admin` has no categories.
3. **Does it reach for data, a route or app state?** If it fetches, imports a
   router, or reads a cart, it is app code. Props only.
4. **Is its vocabulary in the design spec?** "Stat line", "mechanism hue",
   "availability pill", "chip", "card" are in the design. "Cart summary", "order
   row", "search result" are in the domain.

Applied:

| In                                        | Why                                                  |
| ----------------------------------------- | ---------------------------------------------------- |
| Tokens                                    | the reason the library exists                        |
| `StatLine` / `Stat`                       | the design calls it the hero and structural device   |
| `AvailabilityPill`                        | informational colour system, one tiny component      |
| `MechanismTag`, and the title hue binding | the other informational colour system                |
| `Card`, `Panel`                           | 12px radius and the `felt` ground, one definition    |
| `Button`                                  | 6px radius, ink/parchment inversion, no house colour |
| `Chip`                                    | 3px radius                                           |
| `Title`, `Text`                           | the two families and the tracking-by-size rule       |

`Button` is a styled `<button>` that takes an `onClick` and renders it. Taking a
handler is not state; the app owns whatever that handler does.

| Out                                     | Why                                                                   |
| --------------------------------------- | --------------------------------------------------------------------- |
| Disclosure, tabs, stepper, theme toggle | fails 1; belongs to the app, per section 1                            |
| Category grid, cart, checkout           | fails 2 and 4                                                         |
| Navigation, breadcrumbs, search         | needs a router; fails 3                                               |
| Anything named after an entity          | fails 4                                                               |
| Page layouts                            | fails 2; each app's chrome differs                                    |
| A data table                            | fails 2 today; revisit when `admin` and `docs` both want the same one |

### Props are already-formatted values

`StatLine` takes `{ players: '1–5', playtime: '40–70 min', complexity: 'Midweight' }`
plus the ramp stop for complexity. Not a game object, and not numbers. The tier
name is a string the app resolves, because the app owns the wording the same way
it owns the en dash.

The rule generalises for two reasons. A component that takes a domain object is
one step from fetching, because the next request is for the field the object
does not carry yet. And a component that formats owns a locale decision the app
should own — the en-dash in `1–5`, the thousands separator, the unit, the
24-hour clock. Formatting belongs where the request context is, which is the
app.

So: strings for anything displayed, enum members for anything that selects a
token (`mechanism`, `availability`, `complexity` stop), `ReactNode` for slots. No
`Intl` anywhere in the library, and nothing taking a `Date` or a number it would
have to render.

The line is drawn explicitly because a library whose boundary is vague accretes
app code, and the first piece of app code in it is the one that makes the next
piece an obvious precedent.

## 7. The docs app

In scope, and the user's intent is that it adopts the library. It cannot do so in
one step, for reasons specific to Nextra.

`apps/docs/app/layout.tsx` imports `nextra-theme-docs/style.css` and renders
Nextra's `Layout`, `Navbar` and `Footer`. `app/global.css` is one line,
`@import 'tailwindcss'`. The theme owns the shell, the sidebar, the search UI and
the colour scheme, which `next-themes` writes onto `<html>` from a blocking
script. None of that is ours to restyle component by component.

Three steps, of which the first two are proposed now.

**Step 1 — tokens, no components.** `apps/docs` depends on `@evanion/baize-ui`,
imports `@evanion/baize-ui/styles.css` in `app/global.css` after the Tailwind
import, and maps Nextra's theme variables onto Baize tokens in a small override
block. What this replaces: nothing in our code, because there is nothing; it
overrides the theme's defaults. The site gains the baize ground and the two
families and keeps every Nextra behaviour. The component class rules come along
and match nothing until step 2.

I am guessing at the exact variable names Nextra 4 exposes for its theme colours.
They are read out of the installed `nextra-theme-docs` stylesheet during
implementation, not from memory, and if the theme turns out not to expose a
mappable set, step 1 becomes a scoped override on the content area only and the
chrome stays as it is. Say which one happened in the PR.

**Step 2 — components in MDX.** `mdx-components.js` and the playground components
use `Card`, `StatLine`, `Chip` and `Button` from `@evanion/baize-ui`. This
replaces the ad-hoc styling inside `components/PlaygroundExamples.tsx` and
`WidgetPlayground.tsx`, and it makes the docs app a real consumer of the library
the same way the demo-apps spec makes it a real consumer of
`@evanion/react-widget`.

**Step 3 — not proposed.** Replacing `nextra-theme-docs` with our own shell would
mean reimplementing the sidebar, the page map rendering, the pagefind search UI
and the `output: 'export'` behaviour. That is a separate spec, if ever.

### `customConditions: []` applies to every Next consumer

`apps/docs/tsconfig.json` sets `customConditions: []` to override
`tsconfig.base.json`'s `["@evanion/source"]`. The app deliberately resolves
`@evanion/*` through `types`/`import` to built `dist/`, because `next build`
type-checks with a plain `tsc` that does not build project references, and the
`@evanion/source` condition then redirects the import to a declaration output no
target emits — TS6305.

That is not specific to the docs app. `apps/storefront-rsc` needs the same
override for the same reason. So the library cannot rely on source resolution in
a Next app, and two things follow:

- Every Next consumer adds `{ "path": "../../libs/baize-ui" }` to its
  `references`, as `apps/docs` already does for `libs/widget`, and
  `@evanion/baize-ui` must be built before it. nx's `build-deps` ordering handles
  that, the same way it already does for `react-widget`.
- A stale `dist/` is the only way a Next app and an in-repo consumer can see
  different token values, since one resolves `dist/` and the other resolves
  `src/` through `@evanion/source`. Build ordering prevents it; the generator
  test catches a `src/tokens.generated.css` edited by hand.

## 8. Testing

What proves it works rather than compiles. Each guard has a sabotage that makes
it fail, because a guard that has never failed is not a guard.

**Statelessness.** The central rule, checked twice.

- Sabotage the source: add `useMemo` to a component. The source scan fails,
  naming the file. A guard built around the `react-server` condition would not —
  `useMemo` exists there — which is the reason the rule is stated as an
  allowlist.
- Sabotage the build: have a dependency or a bundler upgrade reintroduce a
  `react` import the source does not show. `verify-packaging.mjs` fails on the
  packed entry's specifier list.
- Sabotage the allowlist itself: add `useState` to it. It is two names in one
  place, so that shows up in review as a design change rather than hiding in a
  denylist's absence.
- Sabotage the condition project: remove `resolve.conditions` from the
  `react-server` vitest project. Its first test — the one asserting
  `React.createContext` is `undefined` — fails, so a misconfigured project
  cannot pass silently.

**No CSS import in the JavaScript.** Sabotage: add `import './styles.css'` to a
component. `verify-packaging.mjs` fails on `dist/index.js`, and the runtime
import in the same script fails first, because a plain `node` import of a module
with a CSS import does not resolve.

**Token values against the approved design.** A test asserts the six ground
hexes literally, against the values quoted in the demo-apps spec, with the spec
path in the failure message. Sabotage: change `#142521` to `#142520`; the test
names the token.

**No house colour.** The design's structural divergence is that Baize has none. A
test asserts the exported token set contains no name matching
`/brand|accent|primary-colo|theme-colo/`. Sabotage: add `--baize-accent`; the
test fails. This is the one guard against the design eroding back toward the
pattern it was defined against.

**Tokens and stylesheet in step.** Regenerate `src/tokens.generated.css` in a
test and compare byte-for-byte. Sabotage in either direction: edit a hex in the
CSS, or edit the TS and do not regenerate. Both fail. Separately,
`verify-packaging.mjs` asserts the six hexes are present in `dist/styles.css`,
which catches a build that dropped the `@import` inlining.

**Contrast floors.** Each mechanism hue and each availability colour is checked
against `felt` at the floor stated in the token file. Sabotage: darken one hue
one step past the floor.

**Components not drifting from the apps.** Two mechanisms, because neither alone
is sufficient.

- `verify-packaging.mjs`'s `consumer.ts` names every public export and assigns it
  to an annotated binding, so a removed export or an export whose type became
  unreachable fails `tsc`. Extend it with the components and the token types.
  Sabotage: stop exporting `StatLine`.
- The README's examples execute, through `docExamples()` and
  `docExampleSources()`, and the docs pages render those same regions through
  `@evanion/doc-examples/mdx-region-loader`. A documented prop that stopped
  existing fails the library's own test run, and a renamed region fails the docs
  build. Sabotage: rename a region; `next build` fails.

**Render output.** A stat line renders three figures in document order with the
tabular-numerals class on each, and a card renders the card-radius token rather
than a literal. These are the assertions that catch a refactor that keeps the API
and loses the design.

**Props are formatted values.** A type test asserts `StatLine` rejects
`players: [1, 5]` and `playtime: 70`. Sabotage: widen a prop to `number`; the
type test fails. This is the only mechanical guard on decision 5 — the rest of it
is review.

**What is not tested, and is accepted.** That each app actually loaded Bricolage
Grotesque and Public Sans. The token names them; nothing in this library can
observe an app's font loading. If that turns out to matter, the check belongs in
each app's own render test, not here.
