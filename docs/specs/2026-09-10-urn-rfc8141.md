# urn: RFC 8141 conformance

Status: Implemented in #78. Corrected below where the implementation measured the design wrong.
Package: `@evanion/urn` (repo 2.0.0, npm 1.1.1 — breaking changes are free until 2.0.0 ships)
Closes: #12, #10, #11, #13, #15. Reopens behaviour landed for #8 and #9.

## Decisions

1. Implement RFC 8141: per-role grammar, `pchar` NSS set, percent-encoding
   policy, case-folded comparison.
2. One deliberate deviation, kept: RFC 8141 requires the literal scheme `urn`.
   This library allows any scheme via the overridable `URN.urn` static.
3. The RFC claim is scoped to the default `:` separator. Subclasses that
   override `separator` get separator-derived exclusion instead, and are not
   claimed to be RFC 8141 conformant.
4. #10: drop the NID dedup entirely.
5. #11: `parse` retains a foreign scheme the same way it already retains a
   foreign NID.
6. r-, q- and f-components are deferred to a follow-up issue.

## The structural fact everything rests on

`parse` splits on the separator and rejoins the tail:

```ts
const [urn, nid, ...rest] = urnString.split(this.separator);
const nss = rest.join(this.separator);
```

Split-then-rejoin on the same delimiter is lossless for the tail. NSS therefore
cannot structurally collide with the separator, whatever the separator is. Only
`urn` and `nid` occupy fixed single-token positions and can collide.

This is what resolves the conflict between #8 and #12. Separator-exclusion is
needed for `urn` and `nid` only. NSS keeps the full RFC grammar unconditionally,
under any separator.

## Grammar

### Default separator `:`

| Role        | Grammar                                                                                                    | Source                     |
| ----------- | ---------------------------------------------------------------------------------------------------------- | -------------------------- |
| scheme      | `^[A-Za-z][A-Za-z0-9+.-]*$`                                                                                | RFC 3986 §3.1              |
| NID (write) | `^[A-Za-z0-9][A-Za-z0-9-]{0,30}[A-Za-z0-9]$`                                                               | RFC 8141 §2                |
| NID (read)  | as above, plus length 1                                                                                    | RFC 2141 §2 compat         |
| NSS         | `^(?:[A-Za-z0-9\-._~!$&'()*+,;=:@]\|%[0-9A-Fa-f]{2})(?:[A-Za-z0-9\-._~!$&'()*+,;=:@/]\|%[0-9A-Fa-f]{2})*$` | RFC 8141 §2, RFC 3986 §3.3 |

Neither the RFC scheme grammar nor the RFC NID grammar contains `:`, so under
the default separator the RFC rules and separator-exclusion coincide. There is
no conflict to resolve here.

### Custom separator

Scheme and NID fall back to a generic charset with the separator excluded by
negative lookahead, which works even when the separator is alphanumeric:

```
^(?:(?!SEP)[A-Za-z0-9._~-])+$
```

No RFC length bounds apply. This regime is not RFC 8141 conformant and the
documentation must not claim it is.

NSS uses the same RFC `pchar` grammar as the default case, unconditionally.

### Read-lenient, write-strict

`stringify` enforces the RFC 8141 NID exactly. `parse` accepts the same charset
and ceiling but allows a 1-character NID.

Justification, researched rather than assumed:

- RFC 2141 §2 defines `NID ::= <let-num> [ 1,31<let-num-hyp> ]`, permitting a
  1-character NID. RFC 8141 raised the floor to 2.
- RFC 8141 Appendix B states that all URN namespaces and URNs valid under the
  earlier specifications remain valid.
- Every formal NID in the IANA URN Namespace registry satisfies RFC 8141's
  bound, so nothing else needs relaxing.
- RFC 2141 never permitted `_`, `.` or `~` in a NID, so there is no legacy
  argument for accepting them. The charset stays strict on both paths.

The split matches the WHATWG URL Standard, whose parser accepts legacy input
while its serializer always emits the canonical strict form.

## Percent-encoding

`stringify` does not encode. `parse` does not decode. Both operate on the wire
form. `stringify` validates NSS against the `pchar` grammar and throws
`InvalidError` if given something not already encoded, such as a literal space.
`parse` returns percent-triplets intact.

RFC 8141 §3.1 requires that percent-encoded octets not be decoded for
equivalence purposes, so treating them as opaque is what the standard asks for.
Folding encoding into `stringify`/`parse` invites double-encoding, the most
common bug class in URL libraries.

Two additive pure helpers cover convenience: `encodeNss`, `decodeNss`. An opt-in
`{ encode: true }` option can be added later without breaking anything. Do not
build it now.

## Case-folding

RFC 8141 §3.1: scheme and NID are case-insensitive; NSS is compared
byte-for-byte except that percent-triplet hex digits canonicalise to uppercase;
r-, q- and f-components are excluded from equivalence.

- `parse` returns original case. No normalisation on read.
- `sameNamespace` and `belongsToNamespace` fold scheme and NID before comparing.
  Both are case-sensitive today.
- New `URN.equals(a, b)` implements full §3.1 equivalence. The current API has no
  method for this.

## Public API

```ts
class URN {
  static readonly separator: string;
  static readonly urn: string;
  static readonly nid: string;

  static parse(urnString: string): ParsedURN;
  static stringify(nss: string, nid?: string, urn?: string): string;

  static get schemeGrammar(): RegExp;
  static get nidGrammar(): RegExp;
  static get nssGrammar(): RegExp;

  static isValidFormat(urnString: string): boolean;
  static extractId(urnString: string): string;
  static sameNamespace(a: string, b: string): boolean;
  static belongsToNamespace(
    urnString: string,
    nid: string,
    urn?: string,
  ): boolean;
  static equals(a: string, b: string): boolean;
}

export function encodeNss(raw: string): string;
export function decodeNss(encoded: string): string;
```

`isValid` is removed. One flat regex cannot represent three roles across two
separator regimes. Three getters can, and stay reactive to `this.separator` per
subclass.

`isValidFormat` becomes `try { this.parse(x); return true } catch { return false }`.
Today it checks only for at least three non-empty parts, which is the root of
#9's asymmetry. Delegating makes drift between the read and write paths
impossible.

`extractId` keeps its contract of always dropping a foreign NID, which differs
from `parse().nss` by design, but calls `isValidFormat` instead of hand-rolling
the same check.

`IFullURN` drops its dead fourth type parameter (#15). No call site in the repo
passes four arguments.

## What to change from the landed #8 and #9

`assertValidComponent` applies its `value.includes(this.separator)` guard to all
three roles. Keep it for `urn` and `nid`. Drop it for `nss`. That one change
unblocks every case below.

`isValid` gets two of its three roles wrong: too permissive for NID (allows
`_ . ~`, no length bound) and too strict for NSS (excludes `,`, `/` and the
sub-delims, so it rejects RFC 8141's own example URN). Replace with the three
role-scoped getters.

`isValidFormat` was untouched by #8, so the write path tightened while the read
path did not. #9's asymmetry is still present, inverted.

## Testing (#13)

- Round-trip: `parse(stringify(x)) === x` across the full `pchar` set, including
  percent-triplets, `/`, sub-delims and `:` inside NSS.
- RFC 8141's own example URNs parse and re-emit unchanged.
- NID boundaries: length 1 rejected on write and accepted on read; length 2 and
  32 accepted; 33 rejected; leading and trailing `-` rejected; `_`, `.`, `~`
  rejected on both paths.
- Case-folding: `sameNamespace('URN:user:1','urn:user:1')` is true; `equals`
  covers §3.1 including percent-hex canonicalisation.
- Custom separator: scheme and NID exclude the separator; NSS still accepts the
  default `pchar` set.
- Foreign scheme and foreign NID both retained by `parse`.
- `isValidFormat` agrees with `parse` on every case above.

## Deferred

r-, q- and f-components, tracked in #77 and implemented there. Evidence for
deferring: URN:NBN resolvers do not support r- or q-components, the RFC defines
syntax but not semantics for them, and the two npm packages that implement them
have negligible adoption.

The claim that carried the deferral holds: `pchar` excludes bare `?` and `#`,
so the components split off without touching `nssGrammar`, and the three
optional `ParsedURN` fields are additive.

The split **order** stated here was wrong. `?+`, then `?=`, then `#` mis-parses
a URN whose f-component contains a `?`, because RFC 8141 2.3 lets the r- and
q-components contain a bare `?` while `#` terminates both. `urn:example:foo#f?+x`
has one f-component of `f?+x`, not an r-component. The f-component comes off
first; then the first `?` of what is left introduces the r-component (`?+`) or
the q-component (`?=`), and an r-component runs to the first following `?=`.
